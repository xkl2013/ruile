# 服务空间 V1-1 数据契约

版本：V1-1  
日期：2026-09-27  
范围：决策与数据契约，不包含存量数据回填和运行时权限迁移

## 1. 生效决策

1. `services.id` 是服务空间 ID，所有空间内业务对象使用 `service_id` 作为主归属键。
2. `owner_user_id` 仅表示创建人 / 负责人，不参与团队共享数据的唯一性判断。
3. `space_type` 只允许：
   - `customer_service`：客户服务空间，默认值
   - `operations`：运营空间
   - `research`：研发 / 教研空间
4. `template_key` 表示业务模板，不表示空间类型。
5. `state` 只允许 `draft`、`active`、`paused`、`archived`。
6. `state_changed_at` 和 `state_change_reason` 用于记录空间状态变更的时间和原因；状态动作和审计写入属于 V1-2。
7. 主体是当前服务实际服务、研究、管理或跟进的业务对象，不限定为园所、家长、家庭或孩子；主体类型由服务模板和业务场景决定。
8. 首期不做空间层级嵌套，不做主体、事实、产出物的存量回填。
9. 自然语言 `instruction` 可以生成空间蓝图草案，但模型不能直接写入正式 `space_type`、权限、知识库范围或激活状态。
10. 空间档案和空间摘要页面使用蓝图中的结构化 schema 渲染；指令决定字段和栏目，事实流水决定具体内容。
11. 已审核并发布的模板可以根据当前用户画像直接套用；模板应用不要求用户二次确认，但不能新增权限、扩大知识库范围或写入敏感字段。

## 2. 服务主体契约

### 2.1 定义与边界

`ServiceSubject` 表示某个服务空间正在围绕的业务对象。它可以是个人、家庭、组织、班级、项目、课题或其他由用户实际服务的对象；以上仅为示例，不是平台固定枚举。

主体模型必须满足以下规则：

- 新建的服务主体必须挂 `service_id`，主体数据不能只按 `owner_user_id` 归属。
- `subject_type` 是非空的机器可读类型键，由模板或租户配置约束允许值；平台不把家庭、园所、家长、孩子写成通用数据库枚举。
- `subject_key` 是主体在同一服务空间内的稳定键，唯一性为 `(tenant_id, service_id, subject_key)`；不得再使用负责人作为业务唯一性的一部分。
- `parent_subject_id` 可为空；存在时只表示同一服务空间内的可选层级关系，不赋予固定的“家庭—孩子”语义。V1-1 不实现多对多关系。
- 行业专属属性进入 `metadata`，通用表不新增 `student_name` 等领域专属必填字段；旧字段仅保留兼容，后续版本清理。
- 一个服务空间可以没有主体，也可以有多个主体；是否必须建主体由 `template_key` 和业务规则决定，不由 `space_type` 直接推断。

### 2.2 字段契约

| 字段 | 类型 | 必填 | 默认值 | 约束 |
| --- | --- | --- | --- | --- |
| `id` | varchar(36) | 是 | UUID | 主键 |
| `tenant_id` | bigint / integer | 是 | - | 租户隔离 |
| `service_id` | varchar(36) | 新写入必填 | - | 服务空间归属；存量迁移完成前允许为空 |
| `owner_user_id` | varchar(36) | 存量兼容 | - | 旧负责人字段，不参与新业务唯一性 |
| `subject_type` | varchar(64) | 新写入必填 | 应用层 `custom`；存量为空 | 非空机器键，不设平台封闭枚举 |
| `subject_key` | varchar(255) | 是 | - | 同一租户、同一服务内唯一 |
| `display_name` | varchar(255) | 是 | `''` | 面向用户展示的主体名称 |
| `parent_subject_id` | varchar(36) | 否 | `NULL` | 可选父主体；必须属于同一租户、同一服务 |
| `metadata` | json / text | 是 | `{}` | 模板和行业扩展字段 |
| `visibility_scope` | varchar(64) | 是 | `private` | 沿用现有可见范围 |
| `created_at` / `updated_at` / `deleted_at` | timestamp / datetime | 是 | 数据库默认值 | 软删除兼容 |

### 2.3 V1-1 的实施边界

- 本版本只新增字段、索引和 Go 数据类型，不执行存量主体自动回填。
- 存量记录的 `service_id` 为空、`subject_type` 为空或仍使用 `owner_user_id` 时，进入 V1-2 迁移队列，不阻塞本版本发布。
- 新写入路径必须同时提交 `service_id`、`subject_type` 和 `subject_key`；未绑定服务的主体不得进入新的服务主体写入路径。
- `parent_subject_id` 的同服务校验由应用层完成；数据库只提供索引和约束所需字段，不建立跨方言外键。

### 2.4 指令与空间蓝图契约

空间蓝图是“自然语言指令”与“正式空间配置”之间的中间层，不允许模型直接修改业务表。

| 属性 | 说明 |
| --- | --- |
| `source_instruction` | 用户原始指令，保留原文并版本化 |
| `proposed_space_type` | 只能是 `customer_service`、`operations`、`research` 之一 |
| `proposed_template_key` | 可选模板键；不能通过模板绕过空间形态校验 |
| `subject_policy` | 是否需要主体、允许的 `subject_type`、是否允许层级关系 |
| `profile_schema` | 空间档案字段定义：字段键、标题、类型、是否敏感、展示顺序 |
| `summary_schema` | 空间摘要栏目定义：栏目键、标题、来源范围、刷新策略、展示顺序 |
| `expert_suggestions` | 专家建议，只能作为待确认项，不能绕过成员或权限规则 |
| `knowledge_scope_suggestions` | 知识库 / 技能建议，只能作为待确认项，不能扩大用户实际可读范围 |
| `generation_meta` | 模型、提示词版本、生成时间和校验结果 |

蓝图状态：

- `draft`：仅供预览，不进入运行时、不改变正式空间配置。
- `confirmed`：用户确认后生效，生成新的空间配置版本。
- `rejected`：用户拒绝，保留审计但不影响当前生效版本。
- `expired`：基于旧配置生成、已被新版本替代或超过有效期。

生成规则：

1. 模型输出必须符合固定 JSON schema，未知字段丢弃并写校验日志。
2. 模型只能建议三类 `space_type`，不能创建新的枚举。
3. 蓝图确认和空间激活分成两个动作；未明确确认不得自动激活。
4. 档案页面只能由 `profile_schema` 驱动通用组件渲染，不能生成任意前端代码。
5. 摘要页面只能由 `summary_schema` 驱动；栏目内容必须带事实 / 任务 / 产出物来源和生成水位。
6. 指令修改后生成新蓝图版本；旧版档案和摘要保持可查，不能静默改写。

### 2.5 用户画像模板与免确认契约

用户画像模板是“用户画像”与“正式空间配置”之间的受控快捷路径。模板必须由产品或租户管理员一次性审核发布；普通用户使用已发布模板时，不再重复确认空间形态、主体策略、档案结构和摘要结构。

| 属性 | 说明 |
| --- | --- |
| `template_key` | 租户内稳定模板键 |
| `version` | 模板版本；模板变更必须生成新版本 |
| `status` | `draft`、`published`、`disabled`、`archived` |
| `match_rules` | 用户画像匹配规则：租户角色、部门、工作画像关键词、服务范围等 |
| `blueprint` | 已审核的空间蓝图；必须通过三类 `space_type`、schema 和权限校验 |
| `auto_apply` | 是否允许匹配成功后直接套用 |
| `auto_activate` | 是否允许模板应用后直接激活空间；必须在模板发布时由管理员确认 |
| `risk_level` | `low`、`medium`、`high`；高风险模板不能自动套用 |
| `published_by` / `published_at` | 发布审核人和时间 |

当前用户画像快照至少包括：

- 当前租户角色、部门和工作画像描述；
- 用户可访问的服务范围、知识库范围和租户策略；
- 画像版本号及规范化 hash；
- 生成模板应用记录时使用的快照时间。

模板自动套用规则：

1. 只允许 `published` 状态、版本未过期、`auto_apply = true` 且 `risk_level = low` 的模板。
2. 画像匹配必须得到唯一模板；多个模板同分、匹配置信度不足、画像字段缺失时，回退蓝图预览 / 人工确认，不静默选择。
3. 模板应用必须重新执行空间形态、成员权限、知识库交集、敏感字段和激活状态校验。
4. 模板不得新增成员、改变成员角色、扩大知识库授权、修改租户权限、自动写入方案 / 价格 / 成交阶段，或代表用户发送外部内容。
5. 成功应用视为“模板版本已确认”，生成空间配置、蓝图版本、档案 schema 和摘要 schema；必须保存画像版本、画像 hash、命中原因、幂等键和审计结果。
6. 模板新版本不会静默改写既有空间；既有空间必须通过显式迁移任务切换模板版本。

### 2.6 模板应用记录

模板应用记录用于证明“为什么可以免确认”，不是新的业务事实来源。

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `service_id` | varchar(36) | 是 | 目标服务空间 |
| `template_key` | varchar(64) | 是 | 已发布模板 |
| `template_version` | integer | 是 | 应用时的模板版本 |
| `profile_version` | integer | 是 | 应用时的用户画像版本 |
| `profile_hash` | varchar(128) | 是 | 画像规范化 hash |
| `match_reason` | json / text | 是 | 命中规则和置信度 |
| `apply_mode` | varchar(32) | 是 | `auto` 或 `manual` |
| `idempotency_key` | varchar(128) | 是 | 重复请求返回同一结果 |
| `result` | varchar(32) | 是 | `applied`、`rejected`、`fallback_confirmation` |
| `created_at` | timestamp / datetime | 是 | 应用时间 |

## 4. API 契约

### 创建空间

`POST /api/v1/services`

```json
{
  "name": "秋季招生咨询",
  "instruction": "围绕当前服务对象持续跟进，记录关键进展、风险和下一步动作",
  "space_type": "customer_service",
  "template_key": "admission",
  "description": "服务对象跟进示例",
  "activate": false
}
```

规则：

- 未传 `space_type` 时使用 `customer_service`。
- 传入非三值枚举时返回 400，不写入数据库。
- V1-1 中 `space_type` 由用户或模板明确提供；不会在创建接口内自动调用模型推断。
- 创建成功后返回 `space_type`、`state`、`state_changed_at`。

### 指令生成蓝图

`POST /api/v1/services/blueprint/preview`

```json
{
  "instruction": "我想持续服务一组项目参与者，首页重点看进展、风险和下一步动作",
  "base_service_id": null
}
```

响应只返回 `draft` 蓝图，至少包含 `proposed_space_type`、`subject_policy`、`profile_schema`、`summary_schema`、`expert_suggestions` 和 `generation_meta`；不创建空间、不修改权限、不绑定知识库。

### 用户画像模板

- `GET /api/v1/services/templates`：读取当前用户可用的已发布模板和匹配结果。
- `GET /api/v1/services/templates/:template_key`：读取模板当前发布版本和适用画像条件。
- `POST /api/v1/services/templates/:template_key/apply`：命中模板后直接创建空间，不要求二次确认。

```json
{
  "name": "项目参与者跟进",
  "idempotency_key": "create-space-20260927-001"
}
```

模板应用接口规则：

- 服务端从会话解析当前用户和租户，重新读取用户画像快照；客户端不能提交画像 hash 作为授权依据。
- 只有唯一命中的 `published`、低风险、允许自动套用的模板可以直接成功。
- 应用成功返回 `service_id`、`template_key`、`template_version`、`blueprint_version`、`profile_version` 和 `summary_version`。
- 命中冲突、画像不完整、模板失效或高风险模板返回 `TEMPLATE_REQUIRES_CONFIRMATION`，引导进入蓝图预览 / 确认流程。
- 重复 `idempotency_key` 返回同一空间和同一模板应用记录，不创建重复空间。

### 空间内蓝图确认

- `POST /api/v1/services/:service_id/blueprint/preview`：基于当前空间指令生成新草案。
- `GET /api/v1/services/:service_id/blueprint`：读取当前确认版本和最近草案。
- `POST /api/v1/services/:service_id/blueprint/confirm`：确认草案并生成新版本；请求必须包含 `blueprint_id`、`expected_version` 和幂等键。
- `POST /api/v1/services/:service_id/summary/refresh`：按当前确认蓝图和最新事实刷新摘要。
- `GET /api/v1/services/:service_id/template-application`：读取空间创建时使用的模板版本、画像快照和命中原因。

确认接口规则：

- 只有空间 `admin` / `owner` 可以确认蓝图。
- 蓝图确认不自动扩大知识库、不自动增加成员、不自动激活空间。
- `space_type`、主体策略、敏感字段和对外策略变更必须写审计。
- 当前有未完成的确认任务时，重复提交返回同一任务结果，不生成重复版本。

### 更新空间

`PUT /api/v1/services/:service_id`

V1-1 只允许继续使用现有可编辑字段；`space_type` 在创建后不可通过更新接口修改，避免空间语义漂移。

### 状态接口

`POST /api/v1/services/:service_id/state/:state`

V1-1 只确认 `state` 的枚举契约。状态原因参数和审计动作在 V1-2 实现前，不作为本版本发布条件。

## 5. 迁移和回滚

### Up

- 为 `services` 增加 `space_type`、`state_changed_at`、`state_change_reason`。
- 为 `service_subjects` 增加 `service_id`、`subject_type`、`parent_subject_id`、`metadata` 和按服务空间归属的索引。
- V2 新增 `service_space_templates`、`service_space_blueprints` 和 `service_space_template_applications`，分别保存模板版本、结构化蓝图和免确认应用证据；V1-1 只冻结契约，不执行表迁移。
- 历史空间默认回填 `space_type = customer_service`。
- 历史空间的 `state_changed_at` 回填为 `updated_at`、`created_at` 或当前时间。
- 新增 `(tenant_id, space_type, state, updated_at)` 查询索引。
- 新主体唯一键为 `(tenant_id, service_id, subject_key)`；旧负责人唯一键降级为只约束 `service_id IS NULL` 的存量兼容记录，避免阻塞跨服务主体键复用。
- SQLite 通过触发器限制 `space_type` 枚举；PostgreSQL 使用 CHECK 约束。

### Down

- 删除枚举约束 / 触发器和查询索引。
- 删除新增的三个字段。
- 不删除服务空间数据，不修改原有 `owner_user_id`、`template_key` 和 `state`。
- 主体迁移回滚只删除本版本新增的主体字段和索引，不删除主体记录、不修改旧负责人归属。
- 若已写入的跨服务主体数据无法满足旧的负责人全局唯一键，Down 脚本在删列前预检失败；必须先完成数据清理或回迁，不允许强制回滚造成数据冲突。
