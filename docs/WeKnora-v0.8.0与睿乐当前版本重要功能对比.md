# WeKnora v0.8.0 与睿乐当前版本重要功能对比

## 1. 对比基线

本次只比较两个已提交版本，不把当前工作区未提交的升级实验混入结论：

| 版本 | 提交 | VERSION | 定位 |
| --- | --- | --- | --- |
| 睿乐当前基线 `main` | `5df5a520` | `0.7.0` | 已包含睿乐整理、服务、专家工作流等自研功能 |
| 官方 WeKnora `v0.8.0` | `1edcd54b` | `0.8.0` | 官方上游版本，重点升级 Skill、沙箱、记忆和解析能力 |

## 2. 先说结论

不能把官方 `v0.8.0` 分支直接合并到睿乐。

原因不是页面样式差异，而是两边已经形成了不同的产品模型：

1. 睿乐当前版本有自己的整理、服务、专家包、Agent Run 和服务空间。
2. 官方 `v0.8.0` 没有这些睿乐自研模块，直接对比时会删除对应前端和后端文件。
3. 当前睿乐迁移已经使用了 `000072`、`000078`、`000079` 以及 `000100`～`000107` 等自研语义。
4. 官方 `v0.8.0` 会把 `000071`～`000090` 改成另一套官方迁移语义，其中 `000080`～`000090` 与睿乐历史迁移直接冲突。
5. 官方前端会删除 `OrganizeMenu.vue`、`ServiceHubMenu.vue`、整理/服务页面和相关 API，不能作为睿乐界面基线。

正确方式是：**保留睿乐页面和业务模型，只挑选官方的后端能力、稳定性修复和必要的 API，逐项适配。**

## 3. 对睿乐最重要的功能

### P0：建议优先评估和移植

| 功能 | 官方 v0.8 能力 | 对睿乐的价值 | 当前状态判断 | 移植建议 |
| --- | --- | --- | --- | --- |
| Skill 目录和安装管理 | 租户级 Skill Catalog；支持 ClawHub、SkillHub、GitHub/GitLab、ZIP；安装进度、安装记录、停止、重装、卸载、文件浏览 | 服务模块和专家工作流如果要调用 Skill，这是基础能力 | 当前睿乐已有 Skill 执行能力，但没有官方完整的租户 Skill 目录和安装闭环 | 保留睿乐服务/专家界面，移植目录、安装、快照、文件和安装记录 API |
| Skill 环境变量 | 个人级和空间级环境变量，执行时注入，不允许回读明文 | 适合服务专家调用外部系统、脚本和数据源，同时降低密钥泄露风险 | 当前睿乐没有官方对应的 `tenant_skill_*` 服务体系 | 作为 Skill Catalog 的一部分移植，默认隐藏敏感值，增加轮换和权限测试 |
| Skill 执行权限和作用域 | Skill、文件工具、Shell 工具按空间和会话作用域控制 | 防止服务专家访问错误空间或读取其他用户文件 | 当前睿乐服务和 Agent Run 已有自己的租户/服务作用域，不能直接替换 | 只移植作用域校验和安全修复，适配现有 ServiceID、TenantID 和 AgentRun |
| 知识库解析稳定性 | anydoc 进程内解析 Office；DOCX 表格、PDF 内嵌图片、URL 抓取失败闭环等修复 | 线上真实数据主要是知识库文件，解析失败会直接影响迁移后可用性 | 当前 `main` 没有 `internal/infrastructure/docparser/anydoc/`，也没有官方 v0.8 的完整 parser 修复 | 先移植解析修复；anydoc 单独作为可选构建能力，不强制改变所有解析链路 |
| OIDC 和认证安全 | OIDC ID Token 通过 JWKS 签名校验；补充直接登录入口 | 生产登录和企业环境安全的基础 | 当前睿乐有 OIDC 代码，但需要逐项对比验证是否包含签名校验和 endpoint 修复 | 仅回移安全补丁和测试，不更换登录页面 |
| 高风险配置读取最新值 | 设置页、Agent Skill 选择器避免使用过期表单快照 | 可减少“页面显示已保存、实际仍使用旧配置”的问题 | 与当前服务/整理配置编辑流程高度相关 | 优先移植逻辑和测试，保持睿乐现有页面 |

### P1：第二阶段移植

| 功能 | 官方 v0.8 能力 | 对睿乐的价值 | 风险和建议 |
| --- | --- | --- | --- |
| 会话持久化沙箱 | Docker / E2B / Cube；一个聊天会话一个持久化工作区，支持 Shell、文件读写、附件暂存、产物收集 | 服务专家需要执行脚本、生成文件时很有价值 | 改动大且有安全风险，Docker 后端默认关闭；应先完成 Skill Catalog，再独立引入，保留 feature flag |
| 跨会话长期记忆 | profile、preference、fact、task、interest；用户确认后才生效；支持搜索、导出、强制整合 | 可增强服务员工的客户上下文和个人工作偏好 | 官方 Memory 与睿乐 `organize_memories` 不是同一个模型，不能直接共用表；需要先定义“整理记忆”和“Agent 长期记忆”的边界 |
| Agent 上下文压缩和 Token 使用量 | 长沙箱任务压缩工具历史，保留文件状态；记录每轮模型用量；提示词缓存标记 | 适合长时间服务对话和专家工作流，降低上下文溢出与成本 | 当前睿乐已经有部分 Agent 上下文压缩能力，应做差异移植，不能重复建设两套压缩器 |
| 消息产物和时间线 | 生成文件归档到消息产物抽屉，新增文件提示；问题大纲、消息时间戳 | 与睿乐服务卡片、Agent Run 产物展示有交集 | 优先抽取后端产物语义和接口，前端继续使用睿乐现有服务卡片样式 |
| 知识库自动标签 | 解析后根据知识库已有标签自动打标，不覆盖手工标签 | 对上传文件整理和后续服务检索有帮助 | 需要新迁移和模型调用，放在知识库稳定性之后；默认关闭 |
| XMind 文件解析 | `.xmind` 解析为大纲并入库 | 如果睿乐用户有教研/课程脑图文件，价值较高 | 当前 `main` 没有 `docreader/parser/xmind_parser.py`，可独立移植，不涉及主页面 |
| 数据源扩展 | GitLab 项目、腾讯 IMA 笔记同步 | 对企业知识库和外部资料接入有价值 | 当前线上真实数据主要是上传文件，优先级低于上传解析；按连接器单独接入 |
| 模型和搜索扩展 | LiteLLM、Exa、Metaso | 可扩大模型和搜索选择，服务模块可使用 | 只有在当前模型/搜索能力不足时接入，不能因为版本升级一次性增加配置页面 |
| 复杂密码和系统管理员建号 | 密码复杂度策略、系统管理员创建用户、邀请自动接受 | 适合生产账号治理 | 作为认证/管理补丁单独验证，不能带入整套官方 Admin 页面 |
| 部署能力声明 | `GET /system/capabilities`，前端只展示后端真正注册的模块 | 能避免 Lite、裁剪版或睿乐定制版显示不存在的菜单 | 这是解决当前页面错乱问题的有效基础能力，建议优先抽取接口和菜单判断逻辑 |

### P2：暂不优先

- DeepSeek Harness 插件：对睿乐核心 Web 产品不是当前阻塞项。
- GitLab、IMA、Exa、Metaso：除非明确有对应数据源或搜索需求，否则不应增加运维和配置复杂度。
- 全套官方 CLI、Admin 页面和官方主题：与睿乐当前产品边界不同，不应整体移植。
- 官方聊天页面重构、菜单重排、设置页重构：属于上游产品界面，不属于功能升级，必须保留睿乐当前交互。

## 4. 睿乐当前必须保留的能力

以下不是官方 `v0.8.0` 的可替代品，不能因为升级而删除：

### 前端

- `frontend/src/views/organize/` 整理工作台、我的整理、记忆、发现、编辑器和配置详情。
- `frontend/src/views/service/` 服务工作台、服务创建、专家选择和产物展示。
- `frontend/src/components/OrganizeMenu.vue`
- `frontend/src/components/ServiceHubMenu.vue`
- `frontend/src/components/MemoryDiscoverMenu.vue`
- 当前整理和服务的路由、文案和页面布局。

### 后端

- `internal/application/service/organize*`
- `internal/application/service/service_space.go`
- `internal/application/service/agent_run*`
- `internal/application/service/expert_*`
- 对应的 Handler、Repository、Types 和 Agent Run 任务队列。

### 数据库

- 睿乐当前 `organize_*`、`services`、`service_members`、`service_artifacts`、`agent_runs`、`expert_packages` 等业务表。
- 当前 `000072`、`000078`、`000079` 和 `000100`～`000107` 的业务语义。
- 线上已有知识库文件和对象存储引用。

## 5. 不能直接合并的部分

### 5.1 官方迁移文件

不能直接把官方 `migrations/versioned` 覆盖到睿乐：

| 迁移区间 | 睿乐当前含义 | 官方 v0.8 含义 | 结论 |
| --- | --- | --- | --- |
| `000071`～`000079` | 成员画像、整理、目录、知识库图标、OCR、排序、服务模块 | 平台 API Key、认证时间、KB Activity、MCP OAuth、Wiki 修订、Chunk 编辑、目录 | 同号不同义，必须做转换 |
| `000080`～`000090` | 睿乐自研租户、组织、提示词、计费和成员配置 | 自动标签、消息产物、沙箱、长期记忆、Skill Catalog | 直接执行会破坏迁移历史 |
| `000100`～`000107` | 专家包、Agent Run、服务空间、整理工作台 | 官方版本不存在 | 必须保留 |

推荐做法：

1. 保持当前官方迁移历史和睿乐自研迁移历史不变。
2. 新增一组专门的上游能力迁移，使用新的单调版本号或独立迁移表。
3. 每个功能先做 `CREATE TABLE/ADD COLUMN` 的兼容迁移，禁止删除睿乐字段。
4. 对长期记忆、Skill Catalog、沙箱配置分别建迁移，不要一次性导入全部 `000080`～`000090`。

### 5.2 官方前端页面

官方 v0.8 的前端差异中包含删除睿乐整理/服务页面和菜单的操作。页面层只能参考：

- API 类型和请求方式。
- 必要的状态字段。
- 单个功能控件。
- 安全提示和错误处理。

不能直接复制：

- `App.vue`、`menu.vue`、`router/index.ts` 的整体结构。
- 官方 Settings、Admin、Skill Sandbox 页面。
- 官方主题、布局和导航层级。

## 6. 推荐落地顺序

### 第一步：知识库稳定性

先完成：

1. DOCX/PDF/URL 解析修复。
2. anydoc 可选解析引擎。
3. XMind 解析（如有实际文件需求）。
4. 解析失败记录和重试验证。

验收重点：线上已有知识库文件重新解析后，文件数量、文件名、解析状态、预览和检索结果不退化。

### 第二步：Skill Catalog 和服务专家能力

先不改睿乐服务页面，新增：

1. 租户 Skill 目录。
2. 安装来源和安装任务记录。
3. 快照版本。
4. Skill 文件浏览和编辑。
5. 个人/空间环境变量。
6. Agent Run 的 Skill 作用域校验。

验收重点：服务专家只能访问授权 Skill、授权知识库和授权工作目录；密钥不能通过 API 或日志回读。

### 第三步：长对话和长期记忆

先定义边界：

- `organize_memories`：用户主动记录、录音转写和整理模块的原始记忆。
- 官方 `memory`：模型抽取的用户偏好、事实和任务上下文。
- 服务模块：基于当前用户授权的记忆和公共知识库生成服务建议。

确认边界后，再决定是新建官方 Memory 适配层，还是扩展睿乐现有记忆模型。不能把两套表直接合并。

### 第四步：安全、配置和部署

移植 OIDC JWKS、复杂密码、配置最新值、部署能力声明和 nginx/API 代理修复，保持睿乐当前页面和部署方式。

## 7. 最终建议

本次不要再以“升级到 v0.8”为目标直接合并官方分支。应改成：

> 以睿乐当前版本为主线，建立 v0.8 能力清单，按知识库稳定性、Skill/服务能力、长期记忆、安全配置四个主题做增量移植。

第一批建议只做以下五项：

1. 知识库解析稳定性修复。
2. Skill Catalog 后端和安装记录。
3. Skill 环境变量和作用域安全。
4. Agent 长对话压缩与用量记录的差异补齐。
5. OIDC、安全配置和部署能力声明。

暂缓：

- 官方整体前端页面。
- 官方菜单和路由替换。
- 官方迁移目录覆盖。
- 官方 Admin 页面整体替换。
- 沙箱后端全量切换。
- 官方长期记忆直接替换睿乐整理记忆。

这样可以获得 v0.8 中对睿乐真正有价值的能力，同时保持当前睿乐页面、服务、整理和线上知识库数据边界不变。
