# 多条记忆的整理：现有能力与改进方案

> 前置：[招生顾问Agent可行性核查.md](./招生顾问Agent可行性核查.md)（记忆模块真实边界）、[整理能力与10个模板匹配度评估.md](./整理能力与10个模板匹配度评估.md)（模板能力匹配度）

## 结论先行

1. **能做**，而且平台已经有一条**零开发**的可用路径（定时 / 立即整理，自动取最近一批记忆聚合）。但它的选材规则是**写死的**：「最近 50 条、按发生时间倒序」，**不能按类型 / 关键词 / 客户选**。
2. 真正卡住的不是「能不能合并」，而是三件事：**范围不可指定**、**一条未就绪整批失败**、**超出预算静默截断**。
3. **好消息**：按类型 / 关键词筛选的**底层能力已经就绪** —— `ListMemories` 支持 `Kind` 精确过滤 + `Keyword`（title/content/source）模糊匹配（`internal/application/repository/organize.go:160-163`），只是整理任务「选记忆」那一步**没把参数传下去**。最小接线的工作量集中在**1 个函数 + 1 个配置字段**。

---

## 一、现状：把多条记忆送进整理的四个部件

| 部件 | 代码位置 | 真实行为 |
|---|---|---|
| **选记忆** | `organize_workbench.go:550-573` | 有传入 ID 就用传入；否则取**最近 50 条**。构造查询时**只传 TenantID/UserID/Page/PageSize**，`Kind`/`Keyword` 都留空 |
| **装配提示词** | `organize_workbench.go:904-952` | 每条记忆标 `[M#] 标题/类型/时间/来源/内容`；单条截断 **2200** 字符；总量预算 **18000**；**先写后判 + 整体尾部硬截断** → 超出部分**静默丢弃，用户无感知** |
| **就绪校验** | `organize.go:274-300` | 选中集合里**任何一条**附件未就绪 / 转写未完成 → **整批抛 `ErrOrganizeMemoryNotReady`**；只有 `allow_partial=true` 才放行 |
| **输出落库** | `organize_workbench.go:636-668` | 正文为 Markdown（强制保留章节 + `{{citations}}` + `{{tags}}`）；`fields` 只落 **6 个系统级元数据**（主题/模板/版本/时间范围/待办数/来源数），**不是业务字段** |

**关键常数**（`organize_workbench.go:30-33`）：

| 常数 | 值 | 含义 |
|---|---|---|
| `organizeJobMemoryLimit` | 50 | 默认取数上限（仅在未指定 ID 时生效） |
| `organizeJobPromptBudget` | 18000 | 提示词总预算（字符） |
| 单条截断 | 2200 | `sampleRunes(content, 2200, "…")` |

**容量参考**：18000 ÷ 2200 ≈ **8 条最坏情况**（每条都写满）；按一线常见的 AI 笔记长度（约 800–1200 字符）估，实际约 **15–25 条**。超过即被尾部截断。

## 二、三条真实可用的路径

| 路径 | 入口 | 能否指定记忆范围 | 触发方式 | 现状 |
|---|---|---|---|---|
| **A 定时配置** | `POST /organize/configs`（含 `schedule`） | ❌ 只能吃默认「最近 50 条」 | `daily` 08:00 / `weekly` 周一 09:00 / `monthly` 1 日 09:00（Asia/Shanghai） | ✅ **已接线，零开发** |
| **B 立即整理** | `POST /organize/configs/:id/run` | ❌ 同上 | 手动点「立即整理」 | ✅ **已接线** |
| **C 手动建任务** | `POST /organize/jobs` | ✅ **API 支持 `memory_ids` 数组 + `allow_partial`** | 单次 | 🔶 **前端只传单条**，无多选 UI |

> 说明：`OrganizeJobInput.memory_ids`（`frontend/src/api/organize/index.ts:375-381`）是**真实能力**，但前端两个发起点（`OrganizeDocumentEditor.vue:1230-1231`、`OrganizeWorkspace.vue:1732-1733`）都是 `memory_ids: [单条 ID]`。配置页「立即整理」也不传（`OrganizeConfigDetail.vue:216-220`），等价于走路径 A 的默认取数。

## 三、五个卡点（其中三个是「有定义、零消费」）

1. **范围不可指定** → `createScheduledOrganizeJob` 调 `selectOrganizeJobMemoryIDs(..., nil)`（`organize_workbench.go:801`），**完全不读 config**。这是"批量整理只能吃全量"的主因。
2. **一条未就绪 → 整批失败** → `organize.go:290-297`。而 `allow_partial` **前端只声明、无调用点**（`api/organize/index.ts:248,380`）。
3. **预算静默截断** → `:945-952` 先写后判。且 `validateMemoryIDs`（`organize.go:954-967`）**不校验条数上限**：传 200 个合法 ID 不报错，只是静默丢弃大部分。
4. **`config.Metadata` 零消费** → DB 是 jsonb、前后端类型都有这个字段（`types/organize_workbench.go:154`、`api/organize/index.ts:84`），但调度时从没读过它。← **最干净的扩展点**
5. **无多选 UI** → 记忆列表只有**前端本地关键词过滤**（`OrganizeWorkspace.vue:642, 851-857`），一次拉 100 条再本地筛，**没有勾选 / 全选 / 批量**。

## 四、方案：四层，按成本升序

### L0｜今天就能用（零开发，0 行代码）

用现成的**定时配置**（或配置页「立即整理」），接受「最近一批」的范围规则。

- **适合**：每日线索跟进清单、每周渠道/复盘周报、每月成交与流失复盘。
- **不适合**：按客户 / 按主题 / 只挑某几类记录的聚合。
- **必须告知用户**：结果只覆盖**最近的一批**记忆，不是全部。否则会误判成「AI 漏了」。

### L1｜给「选记忆」接线筛选条件（推荐先做）

把筛选条件挂到**已经存在但没人读**的 `config.Metadata`，在 `selectOrganizeJobMemoryIDs` 里读出来，填进 `OrganizeListQuery`。

```json
{
  "memory_filter": {
    "kinds": ["record", "audio_card"],
    "keyword": "试听",
    "limit": 30,
    "allow_partial": true
  }
}
```

| 项 | 内容 |
|---|---|
| **后端改动** | 1 处：`organize_workbench.go:550-573` 增加「读 config.Metadata → 填 `Kind`/`Keyword`/`PageSize`」；`:801` 把 config 传进去 |
| **仓储改动** | **0** —— `ListMemories` 已支持 `Kind` 精确 + `Keyword` 模糊（`repository/organize.go:160-163`），排序 `occurred_at DESC` 现成 |
| **前端改动** | 配置表单加 2 个控件（记忆类型下拉、关键词输入） |
| **能力边界** | ✅ 按类型 / 关键词筛；❌ **不支持时间范围**（`ListMemories` 没有 `occurred_at` 条件下推，要新增属 L1.5） |
| **收益** | 定时 / 立即整理从「只能吃全量」变成「只整理录音类」「只整理含'试听'的」 |

> 这是**性价比最高的一步**：仓储能力已经躺在那儿，接线成本远小于新建功能，且不需要改数据模型。

### L2｜前端多选 + 批量发起

- **只改前端**：记忆列表加勾选 + 「批量整理」入口 → `POST /organize/jobs` 带 `memory_ids: [...]`（API 已就绪）。
- **必须同时做两件事**，否则会踩坑：
  1. **显示覆盖提示**：「已选 N 条 / 上限 M 条 / 超出将被截断」；
  2. **带 `allow_partial: true`**，否则选中的批量里只要有一条录音还在转写，**整批直接失败**。
- 同时建议服务端在 `validateMemoryIDs` 加**条数上限校验并明确报错**（现在是不报错、静默丢）。

### L3｜真正按主体聚合（数据模型改动，慎做）

要做到「按某个家长 / 某个主题聚合记忆」，必须补 `subject_id`（或引入「记忆集合」概念）。这属于数据模型演进，不是提示词能解决的 —— 与 [招生顾问Agent可行性核查.md](./招生顾问Agent可行性核查.md) 的结论一致。

### 横切｜预算分段策略

当候选记忆超过预算承载量时，二选一：

| 策略 | 做法 | 代价 |
|---|---|---|
| **切分** | 按时间窗口 / 类型拆成多个任务分别跑，产出多份成果 | 需前端或调度侧支持分批 |
| **提示** | 成果上显示「本次覆盖 N / M 条记忆」 | 极小（推荐先做这个） |

## 五、推荐落地路线

| 批次 | 内容 | 成本 |
|---|---|---|
| **第一批** | L1 接线筛选 + `allow_partial` 接线 + 成果页「覆盖 N/M 条」提示 | 后端 1 函数 + 前端 2 控件 |
| **第二批** | L2 记忆列表多选 + 批量发起（含覆盖提示与 `allow_partial`） | 纯前端 |
| **第三批（按需）** | L1.5 时间范围筛选 → L3 `subject_id` 主体聚合 | 中 → 大 |

---

## 六、一句话口径

**现在就能做「按定时把最近一批记忆整理成清单」，也能做「按类型 / 关键词圈定一批来整理」（只差一次接线）；但还不能做「按某个客户或某个主题自动聚合」——那需要先补数据模型。**
