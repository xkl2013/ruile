### 0.5 设计原则（所有界面改动必须过一遍）

**尽可能简洁，让使用者一眼看上去就知道如何使用。** 落地为四条可检查的规则：

1. **一屏一件事**：每个页面 / 每个 tab 只讲一类内容，不把多种明细堆进一屏。
2. **一屏一个主按钮**：底部只保留一个主 CTA / 视觉锚点（例：概览底部只有一个会话输入条）。
3. **同一条信息只出现一次**：同一数字、同一入口不重复出现（例：文件有 tab 就不再放快捷卡片；待办数只在摘要出现、tab 一律不带角标；用户信息 / 动态已在右侧常驻栏，空会话内容区就不重复铺）。
4. **能一行说完就不做卡片**：次要信息用一行带「›」呈现，不做 tile / 二级页入口卡。

### 0.6 v1 模型口径：一个服务 = 一个客户

**第一版固定成一服务一客户，聚焦园所工作场景。** 这是模型层的硬约束，所有界面按此收：

| 项 | v1 口径 |
| --- | --- |
| 绑定关系 | **1 : 1**——一个服务绑定**一个客户**（家长 / 学员家庭，如「果果家」）；绑定在**后台配置**（前端创建不选客户），之后不可再挂第二个 |
| 界面称呼 | 模型层叫「客户」，**界面不出现「客户」一词**（客户 / 商机 / 工单属对外交付语汇）；界面**直接显示家庭名**，必要处用「家长与学员」 |
| 客户信息 | 只保留园所真正会用的三项：**家庭名 / 学员（姓名 · 班级）/ 主班老师**；其余（`subject_type` / `subject_key` / 层级）全部后端生成，界面不出现 |
| v1 覆盖场景 | ① **招生跟进**（线索 → 到访 → 成交，与已交付的招生整理模板同源）② **家长沟通与服务** ③ **新生入园适应与班级保教**。场景在**后台配置**（前端不选） |
| v1 不做 | 园所运营与检查（保育巡查 / 安全检查 / 食堂等）后置；**不做**多对象 / 对象列表 / 对象层级 |
| 连带删除 | 「服务对象」整页（列表与详情）**不建**——**注意：代码里已存在 `ServiceSubjectsView.vue` 与 `/subjects` 路由，属本版要删的存量**（§3.9）；`⋯ → 更多 › 服务对象` 菜单项删除；服务头与概览的**成员数 / 对象数**删除（改显示这一个客户）；**前端创建表单只留「服务名称 + 描述」** |
| 不受影响 | 重点记录（= 这个客户的事实变化，自动派生）、动态（= 这个客户 + 本服务的动作）、待办、文件——都是“这一家”的视角，模型不用改 |

**为什么这么收**：此前的模型是“一个服务装多个对象”，于是每个服务都要先解释“这是谁的对象”，创建时要手填机器键，用起来像一套通用 CRM —— 但园所的真实工作是**围着一个个家庭转**的（这个家庭在招生跟进、那个家庭在入园适应）。把对象收成 1:1 之后，「服务」就等于「这一家 + 该场景的活」，界面上不再需要对象列表、成员名单、对象筛选这些概念。

### 4.2 重点记录由工作指令派生

- **规则（P1 先规则，后续可换 LLM、规则兜底）**：工作指令里写了「记录 / 重点记录 / 关注 / 跟进 + 名词短语」，X、Y 直接解析为该服务的字段（`Label` = 指令原词，`ExtractionHint` = 指令原句片段，`Aliases` 含指令措辞），带「指令」角标，排在默认字段之前。**界面侧已有「指令」角标位**（`ServiceSettingsView.vue:97-142`）；**需核对后端 `buildInstructionBlueprint`（`service_space.go:2220`）是否已含这条规则抽取**——这是本版唯一的「读到就不能算完」的点。
- **为什么必须加**：`buildInstructionBlueprint(instruction)` 原设计只做两件事——按关键词定空间类型、指令含“会员 / 家长 / 续费 / 孩子”就切到固定 5 个会员字段否则用默认 3 个。**指令里点名的信息不会变成字段**。最直接的证据：内置模板 t1「招生咨询全流程」的指令原文写着“记录家长顾虑、到访意向和下一步跟进”，但它带的 `commonFields` 里**没有“到访意向”**——模板自己的指令和字段都对不上。
- **字段名称不是普通文案，它决定 AI 抽取命中率**：抽取按「`Label` + `Key` + `Aliases`」在对话文本里做字符串匹配。写「到访次数」匹配不到家长说的「今天来了 3 次」。因此：推荐字段的措辞按家长说话习惯预置；**别名**收进次级设置；已选字段用**可删除的标签**展示；右侧给**实时预览卡**（现状已有雏形）。
- **边界**：改指令**不会**静默重算已配好的字段（避免运行中的服务被静默变更）——「↻ 按新指令重新推荐」入口放在「重点记录」面板里，由用户确认后追加；指令没提任何“记录 X”时维持现状默认字段。
- **蓝图退场后的残余风险**：用户希望“整体重排概览栏目”时没有一次性动作，只能靠改指令间接触发；若内测出现此类诉求，再考虑给「按新指令重新推荐」加一个覆盖概览的范围选项。

> **为什么不干脆删掉蓝图**：它是服务空间数据契约里为“模型不许直写业务表”立的护栏，且 `service_space_blueprints` / `template_applications` 两张表与审计字段在跑。删掉等于回退契约。本版只做一件事：**把护栏收回墙里**（`POST /:service_id/blueprint/preview|confirm` 保留，界面不设入口）——**这一步已经做完 ✅**。

### 11.3 目标设计

#### 11.3.1 作用域：记忆挂在「服务」上，不挂在「对象」上

§0.6 已定 v1 一服务一客户 ⇒ **记忆作用域 = `service_id`（= 一个家庭）**，三层：

| 层 | 载体 | 作用域 | 注入方式 |
| --- | --- | --- | --- |
| L1 会话工作记忆 | `session` / `agent_runs` | 单次会话 | 对话内自带 |
| L2 **服务档案（核心）** | `service_facts` + `profiles` + `summaries` | 一个服务（= 一家） | 会话启动必带（分层，见 11.3.4） |
| L3 组织记忆 | 知识库 / 平台模板 / 专家 | 租户（跨服务共享） | 检索式，**不常驻** |

`subject_id` **保留列但不再要求**：`SubjectPolicy.Required` 置 `false`（后台可关），新增事实一律 `subject_id=''`——与 `refreshServiceProfileFromFacts:1388` 的既有取值口径一致，不改代码语义。

#### 11.3.2 存什么：`fact_type` 从 2 种扩到 4 种

| # | 类型 | `fact_type` | 有 schema | 抽取方式 | 界面落点 |
| --- | --- | --- | --- | --- | --- |
| 1 | 画像字段（含服务偏好 / 关注点） | `profile_field` | ✅ | 规则 + LLM 兜底 | 概览「重点记录」 |
| 2 | 进展 | `progress` | — | LLM | 概览摘要「进展」 |
| 3 | 决策与承诺 | `decision` | — | LLM | 概览摘要「阶段结论」 |
| 4 | 外部来源 | `organize_output` | — | 导入整理产物（已有） | 文件 / 资料 |

「偏好与关注」**留在 `profile_field`**（已有 `service_preference` / `key_focus` 字段），不另立类型——避免一个概念两处存（§0.5 第 3 条）。
**「未完成项」（原 `open_loop`）已砍（v3.2）**：它跟「待办」是同一件事的两份存法。从对话里抽出的"还没做完的事"**直接落成一条待办**（进 `service_reminders`），不做记忆写入——见 §11.3.7。

#### 11.3.3 写入：四道闸（把现有链路补全）

```
用户消息 / 整理产物 / 待办变更
  ↓ 闸1 抽取     规则命中 ∪ LLM 兜底（有成本，见下）
候选事实
  ↓ 闸2 判重     同 (service_id, fact_key) 已有事实 → 不新建提案，转「更新建议」
  ↓ 闸3 冲突     同 fact_key 多值 → 提案并列 old / new，冲突入待确认
  ↓ 闸4 作用域   固定 subject_id=''
pending 提案 → SSE 内联卡片 → 用户确认 / 拒绝 → AppendFact（只追加，永不 UPDATE）
```

**闸1 的 LLM 兜底（控成本三条件，全满足才触发）**：① 规则零命中 ② 消息长度 ≥ 阈值 ③ 同会话连续未抽到轮次 ≤ N。走**租户本地模型**；模型不可用时**静默跳过、不阻塞主流程**（与整理模块的兜底口径一致）。
**闸3** 需给 `proposal_items` 增加 `conflict_with` 字段（存被覆盖的事实 ID）。

#### 11.3.4 注入：从「全量拼」改为「分层 + 按需」

现状 `ReadMarkdownContext:3793` 是 facts → context_sources → artifacts 共用一个 256KB 池先到先得。改为三档预算：

| 档 | 内容 | 预算 | 何时读 |
| --- | --- | --- | --- |
| 常驻 A | `profile_values`（≤ 10 项）+ `summary.sections` | ≤ 4 KB | 每次会话 |
| 常驻 B | `facts` top-K，排序 `created_at DESC`（新近度；v3.4 去掉 `confidence`，见 §11.3.10） | ≤ 12 KB | 每次会话 |
| 按需 | `context_sources` 摘要 + 产物 markdown 全文 | ≤ 240 KB | 命中关键词 / 用户 `@` 引用 |

对齐 WorkBuddy「精选优于堆砌（selection over stuffing）」与「廉价身份、深记忆按需」。**画像是小且稳定的高价值信息，必须先占预算；产物全文是长尾，只在需要时读。**

#### 11.3.5 治理：补齐六件事

| 能力 | 现状 | 本版做法 |
| --- | --- | --- |
| 来源查看 | 数据有（`source_type/source_id/source_version`），界面无 | 事实卡片一行小字「来源 · 日期」+ evidence 原文，可跳原会话 |
| 纠正 | 无 | `ResolveFactProposal` 已支持传改后的 `items` 入参（界面未用）→ 补「改一下再确认」：卡片<b>原地展开编辑表单</b>，<b>只改值</b>（标签 / key 不动）、不弹窗不跳页；确认后新值 append 成新事实（evidence 标注「用户改过：原建议 X」），旧事实照常标 `superseded_by`，改前 / 改后 / 修改人进审计（原型 v1.34 场景 12 / 13 可点开看）。**编辑器分两型（v1.37）**：值含并列项（、/；分隔且 >1 项，如「家长关注点 = 时段冲突、价格、接送距离」）用 **chips 逐项增删**——点 × 删一项、虚线框加一项、确认按钮实时显示项数「确认修改（N 项）」，确认时按整组走 items 入参；单值（如「意向班型」）仍是文本框。**编辑态接管按钮行（v1.41）**：进入编辑后卡片常驻的「确认 / 忽略」按钮行（含提示行）**整行隐藏**，编辑表单的「保存修改 / 取消」是这一屏唯一的按钮组——一屏出现「确认」和「保存修改」两个主按钮，用户必然犹豫点哪个（§11.3.8 原则 1/2 的直接推论）。不提供并列项整段文本改写：并列项边界肉眼不可靠，整段改容易把「接送距离」误改成「接送 距离」。**v1.38 简化：「改一下再确认」不再是按钮**——点值本身即进入编辑（值行 hover 变浅绿），编辑态主按钮文案「保存修改 / 保存修改（N 项）」；卡片常驻按钮由 3 个降到 2 个（确认 / 忽略） |
| 冲突替换 | 无 | `proposal_items.conflict_with` + 确认后新事实写入、旧事实标 `superseded_by`（仍只追加） |
| 时间衰减 / 降权 | 无 | 新增 `decay_at`；画像取值排序 = `created_at`（v3.4 去掉 `confidence`）；长期未复述的进展类事实降权 |
| 删除 / 回滚 | 无 | `service_facts.deleted_at` 软删 + 审计；提案 `rejected` 可翻回 `pending` |
| 临时停用 | `frozen` 只在 profile/summary | 补 `service_facts.disabled_at`（例：孩子升班后，旧班级信息不再注入） |

> **界面暴露口径（v1.38）**：上表是**数据层能力**（8 项），界面**只暴露 3 个动作 + 2 个状态自适应切换**——档案行尾 ⋯ 只给「改这条 / 临时停用（停用态→恢复启用）/ 删除（删除态→恢复这条）」；「查看来源」不是菜单项（行内「来源」列本来就能点开）；**降权不给用户旋钮**（系统自动衰减，界面只显示「已降权」状态）。原则：系统能自己做的事不摆到用户面前。

#### 11.3.6 界面：三处承接（过一遍 §0.5 四条）

1. **对话流内联卡片**（已有 `ServiceFactProposalCard.vue`）：保留，改「一行摘要 + 展开看证据」，默认收起；**常驻按钮 2 个**（确认 / 忽略），改 = 点值本身（v1.38）。按钮行右侧**常驻一行小字「提取的不对？点上面的值直接改」**（v1.39，对话流与台账两处）——「点值即改」看不出来能点等于没有：可发现性靠这句话兜底，不靠用户猜。**处理后的收束 = 一行「数据变更语句」（v1.42）**：点「确认 / 忽略 / 保存修改」后，卡片**原地收成一行具体陈述**，四型——① 新增：`已写入服务档案 · <标签> = <新值>`；② 覆盖：`已写入服务档案 · <标签>：<原值> → <新值>（原值标注为已被替换）`；③ 改过值的新增类：附「你改过，原建议 X」（覆盖类改前已在句中，不再附）；④ 忽略：`未写入档案 · <标签> 的这条建议已忽略（可翻回）`；句尾统一 `· 时间 · 操作人`。**数据来源**：`ResolveFactProposal` 返回的 `proposal.items + status + resolved_at/resolved_by` + 卡片已有改前值，前端零新增接口（真实组件 `ServiceFactProposalCard.vue` 的 `resolvedMessage` 已同步改为具体语句，替换原「事实已写入服务空间档案」泛化文案）。**为什么不加第二条聊天气泡**：同一件事说两遍违反「信息只出现一次」；卡片原位折叠天然保序。⚠️ **但请区分「实时态」与「持久态」**：上面这行语句目前**只存在于 Redis 24h 回放缓冲里**（`stream/redis_manager.go:40`），**刷新页面后卡片即消失**——历史重建的两条路径（agent 模式走 `reconstructEventStreamFromSteps`、RAG 模式走 `rag-pipeline-history.ts`）都不认识 `service_update_proposal` 事件类型。补齐「落库 + 刷新归位」的工程做法见 **§11.3.11**，这是 v1.42 界面上线的前置依赖。**语句里不放「撤销」**：确认后发现错走「服务档案 → 行尾 ⋯ → 改这条」（软删 + superseded，审计可查）。**计数联动**：已处理提案即时退出「要你确认」组与服务头「待办 N」（`pendingProposals()`，与待办 `openTodos()` 同口径）——一本账越处理越短。
2. **「待确认」并入服务头「待办」**（v3.2 修订，见 §11.3.7）：待办面板两组「要你去做 / 要你确认」，pending 提案集中在「要你确认」组——补上"查看和纠正"的入口（解决 G4），且不再新增第二个计数入口。
3. **概览「重点记录」可溯源**：每条值下一行「来源 · 日期」，点开看 evidence；**不设类型筛选**（v1.38 砍掉 4 个 chips——一家十几条记录，筛选是多余的一步）。

> **计数只出现一次**：处理量只在服务头「待办 N」出现（N = 待办 + 待确认），对话流卡片与面板标题都不带数字（§0.5 第 3 条）。

#### 11.3.7 待办与待确认：一个入口，两组活（v3.2 修订）

**问题**：v3.1 给「待确认」单开一个入口（右侧常驻栏「待确认 N ›」），与「待办 N」并排后是**两个数字、两个入口在说同一件事**——"等你处理"。用户反馈"分类太多用不明白"，且本模块历史上已犯过一次同类错（`service_reminders` 默认状态机 9 态里混进 `candidate` / `generated` / `recompute_required` 等 AI 提案生命周期，见 §4.3.4）。

**裁定：实体不合并、入口必须合并。**

| | 待办 | 待确认 |
| --- | --- | --- |
| 实体 | `service_reminders` | `service_fact_proposals` |
| 回答的问题 | 这件事**做了没有** | 这条信息**对不对** |
| 完成动作 | 去做 / 勾完成 / 推进状态 | 确认 / 改一下再确认 / 忽略 |
| 有无负责人 / 评论 / 子待办 | 有 | 无（归属记忆系统） |

二者完成动作不同，混一张表会让每条的按钮都不一样，**不能合成一个实体**；但用户心理上是同一个动作——"有事等我处理"，**呈现必须收敛成一个入口**：

1. **一个入口**：服务头「待办 N」，N = 未完成待办 + pending 提案。右侧常驻栏**撤掉**「待确认 N ›」（不再有第二个数字）。
2. **面板两组、用动作词命名**：「**要你去做 · N**」（`service_reminders`）/「**要你确认 · N**」（`service_fact_proposals`，含 old → new 冲突并列）。分组按动作命名而非对象分类——用户照着做，不是照着学。
3. **一句话边界**：**AI 产出"要去做的事"→ 落成待办；AI 产出"要改档案的信息"→ 进待确认**。从对话抽出的"还没做完的事"直接落成待办，不再存成 `open_loop` 记忆（fact_type 5 → 4，见 §11.3.2）。
4. **顺带收窄**：`service_reminders` 的 AI 生命周期态（`candidate` / `generated` / `recompute_required` / `stale`）继续按 §4.3.4 不下发前端渲染。
5. **行内动作收窄（v1.38）**：待办行**点行首 ○ 即完成**（唯一主动作）；「开始处理 / 不做了」收进行尾 ⋯；协作数改为信息行（非按钮）。原来「点行展开 4 个按钮」要两次点击才能完成一件事，现在**一次点击完成最常见的事**。

> 对应原型 v1.35：场景 13「待办 · 一个入口两组活」（原「右侧常驻栏 · 待确认台账」取消，常驻栏撤行）；场景 12 卡片计数文案同步。

#### 11.3.8 交互简化：一条信息只有一个动作（v3.3 新增 · 原型 v1.38）

**动机**：v1.34–v1.37 迭代里动作越加越多（卡片 3 按钮、待办 4 按钮、档案菜单 5 项）——**没人愿意用的功能等于不存在**。原则四条：

1. **能点对象就不加按钮**：点值即改（待确认卡）、点 ○ 即完成（待办行）——最高频动作零学习成本。
2. **例外动作收进 ⋯**：开始处理 / 不做了；用户不用先学分类再找按钮。
3. **按状态自适应**：已停用的行只给「恢复启用」、已删除的行只给「恢复这条」——不可能出现的动作不出现。
4. **系统能做的事不给用户旋钮**：降权由系统按 `decay_at` 自动衰减，界面只显示状态。

| 位置 | 简化前 | 简化后 |
| --- | --- | --- |
| 待办行 | 点行展开 4 按钮（完成 / 开始处理 / 协作 / 不做了） | **点 ○ 即完成**；⋯ 收 2 项；协作数 = 信息行 |
| 待确认卡 / 台账项 | 3 按钮（确认 / 改一下再确认 / 忽略） | **2 个**（确认 / 忽略）；**点值即改**，编辑态主按钮「保存修改」 |
| 档案行尾 ⋯ | 5 项菜单 | **3 项**（改这条 / 停用↔恢复启用 / 删除↔恢复这条），状态自适应 |
| 概览「重点记录」 | 4 个类型筛选 chips | **砍掉** |

> **能力不删，只收窄暴露面**：治理数据层仍是 8 项能力（§11.3.5），界面只暴露 3 动作 + 2 状态切换；提案的「改一下再确认」能力仍在（点值即改）。**能一行说完的不做卡片，一个动作能办完的不给第二个按钮**（§0.5）。

#### 11.3.9 明确不做（防蔓延 / 合规红线）

1. **不做跨服务记忆**：一服务即一家，跨服务共享记忆 = 隐私越界。
2. **不做儿童画像类事实**：`profile_field` 禁止出现性格 / 行为 / 发育 / 能力评价类字段（合规：不对儿童安全、行为、发育做判断）。
3. **不做绕过确认的自动画像改写**（`organize_output` 这类用户主动导入的既有路径除外）。
4. **不做程序性记忆**：工作指令（`instruction`）与专家是"怎么做"的载体，**绝不进 `service_facts`**——`:2641` 已显式排除「语气 / 口吻」，本版把这条边界升级为硬规则；要沉淀固定做法请走后台模板 / 专家。
5. **不做事实编辑历史浏览界面**（只保 `superseded_by` + 审计可查）。

#### 11.3.10 删掉「置信度」：一个恒真的假信号（v3.4 新增 · 原型 v1.40）

**问题**：`service_facts.fact_value` 里带一个 `confidence`，卡片上显示成「置信度 90%」，逼用户做一次判断——"90% 算高吗？我要不要信？"。实测下来它**不承载任何信息**：

| # | 事实 | 代码依据 |
| --- | --- | --- |
| 1 | 它是**硬编码常量**，不是置信度 | `service_space.go:1851` `confidence := 0.9`；唯一变化是"字段阈值更高时抬到阈值"（`:1852-1854`）。所有抽取结果一律 ≥ 0.9——不管是"孩子下个月升大班"这种明确句，还是含糊表述 |
| 2 | 它的准入门槛**恒真**，从未拦下任何一条 | `profileFactMeetsConfidence`（`:1226-1235`）比较 `confidence >= field.ConfidenceThreshold`；模板字段阈值恒为 `0.8`（`:2549-2581`）⇒ `0.9 ≥ 0.8` **永远成立** |
| 3 | **只在一半的事实上有，且那一半是假的** | 用户确认路径才写入（`:1756`）；系统导入整理产物的事实（`:2099`）**根本不带** confidence ⇒ 读取时 `.(float64)` 失败，`profileFactMeetsConfidence` 直接 `return true`（等于没有这道闸） |

#### 11.3.11 数据变更语句的持久化：引擎零改动的 12 文件改动（v3.7 新增）

### 12.2 三个漏点

**漏点 1｜漏带 header 就静默退回个人作用域**（`agent_run.go:55-58`：无 header 直接 `c.Next()`）。前端带 header 的只有 9 处（`api/chat/index.ts:19 / 25 / 39 / 69 / 83 / 97 / 107` + `views/chat/index.vue:887 / 1896`）；**没带的**：`generateSessionsTitle`（`api/chat/index.ts:29`）、`stopSession`（`:101`）、`createSessions`（`:5`）、旧 `knowledgeChat`（`:43`）/ `agentChat`（`:48`）。
→ 成员 B 在空间里：**列表能看到（空间级），点开 / 停回合 / 生成标题 404**（`user_id=B` 不匹配 → `ErrSessionNotFound`）。**单账号下永远复现不出来。**

**漏点 2｜创建口完全绕过中间件**（`agent_run.go:60-67`：path 里没有 session_id 就放行）。通用 `POST /api/v1/sessions`（`handler/session/handler.go:94-141`）只写 `TenantID / Title / Description / UserID`（`:122-132`），**既不读 `X-Service-ID`、也不接受 `service_id`**。

**漏点 3｜写入路径同样按作用域，且静默失败**。`SetPinned`（`session.go:255`）、`Update`（`:282`）、`UpdateLastRequestState`（`:311`）共用同一作用域 ⇒ 跨成员时 `RowsAffected = 0` 而**不报错**：**置顶、改名、输入栏状态记忆静默不生效**。

### 12.3 建议改法：把「由 header 决定」改成「由 session 自己决定」

1. **中间件**：path 里有 session_id 时，先用 **tenant 作用域** `GetByID` 取该行；若 `ServiceID != ''` → 走空间授权 + 塞 ctx，**header 降级为一致性校验**（带了但与 session 的 `service_id` 不符 → 403）；若 `service_id=''` → 保持个人作用域。**这一改同时消灭漏点 1 和 3**——前端漏带 header 从此只是「行为一致」问题，不再是 404。
2. **创建口**：通用 `CreateSession` 接受 `X-Service-ID` / `service_id`，在 `service.Authorize` 校验成员资格后写入 `ServiceID`（`handler/session/handler.go:94-141`）。
3. **前端**：**无需新增调用点**——空间内创建已全部走 `createServiceSession`（`ServiceHubMenu.vue:132 / 143`、`ServiceHub.vue:786 / 1310`），header 由该封装统一带上。漏点 2 的修复主战场在**后端兜底**（上一条），前端从此**不再依赖「调用方记得带 header」**。

**改动量：中间件 ~25 行（多一次 `GetByID` 查询）+ 创建口 ~20 行；前端 0 处、零迁移**（字段与索引都在）。比 §11.3.11 那 230 行小得多，而且它修的是同一类老坑——**「列表能看、点开 404」**。

> ⚠️ **待核项**：**存量空间会话的 `service_id` 是否都已回填**。本机 docker 未起，查不了库。若历史会话是 `service_id=''`，它们现在处于游离状态 —— 那除了改代码，还要补一条**回填**（或提供 `SetOwnerID` 那样的修复通道，`session.go:296` 已有先例）。

### 13.2 任务二：跨成员会话归属与协作一致性

**目标**：完成 U2。把服务会话归属从“调用方记得带 `X-Service-ID`”改成“后端根据 session 自己判定所属服务”，消除跨成员场景下“列表能看到，点开 / 停止 / 改名 / 置顶却 404 或静默失败”。

**实施范围**：

| 层 | 必做内容 | 主要落点 |
| --- | --- | --- |

| Header | `X-Service-ID` 从归属真源降级为一致性校验；传入值与 session 归属不一致时返回 403 | 同上 |
| 创建 | 通用创建接口接受服务归属；写入前调用服务授权；无服务参数时保持个人会话行为 | `internal/handler/session/handler.go` |
| 写路径 | 置顶、重命名、停止、标题生成、请求状态更新都使用 session 推导出的服务作用域 | session repository / handler |
| 历史数据 | 上线前统计 `service_id=''` 的疑似历史服务会话；有数据时先给出明确回填规则，不按时间或标题猜归属 | SQL 审计 / 一次性修复脚本或迁移 |

**兼容与发布要求**：

- 不新增表、不修改 `sessions.service_id` 类型；正常代码改动应零迁移。

- Header 冲突返回 403，不得静默切换到另一个服务，也不得退回个人作用域。
- 历史游离会话只允许依据可证明的关联回填；无法证明归属的记录保留原状并输出审计清单。
