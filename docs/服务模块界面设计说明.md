## 1. 设计来源与视觉基线

### 1.1 参考对象与取用方式

本设计参照 WorkBuddy 项目模块列表页的信息架构与版式节奏，**只取结构与交互范式，不取视觉皮肤**（原因见 1.2），**也不取用词**（原因见 7.1 行业语汇约束）。"取结构"是因为服务与项目同构（PRD D10）；"不取皮肤、不取词"是因为面向对象不同（PRD D12）。

参考页的可取之处（判断依据）：

| 可取 | 理由 |
| --- | --- |
| 页头 + 主操作按钮 + 分组列表 + 模板区 的四段式结构 | 一屏内同时给出"我已有的"和"我能新建的"，用户不需要二次寻找入口 |
| 卡片网格承载列表（非表格） | 服务/项目这类实体数量少（个位数到几十），卡片能携带图标与状态标签，比表格行更易扫视 |
| 模板区独立成组 | 把"新建"从单按钮升级为"选择题"，降低新用户第一步的决策成本 |

**不取之处**：参考页是黑白灰 + 无品牌色的视觉体系，与 Ruile 不一致；部分信息取舍（只显示加入时间）在 Ruile 的领域下不成立。详见 1.2、1.3。

### 1.2 视觉基线（Ruile 既有，不新造）

设计稿必须使用 Ruile 现有主题令牌，不得引入新色值。已核对的基线：

| 令牌 | 值 | 出处 |
| --- | --- | --- |
| 品牌主色 | `#07c05f`（`--td-brand-color-4` / `--brand-main`） | `frontend/src/assets/theme/theme.css` |
| 品牌深色（文字用） | `#038626`（`--td-brand-color-7`） | 同上 |
| 品牌浅底（标签底） | `#e9f8ec`（`--td-brand-color-1`） | 同上 |
| 圆角 | 卡片 6px（`--border-radius-md`）/ 大容器 12px / 胶囊 999px | 同上 |
| 页面底 / 卡片底 | `--td-bg-color-page` / `--td-bg-color-container` | 同上 |
| 文字层级 | 主 `rgba(0,0,0,.9)`、次 `.6`、占位/辅助 `.4` | 同上 |
| 组件库 | TDesign Vue Next（`tdesign-vue-next`） | `frontend/src/main.ts` |

**结论**：参考页的主按钮是黑色实心，Ruile 版一律改为品牌绿 `#07c05f` 实心；标签底一律用 `#e9f8ec` + `#038626` 文字。设计稿中出现的绿色均为上述令牌，非新增色。

### 1.3 逐项对齐表（含 5 处刻意差异）

| # | 参考页元素 | Ruile 落位 | 关系 |
| --- | --- | --- | --- |
| 1 | 标题「项目」+ 副标题「多人协同，打造超级团队」 | 「服务」+「每个服务一个空间，专家在里面干活」 | 同位替换 |
| 2 | 右上角装饰插画 | 保留同位，但降为可选（P2），首版可用抽象线稿占位 | 同位替换 |
| 3 | 主按钮「+ 新建项目」 | 「+ 新建服务」，品牌绿实心 | 同位替换 |
| 4 | 分组「我的项目」 | 「我的服务」 | 同位替换 |
| 5 | 卡片副行「添加于 19 分钟前」 | **改为**「最近活动时间 · 成员数」 | **刻意差异，见 D-1** |
| 6 | 卡片只有 图标/名称/时间/菜单 | **增加**「模板标签」与「我的角色徽标」 | **刻意差异，见 D-2** |
| 7 | 卡片「···」菜单 | 保留，但**按角色差异化**菜单项 | **刻意差异，见 D-3** |
| 8 | 右上「搜索项目」 | 「搜索服务」；无服务时不渲染 | 同位替换 |
| 9 | 分组「从模版创建」+ 5 张模板卡 | 「从模板创建」+ 6 张服务模板卡 | 同位替换，内容改为教培场景 |
| 10 | 两个创建入口（按钮 + 模板卡）语义不同 | **合并为一条路径**：按钮进表单，模板卡进表单并预填 | **刻意差异，见 D-4** |
| 11 | 无空态（该账号已有 11 个项目） | 新增首屏空态设计（第 4 章） | **刻意差异，见 D-5** |

**差异理由**：

- **D-1 为什么把"添加于 X 前"换成"最近活动 · 成员数"**：这是**信息增强**，不是构件差异——服务与项目本就是同一个东西（PRD D10）。参考页副行只回答"我什么时候进来的"，而列表页真正要回答的是"哪个服务需要我现在去看"：加入时间答不了这个问题，"最近有没有人动过"才答得了。因此副行同时给出**最近活动时间**与**成员数**，列表默认排序也据此改为按最近活动倒序。加入/创建时间不删除，收进卡片菜单的「服务信息」里。
- **D-2 为什么给卡片加两个标签**：Ruile 的服务有**四档空间角色**（owner / admin / editor / viewer，见 PRD §8），而参考页的成员只有三档且不分角色显示。用户的 10 个服务里可能有 3 个他是 viewer——点进去能改什么，与 owner 完全不同。**角色必须在外层可见**，否则用户每次都要点进去才发现"我改不了"。第二个标签是**模板标签**：服务由哪个模板创建（如"招生咨询全流程""家长续费跟进"）是列表上唯一的分类线索——PRD D9 已删除独立的"服务类型"字段，类型语义由模板承载，因此这里显示模板名；未经模板创建的显示「自定义」。
- **D-3 为什么菜单要按角色差异化**：见 3.5。参考页的菜单项对所有成员一致，因为它只区分"能看见项目"的人；Ruile 需要在菜单层面就做权限收窄，避免"点开→报 403"的挫败路径。
- **D-4 为什么合并创建入口**：参考页的「+ 新建项目」和模板卡是两个不同语义的入口（空白 vs 有预设），用户需要先想清楚"我要不要模板"才能选对按钮。Ruile 版把"要不要模板"这个决策**后移到表单内部**——按钮永远进表单，表单中指令框右上角是"模板：xxx / 更换"入口（PRD D11），从模板卡点进来的则已预填指令与专家区。这样两个入口殊途同归，用户不需要预判。
- **D-5 为什么必须设计空态**：参考页看不到空态是因为它的账号已有数据。Ruile 是重构后的新模块，**存量用户的第一次打开就是空态**（原有画像会被迁移成默认服务，但未创建过服务的用户是真空）。空态做成"空白 + 一排模板卡"会让首屏显得残缺；正确做法是把模板区提权为主视觉（第 4 章）。

## 2. 路由与信息架构

### 2.1 现有路由实况（代码事实）

前端基路径常量在 `frontend/src/views/service/serviceRoutes.ts`：

- `SERVICE_ROUTE_BASE_PATH = '/platform/service'`
- `SERVICE_MESSAGES_ROUTE_PATH = '/platform/messages'` ← **注意不是 `/platform/service/messages`**
- `SERVICE_CUSTOMERS_ROUTE_PATH = '/platform/service/customers'`
- 侧栏菜单目前只有两项：`messages`（服务提醒）、`customers`（客户空间）；`review`（日报）走 `/platform/organize/daily`

> **这三项目前正是"目录"形态**——它们作为**应用级侧栏**入口出现。**按 D19（v1.11），三项都不再作为目录**：`messages` 按 D17 并入服务内的「事项」，`customers` 与 `review` 直接移除入口。**本节记的是代码事实，不改**；目标形态见 §2.3 与 §10.2。

> **另有一处与会话列表有关的事实**：现状 `ServiceWorkspace.vue` 里的会话列表是**服务空间内部的一栏**（左侧 rail）。**按 D21（v1.14），会话列表移到应用级侧栏的服务名下方，服务空间内不再保留这一栏。** 本节同样只记事实；目标形态见 §2.3 与 §8。

`frontend/src/router/index.ts` 中：

- `service` 路径当前是 **redirect**：`redirect: (to) => resolveServiceRoutePath(to.query.tab)`，即 `/platform/service` **不会停在自身**，会跳到默认 tab（当前为 `/platform/messages` 工作台）。
- 服务相关的页面组件只有两个：`ServiceWorkspace.vue`（工作台）与 `CustomerSpace.vue`（对象工作台）。

**结论**：现状**没有服务列表页**，`/platform/service` 也不是"服务模块首页"，而是一个跳转入口。

| `/platform/service/:serviceId/messages` | 服务提醒 | 由现状 `/platform/messages` 迁入服务上下文 |
| `/platform/service/:serviceId/subjects` | 服务对象列表 | 由现状 `/platform/service/customers` 迁入，路由段按 D12 语汇约束统一为 `subjects`。**应用级侧栏不再有「客户空间」入口**（D19）；存量路由段的迁移与重定向见 PRD Q38 |
| `/platform/service/:serviceId/subjects/:subjectId` | 对象工作台 | 承接现有 `CustomerSpace.vue` |
| `/platform/service/:serviceId/sessions`（含 `/:sessionId`） | 会话工作台（空间默认视图，§8） | **路由保留**（深链与旧书签继续有效）；但**界面上不再有指向它的入口**——会话列表已在应用级侧栏（D21），进服务就是当前会话的对话区。**要不要给它一个入口见 UI-Q11** |
| 其余（artifacts / runs / agents / members / statuses / field-options / settings） | — | 见 PRD §10.1 全表 |

> **迁移风险点**：`SERVICE_MESSAGES_ROUTE_PATH` 目前指向 `/platform/messages`，是**平台一级路径**。迁入 `/platform/service/:serviceId/messages` 会改变 URL 结构，若该路径已被书签、通知链接、埋点引用，需要保留 301/透传重定向。此点列入第 10 章待确认。

### 2.3 路由与呈现（路由 ≠ 界面）

```
/platform/service              ← 服务列表（本模块总入口）
   └── /new                     ← 创建表单
   └── /:serviceId              ← 某个服务 = 服务空间（**进来就是会话工作台**，D15）
          ├── sessions          会话工作台（空间默认视图，§8）
          │      └── :sessionId  会话详情（消息流 + 输入框 + 实时步骤）
          ├── reminders         事项（含子任务、多负责人、评论、历史）
          │                     └ 「服务提醒」并入此页，作为默认视图（D17）
          ├── artifacts         产物
          ├── subjects          服务对象（PRD 已改用 `subjects`；应用级侧栏无此入口，见 D19）
          ├── overview          服务概览（统计）
          ├── runs              运行记录
          └── settings          服务设置
                 ├── members           成员（含"已离开"视图）
                 ├── experts           专家绑定
                 └── reminder-config   事项配置（状态 + 字段选项，同页分区）
```

**路由 ≠ 导航清单（D18）。** 上表是**路由**——它保证深链稳定，也让"把某份东西的地址发给同事"成为可能。界面上**不再有一列导航**：

```
服务空间（D18：没有服务级导航栏；D21：也没有会话栏）
├─ 对话区（自适应，原型实测 956px）：消息流 + 输入框 + 会话标题行
└─ 右侧面板（约 320px，按需浮出）
     产物预览 / 产物列表 / 事项列表 / 服务概览 / 服务设置
     ↑ 由服务头的产物 / 事项入口、对话里的产物卡，或 ⋯ 的「更多 ›」唤起

服务头一行：← 返回列表 │ 服务名 │ 模板徽标 │  产物 3 │ 事项 3 │ 状态 │ ⊕ │ ⋯
                                                            └─ 新建会话 ─┘  └─ 菜单：
              ┌─ 修改服务名称
              ├─ 修改服务描述
              ├─ 分享设置
              └─ 更多 › ─── 服务概览 / 服务对象 / 运行记录 / 服务设置 / 归档 / 删除
```

（**会话列表不在服务空间里**——它在应用级侧栏的服务名下面。见本节下方与 §8.2。）

**为什么把导航栏彻底去掉（D18）**：导航栏的存在本身就在问用户"你要去哪个页面"，可进了服务之后用户只有一个意图——**接着干活**。三版方案（横向 tab 条 → 左侧文字栏 → 左侧图标栏）都还在回答一个用户没在问的问题。**D21 把同一条道理用在了会话列表上**：它和侧栏回答的是同一个问题（"这个服务里有哪些工作"），所以也应该只有一个答案。

服务空间里真正高频的只有"接着干这一段"，次高频的是"这次跑出来的产物和事项"，剩下的是配一次就忘的。所以按**离工作有多近**分三层：

| 层 | 内容 | 位置 | 理由 |
| --- | --- | --- | --- |
| 天天要点 | 会话 | **应用级侧栏，服务名下方** | 会话是工作的单位；挂在服务名下面，从产品任何位置一次点击就能回到那一段工作（D21） |
| 天天要点 | 产物 / 事项 | **服务头右侧**（带计数） | 它们是会话跑出来的沉淀物，与会话同源；服务头是唯一还属于"服务级"的位置（D21 前它贴着会话栏底部） |
| 偶尔要用 | 概览 / 服务对象 / 运行记录 / 服务设置 | ⋯ 菜单的「更多 ›」 | 配一次就忘，不该跟工作入口抢位置 |
| 服务本身 | 名称 / 描述 / 分享 | ⋯ 菜单一级 | 改的是"这个服务是什么"，不是"服务里有什么" |

**量化收益**：去掉 48px 图标栏后，对话区由 704px 增至 **766px**（D18）；v1.14 会话栏上移到侧栏后进一步增至 **956px**（D21，原型实测——省下 236px 会话栏 + 14px 间距）。

> **`sessions` 与 `runs` 是两层不同的东西，不要合成一个入口。** `sessions` 是"我们在做什么"（按会话更新时间排序），`runs` 是"某次执行调了什么"（按运行创建时间排序）。一个会话可以有零次或多次运行，详见 §8.5。运行记录现收在 ⋯ 的「更多 ›」里（D18）——它不是高频入口，但必须可达。

**应用级侧栏里，服务类入口只有「服务」一项**（D19），其下**直接列出服务作为二级项**（D20），每个服务再往下**挂它自己的会话**（D21）——一级项指向服务列表页 `/platform/service`，二级项就是服务本身，**点一下直接进那个服务的工作台**，三级项是具体的某一段工作，**点一下连会话一起打开**：

```
应用级侧栏（D19 / D20 / D21）  —— 视觉规格以 KnowledgeBaseMenu.vue 为基准，见 §2.3.1
服务          8  ⌄          ← 一级项：进服务列表页；⌄ 是折叠控件（hover 才现）
  秋季招生咨询          ⌄     ← 二级项：点一下直接进服务空间。**只有文字、没有图标**（v1.15）
    秋季招生线索跟进         ← 三级项：该服务下的会话（D21），点一下直接打开这一段工作
    家长顾虑类型归纳
    开放日到访名单整理
  教研资料沉淀          ⌄     ← 未展开的服务只显示自己（手风琴：同时只展开一个）
  家长续费跟进 ●        ⌄     ← ● 右侧绿点 = 当前所在服务
    …
  （草稿与归档不进二级）
```

> **三级只靠缩进分层，不靠图标**（v1.15）：一级文字 14px → 二级文字 34px → 三级文字 54px，**每级步长 20px**。原先二级文字被 20px 模板图形推到 54px，三级为了"与父项文字左对齐"也写在 54px；图标删掉后那个前提不存在了，三级改为**再缩进一级**（步长与一级→二级一致）。

> **文案口径（v1.13）**：一级项文案是「**服务**」，不是「我的服务」。「我的服务」在本产品里**另有所指**——它是服务列表页内的**分组标题**（§3.1，与「从模板创建」并列）。两处不要混改。

| 规则 | 口径 |
| --- | --- |
| 一级项 | 点击 → **服务列表页**；已经在列表页时只给一句「已在服务列表」提示，不重复渲染 |
| 二级项 | 点击 → **直接进该服务的工作台**（不是"先回列表再高亮"）；**已经在那个服务里就什么都不做**——会话选中态与右侧面板都还在，别重建界面把人从工作里弹出来。同时**在侧栏展开这个服务的会话列表** |
| 三级项 | 点击 → **进那个服务、并直接打开这一条会话**；**已经在这个服务里就只切会话**，不重建界面。已在空间内时，打开的是对话区那一条（§8.1） |
| 二级项的折叠箭头 | 该服务**有会话可看**时都有箭头，**hover 才出现**（占位固定，出现时不挤动文字）；**手风琴**——同时只展开一个服务，点开一个就收掉上一个。理由：全展开会把侧栏撑成一面墙，"我要去的那个服务"反而找不到；一次只开一个，也正好把"我手上正干着哪个服务"讲清楚 |
| 展开态的默认值 | **进入服务空间时自动展开当前服务**，其余折叠。否则会出现"进了服务却看不到会话列表"——**会话栏已经不在了，侧栏是会话列表唯一的落点**。反过来，从服务空间回到列表页时**保留展开态**（只是不再高亮），方便再点回去 |
| 列什么 | 二级只列**可进入工作的服务**（活跃 / 暂停）。**草稿不进二级**——草稿不是一个能进去干活的工作现场（点它只会回到创建表单），留在列表页更合适；**归档不进二级** |
| 顺序 | 二级按**最近更新**（与列表页默认排序一致）；三级按**置顶优先 → 最近更新**（与 §8.3 同一口径：`sessionsOf()` 一处排序，侧栏与概览统计共用）。侧栏是全局导航，**不跟随列表页的搜索与排序**变化 |
| 三级列多少 | 每个服务最多列 **8 条**，超出时末尾给一行「**还有 N 个 ›**」，点了把这个服务的会话全部列出（该容器独立滚动）。侧栏是导航不是全量列表；条数上限是否调整见 PRD Q39 |
| 当前项 | 所在服务在二级里**高亮**——底板变灰 + **右侧 12px 品牌绿点**。**注意不是绿字**：light 主题下 hover 与当前项的底色同值（`#f3f3f3`），当前项**没法靠底色表达**，只能由右侧圆点承载（知识库是同一做法）。在列表页与创建表单里，二级**没有**高亮项 |
| 当前会话 | 当前打开的那一条**加底色 + 文字转主色 + 字重 500**。**这里不用圆点**：三级行右侧的位置要留给 hover 才现的 ⋯，靠三个属性一起表达才有足够区分度（底色与 hover 同值）。同样只在服务空间里算 |
| 会话行的 ⋯ | 只在**当前所在的那个服务**的会话行上出现（hover 到行才显示），菜单是**重命名（行内）/ 置顶 / 删除**，与列表页卡片菜单同构。别的服务是"入口"，进来才是"在里面"——写操作都发生在自己脚下，不会出现"在列表页顺手删掉某个陌生服务里的会话"这种事故 |
| 没有会话的服务 | 展开后给一行「**还没有会话，去开一段 ›**」——是**入口**，不是说明文字（点它进这个服务并把光标落在输入框）。这与 §8.4 第 3 条"空态不是空白"是同一条规矩 |
| 计数 | 「服务」右侧计数 = **二级条数**（不含草稿与归档）。与二级列出的内容**严格一致**，避免"计数比列表里多一个"的疑问；是否把草稿计入见 PRD Q39 |
| 长名称 | **单行截断**（`text-overflow:ellipsis`）并挂 `title` 全名——侧栏宽度固定，服务名可达 255 字符、会话标题也可达同样长度，不截断会把侧栏撑开 |
| 空态 | 没有服务 → 「还没有服务」；服务都已归档 → 「服务都已归档」。与列表页 §4.2 的两态口径一致，都是**灰字一行、不给操作按钮**（侧栏不是操作区） |
| 在创建表单里点侧栏 | 等同**离开表单**，走与「取消」同一套二次确认（§5.5）；确认离开后**落到你点的那个地方**——点一级项回列表，点二级项进那个服务，点三级项进那个服务并打开那条会话 |

**为什么要挂二级（D20）**：v1.11 把侧栏收敛成一项之后，"进服务"变成**先进列表、再点一次卡片**。而侧栏本来就是导航——**能一次到位就不该让用户中转**。
**为什么二级也带折叠控件**（v1.13 修订）：v1.12 曾写"不做折叠控件，折叠没有信息量"——**该判断作废**。理由是同一条侧栏里不该出现两种折叠范式：知识库（`KnowledgeBaseMenu.vue`）的一级标题右侧就有一个 hover 才现的折叠箭头，服务这一项若没有，两个模块的交互会长得不一样。默认**展开**（"我手上是哪几个服务"本身就是有用的信息），箭头照知识库的规矩 **hover 才出现**。
**为什么会话要挂到服务名下面（D21）**：WorkBuddy 的项目就是"项目名下面直接是会话"——**用户理解工作的单位是会话，不是服务**（这是 D14 的话在信息架构上的又一层落地）。会话原先被锁在服务空间内部的那条会话栏里，意味着"想接着上次那段工作"必须**先进服务、再在一列里找**；挂到侧栏之后，从产品任何位置**一次点击就回到那一段工作**。代价是服务空间少了一条腿——但那条腿本来就只回答"这个服务里有哪些工作"，而这个问题现在由侧栏回答，**同一件事不该有两个答案**。
**为什么不把列表页搬进侧栏**：列表页仍在（搜索 / 排序 / 创建 / 空态都在那儿），二级只是**同一批数据的快捷方式**，入口与列表页不是二选一。
**服务空间本身**：二级与三级都只是"从外面进来"的近路，服务空间里仍是对话区 + 右侧面板两块，连服务头的 `← 返回服务列表` 也保留。

#### 2.3.1 视觉规格：以知识库菜单为唯一基准（v1.13 / v1.14 / v1.15）

这一组**不自己定样式**，整组照抄产品现有组件 `frontend/src/components/KnowledgeBaseMenu.vue`（侧栏容器取自 `frontend/src/components/menu.vue`）。理由：**同一根侧栏里出现第二种菜单样式，比"少一点个性"更难解释**。

| 元素 | 规格 | 来源 |
| --- | --- | --- |
| 侧栏容器 | 宽 **260px**、内边距 `8px 6px 6px`；logo 行高 50px | `menu.vue` 的 `.aside_box` / `.logo_row` |
| 栅格基数 | `--inset-x: 14px`——**一级项文字的起算点**，也是整组缩进链的基准（二级 = 基准 + 20px、三级 = 基准 + 40px） | `menu.vue` 的 `--sidebar-inset-x` |

> **三处最容易做错**：① light 主题下 `hover` 与 `secondarycontainer` **同值**（都是 `#f3f3f3`）——所以"当前项"**没法靠底色表达**，必须靠右侧圆点（二级）或文字色 + 字重（三级）；这不是可选装饰。② 一级项**不加激活底色**（知识库标题本身不表示"当前在哪个知识库"），当前项一律由二级列表里的圆点负责。③ **三级与二级的缩进关系，取决于二级有没有图标**——v1.14 原型第一版给三级用了 46px，真浏览器里看是"三级比二级更靠左"，那就不像子项了；**当时二级文字被 20px 图标推到了 54px**，所以得出的结论是"子项文字应与父项文字左对齐"（同为 54px）。**v1.15 图标删掉、二级文字回到 34px 之后，那条结论的前提就不存在了**，三级改为"在父项文字基础上**再缩进一级**"（54px，步长 20px，与一级→二级一致）。**教训：一条布局结论要连同它的前提一起记下来，否则前提变了、结论还留着。**
>
> **四处对本基准的有意偏离（都已在原型里验证）**：① **二级项右内边距由 12px 收为 8px**——右侧多了折叠箭头，收 4px 之后箭头右边缘与一级项的箭头右边缘正好对齐（同为容器右边界内 8px）；不收就会出现"两个折叠箭头差 4px"的错位。② **三个右侧控件恒为占位、只切 `opacity`**——若让箭头"出现时才占位"，鼠标一划过来左侧文字会横向抖一下。③ **侧栏自身独立滚动**（视口高度 + `overflow-y:auto` + `position:sticky`）——会话挂到侧栏之后，一个服务展开、再点「还有 N 个 ›」可能列出几十行；不独立滚动就会把整页撑长、侧栏跟着页面一起滚走（真实产品里侧栏本来就是固定的）。④ **二级项不设左侧模板图形**（v1.15，按老师意见删除）——知识库的二级项（`.kb-menu-item`）左侧有一个 20px 的 scope 图形，本组**不要**：一级项「服务」本身就不带图标，二级再带一个会让"服务列表"看起来像另一套菜单；去掉之后整根侧栏彻底无图标，层级改由**等距缩进**（每级 20px）表达。**代价有两项，都要知道**：① 侧栏不再表达"这个服务用的是哪个模板"——模板信息只留在**列表页卡片**上（`.card-icon` + 模板徽标，同一对函数 `tplIconPath()` / `icon()` 继续服务那一处）；② 与知识库菜单**少了一个对齐点**，这一节不再能整组照抄。**为什么这笔交换划算**：侧栏的首要任务是"把我常去的那几个服务放在手边"，而图标从来不是识别服务名的主要手段（名字就在旁边），八个图形挤在一列里反而是噪声。
>
> **实现注意（v1.14 真机验证时发现）**：**二级项与折叠箭头是两个独立可点区域**——点项目本身是"进服务"，点箭头只是"展开 / 收起会话列表"。原型里箭头是嵌在二级项内部的 `span[role=button]`，靠 `stopPropagation` 区分。**实现时不要写成 `<button>` 嵌 `<button>`**（HTML 不允许，屏幕阅读器会读成两个按钮却分不出层级）：二级项用 `div` + `role="button"` + `tabindex="0"`，箭头作为**兄弟节点**放在同一行容器里，两者各绑各的事件，并将 **`aria-expanded` 挂在箭头上**。**键盘可达是硬要求**：箭头本身要能 `Tab` 到、`Enter` / `Space` 能触发展开（原型的 hover 才现只是视觉，不改变可达性）。
>
> **v1.13 撤掉的两处自创做法**：一级项的浅绿激活底、二级项的左侧竖线 + 缩进。原型里两者都已改掉——前者让一级项看起来像"被选中的标签"（真实侧栏里没有这种范式），后者在真实产品里也不存在。
>
> **知识库若将来也加三级**：以它为准重新对齐这一节；现在三级规格是本模块按同一套栅格延出来的，**不是**从组件里抄的。

D18 删掉了**服务空间内**的导航栏，D19 是同一件事在**上一层的延续**：**不用"目录"到达能力，用"工作流"到达能力**。原先摆在侧栏的三项各有去处：

| 原侧栏项 | 处置 | 去处与理由 |
| --- | --- | --- |
| 服务提醒 | **移除**（D17） | 并入每个服务内的「事项」——它是**某个服务里的**待办，不是一份跨服务的全局列表。做成全局目录，用户点进去还得再选一次"哪个服务" |
| 客户空间 | **移除**（D19） | 「服务对象」是**服务内的构件**（D7 / D12），入口在服务头 ⋯ 的「更多 ›」里。它天然带服务上下文，脱离服务单独成页反而说不清"这是谁的对象" |
| 日报 | **移除**（D19） | 日报是工作跑出来的**结果**，与会话/产物同源（同 D18 对产物与事项的判断），不是要去逛的一级页面。**落点待定，见 PRD Q38** |

> **别按旧描述改。** v1.11 及以前这里写的是"置于服务类入口的**最上方**"、"不要再按放在「服务提醒」之上来描述"——**参照物已经不存在了**，那三项都不在侧栏里。现在侧栏只有一项（外加它的二级列表），也就无所谓"上下"。

## 3. 页面一：服务列表页

### 3.1 布局结构

自上而下四段，与参考页同构：

```
┌ 页头：标题「服务」+ 副标题                    [插画位（可选）] ┐
│ [+ 新建服务]                                                    │
├ 分组头：「我的服务」                              [搜索服务]     │
│ 卡片网格（4 列，自适应降到 3/2 列）                              │
├ 分组头：「从模板创建」                                           │
│ 模板卡片网格（4 列）                                             │
└─────────────────────────────────────────────────────────────────┘
```

- 内容区最大宽度对齐 Ruile 其他列表页，超出时卡片网格自动换行，不出现横向滚动。
- 两段之间的垂直间距 26px，段内卡片间距 10px，段头与网格间距 10px。

### 3.2 页头

| 元素 | 规范 |
| --- | --- |
| 标题 | 「服务」，16px / 500 / 主文字色 |
| 副标题 | 「每个服务一个空间，专家在里面干活」，12px / 次级色，标题下 4px |
| 插画位 | 右上角，宽约 120px，**可选项**。首版允许不实现；实现时用单色线稿（非彩色插画），避免与品牌绿抢占视觉重心 |

副标题文案说明：不用"多人协同，打造超级团队"这类口号式表达——Ruile 的服务模块是 **AI 助理 + 小范围协作**，主要使用者可能只有 1 人，"团队协同"会给用户错误预期。

### 3.3 主操作区

- 单个主按钮「+ 新建服务」：品牌绿 `#07c05f` 实心，白字，12px / 500，内边距 7×14，圆角 6px。
- 位置：页头下方，左对齐，与下方分组间距 24px。
- 点击行为：进入 `/platform/service/new`（不带模板参数）。
- **不设第二个主按钮**。参考页也只有一个，这是对的——次要路径（空白/模板）在表单内部消化。

### 3.4 「我的服务」卡片网格

**网格**：`repeat(4, minmax(0, 1fr))`，间距 10px。窄屏按 4 → 3 → 2 列降级。

**卡片规格**（三行，高约 74px）：

```
┌────────────────────────────────┐
│ [图标24] 秋季招生咨询       ··· │  第 1 行
│ [招生咨询] [管理员]             │  第 2 行
│ 2 小时前 · 5 人                 │  第 3 行
└────────────────────────────────┘
```

| 元素 | 规范 |
| --- | --- |
| 卡片容器 | 白底、0.5px 边框（`--td-component-stroke`）、圆角 6px、内边距 10×11 |
| 图标 | 24×24，圆角 7px，底 `#e9f8ec`，内含品牌绿图形。**同一模板用同一图形**（图形取自 `service_templates.icon`），不同服务不靠颜色区分 |
| 服务名 | 12px / 500 / 主文字色，单行省略（`text-overflow: ellipsis`） |
| 菜单 | 第 1 行最右，`···`，12px / 占位色；hover 变主文字色 |
| 模板标签 | 11px，底 `#e9f8ec`，字 `#038626`，内边距 1×5，圆角 3px。取值 = 该服务所用模板的 `name`（经 `services.template_key` 解析）。**`template_key` 为空时显示「自定义」**，样式降级为灰底（底 `--td-bg-color-secondarycontainer`、字次级色），不占用模板标签的绿色语义 |
| 角色徽标 | 11px，底 `--td-bg-color-secondarycontainer`，字次级色，同一规格。取值 = 当前用户在该服务的角色（拥有者 / 管理员 / 编辑者 / 只读） |
| 副行 | 11px / 占位色，格式「<相对时间> · <N> 人」 |

**交互**：

| 操作 | 行为 |
| --- | --- |
| 点击卡片主体 | 进入 `/platform/service/:serviceId`。若该服务状态为 `active` 直接进；`draft` 进入创建表单的续填页 |
| 点击 `···` | 展开菜单（3.5），**不触发**卡片跳转（需 `stopPropagation`） |
| hover | 卡片边框提到 `--td-component-border`，背景不变（不用阴影，与 Ruile 其他列表页一致） |

**信息量取舍说明**：卡片上不显示"待办数"。待办数在服务之间不可比（一个服务 3 条待办可能是健康，另一个 30 条可能是堆积），放在列表页会诱导错误比较；它属于服务空间内的概览指标。若后续数据表明用户确实需要在列表页看积压，再加为状态徽标（如"有逾期事项"）。

### 3.5 卡片菜单（角色差异化）

参考页的菜单对所有成员一致；Ruile 必须按角色收窄，**不能出现"点开才报 403"**。

| 菜单项 | 拥有者 | 管理员 | 编辑者 | 只读 |
| --- | --- | --- | --- | --- |
| 打开服务 | ✓ | ✓ | ✓ | ✓ |
| 设为默认服务 | ✓ | ✓ | — | — |
| 重命名 | ✓ | ✓ | — | — |
| 服务信息（创建时间 / 我加入的时间） | ✓ | ✓ | ✓ | ✓ |
| 成员管理 | ✓ | ✓ | — | — |
| 服务设置 | ✓ | ✓ | — | — |
| —— 分隔线 —— | | | | |
| 归档服务 | ✓ | — | — | — |
| 退出服务 | — | ✓ | ✓ | ✓ |

规则：

- 「退出服务」对拥有者隐藏——拥有者退出会导致服务无主，必须先转移所有权（走服务设置内的"转让"流程）。
- 「归档服务」仅拥有者可见，二次确认弹窗需输入服务名（不可逆操作的防误触，见第 6 章状态机 `active → archived`）。
- 只读角色的菜单只有两项（打开 / 服务信息 / 退出），三项也要保持菜单形态而非直接省略入口，否则用户会疑惑"为什么我没有菜单"。
- 「设为默认服务」对应 PRD 的 `services.is_default`，全局唯一（同用户下至多一个）。已是默认时该项显示为「默认服务」并置灰。

### 3.6 排序与搜索

- **默认排序**：最近活动时间倒序。活动 = 该服务下任一事项/产物/运行的时间戳更新。
- **排序切换**：分组头右侧提供排序下拉（最近活动 / 创建时间 / 名称），默认隐藏在选择器内，不占用卡片区。
- **搜索**：分组头右侧输入框，宽 150px，占位文字「搜索服务」。匹配服务名称与描述，前端防抖 300ms，**不搜服务对象与产物内容**（那是服务空间内搜索的职责）。
- **无结果时**：网格区替换为空结果提示「没有匹配「<关键词>」的服务」+「清除筛选」文字按钮，**不隐藏分组头**（否则用户找不到输入框清空）。

### 3.7 「从模板创建」

> **这一节在 v1.17 之后多了一层身份：它现在是模板的*唯一*入口（D23）。** 创建表单里那个"选择模板"按钮已删掉——用户要么从这里带着模板进创建页，要么从页头「+ 新建服务」/ 空态「从空白创建」空白进。因此原本"表单里也能换模板"的退路没有了，**这一节的两个要素变得关键**：① 卡片上那行「预置 N 个专家 · M 个事项状态」是用户点进来之前唯一的判断依据（见本节末）；② 末尾的「全部模板」入口要真的能到模板中心，否则模板数超过 8 个时用户看不到其余模板、又不能在表单里换。**点击后的行为不变**：进 `/platform/service/new?template=<id>`，指令与专家预填、**知识库与技能仍为空**（§5.1）。

| 元素 | 规范 |
| --- | --- |
| 分组标题 | 「从模板创建」，13px / 500 |
| 网格 | `repeat(4, minmax(0,1fr))`，间距 10px |
| 卡片 | 0.5px 边框、圆角 6px、内边距 10×11、白底 |
| 卡片内容 | 图标（20×20，圆角 6px，`#e9f8ec` 底）+ 模板名（12px / 500，单行省略）+ 描述（11px / 占位色，最多 2 行） |
| hover | 边框提到 `--td-component-border`，光标 pointer |
| 末尾 | 「全部模板」虚线卡片，指向模板中心（若模板数 ≤ 8 则隐藏此项） |

**模板卡片必须标注"预置了什么"**。参考页的模板卡只有名称 + 一句描述，用户点进去之前不知道模板会带来什么。Ruile 版在描述下方加一行 11px 占位色小字：「预置 N 个专家 · M 个事项状态」。这一行是模板价值的唯一可量化表达，成本极低但直接决定用户选不选。

**模板与 ExpertPackage 的关系**：服务模板是"服务级预设"（预填**专家组合**、事项状态机、字段选项），与技术侧的 `ExpertPackage`（管理员发布的专家包，见 PRD §5）**不是同一层，且不耦合**——PRD D8 已定模板独立存储为全局表 `service_templates`，其 `config` 携带状态机、字段选项定义与 `experts` 引用清单；`experts[].expert_ref` 指向**内置专家**（产品方随版本预置），不指向租户自建的专家包。二者的关系见第 10 章 UI-Q3。

**模板与「服务类型」的关系（PRD D9）**：模板同时承载类型语义，**PRD 已删除 `service_type` 字段**。因此本设计的卡片标签与图标选取都取自模板定义，不再有"类型字段选项"这一来源。未选模板的服务标签显示「自定义」。

首版建议内置 6 个模板（对应参考页的 5 张，另加一个教培特有场景）：

| 模板名 | 描述 | 预置专家（岗位名） | 预置 |
| --- | --- | --- | --- |
| 招生咨询全流程 | 从线索进入、跟进到转化，含提醒与话术 | 招生顾问 · 教务主管 | 2 个专家 · 5 个事项状态 |
| 家长续费跟进 | 续费窗口提醒、沟通话术与结果归档 | 教务主管 | 1 个专家 · 4 个事项状态 |
| 一日流程巡查 | 巡班记录、异常上报与每日汇总 | 带班老师 · 保育员 | 2 个专家 · 6 个事项状态 |
| 新教师带教 | 带教计划、阶段评估与反馈沉淀 | 教务主管 · 带班老师 | 2 个专家 · 4 个事项状态 |
| 活动筹备 | 排期、通知与活动后复盘 | 后勤主任 | 1 个专家 · 5 个事项状态 |
| 教学教研沉淀 | 观察记录、教研资料与经验沉淀 | 带班老师 | 1 个专家 · 4 个事项状态 |

> 上表为设计建议值，实际预置项以 PRD §5.2.9 的 `service_templates.config` 为准（D8 已定本期纳入模板，展开规则见该节）。模板由产品方预置，租户不可增删（PRD FR-514）。**专家一列按 D13 用岗位名**，"预置 N 个专家"的 N 与岗位个数一致——原型按本表同步。

## 4. 页面二：空态

触发条件：当前用户可见服务数为 0（首次进入、或所有服务已归档后）。

### 4.1 设计立场：空态不做"空"

参考页没有空态可参照，但这是新模块**必然的第一次打开**。两种做法：

| 方案 | 问题 |
| --- | --- |
| 只显示「还没有服务」+ 一个按钮 | 首屏信息密度过低，用户对"这模块能干什么"没有概念，创建意愿低 |
| 保留两个空分组骨架 | 两个空分组互相加重空洞感 |

采用方案：**把模板区提权为主视觉，用引导卡代替空的"我的服务"分组**。

```
┌ 页头：标题 + 副标题                          [+ 新建服务] ┐
│ ┌ 虚线引导卡 ─────────────────────────────────────────┐ │
│ │ 还没有服务                                          │ │
│ │ 选一个模板开始，配置都预置好了，创建后随时能改。      │ │
│ │ 也可以从空白服务自己配全套。        [从空白创建]      │ │
│ └─────────────────────────────────────────────────────┘ │
├ 「从模板创建」                                  [搜索模板] │
│ 模板卡片网格（3 列，卡片规格放大）                          │
└───────────────────────────────────────────────────────────┘
```

要点：

1. **隐藏「我的服务」分组头**，用一张虚线引导卡顶替其位置（保持版面节奏不塌）。
2. **模板网格由 4 列放宽为 3 列**，卡片内边距加到 12px，描述允许 1 行长句 + 1 行预置说明。空态是唯一有空间展示完整模板价值的时刻。
3. **「从空白创建」是文字按钮（次要样式），不是第二个主按钮**——模板路径是推荐路径，空白路径要可达但不争抢。这条与 3.3 的"只设一个主按钮"一致：空态下主按钮仍是页头的「+ 新建服务」，引导卡内的「从空白创建」是它的等效入口（都进表单），视觉上必须弱于它。
4. 文案第二句「也可以从空白服务自己配全套」必须保留——否则用户会以为只能从模板创建。

### 4.2 边界

| 情况 | 表现 |
| --- | --- |
| 搜索无结果（非空态） | 见 3.6，保留分组头 |
| 全部服务已归档 | 视为空态，但引导卡文案改为「服务都已归档」+「查看归档服务」链接，模板区保留 |

## 5. 页面三：创建表单

### 5.1 入口与路径合并（对应 D-4）

| 入口 | 行为 |
| --- | --- |
| 页头「+ 新建服务」 | 进 `/platform/service/new`，表单空白（知识库与技能也是空的） |
| 列表页「从模板创建」分组的模板卡片 | 进 `/platform/service/new?template=<id>`，**指令框与专家区已按模板预填**；**知识库与技能仍为空**——模板是跨租户的全局表，它预置的知识库 ID 在别的租户下并不存在（PRD §5.2.9 展开规则第 5 条） |
| 空态引导卡「从空白创建」 | 同「+ 新建服务」 |

> **本表单没有「选择模板」入口（D23）。** v1.16 及以前，指令框右上角有一个文字按钮（未选时显示「选择模板」、已选时显示「模板：招生咨询全流程 · 更换」），点开是一个模板选择浮层、选定后覆盖指令框内容。**已整块删除**——**模板的唯一入口是列表页的「从模板创建」分组**。理由：模板会**同时**覆盖指令与专家两处，留在表单里就与"手选专家"形成两套来源，还得额外规定谁覆盖谁；挪走之后**要走模板的人从列表页进、要自己配的人从表单进**，一条路径只承载一种意图。用户仍知道自己在用什么——页头保留模板名与来源标签，指令与专家区能直接看出是预填的。

### 5.2 结构

- 形态：**整页路由**（`/platform/service/new`），非模态弹窗。理由：专家、知识库、技能三处选择都需要较大的画布；整页也支持刷新续填草稿。
- **单页表单，无步骤条**（D11）。**只做四件事：填名称、写指令、选专家、选知识库与技能**（D23）。字段自上而下排布：**名称 → 指令 → 专家 → 知识库 → 技能**。
- **没有折叠区**（D23）。v1.16 及以前，表单底部还有「服务范围（校区 / 课程）」与「服务描述」两个默认收起的折叠区——已删除，两处配置改到服务空间内（去处见 §5.3 末三行）。表单因此**一屏可见**，不再有"藏在折叠层里的字段"。
- 底部操作条：左「保存为草稿」（文字按钮，后跟浅色提示「可稍后继续」），右「取消 / 创建服务（品牌绿实心）」。**服务名为空时「创建服务」置灰不可点**（§5.4 阻断项），随输入实时切换。
- 窄屏：纵向单列；三个选择区（专家 / 知识库 / 技能）的已选内容**横向换行**，不横向滚动、不出现横向滚动条。

**指令框的占位文案（给可照抄的例子，而非空提示）：**

> 例如：跟进 2026 秋季招生线索，语气亲切不催促，重点记录家长顾虑与到访意向；涉及课程与价格时先查知识库再回答。

> **为什么把「记忆范围」「语气偏好」并入指令（D11）**：这两个字段要求用户先理解系统内部概念（"记忆范围"是什么？"可跨服务复用"会发生什么？），门槛高于价值。自然语言指令的表达力更强——"语气亲切不催促"比下拉选「亲切专业」更准确，而且能带上任何系统没预见的约束。

> **为什么"知识库与技能"在服务级、而不在专家级（v1.17 修订 / D23）**：v1.12–v1.16 一直把知识库范围与技能放在**每个专家**身上，并据此写下了"不要让用户逐项配"的理由。**那条理由针对的是"逐专家各配一遍"**（加 3 个专家就要选 3 遍同一批库）；D23 把这两项**上移到服务级**之后，"逐项配"这件事本身就不存在了——**原来的结论不是被推翻，而是它反对的那个前提被消掉了**。判断依据：**"这个服务能查哪些资料、能用哪些能力"是服务级的授权边界，不是某个岗位的属性**——同一个服务里的招生顾问和教务主管，看到的是同一批家长资料。**留在岗位级的**才是真正属于岗位的东西：这个岗位把过程写到哪个目录、输出成什么形态、带哪些记忆（这些在创建表单里不出现，进服务后在「服务设置 › 专家」里配）。

> **两处"空"都是"不启用"，不是"不限"（D23）**：知识库留空 = 该服务**不检索任何知识库**（该语义待 PRD **Q41** 最终确认，未定前按"不使用"实现）；技能留空 = **不启用任何内置技能**。**为什么默认从严**：内置技能里包含联网检索这类**会把内容送出园**的能力，知识库里则是家长与学员资料——默认开启等于默认放行，而用户并不会意识到自己开了一个口子（与 D22 对"不保存就不算存储"的处理同源：**不留看不见的口子**）。

> **专家用岗位名，且可以加多个（D13，PRD §3.5.5）**：本模块的专家是**按教培岗位封装的 AI 协作角色**——招生顾问、教务主管、带班老师……**一个服务里可以配多个**，各承担一摊职责。心里模型是"**组建一个小团队**"：指令框写的是这个团队要干什么，专家区是团队里有哪几个岗位，知识库与技能区是这个团队能查什么、能用什么（D23）。
>
> 界面要求：
> - 专家卡与选择浮层一律显示**岗位名**（"招生顾问"），**禁止**显示"线索跟进专家"这类能力名或 `lead_intake` 这类技术标识；
> - 选择浮层里每项显示「**岗位名**」，下方小字标注**所属职能 · 一句话职责**（如「招生顾问 / 招生 · 线索跟进、家长沟通与转化建议」），并**按职能排序**便于按岗位找；专家数量变多时再升级为按职能分组的分节列表；
> - 已选区是**列表**，不是单选——允许 0 个（黄条提示）、1 个、多个；
> - 不要让用户"选一个主专家"。多个专家是并存的岗位，不是主从关系（是否需要主责专家见 PRD 开放项）。

> **表单不设「服务类型」下拉（参考图有，本设计不采纳）。** 类型信息由模板承载，模板名即类型名——参考图里那个下拉（招生咨询 / 续费 / 健康 / 教学 / 培训 / 活动 / 回访 / ＋新增类型）在本设计中被"模板"整体取代（PRD D9 / D11）。理由有二：一是同一件事问两次（选模板又问类型），二是两个来源可能给出不同答案（模板说"续费跟进"、字段选"招生咨询"），之后无法判断以谁为准。未选模板的服务，其类型为"自定义"，无需在表单上显式选一个叫"自定义"的选项。**v1.17 补一句**：D23 之后模板入口已不在表单上，"未选模板"就是"从页头『+ 新建服务』或空态『从空白创建』进来"的那一支——`template_key` 留空、按平台默认模板展开初始配置（PRD FR-109）。

### 5.4 校验与降级

区分**阻断性**与**提示性**两类（参考页无此区分，但本表单存在"可以空、但会残废"的配置）：

| 类型 | 触发 | 表现 | 是否阻断提交 |
| --- | --- | --- | --- |
| 阻断 | 服务名称为空 / 超过 255 | 字段下红字 + 输入框红描边，主按钮不可点 | 是 |
| 阻断 | 服务指令超过 4000 字 | 指令框下方红字 + 字数标红 | 是 |
| **阻断** | 选中的知识库已无权访问 / 技能已不在内置技能库中 | 提交时拒绝（PRD FR-322），提示「该项已不可用，请重新选择」并把它在已选区标灰 | 是 |
| **提示** | 专家区为空 | 专家区**黄底提示条**：「未添加专家，创建后可随时添加；未添加前无法发起 Agent 工作」 | **否**（允许带提示提交） |
| **提示** | 知识库区为空 | 轻提示（非黄条）：「未选知识库，专家将只依据指令与对话回答」 | 否 |
| **提示** | 技能区为空 | 轻提示（非黄条）：「未启用内置技能」——**不是错误**，默认就不启用 | 否 |
| 提示 | 指令为空 | 不提示。指令是选填项 | 否 |

**为什么"未添加专家"不阻断**：一个只做事项协作、不发起 Agent 运行的服务是**合法用法**。阻断会把正常需求挡在门外；但完全不提示又会让用户创建完才发现开不了工，所以给黄底提示条 + 允许提交（PRD §10.2、AC-15 同口径）。知识库与技能为空只影响"回答得好不好"，不影响"能不能用"，因此给更轻的提示、不进黄条。

**为什么"选了但不能用"要阻断（v1.17 新增）**：这是四类阻断里唯一一类**授权问题**（前两类是格式问题）。放过去等于创建了一个用户以为能用、实际静默不生效的服务——**"看着配好了、跑起来才发现没带上"比创建时报错贵得多**（同 PRD §10.2 的判断）。

> **v1.17 修订（连同它的前提一起改）**：v1.12 曾把参考图里"未配知识库"的黄条升级为"未添加专家"的黄条，理由是"**D11 之后用户不再逐项配知识库，而是添加专家**"。**D23 把知识库放回创建表单**，那条理由随之失效——现在是**两条提示并存，但轻重不同**：专家区为空给**黄底提示条**（会导致"开不了工"，是能力缺失），知识库 / 技能为空给**轻提示**（只影响回答质量，是范围缺失）。
>
> **为什么两者不该给同一种提示**：把"没专家"和"没知识库"都做成黄条，用户会分不清哪一条真的会挡住自己；反过来若把"没专家"降成轻提示，又会有人建完服务才发现研究不了。**提示的权重应当对应该项缺失的后果，而不是对应该项在表单上的位置。**

### 5.5 草稿

- 「保存为草稿」存 `services.state = 'draft'`，字段完整度不校验（校验只在提交时执行）。
- 草稿服务**出现在列表页卡片区**，卡片副行显示「草稿 · 未启用」，点击进入表单续填（见 3.4）。
- 同一用户草稿数上限建议 5 个，超出时新建时提示「草稿过多，请先完成或删除」（上限值见第 10 章 UI-Q4）。

### 5.6 提交后

1. 校验通过 → 创建服务 + seed 默认事项状态机与系统字段选项（PRD FR-501）→ 跳转 `/platform/service/:serviceId`。
2. 若模板带预置项 → 在同一个事务内写入**专家绑定**、事项状态、字段选项（展开规则见 PRD §5.2.9）。**用户已自行填写的指令不被模板覆盖**（PRD §5.2.9 展开规则第 6 条）。**知识库与技能不由模板预置**（D23）——模板是跨租户的全局表，它预置的知识库 ID 在别的租户下并不存在；这两项**只来自本表单上用户的选择**。
3. 落地页顶部显示一次性引导条：「事项状态已按模板配好，去调整」；若专家区为空，另加「去添加专家」。可关闭，不重复出现（存用户级已读标记）。

## 8. 页面四：服务空间 · 会话工作台

> 上游依据：PRD **D14**（会话是空间内的工作单元）、**D15**（服务空间 = 会话工作台）、**D18**（服务空间无导航栏）、**D21**（会话挂到应用级侧栏的服务名下方，服务空间由三块变两块；产物 / 事项与 `⊕` 提到服务头）、**D22**（产物计入租户存储，配额不足时在开工前拦下）与 §10.3 / §10.4。本文只规范界面；会话的数据结构与接口契约见 PRD §5.3、§9.2，产物的交互协议见《Web端Agent实时执行与产物交互PRD》§6–§7、§12，产物的存储计量见 PRD §5.2.5 与 FR-318~320。

### 8.1 设计立场：会话是工作现场，不是一张列表

用户进入一个服务的动机几乎总是"**接着干活**"：说一句、看专家跑一轮、拿产物、再追问。所以服务空间**进来就是会话工作台**——左边一列会话，右边是当前会话的**完整对话**，产物直接挂在对话里。

**本页最容易做错的一件事**：把"会话"做成列表页里的一行行，点开才弹个框。那样用户看到的是**目录**，不是**工作**。WorkBuddy 的项目也是这个形态：点进项目，左边是会话，右边就是对话和产物。

由此确定三件事：

- **一个服务下有很多会话**，而不是"一个服务一个会话"。会话才是用户理解工作的自然单位，服务只是它们的容器——**所以会话挂在服务名下面**（D21），与 WorkBuddy 的项目一致。
- **服务空间里没有导航栏**（D18），**也没有第二个会话列表**（D21）。高频的只有"接着干这一段"这件事本身：会话在侧栏手边、产物与事项在服务头，其余收进 ⋯ 菜单。不要用一列导航去暗示"这个服务有九个页面"——用户进服务不是为了逛页面。
- **产物与会话同源**：它们不是"另一个页面"的内容，是这段工作跑出来的东西，所以入口与服务头并排（§8.2）。

### 8.2 布局结构

**两块**（v1.14 起；D18 的三块 → D21 的两块）：

```
┌─ 服务头：← 返回列表 │ 服务名 │ 模板徽标 │  ▤ 产物 3  ☑ 事项 3  │ 状态 │ ⊕ │ ⋯ ──┐
├─ 对话区（自适应，原型实测 956px）────────────────────────────────────────────┤
│  会话标题 · 专家 · 时间                                                     │
│ ────────────────────────────────────────────────────────────────────────────┤
│                                    我：把东苑分园那 4 条也并进来…           │
│                                                                             │
│  招生顾问  已完成                                                           │
│  › 执行过程 · 4 步（默认折叠）                                              │
│  ┌ 服务卡片 ──────────────────────────────────────────────┐                 │
│  │ 已更新：秋季招生线索跟进表                              │                 │
│  └────────────────────────────────────────────────────────┘                 │
│  [XLSX] 秋季招生线索跟进表.xlsx                                             │
│  继续追问   重新生成                                                        │
│                                                                             │
│  说点什么…                                         [招生顾问 ▾] 发送        │
└─────────────────────────────────────────────────────────────────────────────┘
   │
   └─ 右侧面板（约 320px）是**浮层**：点对话里的产物卡、或点服务头的
      产物 / 事项入口才出现，不挤压对话区、不改变消息的横向位置
```

**会话列表不在这张图里——它在应用级侧栏的服务名下面**（D21，见 §2.3）。三件事分给三处：**侧栏回答"这个服务里有哪些工作"**，**对话区回答"这一段工作在干什么、干出了什么"**，**右侧面板回答"这东西具体长什么样"**。不要再往任何一处塞另外两件事。

**为什么把会话栏撤掉（D21）**：它和侧栏回答的是**同一个问题**。会话挂到侧栏之后，同一条会话会同时出现在两处，用户还得自己判断"置顶该在哪边做""哪边才是全的"——**同一件事不该有两个答案**。

**产物 / 事项为什么搬到服务头**：它们是这一段段工作**沉淀下来的东西**——产物是交付物，事项是待推进的动作。原先它们贴着会话栏底部（"过程在上、结果在下"，D18）；会话栏撤掉后，**服务头是唯一还属于"服务级"的位置**，与 `⋯`（管服务本身）的分工也最清楚。**带计数是必需的**：这两个入口没有页面标题可以承载"有多少"，数字只能挂在入口上；计数也让人一眼看出"这个服务攒下东西了没有"。

> **`⊕` 为什么也在服务头**：它的语义是"往这条工作线上**再加一段**"（新建会话）。会话列表在应用级侧栏里，而侧栏是别人的容器——把 `⊕` 塞进侧栏不合适；放在服务头与 `⋯` 并排（两个圆钮）最直接。**但不要把它和 `⋯` 合并成一个菜单**：`⊕` 是"开新的一段"，`⋯` 管的是**服务本身**（名称 / 描述 / 分享 / 更多）——作用对象不同。详见 §8.8。

### 8.3 会话行规范（侧栏三级项）

会话行现在长在**应用级侧栏**里（D21），一行可用宽 **248px**——"能不能挤下"是所有取舍的出发点。

| 位置 | 内容 | 规则 |
| --- | --- | --- |
| 标题 | 会话标题 | **单行截断**（`text-overflow: ellipsis`）+ `title` 全名。默认由首条用户消息自动生成，用户可重命名。**不用拼音或 id 兜底**——无标题时显示"新会话" |
| 当前态 | 我在看的这一条 | **底色（`#f3f3f3`）+ 文字转主色 + 字重 500**。这里**不用圆点**：三级行右侧的位置要留给 hover 才现的 `⋯`，只用底色又和 hover 同值——三个属性一起才有足够区分度 |
| 置顶标记 | 标题右侧一个 8px 品牌色 `●`，**固定占位 10px** | 只有置顶的行显示内容。**放右侧且恒占位**：放标题左侧会让置顶行与非置顶行的文字起点差出 17px（原型里真浏览器实测 63 vs 46），一列看下来文字左右跳 |
| 更多 | 悬停显示 `⋯` → 重命名（行内）/ 置顶 / 删除 | **只在当前所在服务的行上出现**（§2.3 口径表）。菜单项与列表页卡片菜单**同构**（同样的图标与排列习惯）；`⋯` 的宽度也必须固定占位，否则 hover 时标题会被挤短一截 |
| **刻意不出现** | 专家名、相对时间 | 一行 248px 塞三样东西的结果是每样都被截断。它们留在**对话区头部**（`会话标题 · 专家 · 时间`，见 §8.2 布局图）——侧栏只负责回答"点哪一条" |

**排序**：置顶优先 → 最近更新，**全模块一处口径**（原型里是 `sessionsOf()`）——侧栏三级、"进入服务时落在哪一条"、面板里的服务概览三处共用，免得跑偏。**不提供排序切换器**——会话列表的默认顺序就是唯一合理的顺序（WorkBuddy 亦然），加了反而让人怀疑是不是漏了什么。

**列多少**：每个服务最多 **8 条**，超出给一行「还有 N 个 ›」，点了在侧栏内全部列出（侧栏自身滚动，见 §2.3.1 末注）。上限是否调整见 PRD Q39；"会话多到侧栏放不下时要不要给一条独立的全部会话入口"见 UI-Q11。

**为什么不分组**：服务空间的旧会话栏按"置顶 / 今天 / 昨天 / 7 天内 / 更早"分过组（v1.10–v1.13）。搬到侧栏之后，**分组标题本身要占掉 5 行**（约占一个服务全部 8 条预算的一半），而侧栏的首要任务是"把我常去的那几个服务放在手边"——分组把这件事挤掉了。**排序足以表达时间先后**，分组标题在这个宽度里是奢侈品。

### 8.4 三条硬约束

1. **当前高亮与置顶是两个维度，不得混用。**
   正在查看的会话在**当行**表达"我在看这条"（底色 + 主色文字 + 字重）；置顶会话在**排序上永远优先**（表示"这条重要"），并在行尾带一个 `●`。
   两者的视觉表现不同，**各占一行的两端**（当前态在文字与底色，置顶在右侧小点），互不抢位。**不要用置顶来实现高亮**——那会让用户以为自己的会话被莫名置顶了。

2. **不显示任何技术标识。**
   行内不得出现 `session_id`、`thread_id`、`expert_ref`、`model_id`、`run_id`。参照 §7.1 反面清单第 3 条。

3. **空态不是空白。**
   服务内尚无会话时，**输入框保持可用**，并给出行业化的示例引导（如"试试问：本月哪些孩子该做视力复查？""把本周的晨检异常汇总一下"）。**不显示"暂无数据"**——那会让用户以为功能坏了，而实际上功能就在他眼前。
   **同一件事在侧栏还有一面**（D21）：该服务的三级列表给「还没有会话，去开一段 ›」，它是**入口**不是说明文字——点了进这个服务、光标落在输入框。两处口径一致：**空的时候给下一步，不给一句陈述。**

### 8.5 与「运行记录」页的分工（务必分开做）

| | 会话列表（侧栏三级，D21） | 运行记录页 |
| --- | --- | --- |
| 一条代表 | 一段连续的工作对话 | 一次 Agent 执行 |
| 排序键 | 会话**更新时间** | 运行**创建时间** |
| 数量关系 | 1 个会话 ⊇ **0..N** 次运行 | 每次运行**必定**属于某会话 |
| 回答的问题 | "我们在这个服务里做过什么" | "那次到底调了哪些工具、每一步是什么" |
| 无运行时 | 仍会出现（用户只问了句话） | 不出现 |

> **最容易犯的错**：把两者合成一个列表，按时间混排。那样用户既看不到"工作全貌"，也追不到"某次执行细节"。**这是两个不同的心智对象，界面必须分开。**

### 8.6 输入框与专家切换

- **输入框常驻**在对话区底部（不折叠、不藏在按钮后面）。这是"工作现场"的视觉锚点——它同时也是"紧接着说下一句"的入口。
- **专家选择器**置于输入框内右侧，显示当前岗位名（如「招生顾问 ▾」）。默认取服务的**首选专家**；用户可在此切换，切换后写入 `sessions.expert_ref`。
- **首次发送即建会话**：当前无会话时，发送动作先创建会话再发起运行（PRD FR-210）。**不给用户看"先建会话"这一步**——它只是实现细节。
- **「⊕ 新建会话」放在服务头右侧**（圆形图标按钮，与 `⋯` 并排——两个圆钮，对齐 WorkBuddy 项目头。v1.14 起由会话栏头部搬来：会话列表已经在侧栏了，见 D21）：发送建会话是主路径，但用户想**换一个话题**（不接着上文）时需要显式的"另起一段工作"入口。点它只把当前选中清空、光标落到输入框——**不弹窗、不跳页**。它与上面那条不冲突：前者是流程细节不出现在界面上，后者是用户主动的"我要开新的"。
- **为什么这里用图标而不是文字按钮**：服务头右端已经排了产物 / 事项两个带计数的胶囊按钮与状态标签，再插一个「＋ 新建」文字按钮会让这一行明显变重。**一个动作的分量应该匹配它的位置**——加号在服务头是通用语汇（WorkBuddy 的项目头就有一个），不需要文字解释。它与 `⋯` 是**同一类东西**（都是"对这个服务做一次动作"的圆钮），并排读起来是一组；但**不要把它并进 `⋯` 的菜单**——`⊕` 开新的一段，`⋯` 管服务本身（§8.8）。
- **未添加专家时的黄条**：与创建表单共用同一条规则（§5.4）——不阻断发送，但提示"该服务未添加专家，将以默认助手响应"。黄条**贴在输入框上方**，不弹窗。
- **运行中**：输入框下方的消息区实时展示步骤；`发送` 按钮切换为 `停止`。

### 8.7 右侧面板：一个位置装五种内容

面板是**统一的内容查看区**——产物预览、产物列表、事项列表、服务概览、服务设置都在这里。用户不需要记住"哪个东西在哪个页面"，只需记住"点它，右边看"。

| 唤起方式 | 面板内容 |
| --- | --- |
| 点对话里的**产物卡** | 该产物的**预览**（标题 + 元信息 + 正文/表格），底部给「下载」「新窗口打开」 |
| 点服务头「**产物**」 | 本服务的**产物列表**（格式徽标 + 名称 + 版本/大小），点任一条切到该产物的预览 |
| 点服务头「**事项**」 | 本服务的**事项列表**（标题 + 状态 + 负责人 + 时间 + 来自哪个会话） |
| 点 ⋯ 的「更多 › → **服务概览**」 | 四个计数卡：会话 / 产物 / 事项 / 待推进 |
| 点 ⋯ 的「更多 › → **服务设置**」 | 成员 / 专家 / 事项配置 / 运行记录 / 知识库范围 |

**六条规矩：**

1. **面板是浮层，不占布局位。** 它压在对话区右侧（约 320px），打开与关闭都**不改变对话区宽度**——否则消息会横向跳动，用户刚看到的那句话会挪位（《Web端Agent实时执行与产物交互PRD》§6.5「回到原聊天位置」）。
2. **面板不是新页面。** 关掉面板，用户还站在原地；不产生路由变化、不推历史记录。深链仍由 §2.3 的路由保证（`/artifacts`、`/reminders` 等）。
3. **入口与内容同源高亮。** 面板显示产物列表时，服务头的「产物」入口保持选中态——让用户知道"这个面板是谁打开的"。再点同一个入口即收起。
4. **空态说下一步，不说"暂无数据"。** 产物为空时写"在会话里让专家跑一轮——产物会先出现在对话中，也会汇总到这里"；事项为空时同理。
5. **只读角色不降级面板。** 面板是**查看**行为，与 `viewer` / 归档服务无关——他们要能看产物和事项，只是不能改。这与输入框的置灰（§8.9）是两回事。
6. **面板不得压住输入框。** 浮层的定位基准是**消息区**（对话区里滚动那一段），**不是整个对话列**。贴着整列做，面板会把输入框右端的**专家选择器与发送按钮**一起盖住——**面板一开就没法发消息**。（原型实测：贴着整列时，`elementFromPoint` 在专家选择器中心取到的是面板而非按钮；改为贴合消息区后取到的才是按钮本身、发送按钮同理，且对话区宽度不变——v1.14 撤掉会话栏后实测 954 → 954px。）

### 8.8 服务头 ⋯ 菜单：管的是"服务本身"

| 位置 | 菜单项 | 说明 |
| --- | --- | --- |
| 一级 | 修改服务名称 | 写入 `services.name`；仅成员可见，不对外 |
| 一级 | 修改服务描述 | 写入 `services.description`；会显示在服务列表卡片上（最多两行截断） |
| 一级 | 分享设置 | 三档可见范围：仅我可见 / 服务成员可见 / 持有链接可见 |
| 一级 | 更多 › | 二级菜单，见下 |
| 二级 | 服务概览 / 服务对象 / 运行记录 / 服务设置 | 唤起右侧面板或跳对应页 |
| 二级 | 归档服务 / 删除服务 | **仅 owner / admin 可见**；非拥有者显示「退出服务」 |

**为什么一级只留三项**：菜单一长就"什么都没突出"。改名 / 改描述 / 分享是服务级的日常动作，其余是"偶尔才去"的，进二级不损失效率。二级**向左展开**——`⋯` 本来就在窗口右上角，往右会直接跑到屏幕外。

**分工必须分清**（这三个入口不重叠，也**不要为了"少一个入口"而合并**——合并后用户会分不清"我改的是这个服务，还是这个服务里的某个东西"）：

| 入口 | 管什么 | 例子 |
| --- | --- | --- |
| 服务头 **⋯** | **服务本身** | 叫什么名、怎么写描述、谁能看到 |
| 右侧面板 **服务设置** | **服务里的东西** | 成员、专家、事项配置、运行记录、知识库范围 |
| 服务头右侧 | **工作产生的沉淀** | 产物、事项（带计数） |

**两个模态的共用规矩**：修改名称与修改描述共用一个轻量模态（标题 + 输入 + 说明 + 取消 / 保存）；分享设置用同一外壳装三档单选。**点遮罩即关闭**；名称为空时**保存不生效并提示**，不静默失败；保存后服务头立即更新。

> **分享范围 ≠ 会话可见性。** 这里管的是**服务**的可见范围。服务里单个会话能否共享给其他成员，是另一件事——PRD Q31 尚未定，**界面不默认实现**。

### 8.9 状态与边界

| 场景 | 表现 |
| --- | --- |
| 加载中 | **侧栏三级**（会话列表）用**骨架屏**（3 条），不用转圈；服务空间本身直接进对话区，不等列表 |
| 无会话 | 见 8.4 第 3 条：输入框可用 + 示例引导 |
| 只读角色（`viewer`） | 输入框**置灰并显示提示**"你在此服务为只读"，而不是隐藏——隐藏会让人以为这里没有输入框 |
| 服务已归档（`archived`） | 会话与消息**可读**，输入框置灰并提示"服务已归档，恢复后可继续" |
| 服务暂停（`paused`） | 可读；发送时返回 `SERVICE_NOT_ACTIVE`，提示"服务已暂停" |
| 会话被他人删除 | 提示"该会话已被删除"并回到列表，**不静默跳转** |
| 网络中断 | 会话列表保留已加载内容 + 顶部细条提示，不清空为错误页 |

## 9. 埋点与指标

| 埋点 | 事件 | 用途 |
| --- | --- | --- |
| 列表页曝光 | `service_list_view` + 服务数 + 是否空态 | 判断新模块的冷启动情况 |
| 创建入口点击 | `service_create_click` + 来源（页头按钮 / 模板卡 / 空态引导） | 验证 D-4 的入口合并是否有效：若模板卡来源占比远高于按钮，说明用户确实用模板做起点 |
| 模板选择 | `service_template_select` + 模板 id | 决定首版模板的迭代优先级 |
| 表单字段填写 | `service_form_field` + 字段名 + 动作（聚焦 / 填写 / 离开） | 定位哪个字段让人放弃 |
| 表单放弃 | `service_form_abandon` + 停留区域 + 已填字段数 | 区分"被校验拦住"与"主动放弃" |
| 校验触发 | `service_form_validation` + 字段 + 类型（阻断 / 提示） | 若"提示"类频繁出现，说明"未添加专家"黄条的位置需要调整 |
| 卡片点击 | `service_card_click` + 我的角色 | 验证 D-2：若只读角色的点击率显著低，说明角色徽标起作用了（预期它会减少无效点击） |
| 菜单点击 | `service_card_menu` + 菜单项 | 判断哪些操作真正被用 |
| **会话首条发送** | `service_session_first_send` + 是否先选专家 | 区分"直接开问"与"先挑专家"两种起点，验证专家选择器的必要性与位置 |
| **会话切换** | `service_session_switch` + 会话在列表中的位置 | 若位置靠后的会话被频繁切回，说明列表排序或搜索不够用 |
| **会话置顶 / 重命名 / 删除** | `service_session_action` + 动作 | 重命名占比高 → 自动生成标题质量不达标（PRD §14） |
| **会话内切专家** | `service_session_expert_switch` + 第几轮 | 第 1 轮就切 → 默认专家选错了；第 3 轮后才切 → 属正常的多角色协作 |
| **侧栏直达** | `service_nav_click` + 层级（一级 / 二级 / 三级）+ 层级内位置 | 验证 D20 / D21 的价值：二级项占比高 = "一步进服务"确实是主路径；三级项占比高 = "从任何地方一次点击回到某段工作"成立，可据此决定要不要放开 Q39 的条数上限 |
| **侧栏会话动作** | `service_nav_session_action` + 动作（重命名 / 置顶 / 删除） | 侧栏取代会话栏（D21）之后，这些写操作都发生在侧栏行上；若用量集中在"重命名"，说明自动生成标题质量不达标（同上一条） |
| **只读受阻** | `service_session_readonly_block` | 统计只读角色尝试发送的次数，评估权限提示是否清晰 |

核心指标：**空态 → 创建成功转化率**、**表单放弃率**、**模板创建占比**。（D11 后创建为单页表单，用"放弃率"替代原"三步流失率"。）

**会话专项指标（D14，与 PRD §14 同口径）**：
- **单服务会话数分布**——若绝大多数服务只有 1 个被反复使用的"默认会话"，说明用户没理解会话的边界，需要在界面上补引导（或干脆承认会话对用户是隐形的，见 §11 UI-Q9）。
- **会话平均运行次数**——接近 1 说明会话被当成"一次性运行入口"，与设计意图不符。
- **会话标题手动改写率**——过高说明 `generate_title` 的效果不达标。
