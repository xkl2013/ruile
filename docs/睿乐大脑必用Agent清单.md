# 睿乐大脑必用 Agent 清单

> v1.0 · 2026-10-10
> 筛选口径：**WorkBuddy 这类通用产品结构上装不上的**，才算一个 agent 值得立项
> 配套：`docs/Agent模块设计方案.md`（门面形态）· `docs/睿乐大脑商业化方案.md`（定价）· `docs/幼教教培应用对标调研.md`（对标）

## 0. 结论先行

**三个判断，先摆出来：**

1. **平台已经有一台通用 agent 引擎，而这恰恰是最不该继续投入的方向。** 代码事实：`custom_agents` 表（`migrations/versioned/000006_custom_agents.up.sql`，含 `config JSONB` 的 GPTs 式配置）、`/agents` 全量 CRUD + copy + 占位符（`internal/router/router.go:1391-1420`）、专家包注册与发布（`:1432-1440`，表在 `000100`）、持久化运行记录（`000099`）。前端编辑器 `AgentEditorModal.vue` **5938 行**，已覆盖模型、提示词、工具、MCP、外部搜索、分享、嵌入、IM 渠道；列表页 `AgentList.vue` **2652 行**。
   **这套东西 WorkBuddy / Coze 有更全的版本且更便宜。在"配 agent 的能力"上竞争是必输的。**

2. **唯一能赢的战场是"货"，不是"货架"。** 而现状是货架空着：全平台唯一对用户可见的内置 agent 只有 `builtin-quick-answer` 一个（`000097_global_builtin_agent.up.sql`）；用户端 `/agents` 路由更是一个 `ExternalRedirectView`，直接 `redirectToAdmin({ path: '/agents' })`（`frontend/src/router/index.ts:295-308`）。
   **用户端真正能碰到 agent 的地方，只有对话页的 `AgentSelector`。**

3. **所以这 10 个 agent 不是"新功能"，是往已有引擎上装 10 个"通用产品装不上的货"。** 判断标准见 §1，10 个清单见 §2，反面清单见 §3。

## 1. 判据：WorkBuddy 结构上装不上的五条

注意是**结构性**原因，不是"它没想到"。WorkBuddy 再怎么迭代也解不开这五条，因为它们和"通用个人 AI 工具"的定位相冲突。

| 代号 | 结构性原因 | 为什么通用产品解不开 |
|---|---|---|
| **S1** | **数据引力** | 数据在机构自己的业务库、私有知识库、设备里。通用产品没有入口；让用户手工上传，它就退化成个人工具，不再是机构系统 |
| **S2** | **责任比** | Agent 要**改业务系统的状态**（建待办、标风险、发名单、写台账）。通用产品不承担业务正确性责任，因此架构上不会去写别人的业务库 |
| **S3** | **事件在场** | 要**订阅机构的业务事件流**（出勤异常、退费申请、投诉苗头、缴费到期）。通用产品没有你的事件流，只能被"叫醒"，无法主动 |
| **S4** | **口径统一** | 要承载**"本园的立场"**——同一件事全园口径一致，不依赖某个老员工的个人经验。通用产品没有"你的园"这个概念 |
| **S5** | **合规红线** | 儿童人脸、生物识别、发育评估。通用产品会直接声明不做；机构产品必须自己扛（且必须只做案头，见 §4） |

**反向红线（本轮明确）**：凡是"把一件文书做得更好"的场景——写通知、写教案、写总结、排版、翻译、搜资料、做 PPT——**WorkBuddy 会做，而且做得更好**。这类一律**不算 agent 立项**，最多降级为"知识库检索"。

## 2. 十个必用 Agent

按**必用度 × 壁垒厚度**排序，分三档。每项标注：岗位、一句话价值、命中判据、落地形态。

### 第一档｜已经在跑，或改配置就能上（3 个）

> 这一档的共同点：**已有底座**——整理模板机制（`migrations/versioned/000106_organize_workbench.up.sql` + 平台模板 `000106`/`001012`）已经跑通，不需要新表。

#### ① 到访谈单复盘 Agent <!-- S1+S2+S3 -->
- **用的人**：招生顾问（园长看汇总）
- **一句话**：录完一段谈单，自动出"家长关注什么 / 卡在哪一步 / 下一步做什么"，并把下一步**直接建成待办**
- **为什么通用产品做不了**：谈单录音在机构的采集链路里（S1）；复盘要写回跟进状态（S2）；要挂在"每天复盘上一日谈单"的周期上（S3）
- **落地形态**：**✅ 已在线上跑**（daily）。规格见 `docs/招生顾问必用10个整理.md`，key=`visit_review`
- **⚠️ 前置修复（硬）**：ASR 退化——租户未配 ASR 时音频正文会退化成文件名且状态伪成功（`internal/application/service/organize_memory_attachments.go:406-455`）。不修这个，本 agent 在未配 ASR 的租户里就是空转

#### ② 经营数据日报 Agent <!-- S1+S2+S3 -->
- **用的人**：园长
- **一句话**：早上一眼看到异常项 + 需要决策的事，而不是一堆报表
- **为什么通用产品做不了**：吃的是本园出勤/报名/退费（S1）；要给"需要决策的事"挂动作（S2）；定时在每天早 8 点（S3）
- **落地形态**：**✅ 已在线上跑**。归"园所运营"，key=`daily_ops_report`
- **⚠️ 前置修复（硬）**：周期调度时刻写死在代码里（daily 08:00 / weekly 周一 09:00 / monthly 1 日 09:00，`internal/application/service/organize_workbench.go:1175-1204`）。**且周期配置指令必须写「上一个周期」（昨日/上周/上月）**——写"今日/本周"会命中空窗口

#### ③ 今日跟进清单 Agent <!-- S1+S2+S3 -->
- **用的人**：招生顾问
- **一句话**：今天该跟谁、谁的窗口在关、上次卡在哪——一屏一答
- **为什么通用产品做不了**：线索池是本机构的（S1）；"跟进"本身是写回动作（S2）；跨日累积，昨天谈单今天要跟（S3）
- **落地形态**：**改配置即上**——复用整理模板 + 待办落点（`service_reminders` 层，服务空间外壳下线后保留，见 §5）
- **说明**：这是"招生顾问四卡"里的第一张卡，也是分身首页主动一句的数据来源

### 第二档｜接一个数据源就能上（4 个）

> 这一档的共同点：**逻辑已具备，缺数据入口**。要接的出勤/缴费/观察记录目前不在系统里（DB 无 `lead`/`student`/`attendance`/`payment` 业务表，见 §5）。

#### ④ 续费与流失预警 Agent <!-- S1+S2+S3 -->
- **用的人**：园长 / 教务主管
- **一句话**：谁快走了 + 每人该做什么动作（约谈 / 加课 / 转班）
- **为什么通用产品做不了**：要吃在读学员的出勤衰减、互动衰减、缴费到期（S1）；落成风险名单与动作（S2）；随出勤事件持续在场（S3）
- **壁垒厚度**：**最厚的一个**——三条判据全中，且**直接对应收入**。早教/教培的"退费"是一条直线，早发现半个月就是钱
- **落地形态**：接出勤/缴费数据源

#### ⑤ 家庭沟通助手 Agent <!-- S1+S2 -->
- **用的人**：班级老师
- **一句话**：**基于这名孩子在园的真实记录**发声——不是通用话术
- **为什么通用产品做不了**：它没有这个孩子昨天哭了、前天分享玩具的记录（S1）；产出的措辞要能落进家园沟通记录（S2）
- **关键差别**：伪装成它的通用产品会给你"通用的家长沟通技巧"；它给的是"这个孩子这周的情况怎么跟妈妈说"。**这一点是本 agent 存在的全部理由**
- **落地形态**：接观察记录 + 记忆库

#### ⑥ 幼儿成长报告 Agent <!-- S1+S2 -->
- **用的人**：班级老师
- **一句话**：日常观察 → 分领域成长报告 → 可发家长
- **为什么通用产品做不了**：素材是老师自己攒的观察记录与照片（S1）；报告要归档成学期作品集（S2）
- **对标**：Lillio（前 HiMama）的"观察 → 成长领域 → 学期作品集"这条链是它最强的部分
- **落地形态**：接观察记录 + 采集键（照片/语音）
- **⚠️ 红线**：只做**教师已写记录的整理与呈现**，**不得**由 AI 对儿童发育做评估或诊断（见 §4）

#### ⑦ 在园健康与营养 Agent <!-- S1+S2 -->
- **用的人**：保健医 / 后勤
- **一句话**：带量食谱 + 营养分析 + 采购清单 + 过敏台账
- **为什么通用产品做不了**：吃的是本园在册幼儿的过敏史与年龄分布（S1）；出的是可执行的采购清单与厨房台账（S2）
- **落地形态**：**改配置即上**（整理模板机制），key 归"儿童营养与食育"
- **说明**：这是唯一一个"通用产品也能出食谱、但出不了**本园**的食谱"的典型——差别全在过敏台账

### 第三档｜需要新建工程（3 个）

> 这一档的共同点：**要接事件流或要新建数据模型**，不能靠改配置到。

#### ⑧ 投诉与情绪升级预警 Agent <!-- S1+S3 -->
- **用的人**：园长 / 客服主管
- **一句话**：家长的不满苗头，**早半天**发现
- **为什么通用产品做不了**：要从本园的沟通记录里识别情绪走向（S1）；要在连续沟通上持续在场，而不是等你去问（S3）
- **价值定位**：它的价值**不在生成，在时间差**。早教机构里"家长不满 → 投诉 → 退费"是一条直线，抢的就是前面那几天
- **落地形态**：新建（事件订阅 + 情绪信号）

#### ⑨ 园本教研资产 Agent <!-- S1+S3 -->
- **用的人**：教研主任
- **一句话**：跨老师、跨学期，把经验长成**园里的资产**，不随人走
- **为什么通用产品做不了**：资产是本园历次听课评课积累的（S1）；要按学期持续累积（S3）
- **对标**：日本 チャイルドAI 官方用词「**園運営の属人化防止**」（防止运营经验只留在个人身上）——它卖 107.8 万日元/年的核心卖点就是这件事。睿乐的记忆库 + 知识库 + 专家，本质同一件事，**且素材更强：它只有规章，睿乐还有一线记录**
- **落地形态**：接听课评课记录 + 教研库
- **注意**：不要做成"评课写得更专业"（那是通用产品的主场），要做成"**本园的教研库在长大**"

#### ⑩ 渠道转化归因 Agent <!-- S1+S2 -->
- **用的人**：市场 / 园长
- **一句话**：哪条渠道来的线索**真签下来了**
- **为什么通用产品做不了**：只有你的线索来源数据 + 你的成交记录能回答（S1）；结论要回写成渠道投放决策（S2）
- **落地形态**：接线索来源 + 成交数据

## 3. 反面清单：WorkBuddy 会做、所以睿乐不该投入

这一节和执行清单同等重要。**这些场景的员工会自己去用 WorkBuddy，机构不该为它们建 agent。**

| 场景 | 为什么不该做 | 正确的做法 |
|---|---|---|
| 写通知 / 写文案 / 写总结 | 通用产品主场，且免费 | 老师自己用 |
| 写教案 / 写活动方案 / 环创设计 | 同上，提示词就能抄走 | 降级为"知识库检索"——从本园优秀案例里找，而不是凭空生成 |
| 排版 / 翻译 / 做 PPT | 完全通用 | 不碰 |
| 搜资料 / 查政策 | 通用检索更强 | 不碰 |
| 通用问答 / 闲聊 | 通用产品的全部 | 不碰 |
| 儿童人脸识别 / 考勤刷脸 | **S5 合规红线** | 不做 |
| 儿童发育评估 / 行为诊断 | **S5 合规红线** | 不做 |
| 用儿童数据训练第三方模型 | **S5 合规红线** | 合同禁止 |

**一条实操规则**：任何 agent 提案，如果它的"产出"能被完整复制到 WorkBuddy 里重跑一遍得到同样结果，**它就不是 agent，是一段提示词**。

## 4. 两条必须写进验收标准的硬约束

来自对标调研（`docs/幼教教培应用对标调研.md`），且已有行业先行者背书：

1. **先确认，后执行。** Famly（丹麦，10,000+ 园所）2026-10-08 发布 AI 助手 Frankie 时，明确写了一条产品原则：**助手在未获用户确认前绝不执行动作**。这条同时解决合规、误操作、信任三件事。**落地**：所有写回动作先出草稿，用户确认后才落库（原型结果页已按此实现）。
2. **幼教 AI 三红线**：① 只做案头（起草通知、总结老师自己写的记录、标记逾期）；② **不得**对儿童的安全/行为/发育做决策；③ **不得**对儿童做人脸或生物识别；④ 儿童照片与数据**不得**用于训练第三方模型。

## 6. 落地顺序建议

| 阶段 | 做什么 | 依赖 |
|---|---|---|
| **P0**（改配置，最快见效） | ① 到访谈单复盘、② 经营数据日报、③ 今日跟进清单、⑦ 健康与营养 | 已有；需先修 ASR 退化与「上一个周期」口径 |
| **P0.5**（产品化前提） | 补 `tenant_members.job_role` + 用户侧 agent 门面（分身住中央凸起键） | 见 `docs/Agent模块设计方案.md` |
| **P1**（接数据源） | ④ 续费流失预警、⑤ 家庭沟通、⑥ 成长报告 | 需业务数据表 |
| **P2**（新建工程） | ⑧ 投诉预警、⑨ 教研资产、⑩ 渠道归因 | 需事件流 / 新数据模型 |

**排序理由**：P0 四个是"配置即上、且立刻能演示"，用来跑通商业化的样板客户；P1 的 ④ 是收入命门，一旦数据源通了应当立刻插队到最前。

## 7. 待拍板

1. **岗位字段**补不补？（不补，分身按角色换身份这条就落不了地）
2. **业务数据源**先接哪个——出勤、缴费，还是线索来源？（建议**出勤**：它同时喂 ④ 续费和 ⑥ 成长报告两个 agent）
3. 第一档 4 个 agent 的**考核口径**用什么？（建议：不是"生成了多少份"，而是"**有多少条产出被用户采纳/写回**"——直接对应 D2 判据）
