# 招生顾问必用的 3 个 Agent（可行性定稿）

> 版本：v1.0 ｜ 2026-10-06
> 前置文档：[招生顾问Agent可行性核查.md](./招生顾问Agent可行性核查.md)（记忆模块真实能力边界）、[早幼教招生顾问Agent矩阵.md](./早幼教招生顾问Agent矩阵.md)（业务链路全景，已降级为参考）
>
> 本文取代前两份文档的"Agent 数量"结论：**从 10 个收到 3 个**。

---

## 0. 判据：什么才算"必须使用"

上一版按业务链路推了 10 个岗位，问题在于"推得出来"不等于"用得上"。这一版只留同时满足三条硬门槛的：

| # | 门槛 | 说明 |
|---|---|---|
| **1** | **落在唯一已打通的链路上** | 必须是「记忆 → 整理任务 → 成果」这条链，不依赖任何未接线的能力 |
| **2** | **一线每天/每单都在用** | 不是管理者周频报表，是顾问当天就要用的东西 |
| **3** | **不用会直接吃亏** | 丢线索、丢单、丢口碑，三者之一 |

三条同时满足的，只有 3 个。

---

## 1. 结论：3 个 Agent

### ① 线索跟进清单 —— 每天开工第一件事

| 项 | 内容 |
|---|---|
| **触发时机** | 每天早上，或刚接待完一批新线索后 |
| **输入** | 顾问自己录的咨询记录、试听记录、微信沟通记忆 |
| **输出** | 按线索状态分组的跟进清单 + 流失风险标注 + 下一步动作；**48 小时内的回访置顶** |
| **章节骨架** | 线索分组 / 风险判断 / 下一步动作 |
| **现状** | ✅ **已具备，零开发**——平台预置模板 `lead_followup`，状态 `enabled`、版本 `v1`（`migrations/versioned/000106_organize_workbench.up.sql:168-171`） |

**为什么必须**：招生丢单的第一因不是话术不好，是**跟进断档**——线索跟一两次就沉底。这个清单把"今天该跟谁、谁快凉了"直接摆到面前。

---

### ② 到访谈单复盘 —— 每次面谈/体验课后

| 项 | 内容 |
|---|---|
| **触发时机** | 家长到园面谈或上完体验课之后 |
| **输入** | 面谈记录、体验课录音（录音会先自动转写并整理成笔记） |
| **输出** | 客户与需求、我方已呈现的方案、**异议与顾虑**、当前卡点、下一步动作与时间 |
| **章节骨架** | 客户与需求 / 我方呈现 / 异议与顾虑 / 卡点 / 下一步动作 |
| **现状** | 🔶 **需新建 1 条模板，零代码**——后台建单即可（见 §3.2） |

**为什么必须**：谈完不总结，下次见面等于从零开始，同一个价格异议反复卡。这个 Agent 把每单的"谈到哪了、卡在哪"沉淀下来。

**为什么选它而不是"渠道效果周报"**：早幼教的核心转化节点是**到园面谈/亲子体验课**（家长陪同＝双人决策），这是顾问真正需要复盘的环节；渠道周报是园长和市场看的周期性报表，顾问手里往往没有渠道投放数据，用不上。

---

### ③ 沟通复盘 —— 家长提出问题之后

| 项 | 内容 |
|---|---|
| **触发时机** | 家长提出疑问、顾虑、投诉，或需要园所给答复之后 |
| **输入** | 家长沟通记忆 |
| **输出** | 问题类型、处理情况、**待回应事项**（需要园所回应的排最前） |
| **章节骨架** | 问题类型 / 处理情况 / 待回应事项 |
| **现状** | ✅ **已具备，零开发**——平台预置模板 `parent_review`，状态 `enabled`、版本 `v1`（`000106_organize_workbench.up.sql:172-175`） |

**为什么必须**：家长提了问题没人闭环，代价不是这一单——是**不签约 + 不转介绍**。早幼教的转介绍占比极高，这一环直接决定口碑。

**与 ② 的区别**：② 面向**未签约的意向客户**，目的是推进成交；③ 面向**在读/已接触的家长**，目的是把问题跟到底。两者输入、产出、用途都不同，不重叠。

## 2. 被砍掉的，以及砍掉的依据

| 候选 | 裁决 | 依据 |
|---|---|---|
| 渠道效果周报 `channel_report` | ❌ 不入选 | 模板现成（`000106:176-179`），但**是管理者周频报表**，不满足门槛 2；且需要外部渠道数据 |
| 价格异议台账 | ❌ 合并 | 异议处理并入 ② 的「异议与顾虑」章节，单独成 Agent 是冗余 |
| 教研提炼 / 磨课复盘 / 个案观察 / 环创提案 / 发芽复盘 | ❌ 非本岗位 | 属教师成长、空间设计场景，不是招生顾问的活 |
| 线索管家（按家长聚合记忆） | ⛔ **做不了** | `organize_memories` 只有 `tenant_id + user_id`，**没有 `subject_id`**（`000072_organize_section.up.sql:5-22`）——记忆无法归到某个家长名下，这是数据模型问题，不是提示词能解决的 |
| 招生漏斗复盘 | ⛔ **做不了** | 线索在记忆里是自然语言，没有"阶段"字段，算不出漏斗 |
| 渠道投放 ROI | ⛔ **不应做** | 需要 Ruile 明确不接的外部投放数据 |

## 3. 这 3 个 Agent 是怎么"装配"出来的

不是三个功能按钮，而是**同一套机制的三次配置**。

### 3.1 真实链路

```
① 记忆侧（写入时已有 AI 加工）
   录音/上传 → 转写 → 模型生成 {title, summary, tags, note_markdown}
   → memory.Content 存的就是「AI 整理后的笔记」
   证据：organize_memory_audio.go:441-457、organize_memory_attachments.go:566-567
        organize_upload.go:290（提示词要求输出该 JSON 结构）

② 整理侧（用户侧触发，全部 Viewer 权限）
   POST /api/v1/organize/requirements/preview
     → POST /api/v1/organize/requirements/confirm
     → POST /api/v1/organize/jobs          ← 任务真正创建
     → GET  /api/v1/organize/jobs/:id/events（SSE 看进度）
   证据：internal/router/router.go:1493-1533

③ 模型读到的（buildOrganizeJobPrompt）
   模板名 + 模板指令 + 模板 Markdown 骨架 + 参与专家
   + 用户指令 + 勾选的原始记忆（每条 [M1] 标题/类型/时间/来源/内容）
   输出硬约束：每条结论标 [M#]；无依据的字段必须写「记录中未提供」
   证据：organize_workbench.go:903-953

④ 产出落地
   organize_outputs（含 content / fields / citations 证据引用）
   → POST /api/v1/organize/outputs/:id/assign  指派到服务
   → GET  /api/v1/organize/outputs/:id/citation 回看每条结论的记忆来源
```

### 3.2 三个 Agent 的落地成本

| Agent | 需要的动作 | 成本 |
|---|---|---|
| ① 线索跟进清单 | 无需动作，模板已在库中 `enabled` | **0** |
| ② 到访谈单复盘 | 后台建 1 条模板（key 建议 `visit_review`，场景归 `招生增长`，章节按 §1② ） | **≈20 分钟，零代码** |
| ③ 沟通复盘 | 无需动作，模板已在库中 `enabled` | **0** |

建模板的后台接口是齐的（`/api/v1/system/admin/organize/templates` 的 CRUD + `compile` / `preview` / `publish` / `versions` / `rollback`，`internal/router/router.go:1218-1233`），由 `g.SystemAdmin()` 守卫——平台运营自己就能加，不用开发介入。

### 3.3 一个可以立刻用起来的扩展点：把专家绑到模板上

- `GET /api/v1/organize/experts`（`router.go:1512`）—— 用户侧已能列出可用的专家
- 模板表有 `expert_ids JSONB`（`000106:14`），整理任务的 requirement 里有 `参与专家`，`buildOrganizeJobPrompt` 会把它写进提示词（`organize_workbench.go:910-913`）
- **但 8 个预置模板的 `expert_ids` 全部是 `[]`**——通道通了，货还没上架

也就是说：给这 3 个模板各绑一个「招生顾问」专家，即可让整理结果带上顾问视角的判读，**不需要新写代码**。

---

## 4. 落地路径（建议按序）

| 步 | 动作 | 目的 |
|---|---|---|
| **1** | 拿现成的 `lead_followup`，选一批真实招生记忆跑一遍 | 零成本验证整条链路的**实际产出质量**——这是当前最大的未知数 |
| **2** | 按 §1② 在后台建 `visit_review` 模板并发布 | 补齐第 3 个能力 |
| **3** | 给 3 个模板绑上「招生顾问」专家（`expert_ids`） | 让产出带上岗位视角 |
| **4** | 选 2–3 名一线顾问试用两周，对比"用/不用"的跟进及时率 | 拿真实数据决定是否推广 |

---

## 5. 一条必须守住的口径

**所有整理能力的天花板 = 用户录了多少记忆。**

`buildOrganizeJobPrompt` 在记忆为空时会明确要求模型输出「缺少输入的说明」，并禁止生成虚构内容（`organize_workbench.go:948-950`）。这意味着：

- 对一线顾问的价值主张只能是——**「你录进来的，我帮你整理成能用的清单和台账」**
- **不能**承诺「AI 自动帮你盯着客户」——因为服务提醒的自动生成链路（记忆路由器 / `ServiceReminder` 自动填充）在代码里尚未接线（详见 [可行性核查文档 §三](./招生顾问Agent可行性核查.md)）

这既是产品的诚实边界，也是当前最需要向一线讲清楚的一点——否则顾问用一次发现"我没录它就不认识我"，信任就崩了。
