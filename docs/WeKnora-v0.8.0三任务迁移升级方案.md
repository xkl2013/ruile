# WeKnora v0.8.0 三任务迁移升级方案

> 制定日期：2026-09-23  
> 目标站点：`https://weknora.weixin.qq.com/`  
> 当前项目版本标识：`0.7.0`  
> 目标基线：官方 WeKnora `v0.8.0`  
> 实施原则：新环境部署、迁移知识库核心数据、近期业务功能重建、三次任务独立验收

---

## 1. 执行结论

本次升级不在现有数据库上直接叠加官方 `v0.8.0` 迁移，也不通过替换 Docker
镜像完成。采用以下路线：

```text
现网继续运行
    ↓
建立官方 v0.8.0 新基线和独立测试环境
    ↓
重新接入睿乐的服务、整理、专家工作流
    ↓
迁移用户 / 空间 / 知识库原始文件
    ↓
在 v0.8.0 中重新解析并生成索引
    ↓
验收后切换 weknora.weixin.qq.com
```

这样处理的原因：

1. 线上真正需要保护的数据主要是知识库中已上传的文件。
2. 服务、整理等模块是近期功能，历史业务数据可以不迁移。
3. 当前自研分支与官方 `v0.8.0` 的迁移编号已经发生冲突。
4. 新库迁移可以避免修复大量无价值的历史测试表和测试数据。
5. 旧环境完整保留，生产回滚不依赖数据库 `down migration`。

本次升级拆成三次任务。每次任务都必须独立完成、独立验收，验收未通过时不得开始下一次。

## 2. 当前基线与约束

### 2.1 已确认的本地基线

| 项目 | 当前状态 |
| --- | --- |
| Git 分支 | `main` |
| 当前版本文件 | `VERSION=0.7.0` |
| 当前镜像配置 | `.env` 中 `WEKNORA_VERSION=0.7.0` |
| 目标官方版本 | `v0.8.0` |
| 本地数据库迁移 | `106|f`，即版本 106、`dirty=false` |
| 存储配置 | 已配置 OSS，升级时必须保留密钥、Bucket 与对象路径 |
| 自研功能 | 服务模块、整理模块、专家工作流、企业配置等 |

说明：`106|f` 中的 `f` 是 `false`，本地数据库当前不是 dirty 状态。线上数据库必须在任务一重新只读核验，不能用本地结果代替线上结论。

### 2.2 已确认的迁移冲突

当前自研迁移和官方 `v0.8.0` 使用了相同编号但代表不同业务：

| 版本号 | 当前自研分支 | 官方 v0.8.0 |
| --- | --- | --- |
| `000080` | 租户邀请工作画像 | 知识库自动标签 |
| `000081` | 组织成员查询 | 消息产物 |
| `000082` | 个人/组织知识库 | 租户沙箱配置 |
| `000083` | 租户知识库默认值 | 会话沙箱配置 |
| `000084` | 租户开通密钥 | 长期记忆 |
| `000085` | 企业积分 | 消息 Token 用量 |
| `000086` | 计费基础 | 空间 Skill |
| `000087` | 模型用量计费 | Skill 安装记录 |
| `000088` | 移除内置模型 | Skill 快照名称 |
| `000089` | 睿乐提示词身份 | Skill 环境变量 |
| `000090` | 企业成员额度 | Skill 目录 |

当前目录中还同时存在两个 PostgreSQL `000106` 和两个 SQLite `000021`。

因此禁止：

- 直接把官方迁移文件复制到当前 `migrations/versioned`。
- 在旧数据库上执行官方 `v0.8.0` 的 `migrate up`。
- 通过 `migrate force` 跳过迁移冲突。
- 删除 `schema_migrations` 后重新执行全部迁移。
- 生产环境长期使用浮动的 `latest` 镜像标签。

### 2.3 数据迁移边界

| 数据 | 处理方式 | 原因 |
| --- | --- | --- |
| 用户账号 | 迁移或按账号清单重建 | 保持登录主体 |
| 空间/成员关系 | 迁移或重建 | 保持知识库归属和权限 |
| 知识库基础信息 | 重建并建立旧 ID 到新 ID 映射 | 新旧 Schema 解耦 |
| 知识库原始文件 | 必须迁移 | 当前最重要的真实数据 |
| OSS 原对象 | 只读保留，迁入新前缀或重新上传 | 避免覆盖旧环境 |
| 文档元数据 | 通过导入清单重建 | 减少内部表映射风险 |
| 分块和向量 | 不直接迁移，重新生成 | 使用 v0.8.0 解析与索引能力 |
| 会话和消息 | 默认不迁移 | 非核心线上数据 |
| 服务实例和服务历史 | 不迁移 | 近期功能，可重新初始化 |
| 整理配置、任务和产物 | 不迁移 | 近期功能，可重新初始化 |
| 专家测试记录 | 不迁移 | 重新发布专家配置 |
| 模型、搜索、MCP 配置 | 导出配置后人工复核导入 | 包含密钥和版本差异 |

如果任务一盘点发现线上存在必须保留的服务、整理或会话数据，应立即停止当前方案，单独补充数据转换设计，不得在任务三临时处理。

## 3. 三次任务总安排

| 任务 | 名称 | 预计工作量 | 主要结果 | 生产影响 |
| --- | --- | ---: | --- | --- |
| 任务一 | v0.8.0 基线与迁移工具 | 2～3 个工程日 | 新基线可启动、数据清单可导出、迁移链不再冲突 | 无 |
| 任务二 | 重点功能升级与自研模块接入 | 3～5 个工程日 | v0.8.0 重点能力可用，服务/整理功能恢复 | 无 |
| 任务三 | 数据迁移、灰度与生产切换 | 1～2 个工程日 + 72 小时观察 | 知识库迁移完成，域名切换，旧环境可回退 | 短时只读 |

建议总工期：

- 单人串行：7～10 个工作日。
- 前后端并行：5～7 个工作日。
- 工程工作量：约 8～14 人日。

每个任务结束后提交一份验收记录。只有负责人明确确认“任务 N 验收通过”，才进入下一次任务。

## 4. 任务一：建立 v0.8.0 基线和迁移工具

### 4.1 目标

建立不影响现网的 `v0.8.0` 新基线，解决官方迁移与睿乐自研迁移长期冲突的问题，并获得线上知识库的完整迁移清单。

任务一不接入服务、整理页面，不切换生产流量。

### 4.2 分支和环境

建议建立顺序分支：

```text
codex/upgrade-v080-foundation
    ↓
codex/upgrade-v080-custom-modules
    ↓
codex/upgrade-v080-release
```

建立独立预发环境：

```text
域名：upgrade-weknora.weixin.qq.com 或仅内网访问
数据库：全新 PostgreSQL 数据库
Redis：独立 DB 或独立实例
OSS：使用新的路径前缀，例如 weknora-v080/
镜像：固定 v0.8.0，不使用 latest
```

### 4.3 实施内容

#### A. 建立官方基线

1. 以官方 `v0.8.0` 为基础建立升级分支。
2. 保留当前项目名称、品牌、中文文案和部署配置。
3. 合并当前生产需要的 OSS、OIDC、模型、搜索和 Langfuse 配置能力。
4. 使用全新数据库执行官方迁移。
5. 验证 App、Frontend、Docreader、Redis 和 PostgreSQL 健康状态。

#### B. 拆分官方迁移与自研迁移

目标结构：

```text
migrations/versioned/      # 官方 WeKnora 迁移，尽量保持原样
migrations/sqlite/         # 官方 SQLite 迁移
migrations/ruile/          # 睿乐 PostgreSQL 自研迁移
migrations/ruile-sqlite/   # 睿乐 SQLite 自研迁移
```

数据库迁移记录分开保存：

```text
schema_migrations          # 官方迁移
ruile_schema_migrations    # 睿乐自研迁移
```

应用启动顺序：

```text
执行官方迁移
    ↓
官方迁移成功
    ↓
执行睿乐自研迁移
    ↓
两套迁移均成功后开放服务
```

任何一套迁移失败，健康检查都必须返回未就绪，不能继续对外接收写请求。

#### C. 增加线上只读盘点工具

盘点工具只读取生产数据库和对象存储，不修改线上数据。输出：

```text
artifacts/upgrade-v080/
├── environment-summary.json
├── accounts.csv
├── tenants.csv
├── memberships.csv
├── knowledge-bases.csv
├── knowledge-files.csv
├── storage-objects.csv
├── model-config-summary.json
├── integration-summary.json
└── migration-report.md
```

`knowledge-files.csv` 至少包含：

- 旧空间 ID。
- 旧知识库 ID。
- 知识库名称。
- 文件 ID。
- 文件名和类型。
- 文件大小。
- OSS Bucket、对象 Key 或可恢复引用。
- 文件校验值；无法直接取得时至少记录大小和更新时间。
- 当前解析状态。
- 当前索引状态。

敏感信息不写入报告：

- 不输出明文密码。
- 不输出 API Key。
- 不输出 OSS Secret。
- 不输出 JWT、AES 和 OIDC Client Secret。

#### D. 建立备份和恢复脚本

任务一只在预发验证脚本，不操作生产切换：

- PostgreSQL 逻辑备份。
- `.env` 和配置文件加密备份。
- OSS 对象清单导出。
- 当前生产镜像 digest 和 Git commit 记录。
- 旧环境一键恢复说明。

### 4.4 任务一交付物

- 可启动的官方 `v0.8.0` 基线分支。
- 独立的官方/睿乐迁移机制。
- 全新数据库从零安装成功记录。
- 线上数据盘点脚本。
- 知识库迁移清单。
- 备份与恢复操作说明。
- 任务一验收报告。

### 4.5 任务一验收标准

必须全部通过：

1. 全新 PostgreSQL 数据库可自动完成官方迁移。
2. `schema_migrations` 和 `ruile_schema_migrations` 相互独立。
3. 同一迁移流中不存在重复版本号。
4. 预发环境可以登录、创建空间和创建知识库。
5. 可以上传并解析 PDF、Word、图片各一个。
6. 上传文件可以检索、预览和下载。
7. 线上盘点报告中的知识库数量、文件数量与管理后台人工抽查一致。
8. 备份可以在临时数据库完成一次恢复演练。
9. 未修改线上数据库和线上对象。

### 4.6 停止和回滚

任务一没有生产变更。出现以下情况应停止：

- 无法完整读取线上对象存储文件。
- 知识库文件清单和后台数量不一致。
- 官方 `v0.8.0` 全新安装仍出现迁移失败。
- 当前账号、空间和知识库归属无法建立确定映射。

任务一未通过时，删除预发环境即可，线上保持原状。

## 5. 任务二：升级重点功能并重新接入自研模块

### 5.1 目标

在任务一基线上接入官方 `v0.8.0` 的重点能力和 Bug 修复，同时重新移植当前服务、整理和专家工作流。所有近期模块使用新自研迁移流初始化，不迁移旧测试数据。

任务二仍不切换生产域名。

### 5.2 官方能力接入优先级

#### P0：必须合入

- SSRF 和 URL 重定向安全校验。
- Secret、API Key 和登录响应脱敏。
- Refresh Token、OIDC JWKS 和权限校验修复。
- 沙箱路径、文件权限和进程回收安全修复。
- PDF 黑图、DOCX 表格、MHTML 和 PPT/PPTX 解析修复。
- URL 抓取失败时不写入错误页面。
- 文档下载、文件夹上传、分块分页等稳定性修复。
- 上下文压缩和稳定 Prompt Cache 标记。

#### P1：本次正式开放

- anydoc Office 文档解析。
- XMind 解析。
- 文档自动标签。
- 文档分块编辑和版本历史。
- 对话产物和消息时间戳。
- LiteLLM Provider 接入能力。
- GitLab、腾讯 IMA 数据源能力。
- Exa、Metaso 搜索 Provider 配置能力。

Provider 只提供配置能力，未配置对应密钥时不在普通用户界面显示为可用。

#### P2：部署能力但默认关闭

- 跨会话长期记忆自动抽取。
- 空间 Skill 目录。
- Docker、E2B、Cube Skill Sandbox。
- DeepSeek Harness 插件。

默认策略：

```text
长期记忆：关闭
Docker Sandbox：关闭
E2B / Cube：未配置
Skill 自动安装：关闭
复杂密码：先在预发开启，生产由负责人确认
```

关闭原因不是放弃功能，而是避免在一次升级中同时扩大数据、权限和外部执行风险。能力完成测试后可在后续小版本通过开关启用。

### 5.3 自研模块接入

#### A. 服务模块

重新接入：

- 服务列表和创建流程。
- 服务空间。
- 服务专家绑定。
- 服务会话。
- 服务知识库绑定。
- 服务产物和基础权限。

不迁移：

- 旧服务实例。
- 旧服务会话。
- 旧服务产物。
- 旧专家测试运行。

使用 `migrations/ruile` 创建新表和默认数据。

#### B. 整理模块

重新接入：

- 整理工作台。
- 整理模板。
- 整理配置。
- 整理任务。
- 整理产物。
- 记忆、发现和原有编辑能力。

不迁移：

- 旧整理配置。
- 旧整理任务。
- 旧整理产物。

重新初始化官方模板和睿乐业务模板，确保创建整理和立即整理均使用真实后端数据。

#### C. 专家工作流

重新接入：

- 专家包。
- 专家路由。
- Agent Run。
- 运行事件。
- 服务与专家的关联。

旧测试专家包只迁移经过确认的发布版本，其余重新导入。

### 5.4 兼容要求

- 旧知识库 API 保持兼容。
- 旧知识库 URL 和文档预览链接可访问。
- 旧对象存储 Key 不在迁移过程中被删除。
- 新功能默认通过配置开关控制。
- 服务和整理入口在后端初始化失败时不得显示空白页。
- 前端、后端、Docreader 和 Sandbox 必须使用同一发布版本。

### 5.5 Bug 回归清单

任务二必须覆盖近期已发现的问题：

- 整理页面浏览器刷新不再返回 404。
- 创建服务可以成功落库并进入服务空间。
- 新建整理缺少模板时，错误显示在模板控件而不是名称输入框。
- 立即整理可以创建任务并显示状态。
- 服务和整理页面样式与当前确认版本一致。
- 前端静态资源构建后不再加载旧 CSS。
- 服务无专家时使用明确的默认专家策略。
- API 错误显示服务端具体信息，不只显示“创建失败”。

### 5.6 任务二交付物

- 完整可运行的升级候选版本。
- 睿乐独立迁移文件。
- 服务模块和整理模块的端到端测试。
- 官方重点功能测试记录。
- 配置差异说明。
- 任务二验收报告。

### 5.7 任务二验收标准

必须全部通过：

1. `go test ./...` 或项目约定的后端测试集通过。
2. 前端 `type-check`、单元测试和生产构建通过。
3. 全新数据库可以一次完成官方迁移和睿乐迁移。
4. 服务创建、进入、创建会话、发消息链路通过。
5. 整理配置创建、立即整理、状态刷新、产物查看链路通过。
6. 知识库上传、解析、搜索、问答、预览、下载链路通过。
7. PDF、DOCX、PPTX、图片、Excel、XMind 各完成一个样本测试。
8. OSS 文件访问和临时签名地址正常。
9. P2 功能在默认配置下保持关闭。
10. 不依赖旧服务和整理数据也能完整运行。

### 5.8 停止和回滚

任务二未涉及生产流量。验收失败时回退到任务一分支，预发数据库可以直接重建。

以下问题未解决前不得进入任务三：

- 知识库搜索结果明显下降。
- OSS 文件无法下载或预览。
- 用户和空间权限串台。
- 服务或整理接口仍依赖旧迁移编号。
- 官方和睿乐迁移无法从空库一次执行完成。

## 6. 任务三：知识库迁移、灰度和生产切换

### 6.1 目标

把现网用户、空间、知识库和原始文件迁移到新环境，完成重新解析、索引对账、灰度验证和域名切换。

### 6.2 上线前准备

至少提前一个工作日完成：

1. 固定发布 Git commit 和镜像 digest。
2. 完成生产数据库全量备份。
3. 导出现网 OSS 对象清单。
4. 保存旧 `.env`、配置和镜像版本。
5. 准备新数据库和新的 OSS 路径前缀。
6. 导入账号、空间和成员关系。
7. 创建知识库并建立 ID 映射。
8. 导入第一批原始文件。
9. 在新环境完成解析和向量生成。
10. 对不少于 20% 的文件进行人工抽样，文件少于 20 个时全量检查。

### 6.3 知识库迁移流程

推荐通过应用接口重新导入原始文件，不直接复制内部知识表、分块表和向量表：

```text
旧库导出知识库与文件清单
    ↓
新库重建用户、空间、知识库
    ↓
从 OSS 读取原始文件
    ↓
通过 v0.8.0 上传接口导入
    ↓
v0.8.0 重新解析
    ↓
重新分块、Embedding 和索引
    ↓
生成新旧映射与校验报告
```

每条文件迁移记录至少保存：

- 旧文件 ID。
- 新文件 ID。
- 旧知识库 ID。
- 新知识库 ID。
- 原文件名。
- 文件大小。
- 校验值。
- 导入状态。
- 解析状态。
- 索引状态。
- 失败原因。
- 重试次数。

失败文件不阻塞其他文件，但不能从报告中隐藏。生产切换前所有失败文件必须明确选择：

- 修复后重试。
- 经负责人确认暂缓。
- 明确放弃并记录原因。

### 6.4 切换窗口

推荐在低峰期安排 60～120 分钟窗口：

| 时间 | 操作 |
| --- | --- |
| T-60 分钟 | 旧站点关闭注册和文件上传，保留读取和问答 |
| T-45 分钟 | 执行最后一次账号、空间、知识库和文件增量盘点 |
| T-30 分钟 | 导入增量文件并等待解析进入稳定状态 |
| T-15 分钟 | 执行数量、校验值、权限和检索抽查 |
| T-5 分钟 | 新站点进入只读灰度，内部账号验证 |
| T0 | 反向代理切换到新环境 |
| T+30 分钟 | 验证登录、知识库、问答、文件下载和预览 |
| T+60 分钟 | 验收通过后开放文件上传 |
| T+120 分钟 | 验收通过后开放注册和其他写功能 |

旧环境在观察期内保持可启动，数据库和对象存储不得清理。

### 6.5 上线验收

#### 数据对账

- 用户数量符合迁移范围。
- 空间及成员关系全部匹配。
- 知识库数量一致。
- 文件数量一致。
- 文件总字节数差异为 0；若重传改变封装，使用源文件校验值对账。
- 每个知识库至少抽查一个文件的预览、下载和检索。
- 所有失败记录都有明确处置结果。

#### 功能验收

- 登录、刷新 Token、退出登录正常。
- 空间切换和角色权限正常。
- 知识库列表、详情、上传、解析和删除正常。
- 知识库问答能够返回引用。
- 文件预览和下载正常。
- 服务可以创建并进入。
- 整理可以创建配置并执行。
- 管理后台可查看系统版本和迁移状态。

#### 技术门槛

- HTTP 5xx 比例低于 1%。
- 登录失败率无明显上升。
- 解析任务无持续堆积。
- Redis 和 PostgreSQL 无连接耗尽。
- OSS 403/404 无批量出现。
- 数据库迁移状态为 clean。
- 核心 API P95 没有超过旧版本两倍。

### 6.6 回滚策略

本方案使用新数据库和新存储前缀，因此回滚优先切换应用流量，不执行生产 `migrate down`。

#### 可以立即回滚的情况

- 新站点仍处于只读窗口。
- 用户尚未在新站点上传新文件。
- 新环境发生登录、权限、文件访问或检索严重故障。

执行：

```text
关闭新站点写入口
    ↓
反向代理切回旧环境
    ↓
恢复旧站点上传和注册
    ↓
保留新环境用于排查
```

#### 已经产生新写入时

如果新站点已经产生上传、服务或整理数据：

1. 立即关闭新写入。
2. 导出切换后的增量文件清单。
3. 评估增量文件是否需要回写旧环境。
4. 完成增量回写或业务确认后再切回。

因此任务三要求先保持只读观察，再开放文件上传，降低带数据回滚的复杂度。

### 6.7 观察期

| 时间 | 重点观察 |
| --- | --- |
| 0～2 小时 | 登录、权限、知识库列表、OSS、5xx、队列 |
| 2～24 小时 | 解析、检索质量、模型调用、任务堆积 |
| 24～72 小时 | 服务和整理模块、用户反馈、资源使用 |
| 7 天 | 决定是否停止旧应用 |
| 14 天 | 决定是否归档旧数据库 |
| 30 天 | 经确认后再清理旧对象和旧环境 |

旧数据库和旧 OSS 对象至少保留 30 天。

### 6.8 任务三交付物

- 生产备份和恢复验证记录。
- 知识库迁移映射。
- 文件迁移与失败清单。
- 数据对账报告。
- 生产切换记录。
- 回滚演练记录。
- 24 小时和 72 小时观察报告。
