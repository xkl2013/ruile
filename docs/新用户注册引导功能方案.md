# 新用户注册引导功能方案

**版本** v1.0 ｜ **日期** 2026-10-06 ｜ **状态** 待评审 ｜ **适用范围** 睿乐大脑（Ruile / WeKnora）

---

## 1. 需求

### 1.1 目标

新用户注册成功后，通过一个分步引导，采集其「工作场景」与「岗位」，据此**推荐**匹配的整理能力与服务能力，用户确认后**一键批量创建**，同时把岗位写入用户档案，让服务模块的推荐从「前端硬编码」变成「真实画像驱动」。

### 1.2 范围

**做：**

1. 全屏分步引导页（3 步：工作场景 → 岗位 → 确认推荐能力）。
2. 新增 2 个后端接口：取选项、提交并批量创建。
3. 选择结果落库 + 岗位画像回写 `WorkProfileDescription`。
4. 「工作场景 / 岗位 → 推荐能力」映射配置化。
5. 引导完成后，用现有聚光灯体系提示「已为你创建了什么」。

**不做：**

1. 不改注册链路（不引入自动登录）。
2. 不改现有整理 / 服务的表结构（零迁移）。
3. 不做平台后台的引导配置界面（第一期映射表走 YAML 文件）。

### 2.2 三个必须知道的卡点

**卡点 1：普通自助注册后不会自动登录。**

`Login.vue:678-688` 在自助注册成功后切回登录模式并回填手机号，用户需再登录一次。只有邀请注册（`Login.vue:653-669`）会自动登录。

> 结论：「注册成功后引导」在产品口径上应表述为**「首次登录后引导」**。本方案按首次登录实现，不改注册链路。

**卡点 2：岗位 / 行业字段不存在。**

- `User`（`internal/types/user.go:74-108`）只有 username / email / password_hash / avatar / tenant_id / is_active / preferences 等，**无任何岗位或行业字段**。
- `Tenant`（`internal/types/tenant.go:109-167`）只有自由文本 `Business`（`:129`），**无结构化行业字段**。
- 唯一带岗位语义的是 `TenantMember.WorkProfileDescription`（`internal/types/tenant_member.go:157`），其注释明确写着「AI service routing reads this text」。

> 结论：岗位选择的最小落点是 `User.Preferences`（jsonb，零迁移）+ 回写 `WorkProfileDescription`。

**卡点 3：服务模块的「用户画像」与「匹配度」是前端写死的。**

- `currentUserServiceProfile`（`frontend/src/views/service/serviceHubState.ts:352-357`）恒为 `role: '教培工作者'`、`department: '招生与教务'`、`focus: ['招生跟进','家校沟通','教学质量']`。
- 8 个服务模板的 `matchScore`（`serviceHubState.ts:221-350`：96 / 88 / 86 / 80 / 74 / 68 / 61 / 52）是**手写常量**，不是算法结果。

> 结论：这是本功能最大的价值点——引导采集的真实岗位可以直接替换这块假数据，让推荐变成真推荐。**若不做落库与回写，本功能等于只做了个花哨的新手引导。**

## 3. 目标态设计

### 3.1 触发与路由

1. 新增路由 `/onboarding/setup`，meta 为 `requiresAuth: true, requiresInit: false, requiresTenant: true`，守卫规则比照现有 `/onboarding/workspace`（`router/index.ts:474-490`）挂载。
2. 后端在 `GET /api/v1/auth/me` 的响应中增加引导状态字段（见 4.4），前端存入 `authStore`。
3. 登录成功后的跳转判断（`Login.vue:550`）与全局守卫（`router/index.ts:493-501`）统一改为：
   - 有有效租户 **且** 未完成引导 → 跳 `/onboarding/setup`
   - 有有效租户 **且** 已完成（或已跳过）→ 跳 `/platform/knowledge-bases`
4. 引导页可跳过（写 `skipped: true`），也可从「设置」或用户菜单重新进入（复用聚光灯的重开入口模式，`frontend/src/components/UserMenu.vue:120`）。

### 3.2 引导页三步交互

| 步骤 | 交互 | 数据来源 |
|---|---|---|
| ① 选工作场景 | 单选或多选卡片（建议多选，最多 3 个） | `GET /onboarding/options` 的 `scenes` |
| ② 选岗位 | 单选（可附部门） | `GET /onboarding/options` 的 `roles` |
| ③ 确认推荐能力 | 分组勾选清单，默认全选，用户可取消 | `GET /onboarding/options` + 前端按 3.3 规则计算，或直接由后端 `POST /onboarding/apply` 的 dry-run 返回 |

第 3 步展示结构：

```
推荐给你的整理能力（3 项，默认勾选）
  [x] 线索跟进清单   每 2 天自动整理一次   来自：招生增长
  [x] 渠道效果周报   每周一自动整理       来自：招生增长
推荐给你的服务空间（2 个，默认勾选）
  [x] 招生咨询全流程
  [x] 家长续费跟进
```

### 3.3 推荐规则

推荐分两维：**工作场景（主）** × **岗位（加权）**。第一期用确定性映射，不做模型打分。

**工作场景 → 能力映射**（配置在 `config/onboarding_recommendations.yaml`）：

| 工作场景 | key | 推荐整理模板 | 推荐服务模板 |
|---|---|---|---|
| 招生增长 | `admissions_growth` | `lead_followup`、`channel_report` | `t1` 招生咨询全流程、`t2` 家长续费跟进 |
| 家长服务 | `parent_service` | `parent_review` | `t8` 早教机构会员服务 |
| 活动策划 | `event_planning` | — | `t5` 活动筹备 |
| 园所运营 | `kindergarten_operations` | — | `t3` 一日流程巡查 |
| 团队运营 / 领导力 | `team_leadership` | — | `t4` 新教师带教 |
| 儿童营养与食育 | `nutrition_food_education` | — | — |
| 空间设计 / 环创 | `space_environment` | `env_proposal` | — |
| 教师成长 / 教研 | `teacher_research` | `teacher_research`、`lesson_review`、`case_observation` | `t6` 教学教研沉淀 |

> 注：整理模板的 `scene` 列是**中文自由文本**（取值为「教师成长 / 招生增长 / 家长服务 / 空间设计 / 个人沉淀」，见 `000106_organize_workbench.up.sql:152-183`），与发现分类的英文 key 不是同一套，必须显式建映射，不要靠包含匹配。

**岗位 → 加权**（同一批岗位名已在前端服务模板中使用，见 `serviceHubState.ts` 的 `experts` 数组）：

| 岗位 | 加成方向 |
|---|---|
| 招生顾问 | 招生增长（`lead_followup`、`channel_report`、`t1`、`t2`）|
| 教务主管 | 家长服务、教师成长（`parent_review`、`t6`、`t8`）|
| 班主任 | 家长服务、会员服务（`parent_review`、`t8`）|
| 带班老师 | 教师成长、园所运营（`teacher_research`、`lesson_review`、`case_observation`、`t3`、`t6`）|
| 保育员 | 园所运营（`t3`）|
| 后勤主任 | 活动策划（`t5`）|
| 会员服务顾问 | 家长服务（`t8`）|
| 市场研究员 / 竞品分析师 | 研究类（`t7` 市场调研与竞品分析协同助手）|

第二期可把 `matchScore` 从手写常量改为「场景命中权重 + 岗位命中权重」的计算结果，替换 `serviceHubState.ts:221-350` 的硬编码分值。

### 3.4 一键创建：行为、顺序、失败处理

**顺序**（整理在前、服务在后）：

1. 回写岗位画像（`WorkProfileDescription`）—— 快、无依赖，先做。
2. 写 `User.Preferences` 的 `onboarding` 状态（`completed` / `selection`）。
3. 逐个创建整理配置（`POST /api/v1/organize/configs`）。
4. 逐个创建服务（`POST /api/v1/services/templates/:key/apply`）。

**整理配置的入参**（`OrganizeConfigInput`，`internal/types/organize_workbench.go:321-329`）：

```json
{
  "name": "线索跟进清单",
  "template_key": "lead_followup",
  "schedule": "daily",
  "instruction": "",
  "metadata": { "source": "onboarding" }
}
```

> `schedule` 仅支持 `manual / daily / weekly / monthly`（`organize_workbench.go:22-25`）。引导创建的默认建议：周报类用 `weekly`，跟进类用 `daily`，复盘类用 `manual`（不自动跑）。

**幂等**：以 `userId + onboarding` 为幂等域。重复提交时，已存在同名（或同 `template_key`）的整理配置与服务直接跳过，返回 `skipped` 列表，不重复创建。服务侧 `applyServiceTemplate` 本身要求 `idempotency_key`（`frontend/src/api/service/index.ts:420`），沿用现有 `createIdempotencyKey()`（`ServiceHub.vue:1648`）。

**失败处理**：单个创建失败不阻断整体，收集到 `failed` 列表返回前端；前端展示「已创建 N 项，M 项失败（可重试）」。**不要**因为一个失败就回滚全部——这会让用户反复重做前两步。

**硬约束提醒**：`POST /organize/jobs` 的 `config_id` 是必填（`internal/application/service/organize_workbench.go:234-237`），所以一键创建的是 `organize_config`（模板 + 调度），不是直接跑一次任务。整理任务要靠调度器在到期时触发（`internal/container/container.go:1761-1789`，每分钟扫 due config）。

### 3.5 落库与画像回写

**写入 `User.Preferences`（jsonb，零迁移）**，结构：

```json
{
  "LastActiveTenantID": 1,
  "onboarding": {
    "completed": true,
    "skipped": false,
    "completed_at": "2026-10-06T18:40:00+08:00",
    "version": 1,
    "selection": {
      "scenes": ["admissions_growth", "parent_service"],
      "role": "招生顾问",
      "department": "招生与教务"
    },
    "created": {
      "organize_configs": ["cfg_xxx", "cfg_yyy"],
      "services": ["svc_xxx"]
    }
  }
}
```

> `UserPreferences` 当前只有 `LastActiveTenantID`（`internal/types/user.go:24-40`），新增字段属于加字段，不破坏现有结构。

**回写 `WorkProfileDescription`（`internal/types/tenant_member.go:157`）**：以现有默认画像（`tenant_member.go:97-110`）为骨架，把第 1 节的「岗位角色」与第 3 节的「近期业务重心」替换为用户实际选择。这样服务路由（注释明确说会读这段文本）立刻能拿到真实画像。

**边界**：只覆盖注册时写入的**默认值**。若用户已手动改过该字段，则不覆盖（可通过与 `DefaultWorkProfileDescription` 是否相等的比对来判断）。

## 4. 接口契约

### 4.1 新增 `GET /api/v1/onboarding/options`

权限：`g.Viewer()`。返回引导所需的全部选项与推荐映射（避免前端硬编码第二份真源）。

```json
{
  "success": true,
  "data": {
    "scenes": [
      { "key": "admissions_growth", "label": "招生增长", "sort_order": 10 }
    ],
    "roles": [
      { "name": "招生顾问", "department": "招生与教务", "keywords": ["招生", "咨询", "转化"] }
    ],
    "recommendations": {
      "admissions_growth": {
        "organize_templates": [
          { "key": "lead_followup", "name": "线索跟进清单", "scene": "招生增长", "suggested_schedule": "daily" }
        ],
        "service_templates": [
          { "key": "t1", "name": "招生咨询全流程", "space_type": "customer_service" }
        ]
      }
    }
  }
}
```

数据来源：`scenes` 读 `organize_discover_categories`（`001013` 迁移建的表，`status='enabled'` 按 `sort_order` 排序）；`organize_templates` 读 `organize_templates` 表 `scope='platform'`；`service_templates` 读 `builtinServiceTemplates()`（`service_space.go:2212-2284`）；两者之间的映射读 `config/onboarding_recommendations.yaml`。

### 4.2 新增 `POST /api/v1/onboarding/apply`

权限：`g.Viewer()`。入参即 3.2 第 3 步的勾选结果：

```json
{
  "scenes": ["admissions_growth"],
  "role": "招生顾问",
  "department": "招生与教务",
  "organize_templates": ["lead_followup", "channel_report"],
  "service_templates": ["t1", "t2"],
  "schedules": { "lead_followup": "daily", "channel_report": "weekly" },
  "skipped": false
}
```

出参：

```json
{
  "success": true,
  "data": {
    "created": { "organize_configs": ["cfg_1"], "services": ["svc_1"] },
    "skipped": { "organize_configs": [], "services": ["t2"] },
    "failed": [{ "kind": "organize_config", "key": "channel_report", "reason": "..." }]
  }
}
```

服务端在**一个请求内**依次调用现有的 `CreateConfig`（`organize_workbench.go:126-143`）与 `ApplyTemplate`（`service_space.go:236-360`），不新增业务语义，只做编排 + 幂等 + 画像回写。

### 4.3 复用的既有接口（前端不必新增 API 层文件）

| 用途 | 接口 | 前端函数 |
|---|---|---|
| 建整理配置 | `POST /api/v1/organize/configs` | `createOrganizeConfig`（`api/organize/index.ts:424`） |
| 一键套服务模板 | `POST /api/v1/services/templates/:key/apply` | `applyServiceTemplate`（`api/service/index.ts:404`） |
| 取已发布专家 | `GET /api/v1/expert-packages/published` | `listPublishedExperts`（`api/expert-package.ts:176`） |

### 4.4 `GET /api/v1/auth/me` 扩展

响应增加 `onboarding_completed`（bool）与 `onboarding_skipped`（bool），前端存 `authStore` 供路由守卫读取，避免每次路由切换都发请求。

## 9. 风险与边界

1. **「注册后」≠「注册完成时」。** 自助注册不自登录，实际触发点是首次登录；对外文案需统一为「首次登录引导」，否则与用户预期不符。
2. **引导批量创建会污染数据。** 若映射过宽（如默认给某场景配 3 个整理配置），新用户一进来就有多个空的定时任务。建议第一期每类场景**最多 2 个整理 + 2 个服务**，且复盘类默认 `manual`。
3. **整理任务需要记忆才有产出。** 新用户尚无记忆，定时任务会空跑并留下「无记忆不虚构」的空成果。建议：跟进/周报类默认 `daily`/`weekly` 但**首次到点前允许用户关闭**；或第一期全部默认 `manual`，仅创建配置不启动调度。
4. **`WorkProfileDescription` 回写是覆盖式的。** 必须与 `DefaultWorkProfileDescription` 比对后再写，否则会抹掉用户的手工编辑。
5. **映射表是单真源。** 不要在前端再维护一份，否则改一处漏一处。前端只消费 `GET /onboarding/options`。
6. **不建议做「自动登录 + 立刻引导」。** 会改动注册/登录核心链路，收益（少一次登录）与风险不成比例。
