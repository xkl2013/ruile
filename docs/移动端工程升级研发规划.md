## 1. 执行摘要

### 1.1 一句话

> **Web 端这一轮（整理 v1.4 / 服务 v0.22 / 发现 v1.0）已经落地，移动端还停在旧形态；本次升级同时还两笔账：架构债与功能债。**

### 1.2 两个必须同时解决的问题

| # | 问题 | 事实 | 不解决的后果 |
| --- | --- | --- | --- |
| 一 | **架构债** | `mobile/lib/main.dart` 单文件 **18698 行 / 241 个类**，占 lib 总行数 55%；无路由表、无状态管理、网络层双份实现、零 CI | 功能对齐只能继续往这个文件里塞代码，可维护性归零；新人无法接手 |
| 二 | **功能债** | mobile 只调用了 4 个 `organize/*` 接口（`discover` / `memories` / `outputs` / `sprout-reports`），**完全没有接入** `templates` / `configs` / `jobs` | 用户在 Web 端配好的「整理配置」，手机上看不到、用不上；PRD FR-4 承诺的「产物落入手机端」无法验收 |

### 1.3 三个关键结论

1. **mobile 不必等 v0.8.0 就能开工。** 它依赖的 `/organize/*`、`/services/*` 接口在 `main`（0.7.0）上**已经实现**，不必等 WeKnora 基线升级（详见 §4）。
2. **但最终回归必须排在 v0.8.0 任务二之后。** 任务二会「重新接入服务模块 / 整理模块」，接口契约需要一次回归验证（详见 §4.3）。
3. **发现模块不能让 mobile 先做。** 《发现模块重新规划方案》目前**仅方案未实现**（分类表未建、`/organize/discover` 的 `sort` / `status` 参数未实现），mobile 的发现页重构必须等后端 P1/P2。

### 1.4 建议排期（详见 §7、§8）

| 阶段 | 内容 | 工作量 | 可并行性 |
| --- | --- | ---: | --- |
| P0 | 架构地基（拆文件 + 路由 + 状态管理 + 网络层 + CI），**不改任何功能** | 12–18 人日 | 与后端完全并行 |
| P1 | 整理模块对齐（工作台 / 我的整理 / 产物查看 / 整理配置 / 时间线） | 10–15 人日 | 接口已在 main 上，可立即开始 |
| P2 | 记忆与采集联动（状态筛选 / 多选 / 表达要求弹层 / 采集后立即整理） | 6–9 人日 | 同上 |
| P3 | 发现模块对齐（分类下发 / 推荐位 / 状态 chip / 排序 / 冷启动） | 6–9 人日 | **等后端发现模块 P1/P2** |
| P4 | 服务模块对齐 + 原生与发布整改 | 12–17 人日 | 开发并行，联调放 v0.8.0 任务二后 |
| P5 | 全量回归 / 性能 / 发版 | 6–8 人日 | 必须在 v0.8.0 任务二验收后 |
| | **合计** | **52–76 人日** | |

## 3. 目标与边界

### 3.1 目标

| 编号 | 目标 | 衡量口径 |
| --- | --- | --- |
| M1 | 单文件拆解 | `main.dart` ≤ 300 行（仅 bootstrap）；任一文件 ≤ 800 行；任一 `State` 类 ≤ 500 行 |
| M2 | 建立路由体系 | 全部跳转走声明式路由表；Web 端 4 条深链约定（整理 PRD §10.6.4）在移动端可用 |
| M3 | 建立状态管理 | 业务状态一律走 Provider；`setState(` 调用点降至 0（仅保留纯 UI 局部状态并注明理由） |
| M4 | 网络层唯一 | 全工程只有一个 `ApiClient`；`RecordingCardApiClient` 与手写请求头全部删除 |
| M5 | 测试可兜底 | 拆分前先补 characterization 测试；核心链路（登录/记忆/整理/发现/服务）单元+Widget 测试覆盖；关键路径 integration_test |
| M6 | CI 建立 | mobile 独立流水线：`flutter analyze` + `flutter test` + debug 构建（PR 门禁） |
| M7 | 功能对齐整理模块 | 移动端可完成「配置整理 → 执行 → 查看任务时间线 → 查看产物 → 锚点回跳原始记忆」全链路（PRD FR-4 / FR-20） |
| M8 | 功能对齐发现模块 | 分类由接口下发、状态语义明确、排序可切换、搜索可下推（发现方案 D1–D8） |
| M9 | 功能对齐服务模块 | 服务列表 1 列卡片 + 底部动作面板；服务空间「对话区 + 底部抽屉面板」（界面说明 UI-Q7） |
| M10 | 发布就绪 | release 签名就绪、权限与隐私文案齐备、可提审 |

### 3.2 边界

**包含**：`mobile/` 工程架构、移动端页面与交互、移动端所依赖接口的接入与联调、原生侧签名与权限、mobile 的 CI。

**不包含**：

- 后端功能实现（整理模块后端已落地；**发现模块后端未实现，不在本次范围**）
- Web 端 / admin 端 / 小程序端
- WeKnora v0.8.0 基线迁移本身（见 `docs/WeKnora-v0.8.0三任务迁移升级方案.md`）
- 录音卡的 Jieli SDK 剩余验证项（在计划中挂为 P4 尾项，不阻塞主线）
- 新的产品功能（本次只做「已落地能力在移动端的兑现」，不新造需求）

## 4. 依赖分析（关键章节）

> 本节回答老师指定的问题：**mobile 与 Web 重构、v0.8.0 三任务是什么关系，要不要等。**

### 4.1 依赖实况

| 依赖项 | 所在位置 | 状态 | 对 mobile 的影响 |
| --- | --- | --- | --- |
| `/organize/memories` `/discover` `/outputs` | `main` 分支 | ✅ 已实现，mobile 已用 | 无 |
| `/organize/templates` `/templates/scenes` `/configs` `/jobs` `/jobs/:id/events` | `main` 分支（`internal/router/router.go:1446-1464`；handler `internal/handler/organize.go` 966 行） | ✅ **已实现** | **mobile 可直接接入，无需等** |
| 整理模块数据表（`organize_templates` / `organize_template_versions` / `organize_configs` / `organize_jobs`，以及 `organize_outputs` 新增的 `fields` / `citations` / `template_key` 列） | `migrations/versioned/000106_organize_workbench.up.sql` | ✅ **已建表** | mobile 可直接消费 `fields` / `citations` |
| `/services` 列表与创建、服务空间接口组 | `main` 分支（`router.go:1496` 起） | ✅ 已实现 | mobile 可直接接入 |
| Web 端 `OrganizeWorkbench.vue` / `OrganizeOutputDetail.vue` / `OrganizeConfigDetail.vue` / `ServiceHub.vue` | `frontend/src/views/` | ✅ **已落地**（文件修改时间 2026-09-28 17:26，仍在活跃修改） | **可作 mobile 的规格参照物** |
| 发现模块 v1.0（`organize_discover_categories` 表、查询下推、`sort` / `status` 参数、4 个埋点事件） | — | ❌ **仅方案，未实现**（迁移目录无该表；`GetDiscover` 未支持新参数） | **P3 必须等后端** |
| WeKnora v0.8.0 三任务迁移 | `codex/upgrade-v080-*` 分支（**尚未合并 main**） | 🟡 进行中 | 任务二会「重新接入服务 / 整理模块」→ 需一次接口回归 |

### 4.2 结论一：开发可以立即并行，不必等 v0.8.0

理由：mobile 需要的一切后端接口都在 `main`（0.7.0 线）上**已经实现并可用**。P0（架构地基）与后端零耦合；P1/P2（整理与记忆）依赖的接口已就绪；P4（服务模块）的服务接口也已就绪。

**唯一的例外是 P3（发现模块）** —— 它依赖的后端能力目前只有方案、没有实现。因此建议把 P3 排到最后，或与后端发现模块同期启动联调。

### 4.3 结论二：最终回归必须排在 v0.8.0 任务二之后

`WeKnora-v0.8.0三任务迁移升级方案.md` §5.3 明确：

> **B. 整理模块**：重新接入 整理工作台 / 整理模板 / 整理配置 / 整理任务 / 整理产物 / 记忆、发现和原有编辑能力
> **A. 服务模块**：重新接入 服务列表和创建流程 / 服务空间 / 服务专家绑定 / 服务会话 / 服务知识库绑定 / 服务产物和基础权限

这意味着升级到 v0.8.0 基线时，服务与整理模块会被**重新移植到新迁移流**（`migrations/ruile`）。方案 §5.4 要求「旧知识库 API 保持兼容」，但**自研模块的接口契约需要一次实测回归**。

**因此排期为**：后端沿「任务一 → 任务二 → 任务三」推进；mobile 沿「P0 架构 → P1 整理 → P2 记忆 → P4 服务 → P3 发现 → P5 回归+发版」推进。两条线的交点只有一处 —— **P5 联调窗口必须落在 v0.8.0 任务二验收通过之后**（P3 的发现模块还依赖后端发现模块 P1/P2 落地，顺延规则相同）。

### 4.4 结论三：需要一次「接口契约冻结」

Web 端 `OrganizeWorkbench.vue` / `ServiceHub.vue` 在**今天（2026-09-28 17:26）仍在修改**。mobile 接入期间如果后端接口同时在变，会产生返工。

**建议**：进入 P1 前，由 mobile + 后端共同签署一份**接口契约冻结清单**（本文档 §6.3 的「依赖接口」列可直接作为清单底稿），冻结期为 P1–P2 期间；冻结期内接口只做加法不做破坏性修改。

## 5. 架构重构方案

### 5.1 目标目录结构

原则：**按功能域切分（feature-first），而不是按技术层切分**。每个 feature 内部再分 data / domain / presentation 三层。

```
mobile/lib/
├── main.dart                     # 仅 bootstrap：runApp + ProviderScope（目标 ≤ 300 行）
├── app/
│   ├── app.dart                  # MaterialApp.router
│   ├── router/
│   │   ├── app_router.dart       # GoRouter 路由表
│   │   └── routes.dart           # 路径常量 + 深链解析（对齐 Web 约定）
│   ├── theme/
│   │   ├── colors.dart           # 迁移现有 AppColors
│   │   ├── typography.dart       # 迁移现有 AppTextStyles
│   │   └── dimensions.dart       # 迁移现有 AppRadii / AppSpacing
│   └── env/
│       └── app_config.dart       # 封装现有 String.fromEnvironment
├── core/
│   ├── network/
│   │   ├── api_client.dart       # 唯一 HTTP 客户端（dio）
│   │   ├── interceptors/         # 鉴权 / 租户 / 语言 / 日志 / 重试
│   │   └── api_exception.dart    # 迁移现有 _ApiException + 错误码映射
│   ├── auth/                     # 会话与 token（迁移 _AuthSessionStore）
│   └── storage/                  # secure storage + 本地草稿缓存
├── features/
│   ├── auth/                     # 登录、协议、鉴权门（迁移 _AuthGate）
│   ├── organize/
│   │   ├── hub/                  # 整理工作台：我的整理 + 整理模板
│   │   ├── memory/               # 记忆（笔记 / 录音 / 工牌 + 状态筛选 + 多选）
│   │   ├── mine/                 # 我的整理：产物列表 + 字段筛选 + 排序
│   │   ├── discover/             # 发现：分类 / 推荐位 / feed
│   │   ├── config/                # 整理配置表单 + 任务时间线
│   │   └── output/               # 产物查看视图（字段区 + 正文 + [Mx] 锚点）
│   ├── service/                  # 服务列表 / 服务空间 / 会话 / 事项
│   ├── knowledge/                # 知识库 / 客户空间 / 文件预览
│   ├── recording_card/           # 录音卡（保留现役 8 文件结构）
│   └── settings/                 # 设置 / 帮助 / 关于 / 日报
└── shared/
    └── widgets/                  # 通用：卡片 / 空态 / 加载 / 错误 / 底部动作面板 / 抽屉
```

每个 feature 内部：

```
features/organize/hub/
├── data/
│   ├── hub_repository.dart       # 接口调用
│   └── dto/                      # 接口 DTO + fromJson
├── domain/
│   └── hub_models.dart           # 领域模型
└── presentation/
    ├── hub_page.dart             # 页面（≤ 300 行）
    ├── widgets/                  # 子组件
    ├── hub_provider.dart         # 状态
    └── hub_state.dart
```

### 5.2 技术选型

| 关注点 | 选型 | 理由 |
| --- | --- | --- |
| 状态管理 | **Riverpod**（`flutter_riverpod`） | 编译期安全、无 BuildContext 依赖、易测试；相比 Bloc 样板代码少，相比 GetX 无隐藏全局态（当前 118 处 `setState` + 3 个全局 `ValueNotifier` 正是要消灭的东西） |
| 路由 | **go_router** | 声明式、支持深链与 URL 参数，可直接对齐 Web 端 `?tab=` / `?config=new` 的深链约定 |
| 网络 | **dio** | 拦截器机制天然适配「鉴权 / 租户头 / 401 登出」这三件现在手写三遍的事 |
| 序列化 | **freezed + json_serializable** | 当前 2900 行手写 DTO 与 `fromApi`，改为生成式可大幅压缩并消灭手写解析错误 |
| 本地存储 | 保留 `flutter_secure_storage`（token）+ 增加 `shared_preferences`（草稿/筛选态） | 现状已有 secure storage；整理草稿与筛选态需要非敏感持久化 |
| 测试 | `flutter_test` + `mocktail` + `integration_test` | mocktail 与 Riverpod 配合好 |
| CI | GitHub Actions（mobile 独立 workflow） | 与仓库既有 4 条流水线并列，不动现有 |

> **风险提示**：选型会显著改变代码形态。若团队对 Riverpod 不熟悉，Bloc 亦可（样板更多但心智模型更线性）。此点列入 §10 待决策 Q8。

### 5.3 网络层统一

```
├── baseUrl            ← AppConfig（保留 --dart-define 入口，兼容现有构建脚本）
```

## 6. 移动端信息架构与功能对齐

### 6.1 底部 Tab 结构（建议）

**现状**：3 Tab（记忆 / 发现 / 服务）+ 中央采集键

**Web 端现状**（`organizeRoutes.ts:40-73`）：4 页签 = 工作台 / 我的整理 / 记忆 / 发现

**移动端建议**：**4 Tab + 中央采集键（5 槽位，iOS 上限内）**

```
  记忆            整理         ⌃采集        发现            服务
（原始素材）  （工作台 hub）  （录音/文字） （复用入口） （工作）
```

理由：

1. **「整理」必须是一级入口** —— 移动端的核心闭环是「采集 → 整理 → 复用」，采集与整理分开成两级会让主路径断开。
2. **「我的整理」（Web 的 mine）不单独占 Tab**，作为整理工作台的第二段（对齐 Web 的 hub 信息架构：上「我的整理」/ 下「整理模板」）。
3. **「发现」保留一级** —— PRD v1.4 §10.6.2 明确发现是独立页签，且它是「个人知识复用入口」，与整理是两种不同的使用心态（一个在产出，一个在回查）。
4. **中央采集键保留** —— 这是移动端相对 Web 最大的差异化能力（随时录音），不能因为加 Tab 而牺牲。

> 备选方案（列入 §10 Q1）：3 Tab（记忆 / 整理 / 服务）+ 采集并入记忆页 —— 更简洁但会削弱「随手记」的入口强度。
