# Agent 治理方案

> 本文档独立于「服务模块重构」的 D/Q 编号体系，自用 **G 编号**（Governance）。
> 事实基线：2026-09-21 对 `internal/agent/`、`internal/sandbox/`、`internal/mcp/`、`internal/middleware/`、`internal/container/`、`internal/router/` 及 `migrations/` 的通读。

---

## 一、这份文档解决什么问题

「Agent 治理」不是指限流和排队——那部分已经有文档（`docs/worker-pool-governance.md` 管的是 worker 并发与模型配额，属于**容量治理**，不是本文范围）。

本文要解决的是另一个问题：

> **让 agent 在明确的边界内工作，并且事后能举证它当时干了什么、是谁授权的。**

拆成三句可验证的话：

1. **边界在事前定死** —— 谁能用、能用什么、能碰哪些数据，不用运行时猜；
2. **越界在事中拦住** —— 高风险动作要有人点头，不能悄悄做；
3. **轨迹在事后可查** —— 任何一个动作，都能回答"谁、用哪个 agent、调了什么、结果如何、谁批的"。

对教培行业尤其重要：agent 会碰到家长与学生的信息。出事的时候，如果拿不出"当时是谁让它做的"这条记录，损失的不只是数据，是机构的信任。

## 二、治理现状盘点

先说结论：**零件基本齐了，但装配缺失，而且默认值几乎全部朝"放开"的方向倒。**

| L15 | **白名单空值即全允许** | `AllowedTools` 空 → 用默认集（`agent_service.go:444`）；`AllowedSkills` 空 → 全允许（`skills/manager.go:131`） | 默认放开 |
| L16 | **技能无签名、无版本、无审核** | 来源仅内置目录（`skill_service.go:16`），无签名/版本字段 | 供应链无追溯 |
| L17 | **专家包发布无门禁** | `PublishVersion` 只查 blocking 与 definitions 非空（`service/expert_package.go:176-195`），无签名、无 SBOM、无评测、无灰度、无回退 | 坏包可以直接发布到全租户 |
| L18 | **无提示注入检测** | 只有描述与结果的 external/untrusted 前缀（`mcp_tool.go:83、253`）与截断（16000 runes） | 注入只能靠模型自觉 |
| L19 | **工具级权限不存在** | `internal/agent` 内无角色判断 | 无法表达"这个岗位不能用这个工具" |
| L20 | **MCP 文档与代码矛盾** | `docs/MCP功能使用说明.md:16,28` 称支持并推荐 Stdio，代码三处硬禁用 | 运维照着文档配，配不通 |

**把 L1 与 L2 叠起来看，是本方案最需要优先处理的一件事**：外部 MCP 工具要走审批，而能够直接写知识库、删页面、执行脚本、查询数据库的内置工具**一道门都没有**，且这些调用**不留任何记录**。

## 三、核心主张：把默认值翻过来

通读上述缺口会发现一个共同模式：**几乎每一条都不是"没做"，而是"默认放开"。**

沙箱默认关、白名单空即全允许、存储白名单不配就全通、API key 一律放行、审批只挑着 MCP 做。

这在"先把功能跑通"的阶段是合理的取舍——快速上线、少踩配置坑。但到了要交付给教培机构、agent 要碰家长与学生信息的阶段，同一个默认值就变成了风险敞口。**因为默认放开的设计，它的安全性取决于"没人忘记配置"，而这件事在真实运维里不可靠。**

因此本方案的核心主张是一句话：

> **治理的默认值从 default-open 改为 default-closed：能力默认关闭，由配置显式打开；权限默认不足，由授权显式补齐；动作默认留痕，不区分高低风险。**

这条主张落到具体动作上，就是下面六项里凡是带「翻转」标记的部分。翻转的价值不在新增功能，而在把"靠人记得配"换成"靠系统兜底"。

## 四、治理框架：五道闸 + 一本账

把散落在各模块的机制串成一条主链。任何一次 agent 动作，依次经过五道闸，最后落一本账：

1. **准入闸（G1）** — 谁可以用、用哪个专家、能接哪些工具/技能/MCP/模型
2. **授权闸（G2）** — 每一次调用的实时权限判定与数据范围裁剪
3. **审批闸（G3）** — 高风险动作的人工确认
4. **预算闸（G4）** — token、轮次、时长、并发四类配额与超限中断
5. **隔离闸（G5）** — 沙箱、网络、文件系统、凭据
6. **留痕账（G6）** — 全链路审计，可查可溯可保留

主链的读法：

> **主体**（谁）→ **载体**（用哪个专家包）→ **动作**（调什么工具）→ **约束**（在什么边界内）→ **证据**（留下什么）

六项之间的关系是：G1/G2 决定"能不能"，G3/G4/G5 决定"怎么限"，G6 决定"怎么证"。**缺 G6，前五项都不可验证**——这也是为什么留痕排在优先级第一位。

## 五、逐项方案

### G1 · 准入闸

**目标**：agent 能力集合在配置期就定死，运行时不再扩大。

动作项：

- **G1-1（翻转）** 白名单空值语义反转：`AllowedTools` / `AllowedSkills` 为空时**不再等于全允许**，改为等于"仅默认集"并给出配置提示。当前语义见 L15。
- **G1-2（翻转）** 存储白名单 fail-open 改 fail-closed：`STORAGE_ALLOW_LIST` 未配置时**拒绝非 local provider**，而不是全部允许（L14）。
- **G1-3** 新增**模型白名单**：租户级可配允许的模型 provider 与具体模型，未在白名单内直接拒绝（补 L12）。
- **G1-4** MCP server 准入清单：租户级维护"允许接入的 MCP server 域名/IP 清单"，创建时校验，替代目前的"只做 SSRF 校验"（补 L20 相关面）。
- **G1-5** 技能与专家包的**来源准入**：区分内置 / 租户导入 / 平台发布三档，非内置来源需要 Admin 显式启用（为 G1-6 打基础）。
- **G1-6** 技能与专家包的**签名与版本**：导入时记录内容哈希与发布者，发布前做一致性校验（补 L16/L17）。

### G2 · 授权闸

**目标**：每次工具调用前做一次权限判定，而不是信任上下文。

动作项：

- **G2-1（翻转）** **API key 不再短路放行**：至少让 API key 走与登录用户同一套判定路径，或为 API key 单独定义显式的权限集合（当前见 L13，这是整条链上最大的绕过路径）。
- **G2-2** **工具级权限**：给工具打上**风险等级**（`read` / `write` / `execute` 三档），角色 × 风险等级 → 是否可调用。这样"带班老师这个岗位不能用 `execute_skill_script`"才表达得出来（补 L19）。
- **G2-3** 服务级权限模型：目前服务级只靠 `Admin()` 角色闸门 + 租户隔离，需补一层服务内角色到能力的映射。
- **G2-4** 专家绑定的能力收窄：`expert_ref` 指向的专家包自带能力集，服务内可**收窄不可扩大**（收窄有现成字段 `knowledge_base_ids` / `selected_skills` / `instruction_override`）。

### G3 · 审批闸

**目标**：高风险动作必须有人点头，且这个人必须是发起者本人或其管理员。

动作项：

- **G3-1（最高优先）** **把内置写类工具纳入审批**：`wiki_write_page` / `wiki_delete_page` / `execute_skill_script` / `database_query` / `web_fetch` 按风险等级（G2-2）接入现有审批门（补 L2）。
- **G3-2** **审批状态持久化**：`PendingRequest` 落库，进程重启后恢复等待中的请求；跨实例用数据库而非仅 Redis pubsub（补 L3）。
- **G3-3** **审批决定落审计**：批准、拒绝、超时三种结果全部写入审计表，含审批人、时间、理由（补 L4）。
- **G3-4** **超时策略可配**：当前固定 10 分钟超时后返回失败且不重试。教培场景里老师上课时无法响应审批，建议区分"超时暂停"与"超时放弃"两种策略，暂停的 run 可在会话里恢复。
- **G3-5** 审批粒度细化：从当前的 (租户, 服务, 工具) 扩展到可加"单次/本次会话内有效"的授权，避免同一动作反复打扰。

### G4 · 预算闸

**目标**：任何一个 run 都有明确的天花板，撞到就停。

动作项：

- **G4-1** **Token 预算**：租户级与 run 级双上限，达到阈值先告警、超限中断并落审计（补 L11）。
- **G4-2** **Run 级墙钟超时**：当前只有单次 LLM 120s 与单工具 60s，缺整体超时。补 run 级上限，防止"每步都不超时但整体跑一天"。
- **G4-3** **轮次与并发配额**：最大轮次（现默认 20）按租户可配；同租户并发 agent run 数设上限。
- **G4-4** 成本归属：每次 run 记录 token 消耗并归属到租户/服务/发起人，为计费与容量规划提供依据（与 `worker-pool-governance.md` 的模型配额治理层对齐）。

### G5 · 隔离闸

**目标**：默认隔离，而不是默认信任。

动作项：

- **G5-1（翻转）** **沙箱默认值**：当前默认 `disabled`（L8）。建议改为**默认 docker**、降级需显式声明，并让"降级到 local"在启动时打警告（local 模式与宿主同权限，仅有命令校验，无文件系统与网络隔离）。
- **G5-2（翻转）** **技能执行强制只读根文件系统**：给 skills 调用路径补上 `ReadOnlyRootfs=true`（当前未设置，见 L9），保留 `/tmp` 的 `noexec,nosuid` tmpfs。
- **G5-3** 校验器规则**配置化**：把危险命令表与正则外置为可配置项，便于出现新型攻击时快速收紧，而不必改代码发版（补 L10）。
- **G5-4** 沙箱执行**纳入审计**：当前沙箱执行全程无审计写入，需补被执行脚本的哈希、命令摘要、退出码。
- **G5-5** 凭据隔离：MCP OAuth token 已加密（做得好），需补充"沙箱内进程不可读取宿主凭据"的验证用例。

### G6 · 留痕账

**目标**：任何一次 agent 动作都能被完整还原。**这是优先级最高的一项**——前五道闸的效果都要靠它来证明。

动作项：

- **G6-1（最高优先）** **工具调用全量留痕**：新增工具调用记录，字段至少含 `run_id` / `session_id` / `service_id` / `tenant_id` / `actor_user_id` / `tool_name` / `risk_level` / 参数摘要 / 结果摘要 / 耗时 / 成败 / 是否经审批（补 L1）。
- **G6-2** **审计 action 扩展**：补 `agent.*` / `tool.*` / `kb.*` / `session.*` 类动作常量，并补齐当前缺失的敏感操作——知识库增删改与共享、agent 增删改与执行、会话、登录登出、API key 创建（补 L5）。
- **G6-3（翻转）** **审计写入可靠性**：写失败改为**至少本地落盘兜底 + 重试**，不允许 `_ =` 静默忽略（补 L7）。
- **G6-4** 拒绝类事件**取消去重**或改为"去重计数"：保留攻击尝试的完整频次证据（补 L6）。
- **G6-5** 审计保留与导出：保留期可配，支持按 run / 按人 / 按时间导出，供合规举证。
- **G6-6** 治理看板：管理员可见——当前在跑的 run、被拒绝的调用、待审批请求、token 消耗排行。查询接口已有（`GET /api/v1/tenants/:id/audit-log`），需补 agent 维度的视图。

### 补充项 · 内容与文档治理

- **G7-1** 提示注入防护升级：在"前缀标记 + 截断"之上，增加对外部内容的隔离声明与可疑模式检测（补 L18）。
- **G7-2** **文档与代码对齐**：`docs/MCP功能使用说明.md` 明确写支持 Stdio，代码三处硬禁用（L20）——这类矛盾会让运维照着文档配不通，也会在审计时成为"承诺未兑现"的证据。建议全文复查一次 MCP 与 skills 两份文档。
- **G7-3** 子 agent 能力与前缀：D13 已定"一个服务有多个专家"，但引擎目前**无子 agent 机制**。若后续引入并行专家协作，治理上需补：子 run 独立预算、子 run 的权限继承规则（**只可收窄不可扩大**）、子 run 留痕挂在父 run 下。

## 六、优先级与落地路径

排序依据：**交付风险 × 实现成本**。前四项不做，不建议对外交付。

### 第一优先：先能举证（P0）

对应 G6-1、G6-2、G3-1、G3-2、G3-3。

理由：这五项合起来回答"谁让它干的、干成了没有、谁批的"。缺了它们，后面的治理做得再好也无法自证，客户也无从信任。且这五项都建立在已有结构上（审计表已存在、审批门已存在），属于**接线**而非**造件**。

### 第二优先：把默认值翻过来（P1）

对应 G1-1、G1-2、G5-1、G5-2、G2-1、G6-3。

理由：这些都是"改默认值 + 补校验"的小改动，但消掉的是系统性风险。其中 **G2-1（API key 短路）** 需要单独评估——它可能是为兼容存量集成而有意为之，改动要确认影响面。

### 第三优先：把预算接上（P1）

对应 G4-1 至 G4-4。

理由：直接关系到成本可控与客户账单稳定。可与容量治理（`worker-pool-governance.md`）的模型配额层合并推进。

### 第四优先：供应链与规模化（P2）

对应 G1-3 至 G1-6、G2-2、G2-3、G5-3、G5-4、G7-1、G7-3。

理由：这些在单客户交付时压力不大，一旦要同时服务多家机构、或开放技能市场就变成必需。

## 七、需要拍板的分叉

以下几条我不替你定，需要明确后才能写进实现方案：

- **分支一 · API key 的定位**：它是"集成用的全权凭据"（保持现行为、但强制登记与审计），还是"应当受限的主体"（走角色判定）？这决定 G2-1 是改造还是只补审计。
- **分支二 · 沙箱默认值**：默认 `docker` 会抬高客户的部署门槛（要求宿主机有容器运行时）。是否接受？若不接受，替代方案是"默认 disabled 但启动时强提示 + 管理后台显式确认"。
- **分支三 · 审批超时策略**：教培场景老师上课期间无法响应审批。是"超时暂停、事后恢复"，还是"超时放弃"？建议前者，但需要确认 run 的恢复语义（与 D14 的会话模型相关）。
- **分支四 · 预算的责任主体**：token 上限按租户（机构）统一算，还是按服务/按人细分？这影响 G4-4 的成本归属粒度。
- **分支五 · 留痕的保留期与合规边界**：工具调用记录里可能含家长/学生信息片段。保留多久、谁能查、导出给谁——技术措施由本方案提供，**对外提供与告知的手续仍归机构**，两者不相互替代。
