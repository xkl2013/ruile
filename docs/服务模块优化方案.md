# 服务模块优化方案（研发版）

> **定位**：界面与交互层的减法方案 + 必须的后端补全清单。表结构级重构已经落地（`services` / `service_members` / `service_expert_bindings` / `service_artifacts` / `sessions.service_id`，迁移 `000105` 起，实测至 `001009`），本文不重复设计表结构。
> **要解决的问题只有一个**：这层已经建好的能力，在界面上没有被收好，导致使用难度过大、不简洁清晰。
> **配套原型**：`docs/prototypes/服务模块优化原型.html`（v1.20，9 个场景 + 4 个设置分区，黄底批注标注每条改动对应本文哪一节）。改代码前建议先点一遍原型。

### 0.5 设计原则（2026-10-08 拍板，所有界面改动必须过一遍）

**尽可能简洁，让使用者一眼看上去就知道如何使用。** 落地为四条可检查的规则：

1. **一屏一件事**：每个页面 / 每个 tab 只讲一类内容，不把多种明细堆进一屏（服务概览 v1.7 → v1.8 tab 化即此原则）。
2. **一屏一个主按钮**：底部只保留一个主 CTA / 视觉锚点（例：概览底部只有一个会话输入条，v1.9）。
3. **同一条信息只出现一次**：同一数字、同一入口不重复出现（例：v1.10——产物有 tab 就不再放快捷卡片；待办数只在概览 KPI 出现、tab 一律不带角标）。
4. **能一行说完就不做卡片**：次要信息用一行带「›」呈现（例：成员用一行「服务成员 + 名单 ›」，不做 tile / 二级页入口卡）。

### 1.2 五个根因（一句话版）

| # | 根因 | 证据 |

## 2. 目标态

### 2.1 服务头最终形态（全方案最重要的一个改动）

```
┌─ ‹ 返回   ▣ 秋季招生线索跟进   秋季招生咨询        ▤ 产物 3   ☑ 待办 3   ⋯ ─┐
```

- **标题跟随中间内容**：聊天区显示**会话标题**（右侧灰字回落为服务名——服务名左侧栏已有）；产物 / 待办面板是服务级视图，标题显示服务名；新会话态显示「新的会话」。
- 状态徽标（`已暂停` 等）**只在非 active 时显示**（现状 `:263` 无条件显示"进行中"，占位无信息量）。
- 模板徽标收进 `⋯ › 修改名称` 的说明行，头部不再占位。

### 2.2 入口分层

| 层 | 内容 | 位置 | 现状 |
| --- | --- | --- | --- |
| 天天要点 | **产物 N / 待办 N** | 服务头常驻 | ✅ 已在这两个 |
| 天天要点 | **新建会话** | **左侧服务行悬停 `＋`**：平时该位置显示会话计数徽标，悬停服务行时计数换成 ＋（聊天软件惯用交互）；列表页同样可对任意服务直接开新会话 | ❌ 现在是服务头 `＋` |
| 服务本身 | 修改名称 / 修改描述 / 分享 | `⋯` **一级** | ⚠️ 现在是"复制配置 / 暂停 / 归档 / 删除"，改错了东西 |
| 偶尔要用 | 服务概览 / 服务对象 / 动态 / 服务设置 | `⋯ → 更多` 二级 | ❌ 现在是 4 个常驻 pill |
| 撤出服务头 | 来源 / 主体 / 档案 / 摘要 / 设置 | — | ❌ 5 个 pill |

> `＋` 的行为定义：点击**不弹窗、不跳"新增页"**——对话区直接切到**新会话空态**（标题「新的会话」+ 3 条建议问题 + 可用输入框），原会话自动收好。建议问题按服务 `instruction` 生成（替代现状写死的 2 条，`ServiceHub.vue:838-841`）。

### 2.3 `⋯` 菜单（现状 `:265-281`）

| 层 | 项 | 说明 |
| --- | --- | --- |
| 一级 | 修改名称 / 修改描述 / 分享服务 | 改的是"这个服务是什么" |
| 一级 | 更多 › | 展开二级 |
| 二级 | 服务概览 / 服务对象 / 动态 / 服务设置 | 配一次就忘的东西 |
| 二级 · 分隔线后 | 暂停服务 / 归档服务 / 删除服务 | 危险动作用分隔线隔开 + 二次确认 |

「复制配置创建」只保留列表卡片菜单那一处（`:178`），服务头不再放——复制是"从旧服务长出新服务"，属列表页语义。

## 4. 自动化与派生规则

### 4.1 机器键全部自动化（4 处 → 0 处）

| 现字段 | 现状 | 改法 |

| 服务对象 `subject_type` | 手填 `member_family` | **撤出表单**，默认 `custom`；需要时在对象详情里从模板预置类型里选 |

| 档案字段 `key` | 手填 `member_level` | **后端按字段名称生成**（slug 化，冲突回退 `field_<n>`） |

从模板进入时由模板预置、表单不再问。存量服务不重写 `space_type`。

### 4.2 重点记录由工作指令派生

- **规则（P1 先规则，P2 可换 LLM、规则兜底）**：工作指令里写了「记录 / 重点记录 / 关注 / 跟进 + 名词短语」，X、Y 直接解析为该服务的字段（`Label` = 指令原词，`ExtractionHint` = 指令原句片段，`Aliases` 含指令措辞），带「指令」角标，排在默认字段之前。
- **为什么必须加**：`buildInstructionBlueprint(instruction)`（`service_space.go:2146`）现状只做两件事——按关键词定空间类型（`:2151-2159`）、指令含"会员/家长/续费/孩子"就切到固定 5 个会员字段否则用默认 3 个（`:2182-2197`）。**指令里点名的信息不会变成字段**。最直接的证据：内置模板 t1「招生咨询全流程」的指令原文写着"记录家长顾虑、到访意向和下一步跟进"（`:2275`），但它带的 `commonFields` 里**没有"到访意向"**（`:2239-2243`）——模板自己的指令和字段都对不上。
- **字段名称不是普通文案，它决定 AI 抽取命中率**：抽取按「`Label` + `Key` + `Aliases`」在对话文本里做字符串匹配（`extractProfileFieldValue`，`service_space.go:1511`；提案入口 `extractProfileProposalItems` `:1486`）。写「到访次数」匹配不到家长说的「今天来了 3 次」。因此：
  - 配置界面提供**场景化推荐字段**（招生咨询：孩子月龄 / 家长关注点 / 最近到访 / 意向班型…），措辞按家长说话的习惯预置，点选即加，不强迫从空白起名；
  - 真正影响命中的「**别名**」（`Aliases`）从"没暴露"改为收进**点开字段名后的次级设置**；
  - 已选字段用**可删除的标签**展示（点击改名），不用「名称 + 必填 + 删除」三件套表格；
  - 右侧给**服务概览实时预览卡**，配完立刻看到效果。
- **边界**：改指令**不会**静默重算已配好的字段（避免运行中的服务被静默变更）——「↻ 按新指令重新推荐」入口就放在「重点记录」面板里，由用户确认后追加；指令没提任何"记录 X"时维持现状默认字段。
- **蓝图退场后的残余风险**：用户希望"整体重排概览栏目"时没有一次性动作，只能靠改指令间接触发；若内测出现此类诉求，再考虑给「按新指令重新推荐」加一个覆盖概览的范围选项。

> **为什么不干脆删掉蓝图**：它是 `服务空间V1-1数据契约.md` §2.4 为"模型不许直写业务表"立的护栏，且 `service_space_blueprints` / `template_applications` 两张表与审计字段在跑。删掉等于回退契约。本方案只做一件事：**把护栏收回墙里，不让用户撞上它**（`POST /:service_id/blueprint/preview|confirm` 保留，界面不设入口）。

### 4.3 待办状态：全自动、零配置

1. **默认 4 态**（待处理 / 进行中 / 已完成 / 已取消），建服务时自动生成，映射 `category` 的 `open / in_progress / done / dismissed`，`is_initial = 待处理`；界面不出现「配置状态」入口。
2. **工作指令点名才补充**：指令里写了明确阶段（如"试听后进入等家长回复"），AI 在创建时补上对应状态，带「指令」角标——与重点记录同一条链路、同一套规则。
3. **状态流转说明收进待办浮层底部**（一行只读文字）；**不提供任何自定义入口**。要改状态就直接在工作指令里写清楚，走第 2 条。
4. **后端连带建议**：迁移 `000113` 的默认状态机有 **9 态 + 一张流转表**（`candidate/待识别`、`generated/已生成`、`recompute_required/待重新计算` 等），把 **AI 提案生命周期混进了用户待办**——老师不需要知道"待重新计算"。建议把默认机收窄到 4 个用户态，`is_system` 机器态不再下发给前端渲染（**表结构不动，只改种子与下发过滤**）。
