# 服务模块优化方案

> **本文的定位**：这是一份**界面与交互的减法方案**，不是数据模型方案。
> 服务模块的**表结构级重构已经落地**——`services` 实体表、`service_members`、`service_expert_bindings`、`service_artifacts`、`sessions.service_id` 归属链一整套都在（迁移 `000105` 起，实测至 `001009`）。`docs/服务模块重构PRD.md`（272KB）描述的"插入一层 Service 实体"已经完成，本文**不重复设计表结构**。
>
> 本文要解决的问题只有一个：**这层已经建好的能力，在界面上没有被收好，导致使用难度过大、不简洁清晰。**

> 版本：v1.0（待评审）
> 范围：服务列表页 / 创建服务 / 服务空间 / 服务设置 / 应用级侧栏的服务块，**仅方案，不含实现**
> 前置阅读：`docs/服务模块重构PRD.md` §10（前端交互说明）、`docs/服务模块界面设计说明.md`（列表页与创建流程界面规范）

### 1.2 一次真实的"建一个服务并开始干活"路径

把上面的代码事实串成用户实际经历的 9 步。**加粗的是本方案要删掉的步骤。**

| 步 | 用户看到什么 | 需要理解什么 |
| --- | --- | --- |
| 1 | 服务列表页：我的服务卡片 + 从模板创建 | 服务、模板 |
| 2 | 点「新建服务」→ 单页表单 | 服务名称、服务指令、专家、知识库 |
| 3 | 提交 → **弹出 620px「确认服务空间蓝图」对话框** | **空间形态、服务主体（策略）、档案字段（N 个）、首页摘要（N 个模块）** |
| 4 | 点「确认并创建」→ 进服务空间 | — |
| 5 | 服务头一行 **7 个带计数的入口**：产物 3 / 待办 3 / 来源 2 / 主体 5 / 档案 6 / 摘要 4 / 设置 | 每个入口是干什么的、该点哪个 |
| 6 | 想加一个"要跟进的家庭"→ 点「主体」→ 表单要填 **主体类型 `member_family`** 和 **唯一标识 `member-001`** | **表设计的 key 语义** |
| 7 | 想加一个"待跟进"→ 点「待办」→ 一次填 **6 个字段**，负责人要填 **用户 ID 并用逗号分隔** | 优先级、上级待办层级、用户 ID |
| 8 | 想让状态贴合自己的业务 → 点「设置」→ 同一屏里塞着 3 段：**服务名称/描述/指令 + 档案字段（要填 key）+ 待办状态（要填 key + 分类）** | 字段 key、状态 key、状态分类 |
| 9 | 想配"状态怎么流转"→ 该能力只有接口没有界面入口，用户永远碰不到 | — |

### 1.3 五个根因

**根因一：重构期的中间层被直接摆到了产品表面上。**

`服务空间V1-1数据契约.md` §2.4 定义的是「自然语言指令 →（中间层）空间蓝图 → 正式空间配置」，并明确写了"蓝图是自然语言指令与正式空间配置之间的**中间层**，**不允许模型直接修改业务表**"。这是一个**为工程安全设计的护栏**，契约本身没有问题。

问题出在实现：护栏被当成了功能。`ServiceHub.vue:9-67` 的「确认服务空间蓝图」对话框让用户在**创建服务的必经路径上**阅读并确认 `proposed_space_type` / `subject_policy` / `profile_schema` / `summary_schema` 四样东西。紧接着 `档案` / `摘要` / `主体` 三个由蓝图派生的对象，又成了服务头的常驻入口（F2）。

**这四个概念——蓝图、空间形态、档案、摘要——在 `服务模块重构PRD.md` 里一个都没有。** PRD D18/D21 设计的目标形态是干净的"两块布局 + 产物 / 待办两个计数入口"。所以这不是"PRD 没设计好"，而是**实现阶段多加了一层，且没为它做界面收口**。

**根因二：把数据库的机器键当成了输入字段。**

`subject_type` / `subject_key` / 档案字段 `key` / 状态 `key` / 负责人 `user_id` —— 这 5 处是同一类错误（F5/F6/F7/F8）。`服务模块重构PRD.md` §3.5.3 的**反面清单**明确写了界面上不得出现技术标识。让幼儿园园长输入 `member_family` 和 `member-001`，等于要求他先理解表设计与唯一键。

**根因三：入口平铺，丢掉了分层。**

PRD D18/D21 定的是「产物 + 待办」两个常驻带计数入口，服务概览 / 服务对象 / 运行记录 / 服务设置收进 `⋯ → 更多`，判据是"天天要点 vs 偶尔要用"（**其中"运行记录"在 v1.10 被整体删除**，见 §6）。实现成了 **7 个同权重 pill 并排**（F2）——"天天要用"和"配一次就忘"混在一起，用户每次都要在 7 个里找。

**根因四：一个组件一条路由承担两个页面，导航状态被压进 7 个 query 参数。**

`view` 状态（F1）+ 7 个 query 参数（F12）拼装出一套**没有路由语义的导航**：URL 里会出现 `action=archive` 这种**携带写副作用的参数**（F13），`panel` 又不进 URL 所以刷新即丢（F14），浏览器前进/后退与用户预期不符。代价是 F15——换一个服务要人工重置 16 个 ref——和 F16 的组合爆炸。

**根因五：原型阶段的数据留在了生产代码里。**

`serviceHubState.ts` 三处种子数据（F17）是原型期的产物。它同时掩盖了一个真问题：**空态没有被设计过**（因为总有假数据填充）。

## 2. 目标与边界

### 2.1 一句话

**把"建一个服务"从 3 屏 9 个概念，压回"填 4 件事、一屏完成、建完就在对话里干活"。**

### 2.2 目标（可量化）

| # | 指标 | 现状 | 目标 |
| --- | --- | --- | --- |
| G1 | 服务头可点击入口数 | **9**（7 pill + `＋` + `⋯`） | **3**（`产物 N`、`待办 N`、`⋯`；`＋` 合并进 `⋯` 之外的固定位，见 §4.3） |
| G2 | 右侧面板承载的内容种类 | **8** | **3**（产物列表 / 产物预览 / 待办列表） |
| G3 | 创建到开始工作要跨过的界面 | **3** 屏（表单 → 蓝图确认弹窗 → 空间） | **2** 屏（表单 → 空间） |
| G4 | 创建服务需理解的系统概念数 | **9** | **4**（服务名称 / 指令 / 专家 / 知识库） |
| G5 | 需用户手填的机器键 | **4** 处 | **0** 处 |
| G6 | 可深链的独立页面 | **1**（全靠 7 个 query 参数） | **6** |
| G7 | 单组件最大行数 | **3876**（`ServiceHub.vue`） | **≤ 900**（拆为 5 个） |
| G8 | 生产代码里的硬编码种子数据 | **3** 处 | **0** |

### 2.3 边界（本期不做）

1. **不动表结构。** `services` / `service_members` / `service_expert_bindings` / `service_artifacts` / `service_subject_profiles` / `service_facts` 等一律不改。蓝图相关的表（`service_space_blueprints` / `service_space_profiles` / `service_space_summaries`）保留，只把它们的**界面出口**撤掉。
2. **不删能力，只改呈现层级。** 档案 / 摘要 / 主体 / 待办状态机 / 协作（负责人·评论·历史）**都保留**，只是从"常驻入口"降为"二级入口"。唯一真正删掉的是**蓝图确认这一步必经流程**。
3. **不动整理模块（Organize）的产出与带入协议。** 「资料」（整理结果带入服务）的数据链路不动，只改它在服务空间里的呈现位置（§3.4）。
4. **不做服务级 ACL 的完整实现。** F20 是真问题，但属于权限模型重做，本文只提"写操作至少校验服务内 owner/admin 或创建人"这一个最小改动项（§7.3），标记为 P2。
5. **不引入新概念。** 本方案的净效果是概念数减少，不新增任何面向用户的词。

## 3. 总体设计（六个支柱）

### 支柱 1：蓝图从界面退场，改为"静默生成 + 事后可调"

**动作：**

1. **删掉创建服务后的「确认服务空间蓝图」强制弹窗**（`ServiceHub.vue:9-67` 整块删除，连带 `blueprintConfirmVisible` / `pendingBlueprint` / `confirmPendingBlueprint` / `cancelPendingBlueprint`）。
2. 指令 → 蓝图的生成**改为静默**：跑完只写 `service_space_blueprints` 的 `draft` 记录，**界面不出现"蓝图"二字**。
3. 蓝图对用户的价值改为**一句自然语言**，在服务空间概览顶部呈现：
   > "按你说的，我把这个服务的重点放在**进展、风险、下一步动作**上。"
   —— 用 `summary_schema` 的 `label` 列表拼句子，不展示 `key` / `type` / `refresh_policy` 这类字段（`ServiceHub.vue:607-616` 现在展示的正是这些）。
4. **`space_type` 三值不进界面。** 三个值对应的是用户能理解的问法：

   | `space_type` | 界面上问法 | 选项文案 |
   | --- | --- | --- |
   | `customer_service` | 这个服务主要围着谁转？ | 家长与学员 |
   | `operations` | 同上 | 园所日常运营 |
   | `research` | 同上 | 教研与备课 |

   放进创建表单时**只给这一组选项**（默认"家长与学员"），不出现枚举名。若从模板进入，则由模板预置、表单不再问。
5. **蓝图确认能力保留在后端，界面不设入口**（v1.10 修订）：`POST /:service_id/blueprint/confirm` 与 `preview` 保留（护栏不能删，见下），但**不给用户一个"重新生成服务结构"的按钮**——原先设想放在 服务设置 › 高级，该分区已整体删除（§6）。改结构的实际路径改为**改工作指令 → 重点记录 面板的「↻ 按新指令重新推荐」**（v1.5 链路，见支柱 2 §4），由 AI 重新派生重点记录与待办状态；概览栏目随摘要自动更新。这比让老师理解"蓝图"更贴近她的心智。

> **为什么不干脆删掉蓝图。** 它是 `服务空间V1-1数据契约.md` 为"模型不许直写业务表"立的护栏，且已有 `service_space_blueprints` / `template_applications` 两张表和审计字段在跑。删掉等于回退契约。本支柱只做一件事：**把护栏收回墙里，不让用户撞上它。**

### 支柱 2：档案 + 摘要 + 主体 → 收敛为「服务概览」与「服务对象」

**动作：**

1. **「档案」与「摘要」两个入口合并成一个「服务概览」**：
   - 上半：一段 AI 生成的**自然语言进展摘要**（原 `summary`，`ServiceHub.vue:606-617`），刷新按钮保留。
   - 下半：**档案字段的就地展示与编辑**（原 `profile`，`:563-571`）。字段由 `profile_schema` 驱动，**用户看到的是"学员等级"而不是"member_level"**。
   - 结论：两个入口合一，且**不再常驻服务头**，进 `⋯ → 更多`。
2. **「服务主体」改名「服务对象」**，从常驻入口降为 `⋯ → 更多`。
   - 用户只填**名称**（如"果果家"）。
   - `subject_type` 默认写 `custom`；`subject_key` 由后端生成（`subj_` + 8 位随机，或名称 slug 冲突时回退随机）。
   - `parent_subject_id`（层级）不进创建表单，需要时在对象详情里"归到某个对象下"。
3. **档案字段的配置也一并简化**（原在「设置」面板里，`ServiceHub.vue:480-497`）：
   - 只填**字段名称**（如"学员等级"），key 由后端按名称生成。
   - ~~「必填」勾选保留~~ **（v1.3 修订：「必填」直接删掉）**——核实 `ServiceSpaceProfileField.Required`（`internal/types/service_space_blueprint.go:68`）在全仓**零消费**：事实抽取（`extractProfileProposalItems`，`service_space.go:1486`）、档案物化（`materializeProfileValues`）、校验逻辑都不读它，被消费的只有 `SubjectPolicy.Required`（另一个概念）。界面上这个开关是纯装饰控件，保留它等于教用户一个没有效果的设置。
   - **字段名称不是普通文案，它直接决定 AI 抽取命中率**：抽取按「`Label` + `Key` + `Aliases`」在对话文本里做字符串匹配（`extractProfileFieldValue`，`service_space.go:1512`）。写「到访次数」匹配不到家长说的「今天来了 3 次」。因此：
     - 配置界面提供**场景化推荐字段**（招生咨询：孩子月龄 / 家长关注点 / 最近到访 / 意向班型…），措辞按家长说话的习惯预置，点选即加，不强迫用户从空白起名；

     - 已选字段用**可删除的标签**展示（点击改名），不再用「名称 + 必填 + 删除」三件套表格；
     - 右侧给一张**服务概览实时预览卡**，配完立刻看到效果。
   - 移出服务头浮层，进服务设置（**界面用词 v1.6：分区名叫「重点记录」，整个界面不出现"字段"二字**——"字段"是数据库词汇，不在园所老师的日常词汇里。用「重点记录」还有一个回路好处：这个词就是用户在工作指令里自己的说法（"重点记录家长顾虑与到访意向"），设置项与指令同词，用户一眼能对上）。（原型 §设置场景 v1.3~v1.6 已按此重做）
4. **「重点记录」由工作指令派生（v1.5，2026-10-05 拍板）**：建服务时在**工作指令**里写了「重点记录 X、Y」，X、Y 直接解析为该服务的字段，进入这个分区（带「指令」角标，可删可改名），并排在预览最前。

   - **生成规则（先规则后 LLM）**：P1 用规则抽「记录 / 重点记录 / 关注 / 跟进 + 名词短语」模式，切分为候选字段（`Label` = 指令原词，`ExtractionHint` = 指令原句片段，`Aliases` 含指令措辞），排在既有默认字段（当前状态 / 重点关注 / 下一步动作）之前；P2 可用 LLM 结构化抽取替代规则、规则兜底。
