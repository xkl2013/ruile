# 三个重点整理 · 精细化设计（v1.0）

> **范围**：④ 到访谈单复盘（`visit_review`）· ⑥ 顾虑与异议台账（`objection_ledger`）· ⑩ 成交与流失复盘（`win_loss_review`）
> **版本**：v1.0 ｜ **日期**：2026-10-08
> **上游**：《招生顾问必用10个整理》v2.1（§3 组 B ④ / 组 A ⑥ / 组 D ⑩）
> **本文性质**：只做设计，不改库。库侧改动清单集中在 §6，含改动前/后对照与验收标准。

## 0. 为什么先精细化这三个

这不是随机挑的三个。它们是同一条业务链上的三个环节，且互相喂数据：

| # | 整理 | 回答的问题 | 视角 | 节奏 |
|---|---|---|---|---|
| ④ | 到访谈单复盘 | **这一单**谈到哪了、卡在哪一步 | 单次（一单一记） | `daily` 08:00 |
| ⑥ | 顾虑与异议台账 | **所有单**里反复出现的那几类顾虑，我们到底有没有解法 | 共性（跨单归并） | `weekly` 周一 09:00 |
| ⑩ | 成交与流失复盘 | 结果层面为什么成、为什么丢，经验能不能复用 | 结果（成 / 败） | `daily` 08:00 |

三者的咬合关系：

```
   ④ 到访谈单复盘 ────「异议与顾虑」小节 ────┐
        （每次到访一条）                       │
                                              ▼
                                    ⑥ 顾虑与异议台账
                                   （按类型归并 + 判定应对是否有效）
                                              │
                                              │「有效应对 / 待补方案」
                                              ▼
   ⑩ 成交与流失复盘 ◀─── 用台账校验「原因判断」是否成立
        （结果回放）
```

- **④ 是原料**：它逐单产出的"异议与顾虑"，正是 ⑥ 要归并的对象；
- **⑥ 是沉淀**：把散在几十条记录里的同类顾虑一次性归并，形成全园可复用的应对话术——这是最容易变成「机构资产」的一份；
- **⑩ 是校验**：若成交/流失的原因与 ⑥ 的台账吻合，说明书话术真的在起作用；不吻合，就是要补进台账的新方案。

**都踩在已有链路上**：三者都只依赖已有的记忆类型（`note` / `record` / `audio`）与已有整理链路，**不需要新建表、不需要新接口**。这是"能落地"的前提，也是先做它们的理由。

## 1. 三者共同的基座（先把口径钉死）

### 1.1 数据链路

```
记忆 organize_memories
   │  （唯一进 LLM 的通道）
   ▼
整理任务 organize_jobs ──► 逐批 Map（batch） ──► 合并 Reduce（merging）
   │
   ▼
成果 organize_outputs（Markdown + 6 个系统字段 + citations）
```

| 环节 | 实现位置 |
|---|---|
| 记忆 → 提示词（唯一通道） | `buildOrganizeJobPrompt`，`internal/application/service/organize_workbench.go:1214` |
| 单条任务生成 | `generateOrganizeJobContent`，`organize_workbench.go:807-821` |
| 批量 Map（>1 批才走） | `executeBatchOrganizeJob`，`organize_batch.go:15` |
| 合并 Reduce | `mergeOrganizeBatchContent`，`organize_batch.go:187` |
| 合并兜底（模型不可用） | `fallbackOrganizeBatchMerge`，`organize_batch.go:230` |
| 覆盖率统计 | `organizeJobCoverage`，`organize_batch.go:169` |
| 产出落库 | `saveOrganizeJobOutput`，`organize_workbench.go:845-906` |

**预算墙**（超限会静默截断，无提示）：

| 限制 | 值 | 出处 |
|---|---|---|
| 单任务记忆条数 | ≤ 50 | `organize_workbench.go:31` |
| 单任务提示词 | ≤ 18000 字符 | `organize_workbench.go:32` |
| 批量拆批预算 | 14000 字符 / 批 | `organize_selection.go:19` |
| 按要求整理候选上限 | 1000 条 | `organize_selection.go:18` |

> 含义：**一次到访一条记忆**的日常节奏下，三者都远不会撞上限；只有"补历史数据"（一次几十条）才会触发拆批与合并，此时 §2~§4 的"多条语义"就生效。

### 1.2 触发方式两条腿

| 方式 | 入口 | 时间范围由谁定 | 典型用法 |
|---|---|---|---|
| **按要求整理**（即时） | 工作台输入一句话 | 从**输入的文本**里解析时间词 | 谈完 3 分钟就做 |
| **周期配置**（自动） | `organize_configs.schedule` | 从**配置里那条指令文本**解析，不是另设规则 | 每天/每周固定归账 |

> ⚠️ 关键认知：周期任务**不是**"自动扫全部记忆"。它到点后跑的仍是**配置里存的那条指令**（`organize_workbench.go:1214-1221` 把 `template_instruction` 原样送进提示词）。
> 所以——**指令里的时间词，就是周期任务的范围定义**。

### 1.3 时间词规则（本文最重要的一条口径）

调度时刻是**写死在代码里**的，不可自定义（`nextOrganizeRun`，`organize_workbench.go:1175-1204`，时区 Asia/Shanghai）：

| schedule | 执行时刻 |
|---|---|
| `daily` | 每天 **08:00** |
| `weekly` | 每周**一** **09:00** |
| `monthly` | 每月 **1 日 09:00** |

而时间词解析出的是**整段日历窗口，且包含未来**（`parseOrganizeMemoryQueryPlan`，`organize_selection.go:48-89`）：

| 词 | 解析出的窗口 |
|---|---|
| 今日 / 今天 | 当天 00:00 → 次日 00:00 |
| 昨日 / 昨天 | 昨天 00:00 → 今天 00:00 |
| 本周 / 这周 | 本周一 00:00 → 下周一 00:00 |
| 上周 | 上周一 00:00 → 本周一 00:00 |
| 本月 / 这个月 | 当月 1 日 00:00 → 次月 1 日 00:00 |
| 上月 | 上月 1 日 00:00 → 当月 1 日 00:00 |
| 2026年10月1日至10月7日 | 按字面，含首尾 |

**两者相乘的后果**：周期任务若写"今日/本周/本月"，执行那一刻窗口才刚开头——

- `daily` 08:00 写"今日" → 只覆盖当天 00:00–08:00，且当天大多数到访还没发生，**命中近乎为空**；
- `weekly` 周一 09:00 写"本周" → 只覆盖周一 00:00–09:00，**必然空转**；
- `monthly` 1 日 09:00 写"本月" → 同理空转。

⇒ **规则：周期任务的指令必须写"上一个完整周期"。**

| schedule | 指令里应当写 | 语义 |
|---|---|---|
| `daily` | **昨日** | 昨天 00:00 → 今天 00:00 |
| `weekly` | **上周** | 上周一 00:00 → 本周一 00:00 |
| `monthly` | **上月** | 上月 1 日 → 当月 1 日 |

这恰好等于"距上次执行以来的增量"——**不重复、不遗漏**。

> 本文三个整理一律按此口径：④ `daily`→昨日、⑥ `weekly`→上周、⑩ `daily`→昨日。

### 1.4 篇幅与来源标记口径（三个整理统一）

骨架提示词的隐藏约束（`organizeMarkdownTemplatePrompt`，`organize_markdown_template.go:91-101`）已经规定死的部分：

- 必须输出完整中文 Markdown；不得用代码围栏包裹整篇；
- **保留预设中的标题层级、章节名称、章节顺序**，不得新增无关章节；
- `{{...}}` 占位符必须替换，最终结果不得残留占位符；
- **只依据原始记忆生成**，没有依据的栏目写"记录中未提供"，不得猜测、补造；
- 关键事实与结论用 `[M1]`、`[M2]` 来源标记；待办用 `- [ ]` 清单；
- 表格占位符必须展开成完整 Markdown 行，不能压缩成一句话；
- 某章节没内容也**必须保留章节**并标注信息缺失。

在此基础上，三个整理统一追加的**篇幅口径**（写在各自 `default_instruction` 里）：

- 每条要点 **≤ 40 字**；表格单元格 **≤ 30 字**；
- 来源标记**只用在风险判断与关键事实处**，普通跟进动作不逐条标注（控制 `[Mn]` 密度）。

> 为什么必须限字数：单元格超 30 字会在页面上变成"文字堆"，行列对不齐——这是实测发现的主要"不美观"来源。

### 1.5 骨架机制（改骨架前必须知道的三件事）

| 机制 | 说明 | 出处 |
|---|---|---|
| **缺章节自动补回** | 生成结果里少了预设章节，系统按 `# 章节名` 自动补一段"记录中未提供" | `normalizeOrganizeGeneratedMarkdown`，`organize_markdown_template.go:104-148` |
| **占位符残留会被替换** | 未替换的 `{{xxx}}` 统一替换为"记录中未提供" | 同上 `:116` |
| **标题由系统生成** | 产出标题 = `输出标签 · YYYY-MM-DD`，**不需要骨架里写 `# {{title}}`** | `organize_workbench.go:845-848` |

⇒ 所以：**骨架里不要写 `# {{title}}`**（会与页面头部标题重复），也**不要写"依据 / 标签"块**（引用已在页面顶部以 chip 展示，正文再写一遍是重复）。这两条是已完成的瘦身成果，本文三个骨架均已遵守。

## 2. ④ 到访谈单复盘 · `visit_review`

### 2.1 一页速览

| 项 | 值 |
|---|---|
| key | `visit_review` |
| 名称 | **到访谈单复盘**（现库中为"谈单复盘"，待改） |
| 场景 | **招生增长**（现库已在招生增长，无需改） |
| 产出标签 | 谈单要点 |
| 图标 | `user-circle` |
| 排序 | 44（组 B 首位） |
| 节奏 | `daily` 08:00，指令写**昨日** |
| 产出字段 | 决策人 / 意向课程 / 异议类型 / 卡点 |

### 2.2 解决什么问题

**现场痛点**：谈完一单，顾问凭记忆复盘。到第二次见面，上次说了什么、家长当时顾虑什么、答应过什么，全靠回忆——同一类价格异议被反复卡，谈单进度无法交接给同事。

**这个整理干什么**：把"这单谈到哪了"变成一份**可交接、可复用**的结构化记录。谈完随手记一条（文字或录音），第二天早上自动成文；也可以谈完当场「按要求整理」。

**谁在什么时刻用**：

| 角色 | 时刻 | 用法 |
|---|---|---|
| 招生顾问 | 谈完 3 分钟 / 次日早上 | 生成记录，供自己与同事接力 |
| 招生主管 | 晨会 | 看昨日所有到访的卡点分布，决定今天陪访谁 |
| 接手同事 | 家长二次到访前 | 30 秒读完上一单，避免"从零开始" |

### 2.3 输入

| 项 | 说明 |
|---|---|
| 记忆类型 | `note`（文字随手记）、`audio`（面谈录音）、`record`（转写记录）均可 |
| 时间窗 | `daily` 配置下为**昨日** 00:00–24:00 |
| 条数预期 | 日常 1–5 条；补历史时可能几十条 |
| 多条语义 | **一条指令、一份产出**。若昨日涉及多个家庭，产出内**按家庭/孩子分组**（见 2.4），不是每个家庭各出一份 |
| 撞上限时 | > 50 条 / > 18000 字符会拆批：逐批 Map → Reduce 合并，产出仍是**一份**，并带覆盖率 |

### 2.4 产出骨架与逐节规格

**骨架（库中现行 v4，结构保留）**：

```markdown
> {{summary}}

## 客户与需求

{{section_1}}

## 我方呈现

{{section_2}}

## 异议与顾虑

| 异议类型 | 家长原话 | 已用应对与状态 |
|---|---|---|
{{section_3}}

## 当前卡点

{{section_4}}

## 下一步动作

- [ ] {{section_5}}
```

**逐节规格**（这是"精细化"的核心——LLM 与研发都按这个写）：

| 节 | 写什么 | 句式 / 限制 | 无数据时 |
|---|---|---|---|
| `> {{summary}}` | 一句话概括本批到访（列表预览取这一行） | ≤ 40 字，含家庭数与共同卡点 | 系统替换为"记录中未提供" |
| 客户与需求 | 孩子昵称/年龄、家长身份、**决策人是谁**、明确诉求（入园时间、班型、预算区间） | 要点式，3–6 条，每条 ≤ 40 字 | 保留章节，标注缺失 |
| 我方呈现 | 已介绍过哪些课程/班型、报价与优惠、承诺过什么 | 要点式，2–5 条 | 同上 |
| 异议与顾虑 | 表格：`异议类型 \| 家长原话 \| 已用应对与状态` | **表格 3 列**，单元格 ≤ 30 字；"家长原话"要引原话而非转述；状态写明"已化解 / 未化解 / 待跟进" | 表格留一行"记录中未提供" |
| 当前卡点 | 现在卡在哪一步（价格？决策人未定？担心适应？） | 1–3 条，每条一句话点明"卡在谁/什么上" | 同上 |
| 下一步动作 | 带**动作 + 时间**的可勾选待办 | `- [ ]` 清单，每条 ≤ 40 字并含时间点 | 同上 |

**多条语义**（补历史或一天多单时生效）：

> 涉及多个家庭时，在"客户与需求"里按家庭分组（如 `**豆豆家**：…`），异议表格逐行对应不同家庭；不要去重、不要把两个家庭的诉求混写。

### 2.5 结构化字段（读侧筛选可用）

```
决策人 / 意向课程 / 异议类型 / 卡点
```

| 说明 | 内容 |
|---|---|
| 用途 | 支持 `GET /organize/outputs?field.异议类型=价格` 这类**等值筛选** |
| 现状 | **模板里的 `spec.fields` 已配、读侧筛选已通；但产出侧未回填**——产出只写 6 个系统字段（见 §5） |
| 口径 | 字段值是**文本**，只做等值匹配，不做数值/次数统计 |

### 2.6 指令（目标版，待落库）

```
整理昨日到访面谈记录。若涉及多个家庭，按「孩子/家长」分组，每组依次写：客户与
孩子的需求点（含决策人是谁）、我方已呈现的课程与政策、家长提出的顾虑与异议、
当前卡在哪一步、下一步动作与时间。没有记录的内容写"记录中未提供"。

输出要简洁：每条要点不超过 40 字，表格单元格不超过 30 字；来源标记只用在风险
判断和关键事实处，普通跟进动作不必逐条标注。
```

**相对现库的改动**：`本次` → **`昨日`**；新增"若涉及多个家庭，按孩子/家长分组"（解决一天多单混写）。

### 2.7 边界与防编造

- ❌ 不**推断**家长未表达的需求（如未提预算就不写价格敏感）；
- ❌ 不把"我方的期望"写成"家长的意愿"；
- ❌ 不合并两个家庭的异议为一条；
- ✅ 没记录的栏目一律"记录中未提供"，不猜、不补；
- ✅ 卡点必须能从记录里指出来源 `[Mn]`。

### 2.8 落地参数

| 项 | 值 |
|---|---|
| 修改接口 | `PUT /api/v1/system/admin/organize/templates/visit_review` → `POST /visit_review/publish` |
| 必带字段 | 全量覆盖：`name` / `scene` / `output_label` / `icon` / `description` / `default_instruction` / `markdown_template` / `spec` / `sort_order` |
| 周期配置 | `schedule=daily`、指令含"昨日"、指定 `user_id`、可选 `target_service_id` |

### 2.9 验收标准

- [ ] 名称显示为「到访谈单复盘」，分组在「招生增长」
- [ ] 指令含"昨日"，不含"本次"
- [ ] 单条记忆跑通：产出含 5 个章节，无残留 `{{}}` 占位符
- [ ] 多家庭场景：产出按家庭分组，未混写
- [ ] 无记录时各章节显示"记录中未提供"，而非空白或编造
- [ ] `[Mn]` 标记只出现在卡点/关键事实上，密度可读

## 3. ⑥ 顾虑与异议台账 · `objection_ledger`

### 3.1 一页速览

| 项 | 值 |
|---|---|
| key | `objection_ledger` |
| 名称 | **顾虑与异议台账**（现库中为"异议台账"，待改） |
| 场景 | **招生增长**（现库在「团队运营·领导力」，**待改**） |
| 产出标签 | 应对话术 |
| 图标 | `chat-bubble` |
| 排序 | 54 |
| 节奏 | `weekly` 周一 09:00，指令写**上周**（现库为 `monthly` + "本月"，待改） |
| 产出字段 | 异议类型 / 已用应对 / 是否有效 / 待补方案 |

### 3.2 解决什么问题

**现场痛点**：同一个"价格贵"的顾虑，A 顾问化解得好、B 顾问每次都卡；这些解法散落在几十条个人记录里，新人只能自己踩坑。

**这个整理干什么**：把一周内所有沟通记录里的顾虑**按类型归并**，汇总每类已用过的应对并判定有效性，输出一份**全园共用的话术台账**——最容易沉淀成机构资产的一份。

**谁在什么时刻用**：

| 角色 | 时刻 | 用法 |
|---|---|---|
| 招生主管 | 周一上午 | 看上周新出现的异议、哪些还没解法 |
| 全体顾问 | 遇到难缠顾虑 | 照台账找已验证的应对话术 |
| 新人 | 入职带教 | 照台账演练，不依赖个别老顾问 |

### 3.3 输入

| 项 | 说明 |
|---|---|
| 记忆类型 | 面谈录音 / 沟通记录 / 文字随手记 |
| 时间窗 | `weekly` 配置下为**上周**（上周一 00:00 → 本周一 00:00） |
| 条数预期 | 一周通常 10–40 条，**大概率触发拆批** → 走 Map/Reduce 合并 |
| 多条语义 | 天然是"归并"型：多条记忆 → **一份**台账；合并时按异议类型聚合，去重、保留出处 |

{{section_2}}

- [ ] {{section_3}}

## 待确认

**逐节规格**：

| 节 | 写什么 | 句式 / 限制 | 无数据时 |
|---|---|---|---|
| `> {{summary}}` | 一句话概括本周异议全貌（共几类、最突出的是哪类） | ≤ 40 字 | 系统替换 |
| 异议台账 | 表格：`异议类型 \| 典型原话 \| 已用应对与效果`。类型建议落在固定 6 类：**价格 / 效果 / 时间 / 距离 / 师资 / 其他** | **表格 3 列**，单元格 ≤ 30 字；"典型原话"引原话 | 留一行标注缺失 |
| 有效应对 | 从台账里挑出**已验证有效**的做法，可直接照用 | 要点式，每条 = "异议 → 话术 → 为什么有效"，≤ 40 字 | 同上 |
| 待补方案 | 目前**还没有好办法**的异议，可勾选待办 | `- [ ]` 清单，每条 ≤ 40 字 | 同上 |
| 待确认 | 归并中出现的**冲突或存疑**（如同一异议两种说法矛盾、来源不明） | 逐条列出，注明分歧点 | 无冲突时写"本周无待确认事项" |

**归并规则**（写在指令里，是这份质量的关键）：

> 同一类异议**只出一行**；同一类型下若多种原话，取最有代表性的一条；应对若不止一种，按"有效的在前"排列；**保留原文出处**（`[Mn]`）；同一异议涉及多个家庭时在行内注明大致范围。

### 3.5 结构化字段

```
异议类型 / 已用应对 / 是否有效 / 待补方案
```

> ⚠️ `fields` 存的是**文本**，`?field.X=Y` 只做**等值匹配**——所以"出现了多少次"只能定性描述（如"多单出现"），**不能靠它做次数统计**。产出侧回填同 §5 待接线。

### 3.6 指令（目标版，待落库）

```
整理上周含顾虑与异议的沟通记录，按异议类型归并（价格、效果、时间、距离、师资
等），汇总每类已用过的应对并判断是否有效，最后列出还没有好办法的异议。同类异议
只出一行，保留原文出处，涉及多个家庭时注明大致范围。

输出要简洁：每条要点不超过 40 字，表格单元格不超过 30 字；来源标记只用在风险
判断和关键事实处，普通跟进动作不必逐条标注。
```

**相对现库的改动**：`本月` → **`上周`**；新增"同类异议只出一行 / 涉及多家庭注明范围"（归并质量）。

### 3.7 边界与防编造

- ❌ 不**发明**没用过的应对（这是最容易幻觉的一项——"看起来合理的建议"不等于"用过的做法"）；
- ❌ 不把"我们的建议"写成"已验证有效"；
- ❌ 不按次数编排名（系统拿不到精确次数，只能说"多单出现"）；
- ✅ 每条应对必须能指回具体记忆 `[Mn]`；
- ✅ 判"有效"必须有结果侧证据（家长态度转变 / 推进到下一步），不能凭感觉。

## 4. ⑩ 成交与流失复盘 · `win_loss_review`

### 4.1 一页速览

| 项 | 值 |
|---|---|
| key | `win_loss_review` |
| 名称 | **成交与流失复盘**（现库中为"成交复盘"，待改） |
| 场景 | **招生增长**（现库在「团队运营·领导力」，**待改**） |
| 产出标签 | 经验沉淀 |
| 图标 | `task-checked` |
| 排序 | 56 |
| 节奏 | `daily` 08:00，指令写**昨日**（现库为 `monthly` + "本月"，待改） |
| 产出字段 | 结果 / 关键节点 / 主要原因 / 可复用判断 |

### 4.2 解决什么问题

**现场痛点**：个人经验随人流动。某个顾问"一眼看出这家长要跑"的直觉，从没被写成可教的东西；流失的客户没人事后回看，同样的坑反复踩。

**这个整理干什么**：对**昨日**成交或流失的案例逐案回放关键节点，把原因判断与可复用经验写下来，变成主管带教的现成材料。

**谁在什么时刻用**：

| 角色 | 时刻 | 用法 |
|---|---|---|
| 招生顾问 | 每天早上 | 一分钟回放昨天，替代"凭感觉总结" |
| 招生主管 | 周会 / 带教 | 用积累的"可复用判断"做培训素材 |
| 全园 | 季度复盘 | 看成交与流失原因的分布变化 |

### 4.3 输入

| 项 | 说明 |
|---|---|
| 记忆类型 | 面谈记录 / 沟通录音 / 结果类随手记 |
| 时间窗 | `daily` 配置下为**昨日** |
| 条数预期 | **多数日子为 0–2 条**（见下方备注） |
| 多条语义 | 多个案例 → 一份产出，表格多行；**无结果的记录不得当案例** |

> **待复核（重要）**：幼儿园的成交/流失不是每日发生。按"每天 08:00 跑昨日"，**多数日子会空转**（产出全是"记录中未提供"）。
> 两种口径供选择：
> - **A（现状）**：保持 `daily`——胜在"不留隔夜、随手记就成文"，空转日直接忽略；
> - **B（建议）**：改 `weekly` 周一 09:00 + 指令写"上周"——胜在不空转，代价是复盘滞后最多 7 天。
>
> 本文按你给的口径写 `daily`，此项**待你拍板**，不改库。

### 4.4 产出骨架与逐节规格

**骨架（库中现行 v4，结构保留）**：

```markdown
> {{summary}}

## 关键节点回放

| 案例 | 结果 | 关键节点与原因 |
|---|---|---|
{{section_1}}

## 可复用判断

{{section_2}}

## 需改进动作

- [ ] {{section_3}}
```

**逐节规格**：

| 节 | 写什么 | 句式 / 限制 | 无数据时 |
|---|---|---|---|
| `> {{summary}}` | 一句话概括昨日成交/流失概况 | ≤ 40 字 | 系统替换 |
| 关键节点回放 | 表格：`案例 \| 结果 \| 关键节点与原因`。"结果"限**成交 / 流失**两值 | **表格 3 列**，单元格 ≤ 30 字；节点按时间顺序，原因必须带来源 `[Mn]` | 留一行标注缺失 |
| 可复用判断 | 从本批案例提炼的**可教**的经验（"什么样的信号说明…"） | 要点式，每条 = "信号 → 判断 → 动作"，≤ 40 字 | 同上 |
| 需改进动作 | 本批暴露的、需要团队改的动作 | `- [ ]` 清单，每条 ≤ 40 字 | 同上 |

**成对与脱敏**：案例以"家庭/孩子"指代即可，不写全名；若涉敏感信息（如家庭纠纷），在"可复用判断"里只留判断、不留细节。

### 4.5 结构化字段

```
结果 / 关键节点 / 主要原因 / 可复用判断
```

> `结果` 建议只用"成交 / 流失"两值，便于将来按结果筛选；同样受 §5 待接线影响。

### 4.6 指令（目标版，待落库）

```

结果的记录不要当作案例。

输出要简洁：每条要点不超过 40 字，表格单元格不超过 30 字；来源标记只用在风险
判断和关键事实处，普通跟进动作不必逐条标注。
```

**相对现库的改动**：`本月` → **`昨日`**；新增"没有明确结果的记录不要当作案例"（防止把跟进中当成已成交）。

### 4.7 边界与防编造

- ❌ **绝不**把"跟进中"当成"成交"或"流失"；
