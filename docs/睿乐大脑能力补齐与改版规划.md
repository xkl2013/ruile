# 睿乐大脑能力补齐与改版规划

> v1.0 · 2026-10-10 · 基于当前仓库真实实现的能力盘点
> 盘点范围：`internal/`（1335 个 Go 文件）、`frontend/src/views/`（14 个模块）、`admin/src/views/`、`migrations/versioned/`（截至 000119）、`mobile/`
> 配套文档：`docs/睿乐大脑商业化方案.md`、`docs/Agent模块设计方案.md`、`docs/个人版与企业版实现设计.md`、`docs/整理模块未完成需求开发清单与验收.md`

## 0. 一句话结论

**睿乐的能力已经"够深"，缺的是三层上的"最后一公里"。**

| 层 | 现状 | 缺口性质 |
|---|---|---|
| 能力底座 | 整理 / Agent 基座 / 知识库 / 计费 / 组织协作 / 发布渠道**全部有代码** | 基本不缺 |
| 收钱链路 | 套餐、价格、商品、订单后台全通，**但没有在线支付** | 只差最后一环 |
| 用户入口 | **普通用户点"智能体"被重定向到后台管理系统** | 门面缺失 |
| 高价值场景 | 招生转化、续费预警、投诉预警**没有任何业务数据来源** | 缺数据底座 |

**所以这一轮的动作不是"再加模块"，而是三件事**：① 把收钱链路接通（支付闭环）；② 把用户侧门面做出来（分身 + 岗位）；③ 给高价值场景补数据入口（先做招生线索这一条）。**同时清掉 6 笔工程债**，它们正在让已经做完的功能打折。

5. **平台治理后台成体系**：`/system/admin/` 下已有 public-knowledge-bases、public-contents、courses、creators、organize（模板）、skills、billing、expert-packages、discover categories 九个治理面。

## 2. 能力缺口：还要补齐什么

按"影不影响收钱"排序，分四类。

### A. 商业化闭环 —— 决定"能不能自己收钱"

**现状：收钱链路只有"后台人工开通"，没有"用户自己下单付款"。**

| # | 缺口 | 证据 | 影响 |
|---|---|---|---|
| A1 | **在线支付**（支付宝 / 微信） | `个人版与企业版实现设计.md` §20.3 TODO-P0-02/03/04 | 无法自助购买，每一单要人工开 |
| A2 | **订阅生命周期状态机**（试用/月付/年付/升级/降级/续费/取消/到期/暂停/恢复） | 同 §20.2 PART-01 | 定价分了档却无法自动升降级 |
| A3 | **用户自助购买** | TODO-P0-05 | 转化漏斗断在最后一步 |
| A4 | **订单关闭与迟到回调处理** | TODO-P0-06 | 支付异常无兜底（进 `reconciliation`） |
| A5 | 企业用量报表 / 积分流水 / 存储流水 / 账单导出 | TODO-P1-01~05 | 客户看不见"钱花在哪"，续费谈判缺依据 |
| A6 | 运营告警（到期/余额/额度/回调失败/待核对积压） | TODO-P1-06 | 续费前无人提醒 |
| A7 | 自动续费、退款、发票 | TODO-P2-01~03 | 后期必须，但现在不阻塞 |

**判断：A1–A4 是"定价上架后立刻就需要"的四件，属于商业化关键路径。**

### B. 产品化缺口 —— 决定"能不能卖得动"

| # | 缺口 | 证据（代码位置） | 影响 |
|---|---|---|---|
| B1 | **用户侧没有 Agent 入口** | `frontend/src/router/index.ts:295-307`：`/platform/agents` 的 component 是 `ExternalRedirectView`，`beforeEnter` 直接 `redirectToAdmin({path:'/agents'})` | 普通用户点"智能体"被踢进后台。**分身的门面在用户侧根本不存在** |
| B2 | **系统里没有"岗位"概念** | `migrations/versioned/000043_tenant_rbac.up.sql:30`：`tenant_members.role` 仅 `owner/admin/contributor/viewer`（权限角色） | 分身要"按角色换身份"（顾问/园长/老师）**没有数据支撑** |
| B3 | **没有任何业务数据底座** | `migrations/versioned/` 中不存在 lead / student / enrollment / attendance / tuition 任何一张表（命中 0） | 渠道转化归因、续费与流失预警、投诉预警**全部无源可依**；这是商业化方案里"经营档"的硬前提 |
| B4 | **写回目标悬空** | `/organize/outputs/:id/assign` → `AssignOutputToService`（`router.go:1549`），写回目标是服务空间；而服务空间已拍板摘入口 | 分身的 D2 壁垒（产出成为可执行物）**没有落点** |
| B5 | **专家的货架是空的** | 记忆：预置模板 `expert_ids` 全空，`/organize/experts` 接口通但无内容 | 绑专家才带岗位视角，现在绑不上 |
| B6 | **发现模块只有内容池，没有运营闭环** | `/organize/discover` + admin `public-contents` 已有；无使用量、无推荐位、无定向分发 | 留存手段没用起来 |
| B7 | **开箱即空** | 有 `/onboarding/workspace`（`router/index.ts:110`），但没有"园所开户即得的行业预置包" | 新客户第一眼看到空工作台，交付成本全压在人工 |

**判断：B1 + B2 是分身能否成立的前提；B3 是"经营档"能否卖到 7.98 万的前提；B4/B5 是小改动大收益。**

## 3. 优化改版：已有的功能怎么改

### 改版 1：入口结构 —— 从"四个工具 tab"改成"一个门面"

- **现状**：dock 四 tab（记忆 / 整理 / 发现 / 服务）+ 中央凸起采集键（只做"存记忆"）；`/platform/agents` 跳后台。
- **改法**：分身住进中央凸起键，分身页作为冷启动默认落点；dock 结构不动（改动成本最小）；凸起键升级为"点=对话 / 长按=录"。
- **依据**：`docs/Agent模块设计方案.md`（P0 门面壳 + 接已上线整理）。
- **前置**：B1（用户侧入口）、B2（岗位字段）。

### 改版 2：服务空间 —— 摘入口，不删代码

- **现状**：`internal/application/service/service_space.go` 3911 行 + 测试 942 行；`/services` **69 个接口**（`router.go:1567-1650`）；迁移 8 组（000112~000119）；前端 `views/service/` 9 个文件；移动端多处引用。
- **改法**：后端路由摘挂 + 前端入口摘掉，**表与数据保留**。可逆、成本低。
- **必须先做**：**待办层（`service_reminders`）是否单独存活，直接决定 B4 的写回目标**。建议保留待办这一层，把分身的写回目标从"服务空间"改为"直接建待办"。

### 改版 3：整理模块 —— 三层收敛成"一件事一个入口"

- **现状**：使用者要理解"模板 → 配置 → 任务 → 产出"四层概念（`OrganizeWorkbench.vue` 是最大模块）。
- **改法**：
  1. 模板选择从"列表 + 场景"改为**按角色推荐**（顾问只看到招生类，园长看到经营类）；
  2. 配置（周期任务）从"命名 + 定范围 + 选模板"简化为**预设节奏一键开启**（daily 到访谈单复盘 / weekly 顾虑台账）；
  3. 产出列表默认按"最近 + 未读"排，字段筛选上提到首屏（依赖 C4）。

### 改版 4：记忆采集 —— 从"存"改成"出活"

- **现状**：采集键只做入库（`/organize/memories/upload`），录完还要再去整理一次。
- **改法**：录完直接进对应整理（谈单 → 复盘、观察 → 记录），录前讲清三步结果、录后给三步进度。
- **前置**：C1（ASR 退化必须先修，否则未配 ASR 的租户全程空转）。

### 改版 5：计费前台口径 —— 从"云资源"改成"能力档位"

- **现状**：`/billing/overview` 给的是积分进度、存储进度——客户听不懂。
- **改法**：前台只露"当前档位 + 本档能做什么 + 本月出了多少活"，存储/积分收进"用量明细"二级页。
- **依据**：`docs/睿乐大脑商业化方案.md` §3.2 口径对照表。

### 改版 6：后台治理 —— 九个治理面收敛入口

- **现状**：`/system/admin/` 下九个治理面（模板、栏目、技能、专家包、计费、课程、创作者、公开内容、公开库）平铺。
- **改法**：按"内容 / 能力 / 商业"三组收拢导航，减少后台使用者的认知负担。
