# 服务模块 PRD

> 本 PRD 面向教培机构一对一 AI 服务交付场景。用户侧一级模块名称为“服务”，默认首页为“服务提醒”。Ruile 不自建 CRM，不承接客户、线索、商机、订单、正式课表等主数据；这些数据未来通过 Skill 连接外部 CRM / 教务系统。Ruile 负责从记忆笔记中整理服务提醒、客户记忆、跟进信息、话术建议和待确认动作。

## 1. 文档信息

| 项目 | 内容 |
|------|------|
| 产品名称 | 服务模块 |
| 目标用户 | 教培机构员工、AI 工程师、机构管理者 |
| 交付方式 | 一对一服务交付，AI 工程师配置后启用 |
| 一级模块 | 服务 |
| 默认首页 | 服务提醒 |
| 核心输入 | 记忆笔记、录音转写、截图整理、文件摘要、会话摘要 |
| 核心输出 | 服务提醒、客户摘要、跟进记录、话术建议、待确认动作 |
| 核心配置对象 | 工作分身描述、AI 能力方案、结构化能力配置、记忆范围、知识库和 Skill |
| 非目标 | 不做 CRM，不做客户主数据，不做正式课表，不做订单和商机漏斗 |

## 2. 背景与问题

教培机构员工每天要处理大量琐事：线索跟进、试听回访、家长沟通、续费提醒、排课协调、投诉处理、课后反馈和日报复盘。传统 CRM 关注对象管理和流程管控，但普通员工实际需要的是“今天该服务谁、为什么提醒、怎么说、下一步做什么”。

Ruile 已有记忆笔记、知识库、Agent 和 Skill 方向能力，适合把用户的碎片化记忆整理成可执行服务提醒，而不是复制一个 CRM。

当前要解决的问题：

- 记忆笔记里有大量客户相关事实，但缺少稳定归类。
- 多 Agent 如果直接暴露给普通用户，使用成本高。
- 每个机构、每个岗位、每个用户需要启用的 Agent 不同。
- 让 AI 工程师逐项理解和勾选 Agent 成本仍然偏高，需要通过“描述工作分身 -> AI 生成能力方案 -> 工程师确认”的方式降低配置成本。
- 仅按用户启用 Agent 不够精细，需要一个“工作分身”承接岗位、记忆范围、工作档案目录、能力边界和执行策略。
- AI 整理出的客户摘要和跟进信息需要和原始记忆笔记建立证据关联。
- 未来需要连接外部 CRM / 教务系统，但当前不能把外部系统数据复制成 Ruile 主数据。

## 3. 产品目标

### 3.1 业务目标

- 让普通用户进入“服务”后，通过“服务提醒”快速知道今天要处理什么。
- 让 AI 工程师可以按用户描述工作分身，由 AI 生成能力方案，工程师确认后启用服务能力。
- 让记忆笔记自动沉淀为可读的工作档案。
- 保留完整证据链，任何摘要、提醒和动作都能回到来源记忆。
- 为未来 Skill 连接外部 CRM / 教务系统预留接口。

### 3.2 用户目标

普通用户只需要完成：

- 录入或上传记忆。
- 查看服务提醒。
- 点击提醒查看依据。
- 生成话术或下一步建议。
- 确认、忽略、稍后处理动作。

AI 工程师需要完成：

- 为用户创建工作分身，并用自然语言描述用户职责、服务对象、边界和风格。
- 审核 AI 生成的能力方案，确认启用哪些服务能力。
- 确认记忆筛选规则、知识库绑定、Skill 边界和输出策略。
- 必要时进入高级配置调整 Agent 工作档案目录和能力参数。
- 复盘误判、漏判和用户确认动作。

## 4. 产品边界

### 4.1 Ruile 做什么

- 从记忆笔记中识别服务对象、事件、风险和待办信号。
- 为用户维护工作分身配置。
- 生成服务提醒列表。
- 整理线索、客户、排课、风险等 Agent 工作档案。
- 基于公司公共知识库生成建议和话术。
- 生成待确认动作草稿。
- 记录动作确认、忽略、失败和执行日志。

### 4.2 Ruile 不做什么

- 不维护 CRM 客户主档案。
- 不维护线索池、商机阶段、销售漏斗。
- 不维护正式订单和课表主数据。
- 不直接把外部 CRM / 教务系统数据复制进 Ruile。
- 不允许 Agent 绕过用户确认直接写外部系统。
- 不向普通用户暴露 Agent 配置台。

### 4.3 知识边界

```text
公司公共知识库 = 课程、价格、案例、SOP、话术、合规规则
原始记忆笔记 = 这个客户实际发生了什么
Agent 工作档案库 = AI 整理后的线索、客户、排课、风险工作档案
服务提醒 = 普通用户看到的待处理入口
```

客户目录里只放客户事实、摘要、跟进和证据索引，不放机构通用课程、价格政策、话术库和服务 SOP。

## 5. 用户与角色

| 角色 | 主要诉求 | 可见能力 |
|------|----------|----------|
| 招生顾问 | 跟进咨询、试听、报名意向 | 服务提醒、话术、排课建议 |
| 班主任 / 客服 | 家校沟通、续费、风险处理 | 服务提醒、客户摘要、跟进记录、风险提醒 |
| 教务 | 排课、调课、请假补课 | 服务提醒、排课冲突、调课建议 |
| 任课老师 | 课后反馈、学生观察 | 服务提醒、成长记录、家长沟通文案 |
| 校区负责人 | 查看高风险和服务日报 | 风险提醒、日报复盘 |
| AI 工程师 | 一对一配置和调优 | 分身描述、AI 能力方案确认、高级配置、复盘数据 |

### 5.1 工作分身示例

| 工作分身 | 适用用户 | 默认能力方案 | 工作档案目录 |
|----------|----------|------------|--------------|
| 招生顾问分身 | 招生顾问、课程顾问 | 线索识别、招生咨询、试听邀约、排课提醒 | `线索/`、`排课/` |
| 班主任分身 | 班主任、客服 | 客户服务、家校沟通、续费窗口、售后风险 | `客户/`、`售后风险/` |
| 教务分身 | 教务老师 | 排课调课、请假补课、冲突提醒 | `排课/`、`售后风险/` |
| 校区负责人分身 | 校长、校区负责人 | 高风险跟进、服务日报、团队复盘 | `客户/`、`售后风险/`、`日报/` |

工作分身由 AI 工程师创建和启用。第一版不要求工程师从 Agent 清单逐项勾选，而是由工程师描述用户的真实工作分身，AI 生成推荐能力组合、原因和边界，工程师确认后落成结构化配置。普通用户可以感知到“服务助理”的结果，但不需要理解每个 Agent 如何配置。

## 6. 核心概念

### 6.1 记忆笔记

记忆笔记是事实源，来源包括手动记录、录音转写、截图、文件摘要和会话摘要。原始记忆不被 Agent 覆盖。

### 6.2 服务对象

服务对象是从记忆中识别出的家长、学生、客户或线索对象。它是轻量索引，不是 CRM 客户主档案。

### 6.3 工作分身

工作分身是用户在某个岗位或工作场景下的 AI 配置容器，不是会自主行动的数字人。

工作分身用于承载：

- 用户当前岗位，例如招生顾问、班主任、教务、校区负责人。
- AI 工程师对该用户工作分身的自然语言描述。
- 可读取的记忆范围。
- 已确认启用的服务能力和背后的 Agent。
- Agent 工作档案目录。
- 可读取的公司公共知识库。
- 可使用的 Skill。
- 输出口径，例如话术风格、是否生成动作草稿、是否允许外部写回。
- AI 能力方案的生成、确认、回滚和审计记录。

核心关系：

```text
用户 User
  -> 工作分身 Work Profile
  -> AI 能力规划器生成能力方案
  -> AI 工程师确认结构化能力配置
  -> 绑定记忆范围 / 工作档案目录 / 公共知识库 / Skill
  -> 生成服务提醒
```

同一个用户可以有多个工作分身，但第一版建议只启用一个默认分身，避免普通用户理解成本过高。运行时只读取已确认的结构化配置，不允许领域 Agent 在执行时自行扩大能力范围或读取范围。

### 6.4 服务提醒

服务提醒是普通用户看到的消息列表式待办。它来自记忆路由结果、工作分身配置和 Agent 工作档案。

### 6.5 Agent 工作档案库

Agent 工作档案库是内置工作档案，不是公司公共知识库。它按 Agent 或业务域组织 Markdown 文件，承载 AI 整理后的摘要、跟进记录、线索草稿、排课建议和风险事项。

### 6.6 待确认动作

待确认动作是 AI 建议和外部系统之间的缓冲层。用户确认后，未来再通过 Skill 查询、校验或写回外部 CRM / 教务系统。

## 8. 核心流程

### 8.1 记忆入库流程

```text
用户录入记忆
-> 保存 organize_memories
-> 记忆路由器识别服务对象和业务域
-> 写入 metadata
-> 匹配可读取该记忆的工作分身
-> 更新分身绑定的 Agent 工作档案
-> 生成或更新服务提醒
```

要求：

- 每条记忆都保留原文、来源和创建人。
- 路由只做轻量分类，不全量执行领域 Agent。
- 路由结果必须包含置信度。
- 低置信度结果进入待确认，不直接更新客户摘要。

### 8.2 服务提醒查看流程

```text
用户打开服务提醒
-> 系统读取用户默认工作分身
-> 系统读取分身已启用能力
-> 聚合命中的提醒
-> 展示消息列表式服务提醒
-> 用户点击某条提醒
-> 查看来源记忆、摘要、建议和可执行动作
```

要求：

- 打开列表默认不调用大模型。
- 已有路由和工作档案足够生成列表。
- 用户点击提醒或主动生成建议时才执行领域 Agent。
- 多分身用户第一版默认使用当前默认分身，不要求普通用户手动切换。

### 8.3 客户记忆整理流程

```text
记忆命中服务对象
-> 关联 service_subject
-> 更新客户空间 Markdown
-> 建立文档与记忆关联
-> 必要时生成服务提醒
```

客户空间需要包含：

- 客户摘要。
- 学生情况。
- 跟进记录。
- 未闭环事项。
- 风险信号。
- 下一步建议。
- 证据索引。

### 8.4 动作确认流程

```text
Agent 生成动作草稿
-> 用户确认 / 忽略 / 稍后
-> 确认后执行 Skill
-> 返回执行结果
-> 写入动作日志
-> 更新服务提醒状态
```

当前阶段可以只做到动作草稿，不接外部系统。

### 8.5 工作分身配置流程

```text
AI 工程师选择用户
-> 创建或选择工作分身
-> 用自然语言描述该用户的工作分身
-> AI 能力规划器生成能力方案草稿
-> 工程师审核启用能力、原因、风险和边界
-> 工程师确认记忆范围、公司公共知识库、工作档案目录和 Skill
-> 保存为结构化能力配置
-> 用真实记忆测试
-> 开启服务模块入口
```

要求：

- 新用户默认没有启用的领域 Agent。
- AI 生成的能力方案只是配置草稿，不能自动发布。
- 每个工作分身必须有明确的记忆范围和权限边界。
- Agent 只能在工作分身授权范围内生成服务提醒和动作草稿。
- 普通用户不需要进入工作分身配置页。
- 手工逐项调整 Agent 只作为高级配置，不作为第一屏主流程。

### 8.6 AI 能力规划流程

```text
工程师输入分身描述
-> AI 提取岗位、服务对象、负责事项、不负责事项、记忆范围、知识库需求、Skill 需求和输出风格
-> AI 匹配内置 Agent 模板
-> 生成启用/不启用能力建议
-> 给出每项建议的理由和风险
-> 工程师确认或调整
-> 固化为 work_profile_agent_settings
```

分身描述示例：

```text
这个用户是少儿英语机构的招生顾问，主要负责新线索咨询、试听邀约、试听后跟进和报名转化。
他不负责正式排课和课后客服，但需要看到试听时间偏好和家长价格顾虑。
沟通风格要温和、具体，先确认事实再给建议。
外部 CRM 只能查询线索和客户状态，不能自动写回。
```

AI 能力方案示例：

| 能力 | 建议 | 理由 | 边界 |
|------|------|------|------|
| 线索识别 | 启用 | 分身负责新线索咨询，需要从记忆中抽取家长、学生、意向课程和来源 | 只生成线索草稿，不创建 CRM 主数据 |
| 招生咨询 | 启用 | 分身负责试听邀约和报名转化，需要生成跟进话术和异议处理 | 话术必须引用公司公共知识库 |
| 排课提醒 | 部分启用 | 分身需要识别试听时间偏好，但不负责正式排课 | 只生成试听安排提醒，不写正式课表 |
| 客户服务 | 不启用 | 分身不负责课后客服 | 不参与日常服务提醒 |
| 售后风险 | 低强度启用 | 价格顾虑和投诉倾向需要提示 | 只提示风险，不触发升级处理 |

## 9. 功能需求

### FR-01 记忆路由

系统需要在记忆入库、编辑、录音转写完成、文件整理完成后触发记忆路由。

输出字段：

```json
{
  "agent_domains": ["lead_intake", "sales_consulting"],
  "entity_type": "service_subject",
  "entity_name": "张妈妈",
  "student_name": "张同学",
  "intent": "trial_follow_up",
  "risk_label": "价格顾虑",
  "due_at": "2026-09-01T10:00:00+08:00",
  "confidence": 0.82,
  "source_evidence": {
    "memory_id": "memory-id",
    "source": "录音转写"
  }
}
```

验收标准：

- 记忆可以被识别到 0 个、1 个或多个业务域。
- 每个路由结果必须能回到来源记忆。
- 低置信度结果不能直接生成强提醒。

### FR-02 服务对象索引

系统需要把同一客户、家长、学生或线索的多条记忆归并到同一个服务对象。

建议数据对象：

```text
service_subjects
- id
- tenant_id
- owner_user_id
- subject_key
- display_name
- student_name
- relation
- aliases
- external_refs
- visibility_scope
- confidence
- created_at
- updated_at
```

验收标准：

- 同一服务对象的记忆可以聚合查看。
- 服务对象支持别名。
- 服务对象可以保存外部系统引用 ID，但不复制外部客户主数据。

### FR-03 Agent 工作档案库

系统需要为每个启用的业务域维护可读 Markdown 工作档案。

Markdown Front Matter 示例：

```md
---
doc_type: customer_workspace
subject_id: subject-xxx
agent_domain: customer_service
source_memory_ids:
  - memory-001
  - memory-002
updated_at: 2026-08-31T10:00:00+08:00
---

# 张同学 / 张妈妈

## 当前摘要

已完成试听，家长认可老师互动，但对价格有顾虑。

## 跟进记录

- 2026-08-30：家长表示周六上午方便。
  来源：memory-001

## 未闭环事项

- 确认是否报名。
- 发送试听反馈。

## 证据来源

| 记忆ID | 类型 | 作用 |
|--------|------|------|
| memory-001 | 录音转写 | 试听时间偏好 |
| memory-002 | 手动笔记 | 价格顾虑 |
```

验收标准：

- Markdown 中必须保留来源记忆 ID。
- Markdown 可以被重新生成，不能成为唯一事实源。
- 工作档案库不混入公司公共知识库内容。

### FR-04 记忆笔记关联

系统需要建立工作档案和记忆笔记的结构化关联。

建议数据对象：

```text
agent_work_doc_memory_links
- id
- tenant_id
- doc_id
- doc_path
- memory_id
- subject_id
- agent_domain
- link_type
- confidence
- evidence_excerpt
- created_at
```

`link_type` 枚举：

| 类型 | 说明 |
|------|------|
| `trigger` | 触发提醒的记忆 |
| `evidence` | 支撑摘要判断的证据 |
| `follow_up` | 跟进记录来源 |
| `risk` | 风险判断来源 |
| `resolved` | 已闭环依据 |

验收标准：

- 服务提醒、客户摘要、跟进记录都能点回原始记忆。
- 原始记忆被修改后，相关工作档案需要标记为待重算。
- 删除或隐藏记忆后，相关摘要不得继续作为可信证据展示。

### FR-05 服务提醒列表

系统需要提供消息列表式服务提醒入口。

列表字段：

| 字段 | 示例 |
|------|------|
| 头像位 | 张 / 王 / 高风险色块 |
| 标题 | 张同学家长 - 试听回访 |
| 摘要 | 家长认可试听，但对价格有顾虑 |
| 时间 | 今天 / 明天 / 8月31日 |
| 状态 | 待处理 / 已生成话术 / 待确认执行 / 已完成 |
| 标签 | 试听 / 续费 / 排课 / 投诉 |

验收标准：

- 普通用户进入服务模块后默认看到服务提醒，不看到 Agent 配置。
- 列表支持搜索服务对象、学生、提醒内容和记忆关键词。
- 点击提醒可以查看来源证据和下一步建议。
- 加号入口用于新增服务记录、录入沟通笔记或上传语音，不用于新增 CRM 客户。

### FR-06 领域 Agent 执行

领域 Agent 只在用户需要生成建议时执行。

触发时机：

- 用户点击服务提醒。
- 用户点击生成话术。
- 用户点击生成下一步建议。
- 用户在提醒上下文里继续问 AI。

验收标准：

- 记忆入库不触发所有领域 Agent。
- Agent 输入必须包含来源记忆、工作分身配置、公共知识库和可用 Skill。
- Agent 输出必须结构化，包含判断、话术、下一步动作、缺失信息和待确认动作。


验收标准：

- 新用户默认没有启用的领域 Agent。
- 普通用户不能自助创建工作分身或打开 Agent。
- AI 工程师可以输入一段分身描述并生成能力方案草稿。
- 能力方案必须明确建议启用、部分启用和不启用的能力及理由。
- 工程师确认前，能力方案不能生成真实服务提醒。
- 工程师确认后，运行时只读取固化后的结构化能力配置。
- 同一用户可以拥有多个工作分身，但第一版只启用一个默认分身。
- 同一机构不同岗位可启用不同分身模板和 Agent 组合。
- AI 工程师可以按工作分身控制记忆范围、知识库范围、工作档案目录、Skill 和输出策略。
- 高级手工 Agent 开关必须保留审计，不作为普通配置主路径。

### FR-08 待确认动作

系统需要支持 Agent 生成动作草稿。

```text
- summary
- payload

- external_system

- created_at
- updated_at
```

状态流转：

```text

```

验收标准：

- 所有外部写入都必须先形成草稿。
- 用户确认前不写外部系统。
- 每个动作保留来源记忆和执行日志。

### FR-09 Skill 连接外部系统

未来通过 Skill 连接外部 CRM / 教务系统。

Skill 负责：

- 查询外部客户、线索、课表、老师、教室。
- 校验重复线索、字段缺失、排课冲突。
- 在用户确认后写回外部系统。
- 返回外部对象 ID、执行结果和失败原因。

Skill 不负责：

- 不做 Ruile 内部记忆分类。
- 不把外部 CRM 数据复制成 Ruile 主数据。
- 不绕过用户权限直接操作外部系统。

### FR-10 AI 能力规划器

系统需要提供一个后台能力规划器，用于把工作分身描述转换为结构化能力配置草案。

输入：

- 目标用户和所属空间。
- 工作分身描述。
- 可用 Agent 模板清单。
- 该空间可用知识库、Skill 和权限范围。
- 可选的历史记忆样本。

输出：

```json
{
  "profile_summary": "少儿英语招生顾问，负责线索咨询、试听邀约和试听后跟进",
  "enabled_capabilities": [
    {
      "agent_domain": "lead_intake",
      "mode": "enabled",
      "reason": "需要从咨询记录中识别新线索和缺失字段",
      "work_doc_directory": "线索/",
      "confidence": 0.86
    },
    {
      "agent_domain": "scheduling",
      "mode": "partial",
      "reason": "只需要识别试听时间偏好，不负责正式排课",
      "work_doc_directory": "排课/",
      "confidence": 0.72
    }
  ],
  "disabled_capabilities": [
    {
      "agent_domain": "customer_service",
      "reason": "分身描述明确不负责课后客服"
    }
  ],
  "memory_scope": "本人记忆中与咨询、试听、报名、试听安排相关的记录",
  "knowledge_base_requirements": ["课程介绍", "价格政策", "招生话术"],
  "skill_policy": {
    "external_crm": "query_only_until_user_confirmed"
  },

}
```

验收标准：

- 能力规划器只能生成草案，不直接启用 Agent。
- 输出必须包含启用理由、禁用理由和边界说明。
- 草案需要能回填到 `user_work_profiles` 和 `work_profile_agent_settings`。
- 工程师每次确认、修改和发布都需要记录操作人和时间。
- 后续服务提醒生成必须基于已发布配置，不能每次运行时重新让 AI 自由决定权限。

## 10. Agent 模板

第一版建议准备 1 个后台路由器 + 4 个核心 Agent 模板。领域 Agent 不直接暴露给普通用户，而是挂到工作分身上。

| Agent | 默认状态 | 用户侧是否可见 | 主要能力 |
|-------|----------|----------------|----------|
| 记忆路由器 | 后台启用 | 不可见 | 判断记忆属于哪个业务域 |
| 线索录入 Agent | 默认关闭 | 不显示 Agent 名 | 生成线索草稿和缺失字段 |
| 招生咨询 Agent | 默认关闭 | 不显示 Agent 名 | 生成异议处理、邀约话术和下一步 |
| 客户服务 Agent | 默认关闭 | 不显示 Agent 名 | 整理客户摘要、跟进记录、续费窗口 |
| 排课调课 Agent | 默认关闭 | 不显示 Agent 名 | 生成排课/调课建议 |

可扩展 Agent：

- 家校沟通 Agent。
- 售后风险 Agent。
- 续费转介绍 Agent。
- 渠道线索 Agent。
- 日报复盘 Agent。

## 11. UI 要求

### 11.1 服务提醒首页

服务模块默认首页是服务提醒。该页参考消息列表 UI，但不照搬社交产品。

页面要求：

- 一级导航名称使用“服务”。
- 页面标题使用“服务提醒”。
- 用户侧不突出“工作分身”概念，必要时只显示“招生顾问助理”“班主任助理”等业务化名称。
- 搜索框位于列表上方。
- 列表行包含头像位、标题、摘要、时间。
- 高风险、待确认、已完成状态需要清晰区分。
- 移动端优先保证列表可扫描。

不做：

- 不出现“广场、找人”等社交入口。
- 不把每条提醒设计成自由聊天会话。
- 不在用户侧暴露 Agent 选择器。
- 不把加号设计成新增客户或新增商机。

### 11.2 服务提醒详情

详情页展示：

- 提醒原因。
- 来源记忆。
- 客户摘要。
- 推荐话术。
- 缺失信息。
- 下一步动作。
- 确认、忽略、稍后、继续问 AI。

### 11.3 AI 工程师配置页

配置页展示：

- 已配置用户和默认工作分身。
- 分身描述输入框。
- AI 生成能力方案按钮。
- 能力方案预览，包括建议启用、部分启用、不启用能力及理由。
- 工程师确认发布按钮。
- 发布前测试入口，可选择真实记忆样本验证提醒效果。
- 高级配置区，用于调整记忆范围、公司公共知识库、工作档案目录、可用 Skill 和输出策略。
- 配置审计记录。

第一屏只服务“描述分身、生成方案、确认发布”。Agent 逐项开关、目录和 JSON 策略配置应放入高级区，避免 AI 工程师配置成本过高。

## 12. 权限与安全

- 普通用户只能查看自己权限范围内的记忆、服务提醒和工作档案。
- AI 工程师只能配置授权机构和用户。
- 工作分身不能突破用户本身已有权限。
- 工作分身只能读取配置范围内的记忆、工作档案和公共知识库。
- 公司公共知识库与客户工作档案分开授权。
- 外部系统 Skill 必须继承当前用户或机构授权。
- 删除、隐藏、修正记忆后，相关摘要和提醒需要失效或重算。
- 所有 Agent 输出需要保留来源证据。

## 13. 数据与存储设计

### 13.1 MVP 存储方案

第一阶段优先复用现有能力：

```text
organize_memories
  metadata.agent_domains
  metadata.service_subject
  metadata.intent
  metadata.due_at
  metadata.source_evidence

工作分身配置
  可先用配置文件或轻量配置记录
  profile_id
  description
  capability_plan
  capability_plan_status
  enabled_agents
  memory_scope
  work_doc_directories
  confirmed_by
  confirmed_at

内置 Agent 工作档案库
  Markdown 文件
  Front Matter source_memory_ids

服务提醒
  可先由 metadata + Markdown 摘要动态生成
```

优点：

- 改动小。
- 快速验证记忆路由质量。
- 适合一对一人工配置试点。

限制：

- 查询、排序、状态流转能力有限。
- Markdown 不适合作为唯一结构化状态源。

### 13.2 稳定版存储方案

稳定后新增结构化对象：

```text
service_subjects
agent_work_docs
agent_work_doc_memory_links
service_reminders
agent_action_drafts
agent_action_logs
user_work_profiles
work_profile_agent_settings
```

其中：

- `service_subjects` 解决记忆归属。
- `agent_work_docs` 记录 Markdown 文档元数据。
- `agent_work_doc_memory_links` 保证证据链。
- `service_reminders` 承载列表、状态、排序和提醒时间。
- `agent_action_drafts` 承载用户确认前的动作。
- `agent_action_logs` 承载 Skill 执行审计。
- `user_work_profiles` 承载用户的工作分身。
- `work_profile_agent_settings` 承载分身已确认启用的 Agent、记忆范围、目录、知识库和 Skill。

AI 能力方案不应只保存在前端。建议至少保存：

- 原始分身描述。
- AI 生成的能力方案 JSON。
- 工程师确认后的结构化 Agent 配置。
- 工程师修改前后的差异。
- 发布状态和审计信息。

## 14. 状态流转

### 14.1 服务提醒状态

```text
candidate -> pending -> generated -> confirmed -> completed
candidate -> ignored
pending -> snoozed -> pending
pending -> stale -> recompute_required
```

### 14.2 工作档案状态

```text
current
stale
recompute_required
archived
hidden_due_to_source_permission
```

### 14.3 工作分身状态

```text
draft -> testing -> enabled
enabled -> disabled
enabled -> archived
```

说明：

- `draft`：AI 工程师正在配置，普通用户不可见。
- `testing`：用真实记忆测试路由和输出，普通用户不可见或仅灰度可见。
- `enabled`：该分身开始生成服务提醒。
- `disabled`：暂停生成服务提醒，但保留历史配置。
- `archived`：用户岗位变化或服务结束后归档。

### 14.4 记忆修正影响

当原始记忆被编辑、删除、隐藏或权限变化时：

- 相关服务提醒标记为 `recompute_required`。
- 相关工作档案标记为 `stale`。
- 已生成但未确认动作需要重新校验。
- 已执行动作不回滚，但执行日志保留历史证据状态。

## 15. 非功能需求

| 类别 | 要求 |
|------|------|
| 可追溯 | 每个提醒、摘要、动作都能回到来源记忆 |
| 低成本 | 记忆入库只跑轻量路由，不全量跑领域 Agent |
| 可配置 | Agent 默认关闭，由 AI 工程师描述工作分身，AI 生成能力方案，工程师确认后启用 |
| 可重算 | Markdown 摘要和工作档案可以从原始记忆重建 |
| 权限隔离 | 用户只能看到自己权限范围内的记忆和工作档案 |
| 可扩展 | 后续通过 Skill 接外部 CRM / 教务系统 |
| 可解释 | 用户能看到 AI 为什么提醒、依据是什么 |
| 可审计 | 分身描述、AI 方案、工程师修改和发布动作都可追踪 |

## 16. 验收标准

第一阶段验收：

- AI 工程师可以为用户创建默认工作分身。
- AI 工程师可以通过一段分身描述生成服务能力方案草稿。
- AI 工程师可以确认或调整能力方案，并发布为结构化配置。
- 未经确认发布的能力方案不能生成真实服务提醒。
- 新记忆可以写入路由 metadata。
- 服务提醒列表可以按默认工作分身展示命中的服务事项。
- 点击服务提醒可以看到来源记忆。
- 客户工作档案 Markdown 可以展示客户摘要、跟进记录和证据索引。
- Markdown 和服务提醒都能关联回记忆笔记。
- 普通用户不看到 Agent 配置和工作分身配置。
- 不新增 CRM 客户、线索、订单、课表主表。

第二阶段验收：

- 服务提醒有状态流转。
- Agent 可以生成结构化动作草稿。
- 用户可以确认、忽略、稍后。
- 日报可以按服务提醒和风险生成。

第三阶段验收：

- Skill 可以连接一个外部系统。
- 用户确认后可以查询、校验或写回外部系统。
- 外部执行结果进入日志。
- 失败可重试并提示原因。

## 17. 实施计划与成本

### 阶段 1：MVP

目标：验证记忆分流、服务提醒和工作档案是否有用。

范围：

- 记忆路由器。
- metadata 路由字段。
- 工作分身配置模型。
- AI 能力规划器。
- 分身描述与能力方案保存。
- Agent 工作档案库 Markdown。
- 文档与记忆关联。
- 服务提醒列表。
- AI 工程师轻量配置页：描述分身、生成方案、确认发布。

不做：

- 不接 CRM。
- 不写外部系统。
- 不做完整配置后台。
- 不建正式客户、线索、课表主表。

预估：10-15 人日。若先用固定模板生成能力方案，可控制在 8-12 人日。

### 阶段 2：动作草稿与状态

目标：让提醒从“可看”变成“可处理”。

范围：

- 服务提醒结构化表。
- 动作草稿表。
- 状态流转。
- 日报复盘。
- 误判和漏判反馈。

预估：2-3 周。

### 阶段 3：Skill 外部连接

目标：用户确认后连接外部 CRM / 教务系统。

范围：

- Skill 协议。
- 外部对象查询。
- 字段映射。
- 冲突校验。
- 写回和执行日志。

预估：3-5 周，取决于外部系统 API 质量和权限模型。

## 18. 风险与对策

| 风险 | 表现 | 对策 |
|------|------|------|
| 滑向 CRM | 开始建客户、线索、订单、课表主表 | 坚持只存记忆、工作档案、提醒和外部引用 |
| Agent 太多 | 用户不知道用哪个，工程师也不愿逐项配置 | 用户侧一级模块只显示服务，后台主流程改为描述分身后由 AI 生成能力方案 |
| 分身概念过重 | 用户误以为要训练数字人或管理多个身份 | 用户侧弱化分身，只显示服务结果；后台用工作分身承接配置 |
| AI 误配能力 | AI 给用户启用了不该启用的能力 | AI 只生成草案，必须工程师确认；运行时只读已发布结构化配置 |
| 分身越权 | 一个分身读取了不该读的客户记忆 | 分身权限必须受用户权限、记忆范围和知识库范围共同约束 |
| Markdown 失真 | 摘要被当成事实源 | Markdown 必须关联原始记忆，且可重算 |
| 记忆归并错误 | 多个客户混在一起 | 服务对象索引支持置信度、别名和人工修正 |
| 成本失控 | 每条记忆触发多个 Agent | 入库只跑路由，领域 Agent 延迟到用户点击 |
| 权限泄露 | 客户工作档案被无关用户看到 | 工作档案继承记忆权限和工作分身配置 |
| 外部写回失败 | CRM / 教务字段不一致 | 通过动作草稿和执行日志缓冲 |

## 19. 开放问题

- Agent 工作档案库是否复用现有知识库底层，还是单独建工作档案类型。
- 服务对象归并是否第一版允许用户手动合并和拆分。
- 服务提醒是否需要单独结构化表，还是第一版用 metadata 动态生成。
- Markdown 更新是每次记忆入库增量更新，还是用户打开客户空间时延迟生成。
- 工作分身第一版是否允许一个用户多个分身，还是只保留默认分身。
- 工作分身是否在用户侧展示业务化名称，例如“招生顾问助理”。
- AI 能力规划器第一版使用规则模板、LLM，还是二者结合。
- 分身描述是否需要引导式字段，还是只提供长文本输入。
- 外部 CRM / 教务系统第一批优先对接哪一种。

## 20. 推荐结论

推荐第一版采用：

```text
记忆笔记 + 路由 metadata
-> 匹配用户默认工作分身
-> 基于已确认的能力配置决定处理域
-> Agent 工作档案库 Markdown
-> 结构化记忆关联
-> 服务提醒列表
-> 点击提醒执行领域 Agent
```

这个方案能同时满足：

- 普通用户傻瓜式使用。
- AI 工程师一对一描述工作分身，AI 生成能力方案，工程师确认发布。
- 每个工作分身启用的 Agent 有自己的工作目录。
- 客户空间可读、可追溯、可重算。
- 不做 CRM，但未来可以通过 Skill 接外部系统。
