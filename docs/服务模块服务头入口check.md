# 服务头常驻入口 Check

> **检查对象**：服务空间服务头右侧的 7 个带计数常驻入口（`ServiceHub.vue:866-879` 定义、`:251-262` 渲染）
> **结论**：**7 个里有 2 个必要常驻，3 个能力必要但位置错误，2 个概念冗余。** 与《服务模块优化方案》§支柱 4 的结论一致，本文补充 5 条方案未写透的证据（§3.5 为 v1.4 追加）。

## 1. 判定标准

服务头的常驻位是**稀缺资源**，不是"功能目录"。项目在这一点上已经付出过代价、也得过收益，量化记录在 PRD 里：

> 撤掉 48px 左侧图标栏 → 对话区 704 → **766px**；D21 再撤掉 236px 会话栏 → **956px**（`服务模块重构PRD.md:1680`）

因此"该不该常驻"必须同时满足三条：

1. **高频**——每进一次服务就可能点
2. **与当前工作同源**——它是"这段工作跑出来的东西"，不是"配一次就忘的设置"
3. **计数有信息量**——数字变化代表"这里有新东西"

**第 3 条是本次 check 的关键**，现状 7 个入口在这一点上崩得最彻底（见 §3.1）。

## 3. 补强证据（方案里没写透的）

### 3.1 关键发现：「计数」这个设计在 3 个入口上失效了

7 个入口用了统一的 pill 样式（`.service-hub-head-tool`，`:2684-2716`），每项都带一个 `<small>` 计数。但计数的**语义完全不一致**：

| 入口 | 计数表达式 | 语义 | 会变吗 |
| --- | --- | --- | --- |
| 产物 | `activeArtifacts.length` | 数据量 | ✅ 会变 |
| 待办 | `serviceReminders.length` | 数据量 | ✅ 会变 |
| 来源 | `contextSources.length` | 数据量 | ✅ 会变 |
| 主体 | `subjectsTotal` | 数据量 | ✅ 会变 |
| 档案 | `serviceProfile.schema.length` | **配置项个数** | ❌ **恒定** |
| 摘要 | `serviceSummary.schema.length` | **配置项个数** | ❌ **恒定** |
| 设置 | `0` 硬编码（`:877`） | **无** | ❌ **恒 0** |

**"带计数"这个设计的前提是"数字会变、变了代表有新东西"。** 档案（6）、摘要（4）显示的是**蓝图声明的字段条数**——用户不配置就永远不变，配置了也只是换个数字；设置恒显示 0。

也就是说：**7 个 pill 中有 3 个的数字是装饰性的**。它们借用了 pill 的视觉形式，却没有 pill 的信息功能——视觉上宣告"我们七个是同一类东西"，实际上只有 4 个是同类的。这是"不简洁清晰"最直接的机制性来源。

### 3.2 `⋯` 菜单与服务头常驻的职责被完全倒置

PRD D18 的两层分工是：

- **常驻** = 产物 / 待办（会话沉淀物）
- **`⋯`** = 服务本身（一级：名称 / 描述 / 分享；二级「更多 ›」：概览 / 服务对象 / 运行记录 / 设置 / 归档 / 删除）

代码现状（`ServiceHub.vue:265-286`）：`⋯` 里装的是**复制配置创建 / 暂停服务 / 归档服务 / 删除服务**——**四项全是生命周期操作，没有一项是"服务本身"**。而 PRD 规定该进 `⋯` 的东西（设置、概览、服务对象），**全部跑到了常驻位**。

这不是"多放了几个按钮"，是**两层分工被整体调换了**：给"天天要点"的位置塞满了"配一次就忘"的，给"偶尔要动"的位置塞满了"危险且不可逆的"。

### 3.3 小屏下这 7 个入口会横向溢出

`ServiceHub.vue:3837-3846`：

```css
.service-hub-space-actions { justify-content: flex-start; overflow-x: auto; }
.service-hub-head-tool { flex: none; }
```

小屏时服务头右侧变成一条**可横向滚动**的条——7 个入口放不下，用户要左右滑动才能看到"设置"。**入口多到需要靠滚动才能穷尽，本身就是"该减了"的信号。**

### 3.4 团队自己在移动端已经砍掉了 6 个

`ServiceHub.vue:872-879`：`route.meta.mobileEntry` 为真时，`headTools` **只剩「产物」一项**，待办 / 来源 / 主体 / 档案 / 摘要 / 设置全部不渲染。

这是**内部一致性证据**：如果这 6 个真是"每个服务必看"的，移动端不该一刀全砍。

> **证据强度说明**：移动端是最小可用形态，不能据此反推桌面端"待办也不必要"。这条只用来支持一个较弱但充分的结论——**除了产物，「待办」及以下 5 项都不是"不看就会误事"的东西**，它们没有硬性常驻的理由。

### 3.5 追加发现（v1.4）：设置面板里的「必填」是零消费的死控件

顺带核查设置面板时发现：「档案字段」配置里的**必填勾选**（`ServiceHub.vue:487`）背后是 `ServiceSpaceProfileField.Required`（`internal/types/service_space_blueprint.go:68`），**全仓零消费**——

- 事实抽取 `extractProfileProposalItems`（`service_space.go:1486`）只读 `Source / Label / Key / Aliases / ConfidenceThreshold`；
- 档案物化 `materializeProfileValues` 不读它；唯一被消费的 `Required` 是 `SubjectPolicy.Required`（`:1304` / `:1374`），那是"服务对象是否必须存在"，与字段无关。

**处置（v1.3 已进方案 §支柱 2 / 原型设置场景）**：配置界面直接删掉「必填」列。同时配置区重做为：场景化推荐（点选即加）+ 已选标签（点击改名）+ 别名收进高级项 + 右侧实时预览卡——因为**名字直接决定抽取命中率**（抽取就是拿 `Label / Key / Aliases` 在对话文本里做字符串匹配，`extractProfileFieldValue`，`service_space.go:1512`），推荐项措辞按家长说话习惯预置。

**界面用词（v1.4→v1.6）**：分区标题从「概览字段」先改为「要记的信息」（v1.4，避免"字段"这个数据库词汇），再统一为**「重点记录」**（v1.6）——这个词就是用户在工作指令里的原话（"重点记录家长顾虑与到访意向"），**设置项与指令同词**，用户一眼能对上；界面上不出现"字段"二字，副标题一句话说清行为：「家长聊天时说到这些，AI 会自动记到对应家庭名下，写进服务概览」。（"概览字段"保留为文档 / 代码层的概念名。）

这条与 §3.1 同属一个模式：**界面在教用户一个不产生任何效果的设置**（恒定计数的 pill、拨了没反应的开关）。

## 5. 决策项

### 5.1 Q2 · 命名 —— ✅ **已拍板（2026-10-05）：统一叫「服务概览」**

**决策**：档案与摘要合并后的视图，正式名 **「服务概览」**，不新造词，不并列保留两个旧名。

**落地口径（术语收敛）**：

| 项 | 正式名 | 出现位置 | 退役名 |
| --- | --- | --- | --- |
| 合并后的只读视图 | **服务概览** | `⋯ › 更多` 第一项 | ~~空间档案~~ / ~~首页摘要~~ |
| 配置这些字段的地方 | 服务设置 › **重点记录**（v1.6 定名，与工作指令同词；界面不出现"字段"） | 设置面板分区 | ~~档案字段~~ |
| 前端面板 key | `overview` | `ServiceHub.vue` 的 `panel` 取值 | `profile` / `summary` |
| 路由 | `/platform/service/:serviceId/overview` | 复用既有路由 | `?panel=profile` / `?panel=summary` |
| 后端接口 | `GET /services/:id/overview` | `router.go:1568`（**前端零调用，正好接管**） | `/:id/profile` / `/:id/summary`（保留供深链，不再有界面入口） |

**三点说明**：

1. **不需要改动《服务模块优化方案》的任何用词**——方案 §支柱 2、§路由表、§组件表、§概念收敛表第 15-18 行**已经全部使用「服务概览」**。这次确认只是把"建议词"钉为"正式词"。
2. **后端接口天然对齐**：`GET /:service_id/overview`（`router.go:1568`）早已存在且前端从未调用——合并后的面板正好接管它，**不需要新增后端能力**。
3. **命名定了之后要注意的风险**（原话保留）：概览若做成"只有只读文本 + 字段列表"的面板，用户看完会问"这和下面那段对话有什么区别"。**建议它同时承担"打开服务时的第一屏摘要"职责**——即概览的价值在于"我离开一段时间后，一眼知道这个服务现在什么状况"，而不是"把蓝图字段再列一遍"。

| --- | --- | --- |
| 优化方案 §支柱 4（`:209`、`:218`） | 服务概览进 **`⋯ → 更多`**，判据"天天要点 vs 偶尔要用" | **不常驻** |
| 优化方案 §Q2 待决策（`:483`） | 「②→①：**先用常驻摘要条**（信息量足够，不占入口），点开进整页概览」 | **常驻** |

两者互斥：一个说"进 ⋯ 菜单"，一个说"顶部常驻一条可折叠摘要条"。

**我的判断：采用前者（进 `⋯ → 更多`），理由有三。**

1. **与本次 check 的机械性结论一致**——档案/摘要的计数是恒定的配置项个数，不是数据量，**它们连"带计数常驻"的入场资格都没有**（§3.1）
2. **"常驻摘要条"是同一件事的第三次尝试**：PRD 已淘汰横向 tab 条、左侧文字栏、左侧图标栏三版（`PRD:1680`），理由是"在回答用户没在问的问题"。一条常驻摘要条问的是更隐晦的同一句话——"你要不要先看看概览？"，而用户进服务就是想接着干活
3. **摘要条会挤掉对话区**——PRD 为这里争到了 956px，一条常驻条会把这个数字还回去一部分

**折中方案（如果确实需要"打开就能看到状况"）**：不做常驻条，改为**服务空间的空态/首屏一次性呈现**——即"当前服务还没有会话时"，对话区给出概览卡片（含摘要）；一旦有了会话，概览退回 `⋯`。这样"打开就能看到状况"和"不挤占工作区"同时成立。

### 5.3 Q1 · 来源的最终落点 —— ✅ **已拍板（2026-10-05）：取消常驻，不做 chip**

**用户判断**：来源的条数不重要；它是在服务空间/会话这一侧被带入的，不需要单独展示。

**核实结论：判断成立，但其中一处事实需要修正**——带入动作**并不发生在会话里**：

| 事实 | 证据 |
| --- | --- |
| 带入由 URL query 驱动，**只在创建服务时发生** | `ServiceHub.vue:1515-1519`（要求 `create=1`）→ `:1575-1593`（`importPendingContextSource`） |
| **会话里没有任何来源展示** | `ChatView` 只收到 `session_id` / `service-id` / `agent-id` / `kb-ids`（`:288-300`）；来源经后端 `ServiceRuntimeContext.context_sources` **隐式注入给 AI**（`api/service/index.ts:334`） |
| 来源的"详情"本来就在整理模块 | `viewSourceOutput` 跳回 `/platform/organize/outputs/:id`（`:1261-1267`） |
| **撤销只有服务侧能做** | `deleteServiceContextSource` 仅 `:1278` 一处调用；整理模块侧零感知 |

准确说法是：**AI 在会话里"用了"来源，但界面从来没有"展示"过它**——目前唯一能看到它的地方就是那个 pill。

**结论与口径修正**：

1. **计数**：来源的计数形式没有问题（它属于"会变的数据量"，不是档案/摘要那种恒定配置数）。撤掉它的理由**不是"计数失效"，而是"这个信息本身低频"**——"这个服务有几份背景资料"不是用户要盯的东西。两个理由不同，不要混用。
2. **撤回本文档上一版的"输入框 chip"建议**。既然来源是**建服务时一次性带入**（没有"给已有服务追加来源"的前端路径），chip 等于为一个一次性动作新增常驻界面元素，与"最简"目标相反。
3. **硬约束：撤销能力必须保留**。只删 pill 而不给替代落点，用户"带入后想撤回"就无路可走——**那是功能回退，不是减法**。落点：`设置 › 资料`（可查可删）。
4. **残留风险的兜底**：完全不展示后，用户可能忘记"这个服务被喂过什么"，AI 一直用一份过期资料也不自知。兜底应由 **AI 回答时的引用标注**承担（若引用协议支持），而不是靠一个常驻入口。

### 5.4 ⚠️ 连带修正：P0"纯减法"的表述过于乐观

优化方案把 P0 写作"纯减法、不依赖后端改动、可单独上线"。按本次 check，这个表述需要收紧：

| pill | 有无写操作 | 能否"直接删" |
| --- | --- | --- |
| 档案 | ❌ 纯只读 | ✅ 可以直接删（内容原样并进概览） |
| 摘要 | ⚠️ 有「刷新」 | ✅ 可删（刷新是 AI 的补充手段，主路径是自动刷新） |
| 设置 | ✅ 名称 / 描述 / 指令 / 字段 / 状态的**唯一编辑入口** | ❌ 删了就没法改服务名 |
| 主体 | ✅ **唯一添加入口** | ❌ 删了就没法加对象 |
| 来源 | ✅ **唯一移除入口** | ❌ 删了就无法撤回带入 |

**准确口径**：P0 真正"无副作用可删"的只有**档案、摘要** 2 个；另 3 个必须**先建落点再删**。建议二选一：

- **P0 缩小范围**：只删档案 + 摘要（服务头 7 → 5，仍是可见收益且零风险）；
- **P0 保持 7 → 2**：但把"⋯ 菜单项 + 设置 › 资料分区"并入 P0 一起发，性质从"纯减法"变为"减法 + 轻量落点"，工作量仍需评估。
