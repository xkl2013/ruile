## 1. 设计结论

Ruile 的订阅管理采用“工作区订阅主体 + 账号行为审计”的模型：

```text
用户 User
  ├─ 拥有一个个人工作区 Tenant(personal)
  └─ 可以加入多个企业工作区 Tenant(enterprise)

订阅主体 Billing Subject
  └─ tenant_id

套餐 Plan
  ├─ edition_code: personal | enterprise
  ├─ 存储额度: storage_quota_bytes
  ├─ 周期积分: period_credit_points
  └─ 产品能力: feature_json / limits_json

用量 Usage
  ├─ personal_usage: 个人订阅额度和个人充值余额
  ├─ enterprise_usage: 企业总资源池下按成员统计的用量
  ├─ member_monthly_limit: 成员每月可使用的积分上限
  ├─ enterprise_overage_policy: 超额后阻断或继续使用企业余额
  └─ 每次付费调用按 active tenant 解析用量口径
```

核心原则：

1. `tenant` 仍是资源归属、RBAC、存储和审计边界。
2. 套餐订阅必须绑定 `tenant_id`，而不是只绑定 `user_id`。
3. 个人版就是个人工作区的订阅；企业版就是企业工作区的订阅。
4. 用量分成 `personal_usage` 和 `enterprise_usage`：个人工作区消耗个人用量，企业工作区消耗企业资源池并按 `actor_user_id` 统计到成员；成员月度上限是使用策略，不形成独立积分账户。
5. 存储配额继续以工作区为准，优先复用 `tenants.storage_quota` / `storage_used`。
6. 积分不是权限。权限仍由工作区成员、角色、知识库创建者、共享空间和 API Key 策略决定。
7. 前端只显示后端返回的套餐、能力、配额和状态；所有限制必须由后端再次执行。
8. “套餐订阅”和“知识库订阅”必须分开：套餐订阅是付费权益，知识库订阅只是快捷入口，不授予访问权。

## 2. DEEIX-Chat 可借鉴点

### 2.1 可复用能力

DEEIX-Chat 当前实现已经具备完整的用户级账单体系：

| 模块 | DEEIX-Chat 实现 | Ruile 借鉴方式 |
| --- | --- | --- |
| 套餐 | `BillingPlan` 保存 `Code`、`FeatureJSON`、`PeriodCreditNanousd`、`PermissionGroupID` | 保留“套餐定义 + 能力 JSON + 周期额度”的结构，但额度单位改为积分 |
| 价格 | `BillingPrice` 将套餐和 `month/year/lifetime`、币种、金额分离 | 保留套餐和价格分离，便于月付、年付、试用、手工开通 |
| 订阅 | `Subscription` 绑定 `UserID`、`PlanID`、周期起止、取消和自动续费状态 | 改为绑定 `TenantID`，同时记录订阅操作人 |
| 余额 | `BillingAccount` + `BalanceTransaction` 维护用户余额和余额流水 | 改为工作区积分账户和积分流水 |
| 用量预留 | `UsageReservation` 在模型调用前预留预算，限制并发透支 | 借鉴预留机制，按工作区和用量口径锁定预算 |
| 用量账本 | `UsageLedger` 记录模型、Token、调用次数、耗时、费用和快照 | 扩展为工作区账本，保留调用用户、知识库、Agent、渠道等上下文 |
| 支付配置 | `system_settings` 中维护 `billing.payment_providers`、Stripe、EPay 网关、商户号和密钥 | Ruile 复用 SystemAdmin 运行时配置思路，增加支付宝和微信支付配置 |
| 支付收银台 | `/billing/payments/checkout` 先创建内部订单，再创建第三方收银台并保存 `checkout_url` | Ruile 保持“订单先落库，第三方收银台后创建”，但订单绑定 `tenant_id` |
| 支付回调 | Stripe webhook / EPay notify 校验签名、金额、币种和订单号后调用 `CompletePaymentOrder` | Ruile 为支付宝、微信支付增加公开 notify 路由，回调幂等发放积分或存储 |
| 存储配额 | `file_storage_quotas` 以用户为维度记录 `quota/used/reserved`，上传事务内扣占用 | Ruile 已有工作区级 `storage_quota/storage_used`，补齐预留和流水即可 |
| 接口 | 用户侧 `/billing/*`，后台 `/admin/billing/*` | Ruile 增加用户侧、企业管理员侧和 SystemAdmin 侧三层接口 |

源码复用分级：

| 复用级别 | 内容 | 处理方式 |
| --- | --- | --- |
| 直接移植 | Token/按次/按秒/阶梯计费、整数取整、倍率组合、定价快照 | 保留核心算法和测试，字段单位从 `nanousd` 适配为成本纳美元和积分微单位双记录 |
| 适配移植 | 用量预留、结算、释放、待核对、余额流水、支付订单幂等 | 将 `user_id` 改为 `tenant_id` 计费主体，并补充 `actor_user_id`、`usage_scope`、成员策略快照 |
| 参考重写 | Repository、HTTP Handler、DTO、系统设置接入、调用链接入 | 按 Ruile 现有迁移、错误、日志、审计、路由和依赖注入方式实现 |
| 不直接复用 | DEEIX React/Next.js 管理页面、Stripe 专用页面和用户级权限组 UI | Ruile 使用 Vue 3/TDesign 重做，支付渠道以支付宝、微信支付为主 |

### 2.2 必须适配的边界

不能直接照搬的地方：

- DEEIX-Chat 是 `billing_accounts.user_id`、`billing_subscriptions.user_id`、`UsageLedger.user_id` 的用户级计费；Ruile 必须按 `tenant_id` 作为订阅和扣费主体。
- DEEIX-Chat 的 `PermissionGroup` 是模型访问和费率倍率，不等同于 Ruile 的企业成员角色。
- DEEIX-Chat 的文件存储配额是用户维度；Ruile 的知识库文件、索引和默认存储实例已经是工作区维度。
- DEEIX-Chat 的 `FeatureJSON` 可用于套餐展示，但 Ruile 的版本/套餐能力必须在后端服务和中间件中执行。
- DEEIX-Chat 的 EPay 是支付宝/微信聚合支付入口；Ruile 面向国内部署时建议把 `alipay` 和 `wechat_pay` 做成一等支付渠道，EPay 仅作为可选兼容通道。

### 2.3 源码引入和许可证要求

DEEIX-Chat 使用 Apache License 2.0。Ruile 可以复制、修改和分发相关源码，但实施时必须：

1. 在仓库增加 `THIRD_PARTY_NOTICES.md`，记录 DEEIX-Chat 项目、许可证、参考 commit 和移植范围。
2. 在 `docs/third_party/DEEIX-Chat.md` 记录原文件路径、Ruile 目标文件、主要修改和后续同步方式。
3. 保留适用的版权、专利、商标和归属声明；修改后的移植文件增加“已为 Ruile 修改”的说明。
4. 不使用 DEEIX 名称、Logo 或商标作为 Ruile 产品标识。
5. 优先连同对应测试一起移植；不得只复制计算代码而丢弃边界、并发、幂等和异常测试。
6. 每次同步上游修复必须固定上游 commit，经过代码审查和 Ruile 回归测试后再合入，禁止自动覆盖本地适配代码。

DEEIX-Chat 的计费源码位于 Go `internal` 目录，Ruile 不能将其作为外部 Go 包直接导入。因此在 Ruile 内建立独立的 `internal/billing` 边界：

```text
internal/billing/
  domain/          # 套餐、订阅、积分账户、定价、预留和账本类型
  pricing/         # 从 DEEIX-Chat 定向移植的纯计费算法
  repository/      # Ruile 的 tenant 级事务和持久化实现
  service/         # 订阅、积分、存储和结算服务
  transport/       # 用户、企业管理员和 SystemAdmin 接口
```

源码移植的目标是复用经过验证的计费内核，不是把 DEEIX-Chat 变成 Ruile 的运行时依赖。

## 4. 产品版本与套餐

### 4.1 版本定义

只对外展示两个产品版本：

| 版本 | 订阅主体 | 适用对象 | 核心边界 |
| --- | --- | --- | --- |
| 个人版 `personal` | 个人工作区 `tenant_id` | 单账号个人使用 | 无成员管理、无企业共享、无企业发布渠道 |
| 企业版 `enterprise` | 企业工作区 `tenant_id` | 多人协作组织 | 成员、角色、共享空间、企业知识库、渠道和审计 |

兼容状态：

- `legacy` 只用于历史工作区迁移，不作为销售版本。
- `space_type=personal` 可映射为个人版。
- `space_type=organization` 可映射为企业版。
- 无法判定的旧工作区先按兼容策略运行，由 SystemAdmin 分类。

### 4.2 套餐建议

V1 建议四个套餐，具体额度可由运营配置：

| 套餐 code | 版本 | 成员 | 存储 | 周期积分 | 适合场景 |
| --- | --- | ---: | ---: | ---: | --- |
| `personal_free` | 个人版 | 1 | 1 GB | 试用额度 | 注册体验 |
| `personal_pro` | 个人版 | 1 | 20 GB | 中等额度 | 个人长期使用 |
| `enterprise_team` | 企业版 | 10 | 100 GB | 团队额度 | 小团队/园所 |
| `enterprise_business` | 企业版 | 可配置 | 可配置 | 可配置 | 大客户合同 |

说明：

- 免费套餐也走订阅模型，便于统一返回当前权益。
- 企业版成员数应使用 `tenant_members` 活跃成员计数校验。
- 存储是硬额度，默认不自动用积分购买。
- 积分是 AI 计算额度，用于模型、OCR/ASR、重排、摘要、知识图谱、自动问题生成、Agent 和发布渠道调用。
- 企业版周期积分进入企业共享资源池；成员按企业默认或个人自定义的月度上限使用，不再把企业周期积分或余额拆分到成员账户。

```text

  + active subscription plan feature_json
```

禁止规则：

- 个人版即使套餐 JSON 打开了 `workspace.members.manage`，后端也必须拒绝。

- SystemAdmin 运营后台可以调整套餐和订阅，但普通企业管理员不能自行修改套餐能力 JSON。

## 5. 存储设计

### 5.1 配额口径

Ruile 继续以工作区统计存储：

```text
tenants.storage_quota  工作区总存储额度，单位 bytes
tenants.storage_used   工作区已使用额度，单位 bytes
```

计入口径：

- 知识库原始文件；
- 解析后保存在对象存储中的图片、音频、视频、导出文件；
- 检索索引的估算体积；
- FAQ、手工知识、网页导入产生的向量索引估算体积；
- 后续若聊天附件长期保存，也应进入当前 active tenant 的存储占用。

暂不计入口径：

- 日志、审计、数据库普通业务行；
- Redis 队列和临时缓存；
- 可自动清理的临时上传缓存；
- 外部模型供应商侧缓存。

### 5.2 套餐与存储关系

套餐激活时：

1. 读取套餐 `storage_quota_bytes`。
2. 如果新额度小于当前 `storage_used`，订阅仍可变更，但进入 `storage_over_quota` 状态。
3. 超额状态下允许读取、搜索、删除、导出，禁止新增上传、复制、重解析产生新索引。
4. 企业升级或购买存储包后，更新 `tenants.storage_quota` 并记录审计。

降级策略：

- 不删除文件。
- 不自动压缩或迁移存储。
- 不允许继续新增占用。
- 前端显示“已超出当前套餐存储额度”，引导升级或清理。

### 5.3 存储预留

当前上传只在部分链路判断 `storage_used >= storage_quota`，容易在并发上传和解析后写入索引时超出。建议增加工作区级预留：

```sql
CREATE TABLE tenant_storage_reservations (
    id VARCHAR(36) PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id BIGINT NOT NULL,
    actor_user_id VARCHAR(36) NOT NULL,
    ref_no VARCHAR(128) NOT NULL,
    reserved_bytes BIGINT NOT NULL DEFAULT 0,
    status VARCHAR(32) NOT NULL DEFAULT 'active',
    expires_at TIMESTAMP WITH TIME ZONE NOT NULL,
    settled_at TIMESTAMP WITH TIME ZONE,
    released_at TIMESTAMP WITH TIME ZONE,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE UNIQUE INDEX uq_tenant_storage_reservations_ref
    ON tenant_storage_reservations (tenant_id, ref_no);

CREATE INDEX idx_tenant_storage_reservations_active
    ON tenant_storage_reservations (tenant_id, status, expires_at);
```

上传/解析流程：

```text
上传前估算原文件大小
  -> 锁定 tenant 行
  -> 校验 storage_used + active_reserved + new_bytes <= storage_quota
  -> 创建 storage reservation
  -> 文件写入对象存储
  -> 创建 knowledge/resource 记录
  -> 解析、切片、向量化后得到实际 storage_size
  -> tenant.storage_used += actual_storage_size
  -> reservation settled/released
```

如果解析失败：

- 已持久化的原始文件按实际占用结算；
- 未产生的索引预留释放；
- 失败记录仍显示占用，删除失败知识时释放。

### 5.4 存储流水

为审计和问题排查增加存储流水：

```sql
CREATE TABLE tenant_storage_transactions (
    id VARCHAR(36) PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id BIGINT NOT NULL,
    actor_user_id VARCHAR(36),
    type VARCHAR(32) NOT NULL,
    amount_bytes BIGINT NOT NULL,
    storage_used_after BIGINT NOT NULL,
    ref_type VARCHAR(64) NOT NULL DEFAULT '',
    ref_id VARCHAR(64) NOT NULL DEFAULT '',
    ref_no VARCHAR(128) NOT NULL DEFAULT '',
    description VARCHAR(255) NOT NULL DEFAULT '',
    snapshot_json JSONB,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_tenant_storage_transactions_tenant_created
    ON tenant_storage_transactions (tenant_id, created_at DESC);
```

流水类型：

```text
knowledge_upload
knowledge_index
faq_import
manual_knowledge
delete_release
quota_set
subscription_apply
storage_addon
reconcile_adjust
```

### 5.5 存储包发放记录

支付购买存储包后，不能只更新 `tenants.storage_quota`。需要记录每次购买发放，便于幂等、审计、退款人工核对和后续套餐降级计算。

```sql
CREATE TABLE tenant_storage_addon_grants (
    id VARCHAR(36) PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id BIGINT NOT NULL,
    order_no VARCHAR(64) NOT NULL UNIQUE,
    actor_user_id VARCHAR(36) NOT NULL,
    storage_quota_bytes BIGINT NOT NULL,
    effective_at TIMESTAMP WITH TIME ZONE NOT NULL,
    expires_at TIMESTAMP WITH TIME ZONE,
    status VARCHAR(32) NOT NULL DEFAULT 'active',
    snapshot_json JSONB NOT NULL DEFAULT '{}',
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_tenant_storage_addon_grants_tenant
    ON tenant_storage_addon_grants (tenant_id, status, expires_at);
```

规则：

- `order_no` 唯一，支付平台重复通知时不会重复加存储。
- V1 建议存储包长期有效；若运营设置 `expires_at`，到期只影响新增写入，不自动删除历史文件。
- 工作区总存储额度 = 当前套餐额度 + 有效存储包额度 + SystemAdmin 手工调额。

## 6. 积分设计

### 6.1 积分单位

对用户展示整数积分，数据库用微积分避免小数误差：

```text
1 积分 = 1,000,000 point_micros
```

所有扣费、赠送、充值和周期额度字段使用 `BIGINT` 存 `point_micros`。

### 6.2 积分来源与用量口径

积分来源分两类：

| 类型 | 字段 | 生命周期 | 用途 |
| --- | --- | --- | --- |
| 周期积分 | `tenant_subscriptions.period_credit_point_micros` | 当前订阅周期内有效，到期重置 | 套餐包含额度 |
| 余额积分 | `tenant_credit_accounts.balance_point_micros` | 长期有效，除非运营设置过期 | 充值、赠送、超额扣费 |

用量对用户展示和授权时分两类：

| 用量口径 | 工作区 | 来源 | 消耗人 | 管理人 |
| --- | --- | --- | --- | --- |
| `personal_usage` | 个人工作区 | 个人版周期积分、个人充值余额 | 个人工作区 Owner | 本人 |
| `enterprise_usage` | 企业工作区 | 企业版周期积分和企业长期余额组成的企业资源池 | 企业成员本人 | 企业 Owner/Admin |

个人版：

- 个人工作区内的付费调用只消耗 `personal_usage`。
- 加入企业后，在企业工作区内的调用不消耗个人用量。
- 个人充值余额不能自动转入企业，也不能被企业管理员分配。

企业版：

- 企业订阅周期积分和充值、赠送形成的长期余额都属于企业工作区，不拆分为成员余额账户。
- 企业管理页面配置默认成员每月积分上限，以及统一的超额策略。
- 成员可以继承企业默认上限，也可以由 Owner/Admin 设置自定义上限或不限制。
- 企业成员在企业工作区内的付费调用消耗企业资源池，账本按 `actor_user_id` 记录实际使用人，并保存当时生效的成员策略快照。
- 成员月度用量达到上限，或企业周期积分池耗尽时，按照企业超额策略决定是拒绝调用，还是继续扣企业长期余额。
- 企业存储容量属于企业工作区共享池，不向成员拆分存储份额。

消耗顺序：

```text
personal_usage:
  个人周期积分 -> 个人余额积分 -> 拒绝付费调用

enterprise_usage:
  校验成员本月已用量和有效月度上限
    -> 企业本月套餐积分
    -> 超额策略=use_enterprise_balance 时扣企业长期余额
    -> 超额策略=block 或企业余额不足时拒绝付费调用
```

兼容说明：

- `enterprise_allocated_usage` 作为历史枚举值保留一个迁移周期，新账本统一写 `enterprise_usage`。
- 旧能力键 `billing.enterprise_allocation_manage` 作为 `billing.enterprise_usage_policy_manage` 的兼容别名保留，待所有工作区完成迁移后再移除。
- 数据库中的 `allocation_id` 暂时保留，改为记录本次调用命中的成员策略记录；新 DTO 使用 `member_policy_id` 命名。

### 6.5 用量定价与积分换算

新增模型价格表，并仅为 MCP 工具调用保留独立的服务价格表。所有带模型的调用统一按模型 Token 计费，不再叠加服务调用费；MCP 工具调用没有模型时按次计费。模型和 MCP 服务表保存上游基础成本，积分通过统一换算规则计算，不为每个模型单独维护一套不可追溯的积分公式：

```sql
CREATE TABLE billing_model_prices (
    id VARCHAR(36) PRIMARY KEY DEFAULT uuid_generate_v4(),

    output_nanousd_per_m_tokens BIGINT NOT NULL DEFAULT 0,
    cache_read_nanousd_per_m_tokens BIGINT NOT NULL DEFAULT 0,
    cache_write_nanousd_per_m_tokens BIGINT NOT NULL DEFAULT 0,
    call_nanousd_per_call BIGINT NOT NULL DEFAULT 0,
    duration_nanousd_per_second BIGINT NOT NULL DEFAULT 0,
    tiered_pricing_json JSONB NOT NULL DEFAULT '{}',
    model_multiplier_ppm BIGINT NOT NULL DEFAULT 1000000,
    version INT NOT NULL DEFAULT 1,
    effective_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMP WITH TIME ZONE,
    status VARCHAR(32) NOT NULL DEFAULT 'active',
    snapshot_json JSONB,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (model_key, version)
);

CREATE TABLE billing_service_prices (
    id VARCHAR(36) PRIMARY KEY DEFAULT uuid_generate_v4(),
    service_code VARCHAR(64) NOT NULL,
    service_name VARCHAR(128) NOT NULL DEFAULT '',
    pricing_mode VARCHAR(32) NOT NULL DEFAULT 'call',
    nanousd_per_call BIGINT NOT NULL DEFAULT 0,
    nanousd_per_unit BIGINT NOT NULL DEFAULT 0,
    unit_name VARCHAR(32) NOT NULL DEFAULT '',
    service_multiplier_ppm BIGINT NOT NULL DEFAULT 1000000,
    version INT NOT NULL DEFAULT 1,
    effective_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMP WITH TIME ZONE,
    status VARCHAR(32) NOT NULL DEFAULT 'active',
    snapshot_json JSONB,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (service_code, version)

```

单位和倍率：

```text
1 USD = 1,000,000,000 nanousd
1 积分 = 1,000,000 point_micros
1000000 ppm = 1.0 倍
```

SystemAdmin 全局配置：

```text
billing.point_micros_per_usd
billing.default_model_multiplier_ppm
billing.default_service_multiplier_ppm
```

套餐可以通过 `billing_plans.billing_multiplier_ppm` 设置套餐级倍率。模型和服务先分别应用各自倍率，再统一应用套餐倍率，避免把多个服务项重复乘模型倍率。最终计费公式：

```text
model_base_cost_nanousd =
  round_half_up(input_tokens * input_nanousd_per_m_tokens / 1,000,000)
  + round_half_up(cache_read_tokens * cache_read_nanousd_per_m_tokens / 1,000,000)
  + round_half_up(cache_write_tokens * cache_write_nanousd_per_m_tokens / 1,000,000)
  + round_half_up((output_tokens + reasoning_tokens) * output_nanousd_per_m_tokens / 1,000,000)
  + call_count * call_nanousd_per_call
  + duration_seconds * duration_nanousd_per_second

service_base_cost_nanousd =
  mcp_tool_call_count * mcp_nanousd_per_call

base_cost_nanousd =
  model_base_cost_nanousd + service_base_cost_nanousd

rated_model_cost_nanousd =
  round_half_up(model_base_cost_nanousd * effective_model_multiplier_ppm / 1,000,000)

rated_service_cost_nanousd =
  sum(
    round_half_up(
      each service raw cost * effective_service_multiplier_ppm / 1,000,000
    )
  )

rated_cost_nanousd =
  round_half_up(
    (rated_model_cost_nanousd + rated_service_cost_nanousd)
    * plan_multiplier_ppm / 1,000,000
  )

billed_point_micros =
  ceil(rated_cost_nanousd * point_micros_per_usd / 1,000,000,000)
```

规则：

- `reasoning_tokens` 默认并入输出 Token 计费；供应商提供独立价格时再新增独立价格字段。
- `tiered` 根据输入侧 Token 总量选择价格档位，档位和单价必须写入快照。
- 模型或服务记录未设置倍率时使用 SystemAdmin 全局默认倍率；账本快照必须记录最终采用的倍率来源和值。
- 最终积分使用向上取整，避免极小用量长期不扣积分；各成本分项使用四舍五入到纳美元。
- 调价创建新版本，不覆盖历史版本；账本按调用时生效版本写入完整快照。
- 模型或服务未找到有效定价时，`observe` 模式记录异常但不阻断，`enforce` 模式拒绝付费调用。
- 运营后台只配置结构化单价、倍率和阶梯，不提供任意代码或数学表达式编辑器。

### 6.6 用量预留

借鉴 DEEIX-Chat 的 `UsageReservation`，在上游调用前预留预算，避免并发透支：

```sql
CREATE TABLE tenant_usage_reservations (

    reserved_balance_point_micros BIGINT NOT NULL DEFAULT 0,
    period_limit_point_micros BIGINT NOT NULL DEFAULT 0,
    period_start_at TIMESTAMP WITH TIME ZONE,
    period_end_at TIMESTAMP WITH TIME ZONE,
    status VARCHAR(32) NOT NULL DEFAULT 'active',
    usage_ledger_id VARCHAR(36),
    expires_at TIMESTAMP WITH TIME ZONE NOT NULL,
    settled_at TIMESTAMP WITH TIME ZONE,
    released_at TIMESTAMP WITH TIME ZONE,
    reconciliation_at TIMESTAMP WITH TIME ZONE,
    failure_code VARCHAR(64) NOT NULL DEFAULT '',
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP
);

    ON tenant_usage_reservations (tenant_id, ref_no);

CREATE INDEX idx_tenant_usage_reservations_active
    ON tenant_usage_reservations (tenant_id, status, expires_at);
```

预留规则：

1. 为每次模型/服务调用生成 `ref_no`。
2. 根据模型、工具、输入规模预估积分。
3. 按 active tenant 解析 `usage_scope`。
4. 企业工作区必须解析成员当前有效的月度使用策略，并聚合当前周期成员已用积分。
5. 同一事务锁定企业订阅周期额度、企业积分账户和成员月度使用策略，避免并发请求越过成员上限或企业总额。
6. 企业调用先占用企业周期积分；成员达到月度上限或企业周期积分不足时，再根据企业超额策略决定是否预留企业长期余额。
7. 超额策略为 `block`，或企业长期余额不足时，拒绝请求。
8. 调用成功后按真实用量结算。
9. 调用未产生上游费用时释放预留。
10. 上游已产生费用但结算失败时进入 `reconciliation`。

### 7.4 支付渠道设置

参考 DEEIX-Chat 的 `billing.payment_providers`、`epay_gateway_url`、`epay_types` 设计，Ruile 支付配置放在现有 `system_settings`，由 SystemAdmin 管理。生产环境优先使用支付宝、微信支付原生通道；需要快速接入聚合支付时，可保留 EPay 兼容通道。

推荐配置键：

| key | 类型 | 密钥 | 说明 |
| --- | --- | --- | --- |
| `billing.payment_providers` | string_list | 否 | 启用渠道：`alipay`、`wechat_pay`、`epay` |
| `billing.public_api_base_url` | string | 否 | 拼接异步通知地址，生产必须是 HTTPS |
| `billing.public_web_base_url` | string | 否 | 拼接支付成功/取消后的前端返回地址 |
| `billing.display_currency` | string | 否 | V1 固定 `CNY` |
| `billing.alipay_gateway_url` | string | 否 | 默认 `https://openapi.alipay.com/gateway.do` |
| `billing.alipay_app_id` | string | 否 | 支付宝应用 ID |
| `billing.alipay_private_key` | string | 是 | 应用私钥，RSA2 签名 |
| `billing.alipay_public_key` | string | 是 | 支付宝公钥或证书公钥 |
| `billing.alipay_seller_id` | string | 否 | 可选，用于回调校验收款账号 |
| `billing.wechat_app_id` | string | 否 | 微信支付 AppID |
| `billing.wechat_mch_id` | string | 否 | 微信支付商户号 |
| `billing.wechat_api_v3_key` | string | 是 | 微信支付 API v3 密钥 |
| `billing.wechat_private_key` | string | 是 | 商户私钥 |
| `billing.wechat_serial_no` | string | 否 | 商户证书序列号 |
| `billing.wechat_platform_cert` | string | 是 | 微信支付平台证书或证书缓存引用 |
| `billing.epay_gateway_url` | string | 否 | 兼容易支付 `submit.php` 网关 |
| `billing.epay_pid` | string | 否 | 易支付商户 ID |
| `billing.epay_key` | string | 是 | 易支付商户密钥 |
| `billing.epay_types` | string | 否 | JSON 字符串，默认 `[{"name":"支付宝","type":"alipay"},{"name":"微信支付","type":"wxpay"}]` |

配置规则：

- `billing.payment_providers` 为空或 `disabled` 时，前端隐藏在线支付入口，只允许 SystemAdmin 手工开通或调额。
- 启用 `alipay` 时，必须同时配置 `alipay_app_id`、`alipay_private_key`、`alipay_public_key`；生产要求 `billing.public_api_base_url` 为 HTTPS。
- 启用 `wechat_pay` 时，必须同时配置 `wechat_app_id`、`wechat_mch_id`、`wechat_api_v3_key`、`wechat_private_key`、`wechat_serial_no`；生产要求 `billing.public_api_base_url` 为 HTTPS。
- 启用 `epay` 时，必须同时配置 `epay_gateway_url`、`epay_pid`、`epay_key`、`epay_types`。
- 支付密钥不能通过普通 settings 列表明文返回；现有 `system_settings.is_secret` 需要真正用于服务端脱敏和前端“留空表示不修改”的交互，生产环境建议再做数据库加密或只从环境变量/KMS 注入。

支付通知地址：

```text
POST /api/v1/billing/payments/alipay/notify
POST /api/v1/billing/payments/wechat/notify
GET  /api/v1/billing/payments/epay/notify
POST /api/v1/billing/payments/epay/notify
```

协议校验要点：

- 支付宝：下单使用 `alipay.trade.page.pay` 或 `alipay.trade.precreate`；异步通知校验 RSA2 签名、`app_id`、`out_trade_no`、`trade_status`、`total_amount` 和可选 `seller_id`，只有 `TRADE_SUCCESS` / `TRADE_FINISHED` 可以发放权益。
- 微信支付：V1 优先 `transactions/native` 二维码；异步通知校验 `Wechatpay-Signature`、`Wechatpay-Timestamp`、`Wechatpay-Nonce`、`Wechatpay-Serial`，用 API v3 密钥解密 `resource`，校验 `trade_state=SUCCESS`、`out_trade_no`、`amount.payer_total`、`mchid` 和 `appid`。
- EPay：沿用 DEEIX-Chat 的 `submit.php` 页面跳转和 MD5 签名模式，`type` 从 `epay_types` 中选择 `alipay` 或 `wxpay`。
- 所有渠道都必须以 `billing_payment_orders` 的金额、币种、订单号和状态为准；任何第三方扩展字段只写入快照，不作为前端可控权益。

### 7.5 购买商品表

套餐价格仍使用 `billing_prices`。一次性购买积分和存储包使用独立商品表，前端只提交 `item_id`，价格和权益以后端配置为准。

```sql
CREATE TABLE billing_purchase_items (
    id VARCHAR(36) PRIMARY KEY DEFAULT uuid_generate_v4(),
    code VARCHAR(64) NOT NULL UNIQUE,
    item_type VARCHAR(32) NOT NULL,
    edition_scope VARCHAR(32) NOT NULL DEFAULT 'all',
    name VARCHAR(128) NOT NULL,
    description VARCHAR(512) NOT NULL DEFAULT '',
    currency VARCHAR(16) NOT NULL DEFAULT 'CNY',
    amount_cents BIGINT NOT NULL DEFAULT 0,
    credit_point_micros BIGINT NOT NULL DEFAULT 0,
    storage_quota_bytes BIGINT NOT NULL DEFAULT 0,
    duration_days INT NOT NULL DEFAULT 0,
    status VARCHAR(32) NOT NULL DEFAULT 'active',
    sort_order INT NOT NULL DEFAULT 0,
    metadata_json JSONB NOT NULL DEFAULT '{}',
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_billing_purchase_items_type_status
    ON billing_purchase_items (item_type, edition_scope, status, sort_order);
```

商品类型：

```text
topup          购买积分
storage_addon 购买存储包
```

商品规则：

- `topup` 商品必须有 `credit_point_micros > 0`，且 `storage_quota_bytes=0`。
- `storage_addon` 商品必须有 `storage_quota_bytes > 0`，且 `credit_point_micros=0`。
- `edition_scope` 控制个人版、企业版或全部可买；企业版购买入口仅 Owner/Admin 可见和可用。
- `duration_days=0` 表示长期有效；非 0 时支付成功后写入 `tenant_storage_addon_grants.expires_at`。

V1 商品示例：

| code | 类型 | 金额 | 权益 | 适用 |
| --- | --- | ---: | ---: | --- |
| `credit_10000_points` | `topup` | 99 元 | 10,000 积分 | 个人版、企业版 |
| `credit_50000_points` | `topup` | 399 元 | 50,000 积分 | 企业版 |
| `storage_20gb` | `storage_addon` | 29 元 | 20 GB | 个人版、企业版 |
| `storage_100gb` | `storage_addon` | 99 元 | 100 GB | 企业版 |

### 7.6 支付订单表

支付订单参考 DEEIX-Chat 的 `PaymentOrder`：先创建内部订单，再创建第三方收银台；回调只根据内部 `order_no` 幂等发放权益。

```sql
CREATE TABLE billing_payment_orders (
    id VARCHAR(36) PRIMARY KEY DEFAULT uuid_generate_v4(),
    order_no VARCHAR(64) NOT NULL UNIQUE,
    order_type VARCHAR(32) NOT NULL,
    tenant_id BIGINT NOT NULL,
    actor_user_id VARCHAR(36) NOT NULL,
    plan_id VARCHAR(36),
    price_id VARCHAR(36),
    item_id VARCHAR(36),
    provider VARCHAR(32) NOT NULL DEFAULT '',
    payment_method VARCHAR(32) NOT NULL DEFAULT '',
    status VARCHAR(32) NOT NULL DEFAULT 'pending',
    currency VARCHAR(16) NOT NULL DEFAULT 'CNY',
    amount_cents BIGINT NOT NULL DEFAULT 0,
    credit_point_micros BIGINT NOT NULL DEFAULT 0,
    storage_quota_bytes BIGINT NOT NULL DEFAULT 0,
    billing_interval VARCHAR(16) NOT NULL DEFAULT '',
    cycles INT NOT NULL DEFAULT 1,
    external_payment_ref VARCHAR(128) NOT NULL DEFAULT '',
    external_checkout_ref VARCHAR(128) NOT NULL DEFAULT '',
    checkout_url TEXT NOT NULL DEFAULT '',
    qr_code_url TEXT NOT NULL DEFAULT '',
    notify_url TEXT NOT NULL DEFAULT '',
    return_url TEXT NOT NULL DEFAULT '',
    provider_payload_json JSONB NOT NULL DEFAULT '{}',
    notify_snapshot_json JSONB NOT NULL DEFAULT '{}',
    paid_at TIMESTAMP WITH TIME ZONE,
    expired_at TIMESTAMP WITH TIME ZONE,
    snapshot_json JSONB NOT NULL DEFAULT '{}',
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_billing_payment_orders_tenant_created
    ON billing_payment_orders (tenant_id, created_at DESC);

CREATE INDEX idx_billing_payment_orders_status_expired
    ON billing_payment_orders (status, expired_at);
```

订单类型：

```text
subscription
topup
storage_addon
manual_contract
```

订单状态：

```text
pending
paid
failed
expired
closed
reconciliation
```

支付渠道与方法：

```text
provider=alipay      payment_method=page|qr_code|wap
provider=wechat_pay  payment_method=native|jsapi|h5
provider=epay        payment_method=alipay|wxpay
```

支付完成事务规则：

1. 根据 `order_no` 锁定 `billing_payment_orders`。
2. `status=paid` 时直接返回成功，表示重复通知已处理。
3. `status` 不是 `pending` 或订单已过期时，进入 `reconciliation` 或拒绝通知。
4. 校验第三方通知金额、币种、商户号和订单号与订单快照一致。
5. `subscription`：替换或续期 `tenant_subscriptions`，应用套餐存储和周期积分。
6. `topup`：锁定 `tenant_credit_accounts`，增加 `credit_point_micros`，写 `tenant_credit_transactions(type=topup, ref_no=order_no)`。
7. `storage_addon`：创建 `tenant_storage_addon_grants(order_no)`，增加 `tenants.storage_quota`，写 `tenant_storage_transactions(type=storage_addon, ref_no=order_no)`。
8. 同一事务把订单更新为 `paid`，写 `paid_at`、`external_payment_ref` 和回调快照。

## 8. 企业资源池与成员使用策略

企业版积分和存储都属于企业工作区。成员月度额度只控制可使用范围，不把企业积分或存储所有权划拨给成员。

企业管理页面统一展示和配置：

| 项目 | 权威来源 | 是否可在企业页面修改 |
| --- | --- | --- |
| 企业总积分余额 | `tenant_credit_accounts.balance_point_micros` | 只读展示；通过充值、赠送或 SystemAdmin 调整 |
| 企业每月套餐积分 | `tenant_subscriptions.period_credit_point_micros` | 只读展示；随套餐生效 |
| 企业总存储容量 | `tenants.storage_quota` | 只读展示；通过套餐、存储包或 SystemAdmin 调整 |
| 默认成员每月积分上限 | `tenant_billing_policies.default_member_monthly_limit_point_micros` | Owner/Admin 可修改 |
| 超额策略 | `tenant_billing_policies.member_overage_policy` | Owner/Admin 可修改 |

企业级策略表：

```sql
CREATE TABLE tenant_billing_policies (
    id VARCHAR(36) PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id BIGINT NOT NULL UNIQUE,
    default_member_monthly_limit_point_micros BIGINT NOT NULL DEFAULT 0,
    member_overage_policy VARCHAR(32) NOT NULL DEFAULT 'block',
    created_by_user_id VARCHAR(36) NOT NULL DEFAULT '',
    updated_by_user_id VARCHAR(36) NOT NULL DEFAULT '',
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (default_member_monthly_limit_point_micros >= 0),
    CHECK (member_overage_policy IN ('block', 'use_enterprise_balance'))
);
```

`member_overage_policy` 只允许：

| 值 | 行为 |
| --- | --- |
| `block` | 成员达到有效月度上限，或企业周期积分不足时，拒绝新的付费 AI 调用 |
| `use_enterprise_balance` | 允许继续调用，并从企业长期积分余额扣除；余额不足时拒绝 |

补充规则：

- 默认成员每月积分上限首发值为 `100` 积分，由套餐 `limits_json` 写入企业策略。
- 企业策略中的默认上限为 `0` 时，继承该策略的成员不能发起新的付费 AI 调用，不表示无限额。
- 旧系统设置 `billing.default_member_allocation_points` 在兼容期映射为 `billing.default_member_monthly_limit_points`，新代码不再写旧键。
- Owner/Admin 修改默认上限或超额策略必须记录修改前后值、操作人和企业工作区的审计日志。

成员策略继续复用已经落地的 `tenant_member_credit_allocations` 表名，避免破坏线上迁移，但其业务含义改为“成员月度使用策略”。旧的周期分配和余额分配字段进入兼容状态，不再作为新功能的权威字段。

```sql
ALTER TABLE tenant_member_credit_allocations
    ADD COLUMN limit_mode VARCHAR(32) NOT NULL DEFAULT 'inherit',
    ADD COLUMN monthly_limit_point_micros BIGINT NOT NULL DEFAULT 0,
    ADD COLUMN overage_policy VARCHAR(32) NOT NULL DEFAULT 'inherit',
    ADD CONSTRAINT chk_member_limit_mode
        CHECK (limit_mode IN ('inherit', 'custom', 'unlimited')),
    ADD CONSTRAINT chk_member_monthly_limit
        CHECK (monthly_limit_point_micros >= 0),
    ADD CONSTRAINT chk_member_overage_policy
        CHECK (overage_policy IN ('inherit', 'block', 'use_enterprise_balance'));
```

规则：

- `limit_mode=inherit`：使用企业默认成员每月积分上限。
- `limit_mode=custom`：使用 `monthly_limit_point_micros`。
- `limit_mode=unlimited`：不设置成员个人月度上限，但仍受企业周期积分、企业长期余额和超额策略限制。
- `overage_policy=inherit`：使用企业统一超额策略；V1 不开放成员级覆盖，预留该字段仅用于兼容后续合同客户。
- 成员已用量从 `tenant_usage_ledgers` 按 `usage_scope='enterprise_usage'`、`tenant_id`、`actor_user_id` 和当前订阅周期聚合，不依赖前端传值。
- `allocated_period_point_micros` 和 `allocated_balance_point_micros` 标记为 legacy，新接口不再写入；历史记录迁移时将两者之和写入 `monthly_limit_point_micros`，有历史额度的记录设为 `custom`，无历史额度的记录设为 `inherit`。
- 企业总消耗始终受 `tenant_subscriptions.period_credit_point_micros` 和 `tenant_credit_accounts.balance_point_micros` 限制，成员策略不能让企业总账透支。
- 企业存储始终使用 `tenants.storage_quota/storage_used`，V1 不增加成员存储分配字段。
- Owner/Admin 可以查看企业总额、成员用量和成员策略；Contributor/Viewer 只能查看自己的本月用量和有效上限。

## 9. 核心流程

### 9.1 注册个人版

```text
用户注册
  -> 创建 users
  -> 自动创建 personal tenant
  -> 创建 owner tenant_member
  -> 创建 tenant_credit_account
  -> 创建 personal_free subscription
  -> 应用套餐 storage_quota
  -> 返回 /auth/me 的 edition + subscription + storage + credits
```

所有账号入口必须一致：

- 公开注册；
- 管理员创建账号；
- 邀请注册；
- OIDC 首次登录；
- 历史 tenantless 账号修复。

### 9.2 购买/升级个人版

```text
GET /billing/plans?edition=personal
  -> 选择价格
  -> 创建 subscription 支付单
  -> 支付回调幂等确认
  -> 替换当前 personal tenant 的 active subscription
  -> 写入周期积分和存储额度
  -> 返回最新 billing overview
```

约束：

- 只能为自己的个人工作区购买个人版套餐。
- 不能通过个人套餐打开企业成员、共享空间和企业发布能力。
- 升级立即生效；降级到期生效。

### 9.3 开通企业版

```text
个人 Owner 点击开通企业
  -> 创建 enterprise tenant
  -> 创建 owner tenant_member
  -> 创建 tenant_credit_account
  -> 创建 enterprise_trial 或 enterprise_team subscription
  -> 应用企业存储和每月套餐积分
  -> 创建 tenant_billing_policy
  -> 为 Owner 创建 inherit 成员策略
  -> 初始化默认存储、知识库默认配置
  -> 返回可切换工作区
```

不做的事：

- 不改变个人工作区订阅。
- 不迁移个人知识库。
- 不把个人知识库自动共享给企业。
- 不把员工个人积分并入企业。

### 9.4 企业续费/升级

企业 Owner/Admin 可发起订阅变更：

- 升级：立即应用新能力、新成员数、新存储和新周期积分。
- 降级：默认到当前周期结束后生效；如果强制立即降级，必须先校验成员数、存储、API Key、共享空间、Agent 数量等是否超限。
- 续费：延长 `current_period_end_at` 或创建下一段连续订阅。
- 取消自动续费：设置 `cancel_at_period_end=true`，到期变为 `expired` 或回到免费/试用策略。

企业员工不能变更企业订阅，除非其角色是 Owner/Admin 且套餐能力允许。

### 9.5 支付下单通用流程

```text
用户选择购买积分或存储包
  -> 前端读取 /billing/payment-config 和可购买商品
  -> 提交 item_id + payment_provider + payment_method
  -> 后端按 active tenant 判断购买主体
  -> 校验套餐状态、角色权限、商品 edition_scope 和支付配置
  -> 创建 billing_payment_orders(status=pending)
  -> 调用支付宝/微信支付/EPay 创建收银台
  -> 保存 checkout_url / qr_code_url / provider_payload_json
  -> 前端跳转收银台或展示二维码
  -> 支付平台异步 notify
  -> 校验签名、商户、金额、币种、订单号和状态
  -> 同一事务标记 paid 并发放积分或存储
  -> 前端轮询订单状态并刷新 billing overview
```

购买主体规则：

- 个人工作区：本人可以为自己的个人工作区购买积分和允许的存储包。
- 企业工作区：仅 Owner/Admin 可以为企业工作区购买积分、存储包和订阅；普通成员只能查看自己的企业用量和有效月度上限。
- 前端不能传入金额、积分数或存储字节数作为权威值，只能传 `item_id`；后端从 `billing_purchase_items` 或 `billing_prices` 生成订单快照。
- 支付成功权益发放只认异步 notify；前端 return URL 只能展示“支付结果确认中”，不能直接发放。

### 9.6 购买积分

```text
创建 topup 订单
  -> 选择支付宝或微信支付
  -> 支付成功
  -> 锁定 tenant_credit_account
  -> balance_point_micros += order.credit_point_micros
  -> 写 tenant_credit_transactions(type=topup)
  -> 返回新余额
```

充值积分属于当前订阅主体：

- 在个人工作区充值，只能个人使用；
- 在企业工作区充值，进入企业总积分余额；只有超额策略允许时才用于成员超额调用；
- 不在个人和企业之间自动转移。

### 9.7 购买存储包

```text
创建 storage_addon 订单
  -> 选择支付宝或微信支付
  -> 支付成功
  -> 锁定 tenant 行
  -> 创建 tenant_storage_addon_grants(order_no 唯一)
  -> tenants.storage_quota += order.storage_quota_bytes
  -> 写 tenant_storage_transactions(type=storage_addon)
  -> 返回新存储额度
```

购买存储包的约束：

- 个人版是否允许购买存储包由商品 `edition_scope` 和产品策略控制。
- 企业版购买存储包只增加企业工作区存储，不增加员工个人工作区存储。
- 重复支付通知必须命中同一个 `order_no`，不能重复加存储。
- 如果购买前已处于 `storage_over_quota`，支付成功后重新计算状态；仍超额则继续阻断新增写入。

### 9.8 AI 调用扣积分

```text
解析 active tenant
  -> 校验套餐状态和功能
  -> 解析 usage_scope: personal_usage | enterprise_usage
  -> 企业场景解析企业策略、成员有效月度上限和本月已用量
  -> 解析模型/服务定价
  -> 估算本次积分
  -> 创建 tenant_usage_reservation
  -> 调用模型/服务
  -> 计算真实积分
  -> 写 tenant_usage_ledger
  -> 企业场景先扣企业周期积分，按超额策略决定是否扣企业长期余额
  -> 释放/结算 reservation
```

失败处理：

- 用户取消且上游未产生费用：释放预留，不写扣费账本。
- 上游返回可计费用量但前端断连：继续结算账本。
- 上游费用已产生但账本写入失败：reservation 进入 `reconciliation`，后台补偿。
- 幂等重试必须复用 `ref_no`，不能重复扣积分。

### 9.9 知识库上传扣存储与积分

知识库上传同时涉及存储和积分：

```text
校验 KB 写权限
  -> 校验套餐允许知识库上传
  -> 预留存储
  -> 保存原始文件
  -> 创建 knowledge
  -> 解析/切片/向量化
  -> 对 OCR/ASR/Embedding/摘要/图谱等计积分
  -> 结算 storage_used
  -> 写 usage_ledger 和 storage_transaction
```

重要边界：

- 存储不足阻断上传或重解析。
- 积分不足可以阻断需要 AI 的处理步骤；若原始文件已经上传，状态应明确为 `failed` 或 `pending_payment`，不能伪装成解析失败。
- 纯文本入库如果不调用付费模型，可以只计存储不扣积分。

## 13. 后端接入点

### 13.1 鉴权顺序

所有会产生权益或消耗的请求按此顺序：

```text
JWT / API Key 认证
  -> 解析 active tenant
  -> 验证 tenant_members / API Key principal
  -> 解析 subscription + entitlements
  -> 解析 usage_scope、企业策略和成员有效月度上限
  -> 校验 feature / limit / quota
  -> 资源级权限校验
  -> 预留积分或存储
  -> 执行业务
  -> 结算账本
```

注意：

- 资源级权限不能被订阅绕过。
- 订阅状态不能被前端请求体覆盖。
- API Key 的扣费主体是 key 所属工作区，账本 `actor_user_id` 可记录 synthetic principal 或创建人。

### 13.2 知识库链路

需要接入：

- 创建知识库；
- 文件上传；
- URL 导入；
- FAQ 导入；
- 手工知识发布；
- 重解析；
- 知识图谱提取；
- 摘要和问题生成；
- 删除和批量删除释放存储；
- 复制/移动知识时重新校验目标工作区存储和积分。

### 13.3 会话/Agent 链路

需要接入：

- 普通问答；
- Agent 问答；
- 临时文件问答；
- IM/Embed 渠道问答；
- 原生工具调用；
- MCP 工具调用；
- Web Search；
- 模型调试接口。

每次调用都应产生同一类 `tenant_usage_ledger`，方便企业总览和成员排行复用。

### 13.4 支付链路

支付回调路由必须挂在公开 API 下，不要求用户登录，但不能绕过业务校验：

```text
公开 notify
  -> 限制请求体大小和回调频率
  -> 读取支付渠道配置
  -> 验签和解密
  -> 校验商户、金额、币种、订单号和支付状态
  -> 锁定 billing_payment_orders
  -> 幂等发放订阅、积分或存储
  -> 写审计和 notify_snapshot_json
  -> 返回支付平台要求的成功响应
```

支付链路必须保证：

- 第三方回调不能携带或覆盖 `tenant_id`、`actor_user_id`、`credit_point_micros`、`storage_quota_bytes`。
- 支付宝/微信的同步返回 URL 只用于展示，不作为发放依据。
- 订单过期后即使收到迟到回调，也进入 `reconciliation`，由 SystemAdmin 人工核对。
- 支付平台的订单号、流水号、交易状态和原始金额写入 `notify_snapshot_json`，用于后续对账。

## 14. 数据迁移

### 14.1 迁移顺序

1. 步骤一新增套餐、价格、订阅、积分账户和积分流水表，并加入 `billing.enabled`、`billing.enforcement_mode` 等默认关闭配置。
2. 为所有现有 `tenants` 创建 `tenant_credit_accounts`。
3. 根据 `space_type` 或现有分类，为工作区创建默认订阅：
   - `personal` -> `personal_free`
   - `organization` -> `enterprise_team` 或 `enterprise_trial`
   - 未分类 -> `legacy` 兼容订阅，后台待分类
4. 将现有 `tenants.storage_quota` 作为迁移初始额度，不强行覆盖。
5. 从 `knowledges.storage_size` 汇总校验 `tenants.storage_used`，只输出差异报告；生产环境不自动修正。
6. 上线后所有账号创建路径和后台企业开通路径必须立即创建订阅和积分账户。
7. 步骤二 A 先新增模型定价、用量预留和用量账本，仅接入主会话最终模型调用；步骤二 B 再新增服务定价、企业资源策略、成员月度上限、其他 AI 调用链和存储流水。
8. 步骤二 A 先以 `observe` 运行并核对真实 Token、价格快照和积分公式；个人工作区通过核对后才允许切换 `enforce`。企业工作区在步骤二 B 完成企业策略、成员月度上限和超额处理前保持 `observe`。
9. 为企业工作区创建 `tenant_billing_policies`；默认成员上限来自套餐 `limits_json`，超额策略默认 `block`。
10. 扩展历史 `tenant_member_credit_allocations`：旧周期额度与旧余额额度之和迁移为自定义月度上限；两者均为零时迁移为 `inherit`，不删除旧字段。
11. 步骤三新增购买商品、支付订单和存储包发放表，历史订阅和历史积分不通过支付迁移重建。
12. 后台完成 `legacy` 分类且订阅、账本和支付状态均可追溯后，再逐步关闭旧字段的权威写入。

### 14.2 不允许的迁移

- 不修改 `knowledge_bases.tenant_id`。
- 不移动或复制对象存储文件。
- 不重写向量库和资源注册路径。
- 不将员工个人工作区合并到企业。
- 不把知识库快捷订阅迁移成套餐订阅。
- 不删除超出新套餐额度的历史文件。

### 14.3 兼容策略

- 没有订阅记录的工作区，后端创建默认免费/legacy 订阅后再返回能力。
- 订阅服务异常时，涉及付费或企业能力的写操作默认拒绝；读操作可以按历史权限降级展示。
- `storage_quota <= 0` 目前有“不限制”的语义，订阅上线后只允许 SystemAdmin 设置，普通工作区套餐不得使用无限额。

## 15. 三步实施计划

全部 PRD 功能分三步完成。每一步必须独立提交、独立部署、独立回滚；当前步骤验收通过后，才能进入下一步。

通用实施门禁：

- 数据库只做向前兼容的增量迁移，不删除旧字段和旧接口。
- 新字段追加到现有响应，旧客户端不依赖新字段也能继续运行。
- `billing.enabled` 默认关闭；`billing.enforcement_mode` 支持 `off`、`observe`、`enforce`。
- `observe` 只记录能力决策；步骤二接入定价后再计算模拟用量，任何步骤都不因订阅、企业余额或成员月度上限不足阻断历史用户。
- 每一步都必须包含迁移、后端、前端、Admin、自动化测试、监控和回滚说明。
- 从 DEEIX-Chat 移植的代码必须同时提交来源记录、许可证说明和对应测试。

### 步骤一：账单基础、源码移植与兼容上线

明确功能：

   - `base_cost_nanousd` 记录上游成本；

10. SystemAdmin 提供套餐、价格、工作区订阅和积分账户的只读列表；人工调额必须写审计。
11. 保留现有 `enterprise_credits` 作为兼容字段，只读映射到新账户展示，不再作为新的权威写入来源。
12. `billing.enforcement_mode=off|observe`；本步骤的 `observe` 只记录订阅、套餐能力解析、缺失订阅和兼容映射结果，不计算或扣减实际用量积分。

验收标准：

- 新注册、管理员创建、邀请注册、OIDC 首次登录都能得到个人工作区、Owner、默认订阅和积分账户。
- 后台重复提交同一用户的企业开通请求，不会创建重复企业、订阅、积分账户或 Owner 关系。
- 所有历史工作区 backfill 可重复执行，重复执行不增加重复记录。
- 新旧工作区调用 `/billing/overview` 都返回稳定结构；缺失或 `legacy` 订阅不会导致前端崩溃。
- 个人工作区返回个人套餐，企业工作区返回企业套餐；切换工作区后概览同步切换。
- 关闭 `billing.enabled` 后，现有注册、登录、工作区切换、知识库、会话和企业成员功能行为与上线前一致。
- `observe` 模式能够记录套餐能力解析、缺失订阅和兼容映射审计，但不会计算实际用量积分、扣积分或拒绝请求。

- `THIRD_PARTY_NOTICES.md` 和 DEEIX-Chat 移植记录完整，移植算法测试全部通过。
- 数据迁移、默认套餐 seed、后台开通企业和 `/billing/overview` 后端测试通过；主前端与 Admin 类型检查和构建通过。

### 步骤二：用量闭环

步骤二保留为三步总计划中的一个步骤，但拆成 2A 和 2B 两个独立验收门。2A 验收通过前不得开始 2B；2B 验收通过前不得进入支付步骤。

#### 步骤二 A：聊天模型定价与积分账本

目标：先把最清晰、最容易核对的主会话最终模型调用做成闭环，验证模型价格、真实 Token、积分公式、快照、幂等和个人工作区余额结算。

明确功能：

1. 新增 `billing_model_prices`，本阶段运行时支持 `token`、`call`、`duration`；`tiered` 字段保留到步骤二 B 启用。
2. 模型价格按 `model_key + version` 版本化。调价只能创建新版本，不能覆盖历史账本使用的价格快照。
3. SystemAdmin 可配置模型、供应商、输入/输出/缓存读取单价、按次单价、按秒单价、模型倍率和生效时间。
4. 增加套餐倍率 `billing_plans.billing_multiplier_ppm` 和全局配置 `billing.default_model_multiplier_ppm`。
5. 实现模型成本计算：
   - Prompt Token 中的缓存命中部分按缓存读取价格计算；
   - 未缓存 Prompt Token 按输入价格计算；
   - Completion Token 按输出价格计算；
   - 成本分项四舍五入到 `nanousd`；
   - 最终积分向上取整到 `point_micros`。
6. 新增 `tenant_usage_reservations` 和 `tenant_usage_ledgers`。
7. 主会话的 `CHAT_COMPLETION` 和 `CHAT_COMPLETION_STREAM` 在最终模型调用前预估，在返回真实 Token 后结算。
8. `off` 不查询价格、不写账本；`observe` 写真实用量和价格快照但不占用、不扣减、不拒绝；`enforce` 仅对个人工作区启用预留和结算。
9. 企业工作区在步骤二 B 的企业策略和成员月度上限完成前，即使全局设置为 `enforce`，本阶段也降级为 `observe`，不得直接从企业总账户扣成员用量。
10. 缺失模型价格时，`observe` 写 `unpriced` 账本并继续请求；个人工作区 `enforce` 在上游调用前拒绝。
11. 个人工作区 `enforce` 按“周期积分 -> 余额积分”预留；余额不足时拒绝。真实费用超过预留且剩余额度不足时写 `reconciliation`，不得把账户扣成负数。
12. SystemAdmin 提供模型定价配置和全量用量账本；当前工作区可查看自己的最近用量。

验收标准：

- 固定输入 Token、缓存 Token、输出 Token、调用次数、耗时和倍率时，测试结果确定且可重复。
- `base_cost_nanousd`、`rated_cost_nanousd`、`billed_point_micros` 可由账本 `pricing_snapshot_json` 完整重算。
- Prompt Token 不会与缓存读取 Token 重复计费。
- 调价后新请求使用新版本，历史账本仍引用旧版本和旧快照。
- 非流式和流式主会话均能在最终模型返回真实 Token 后生成一条账本。
- 相同 `tenant_id + ref_no` 重试不会重复预留、扣积分或写账本。
- `off` 与上线前行为一致；`observe` 不扣积分、不拒绝；个人工作区 `enforce` 余额不足时在上游调用前拒绝。
- 企业工作区不会在本阶段错误消耗企业总余额，账本明确记录 `enterprise_policy_pending` 降级原因。
- 上游调用失败且未产生费用时释放预留；已产生费用但无法结算时进入 `reconciliation`。
- SystemAdmin 可新建模型价格版本并查看账本；普通工作区不能读取其他工作区账本。
- 数据库迁移、计算、价格版本、预留、结算、幂等、插件接入、接口和 Admin 构建测试通过。

#### 步骤二 B：服务、企业资源池和存储闭环

目标：在 2A 的模型计费内核验收后，扩展到服务项、企业资源池、成员月度使用策略、全部 AI 调用链和存储。

明确功能：

1. 启用 `billing_service_prices`，仅覆盖 `mcp.tool_call` 按次定价；其他 AI 能力均按实际模型 Token 计费。
2. 新增 `tenant_billing_policies`，统一保存默认成员每月积分上限和企业超额策略。
3. 扩展 `tenant_member_credit_allocations` 为成员使用策略，支持 `inherit/custom/unlimited`；停止新增成员余额分配。
4. 企业调用必须解析有效成员策略，按“企业套餐周期积分 -> 根据超额策略使用企业长期余额”结算。
5. Agent、Embedding、Rerank、OCR/ASR、摘要、问题生成、知识图谱、Web Search、MCP、IM 和 Embed 接入统一账本。
6. 新增 `tenant_storage_reservations`、`tenant_storage_transactions`，上传、重解析、复制、移动和删除接入企业共享存储闭环。
7. 主前端增加个人/企业成员用量明细；企业 Owner/Admin 增加企业资源总览、成员排行、默认策略和成员策略管理。
8. SystemAdmin 增加服务定价、存储流水和待核对处理。

验收标准：

- MCP 工具调用按次计费，其他模型调用只按模型 Token 计费，不会叠加服务费用。
- 企业积分不会预先拆分到成员账户，企业总周期积分和总余额与成员用量聚合一致。
- `inherit` 成员跟随企业默认上限，`custom` 使用个人上限，`unlimited` 仅取消个人上限且不能绕过企业总额。
- 超额策略为 `block` 时，在上游调用前拒绝；为 `use_enterprise_balance` 时，先耗尽企业周期积分再扣企业长期余额。
- 并发调用不会越过成员有效上限，也不会使企业周期积分或企业长期余额透支。
- 会话、Agent 和知识库处理三类主链路均生成完整账本。
- 并发上传不会超过配额；删除释放存储；超额只阻断新增。
- 企业存储始终按企业共享池计算，成员策略中没有独立存储分配字段。
- Owner/Admin、普通成员和 SystemAdmin 的用量与策略权限测试通过。
- `observe` 差异未解释前不得将对应工作区切换为 `enforce`。

### 步骤三：订阅支付、商品购买与运营后台

目标：完成套餐变更、积分/存储购买、支付回调、企业运营和全量商业化闭环。

#### 当前实施边界（2026-09-18）

当前部署没有可用的在线支付渠道，因此第三步先交付离线运营闭环，不在用户侧展示购买、收银台或支付回调入口：

1. 已启用：商品目录、人工合同开通、人工积分调额、人工存储调整、订单留痕、存储包发放记录和 SystemAdmin 审计。
2. 订单统一写入 `billing_payment_orders`，离线操作固定使用 `provider=manual`、`payment_method=system_admin`、`status=paid`；权益、流水和订单在同一事务中完成。
3. 支付宝、微信支付、EPay、用户自助购买、支付验签回调、自动续费和到期回收仍保持关闭，待商户配置、证书管理和回调验收具备后再灰度启用。
4. 禁止把离线人工订单伪装成在线付款：页面必须明确显示“人工操作”，且不能暴露任何不可用支付入口。

明确功能：

1. 实现免费、试用、月付、年付、手工合同套餐及升级、续费、降级、取消自动续费状态机。
2. 新增购买商品和支付模型：
   - `billing_purchase_items`
   - `billing_payment_orders`
   - `tenant_storage_addon_grants`
3. 订单类型支持：
   - `subscription`
   - `topup`
   - `storage_addon`
   - `manual_contract`
4. 支持 SystemAdmin 手工合同开通和人工调额，所有操作写审计。
5. 支付渠道：
   - 支付宝原生支付；
   - 微信支付 API v3；
   - EPay 作为可选兼容渠道；
   - DEEIX-Chat 的 Stripe 代码不作为国内 V1 必选范围。
6. 支付流程必须先创建内部订单，再创建第三方收银台；权益只由验签后的异步通知发放。
7. 支付回调校验签名、证书、商户、AppID、金额、币种、订单号和支付状态，并保证幂等。
8. 实现订单查询、支付中、成功、失败、过期关闭、迟到回调待核对和人工补偿。
9. 用户侧提供套餐列表、升级/续费/取消、购买积分、购买存储包、订单和账单入口。
10. 企业 Owner/Admin 可管理企业订阅、购买企业积分和存储、调整企业默认策略及成员月度上限，并导出企业账单。
11. SystemAdmin 提供套餐、价格、商品、支付配置、工作区订阅、支付订单、积分调额、模型/服务定价、用量账本和待核对页面。
12. 增加订阅到期、余额不足、存储超额、回调失败、待核对积压和账本异常告警。
13. 收口企业开通入口：普通用户开通企业必须进入试用或订单流程；后台人工开通继续作为合同/运营入口，不能产生无订阅企业。

验收标准：

- 免费、试用、月付、年付和手工合同订阅均可创建，并返回正确周期、额度、能力和状态。
- 升级立即生效；降级和取消自动续费按配置在周期结束时生效。
- 个人工作区只能购买个人商品；企业商品只能由企业 Owner/Admin 购买。
- 支付成功后，`subscription`、`topup`、`storage_addon` 分别只发放对应权益。
- 支付宝和微信支付的正常回调能够完成订单和权益发放；同步返回 URL 不发放权益。
- 重复回调、重复轮询和并发回调不会重复创建订阅、增加积分或增加存储。
- 签名、证书、商户、AppID、金额、币种或订单号不匹配时，订单不标记成功且不发放权益。
- 订单过期后的迟到成功通知进入 `reconciliation`，SystemAdmin 可以查看、处理并留下审计。
- 企业 Owner/Admin 能看到企业总用量、成员排行、成员策略和企业订单；普通成员只能看到自己的有效上限和用量。
- SystemAdmin 能完成套餐、价格、商品、支付配置、订阅、订单、调额和待核对管理。
- 关闭支付渠道后，人工合同开通和已有订阅继续可用，不影响历史订单和账本查询。
- 用户侧、企业管理员侧和 SystemAdmin 侧端到端测试通过；支付沙箱、回调幂等、状态机和权限矩阵测试通过。
- 三个步骤全部完成后，现有 `enterprise_credits` 不再作为权威余额，所有展示、扣费和调额统一读取新积分账户和账本。

- 购买商品快照和订单金额在回调后可追溯；
- 用量账本按日、成员、模型、知识库聚合准确；
- 用量账本按 `usage_scope`、`actor_user_id` 和成员策略快照聚合准确；
- 企业资源总览等于订阅周期额度、企业积分账户和工作区存储的权威值，不能由成员策略反向修改。

## 17. 风险与决策点

需要产品确认：

- 个人版是否允许付费购买额外存储包。
- 企业版周期积分是否按成员数阶梯增加，以及是否自动提高默认成员每月积分上限。
- 默认成员每月积分上限是否按角色提供预设值；V1 默认所有角色使用同一个企业默认值。
- 积分是否有过期时间。
- 免费版是否允许使用高成本模型。
- `billing.point_micros_per_usd` 的首发换算率，以及后续调整是否只影响新调用。
- 模型/服务倍率用于成本加价，套餐倍率用于套餐折扣或溢价；三类倍率的运营范围和审批规则。
- 支付宝使用电脑网页支付、扫码支付还是两者都支持。
- 微信支付 V1 使用 Native 扫码还是也支持 JSAPI/H5。
- EPay 是否作为兼容通道保留，还是只做支付宝和微信支付原生接入。

需要技术确认：

- 当前所有 AI 调用链路的统一计费切入点。
- 模型和服务基础成本的权威来源、更新责任人、审核流程和生效频率。
- V1 是否统一使用 USD 纳美元记录上游成本；非 USD 供应商成本如何按固定汇率版本换算并快照。
- 调用链返回未知模型、别名或缺失价格时，除拒绝调用外是否允许配置显式兜底价格。
- 向量索引存储估算是否足够准确，是否需要定期 reconciliation。
- 临时文件、导出文件、聊天附件是否纳入工作区存储。
- API Key 账本中的 `actor_user_id` 使用创建人还是 synthetic principal。
- `storage_quota <= 0` 的无限额语义是否继续保留。
- 支付密钥是否需要在 `system_settings` 层做数据库加密，还是全部由环境变量/KMS 注入。
- 微信支付平台证书的下载、缓存和轮换策略。

主要风险：

- 如果只做前端套餐展示，后端仍会越权或超额使用。
- 如果订阅绑定用户，企业多人协作会出现扣费主体混乱。
- 如果没有预留机制，并发调用和上传会透支积分/存储。
- 如果成员月度上限和超额策略只在前端判断，企业成员可以绕过限制直接消耗企业资源池。
- 如果支付配置只做前端校验，错误商户号或回调域名会导致订单长期 pending。
- 如果回调未校验金额和商户，可能出现小额支付发放大额权益。
- 如果没有账本快照，后续调价会导致历史对账不可追溯。
- 如果成本纳美元和用户积分混用同一字段，调价、对账和毛利分析都会失真。
- 如果自动同步 DEEIX-Chat 上游代码或价格而不经过 Ruile 适配和回归，可能破坏工作区计费、成员策略和历史快照。
- 如果把知识库订阅误当付费订阅，会混淆权限和套餐权益。

## 18. 非目标

本设计不包含：

- 发票和税务系统的具体实现；
- 退款、分账和代理商结算；
- 多级集团版/总部版；
- 个人用量和企业用量互转；
- 把企业存储容量预先拆分到成员；
- 自动删除超额文件；
- 个人知识库自动迁移到企业；
- 两套独立部署包；
- 前端绕过后端直接修改套餐能力。
