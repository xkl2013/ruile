# 调研报告：同类产品如何实现「点击记忆 → 自动调用专属整理助理」

## 1. 调研问题

> **用户在记忆列表里点一条记忆的「整理」，如何让它自动调用"专属的整理助理"，而不是让用户每次都去挑方案、写要求？**

先定义清楚三个被拆开的动作，调研就围绕它们展开：

| 动作 | 问题 | 通俗说法 |
| --- | --- | --- |
| **入口** | 用户在哪里发起整理？ | "点哪里" |
| **路由** | 系统怎么决定交给哪个助理？ | "谁来做" |
| **助理形态** | "专属助理"由什么构成？ | "它是谁" |

对应到我们的产品：**专属整理助理 ≈ 整理配置**（`organize_configs`：名称 / 指令 / 专家 / 执行周期，引用平台整理模板）。调研要回答的是：**点记忆的「整理」时，怎么让系统自动选对这条配置，而不是弹一个大选择器让用户自己挑。**

## 2. 六个产品的做法

### 2.1 Tana —— 「标签即路由」（最贴近"自动调用"）

**产品**：大纲式知识工具（tana.inc），核心抽象是 Supertag（给节点打上的结构化标签）。

- **助理形态**：每个 Supertag 可以内嵌 **AI 指令（AI instructions）+ 自动填充规则（autofill）**。例如 `#MeetingDebrief` 标签自带"总结为要点清单"的指令；`#Idea` 标签自带"归类领域 + 生成摘要"的填充规则。**助理不是一个独立的"人"，而是标签的属性。**
- **路由**：**零选择**。语音备忘录录入 → 自动转写 → 按内容的 Supertag 自动填充字段、执行指令。**用户从不"选助理"，打上标签的那一刻路由就完成了。**
- **入口**：一条手机主屏 Widget 可绑定一个 Supertag + 输入类型 —— **入口本身也预先路由好了**（"一个按钮 = 一个助理"）。
- **对我们的启示**：Tana 证明了"专属助理"不需要做成一个可对话的 Agent，**做成"内容类型 → 处理规则"的绑定就够了**，而且体验最顺 —— 因为选择发生在"打标签"时而不是"触发整理"时。

### 2.2 Mem —— 「全自动、无助理选择」

**产品**：主打 self-organizing 的笔记应用（get.mem.ai）。

- **助理形态**：全系统**只有一个隐形助理**。Clean Up（一键把乱记整理成结构化笔记）、Voice Mode（录音 → 结构化笔记）、Mem Agent（Proactive 档：后台跟踪待办、开会前主动简报）。
- **路由**：**系统全权路由**。用户点 Clean Up 就是"交给系统整理"，不选方案、不写要求；收藏进哪个 Collection、和哪些笔记关联，都由 AI 决定。付费最高档（$99/月）卖的就是"完全不用管"。
- **入口**：笔记详情页一键按钮、浏览器扩展一键收藏、邮箱转发。
- **对我们的启示**：全自动的代价是**不可审计**（评测普遍提到"自组织关系难以检查"）和不可定制口径。对园所场景（教师需要固定口径的跟进清单/复盘）**不建议照搬**，但它印证了：**一键入口的"整理"必须是一步到位的，中途出现任何表单都是打断。**

### 2.3 Notion —— 「按钮绑定预置动作」

**产品**：Notion 3.0（2025-09）起从"AI 写作"升级为"AI Agent 执行"。

- **助理形态**：三档 —— ① 数据库 **AI Autofill 属性**（每个属性绑定一条自定义 prompt，新条目自动填充）；② **按钮属性（AI Assist button）**：一个按钮可绑定多个自动化动作，"每按一次省 5–10 分钟"；③ 3.0 的 **Custom Agent**：有一个 Instructions Page（指令页），定义工作风格、参考文档、归档规则（如"所有客户会议笔记自动归档到客户管理数据库并 @负责人"），设置一次长期生效。
- **路由**：**显式绑定**。哪个按钮执行哪个动作、哪个属性用哪条 prompt，都是配置期定死的；运行期点击 = 直接触发，不再询问。
- **入口**：块内 `/ai`、选中文字右键、数据库按钮、侧边栏对话。
- **对我们的启示**：Notion 的"按钮属性"就是**把路由决策前置到配置期**的经典做法 —— 这和我们"整理配置（用户实例）← 整理模板（平台资产）"的两层结构完全同构。

### 2.4 Reflect —— 「保存的 Prompt 即助理」

**产品**：极简双链笔记（reflect.app）。

- **助理形态**：**AI Palette**（选中文字 → 摘要/改写/生成大纲）+ **自定义 Prompt 库**：用户把重复使用的整理指令（如"从会议记录提取待办并格式化为清单"）保存下来，之后一键套用。
- **路由**：**半自动** —— 触发后要选一下（命令面板 / 右键菜单点选保存的 prompt），但**选择的是自己保存过的、一屏能认出来的短名字**，认知成本低。
- **对我们的启示**：Reflect 说明"选择器"本身不是罪，**罪是大而全的表单**。当可选对象是"我自己的 3–5 条配置"时，一个轻量菜单就够了 —— 这正好对应我们"整理配置数量少、个性化"的预期形态。

### 2.5 Obsidian Copilot —— 「自定义命令 = 助理的最小实现」

**产品**：Obsidian 社区插件（Copilot）。

- **助理形态**：**自定义命令四件套：命令名 + 带 `{{占位符}}` 的提示词 + 指定模型 + 显示位置**（勾选后出现在右键菜单）。这就是一个配置化的"微助理"。
- **路由**：右键 → Copilot 子菜单 → 点命令。执行时占位符自动替换为选中文本。
- **对我们的启示**：**"占位符模板 + 固定入口"的极简实现**，和我们整理模板的「变量白名单 + 渲染」机制几乎一样，可视为我们引擎在竞品里的最小镜像，佐证了模板七要素里"输入装配 + 变量白名单"的设计是行业通用做法。

### 2.6 飞书 aily —— 「任务模式 + 定时指派」（国内对标）

**产品**：飞书企业级 Agent 平台（aily 工作助手）。

- **助理形态**：企业可定制专属 Agent（角色设定 + 企业知识 + MCP 业务系统接入）；预置"aily 工作助手"开箱即用。
- **路由**：两种 —— ① **显式指派**（任务模式："我派活它交结果"，一句话下达）；② **定时任务**（每周日下午自动基于日程/文档/会议生成周报，完成后飞书消息通知）。
- **关键优势**：**上下文原生** —— 直接调用飞书内的文档、多维表格、会议纪要、日程，"不需要你反复交代背景"；产出直接落为飞书云文档/多维表格，不导出。
- **对我们的启示**：**执行周期 + 完成后消息通知回列表**的组合，正是我们已经排进 P0–P2 的方向（执行周期字段 → 调度任务）；aily 验证了"定时整理 + 通知"是企业场景的高频刚需。

### 2.7 Mem0 —— 基础设施视角（记忆层怎么做"自动整理"）

**产品**：AI 应用记忆层（mem0.ai，AWS Agent SDK 指定记忆供应商）。

- `memory.add()` 后台**自动抽取事实、分类、去重、解决冲突**（三层 scope：用户 / 会话 / 智能体）；检索按语义查询注入上下文。
- **对我们的启示**：它代表"**记忆的整理发生在写入时**"的另一极端 —— 与其让人点击整理，不如结构化在入库瞬间完成。这对应我们 PRD 里排在 P4 的"转写后自动整理"路线：**行业趋势是往写入时自动化走，但都以"先有明确口径的配置"为前提。**

## 3. 横向归纳：四种路由模式

| 模式 | 代表 | 路由时机 | 用户感知 | 适用条件 |
| --- | --- | --- | --- | --- |
| **A. 标签即路由** | Tana | 打标签/录入时 | 零操作，自动完成 | 内容类型体系成熟、助理规则挂在类型上 |
| **B. 动作即助理** | Notion 按钮 / Obsidian 命令 | 配置期绑定，点击即执行 | 一键直达，零选择 | 动作数量可控、入口可枚举 |
| **C. 保存项轻选择** | Reflect / Obsidian 菜单 | 点击后从"自己的保存项"里点一下 | 一次轻量点选 | 个人配置数量少（≤ 8 个）且高频 |
| **D. 全自动隐身助理** | Mem / Mem0 | 系统决定 | 无感，但难审计 | 用户容忍黑盒、口径无强约束 |

**共性规律（全部六家一致）：**

1. **路由决策都在配置期完成，不在触发期** —— 没有任何一家在用户点"整理"之后弹一个多字段表单。
2. **"专属助理"的本质都是三件套：预置指令 + 固定入口 + 异步执行**，而不是可对话的 Agent。
3. **执行都是异步的**：进度可见、完成后产物落回列表（Tana 回填字段 / Notion 回写数据库 / aily 消息通知）。

## 4. 落地建议：整理模块怎么做「点击记忆 → 自动调用专属整理助理」

结合我们已有设计（整理配置 = 名称/指令/专家/执行周期；记忆带类型与标签；PRD FR-8a 落定快照），建议采用 **「B 为主 + C 兜底」** 的组合：

### 4.1 路由规则（核心增量）

给整理配置增加一个**适用范围声明**（记忆类型 / 标签，与模板 `input.filter` 同源但允许用户在配置里收窄）。点击某条记忆的「整理」时：

1. **唯一命中** → 直接按该配置落定并执行。界面上只出现一个轻提示：**"已交给「教研提炼」整理这条记忆"** + 两个次级动作：「换一个」（打开配置菜单）和「撤销」。
2. **多个命中** → 弹**轻量菜单**（底部 action sheet 或锚定菜单，只列配置名 + 产出形态，一屏可扫完），**不弹**现在的大弹层（大弹层保留给"多选记忆 + 定范围"的重流程）。
3. **零命中** → 不弹空选择器，引导："给这类记忆建一条整理配置" → 进入配置表单并预填名称与指令。

### 4.2 交互细节（从调研直接抄的作业）

| 细节 | 来源 | 落法 |
| --- | --- | --- |
| 列表不打断：hover / 长按记忆条目浮现「整理」按钮，而非点击进详情再找入口 | Notion 块菜单 / Obsidian 右键 | 记忆卡片 hover 态出「整理」 |
| 一键按钮 = 一个助理（入口预路由） | Tana Widget | 记忆类型栏可显示"默认整理"标记，点类型名直接走默认配置 |
| 执行异步 + 完成后产物落回该配置的任务列表（时间线） | aily / Notion | 已有：整理配置 → 任务时间线，通知可后续接站内消息 |
| "指令 + 专家 + 周期"三件套即助理，不做成对话 Agent | 全部六家 | 维持整理配置字段，不加聊天形态 |

### 4.3 与 Tana 的一个关键差异（要挡住的坑）

Tana 的"标签即路由"依赖用户自己维护标签体系，评测明确指出**标签漂移是最大痛点**（#task 和 #todo 分裂后查询静默失效）。我们是平台统一模板 + 园所用户，所以：**适用范围声明的真源在整理配置上，标签只是匹配条件之一；匹配不唯一时永远回退到轻量菜单，不做静默自动路由** —— 宁可多一次点选，不可整理错口径。

### 4.4 对 PRD / 原型的影响（待拍板）

1. **PRD**：新增 FR —— 整理配置的「适用范围 + 默认整理」字段；记忆条目 hover 动作入口；唯一命中直通规则。建议排 **P2**（用户侧能力期），P0–P1 引擎与后台不受影响。
2. **原型**：记忆卡片加 hover「整理」按钮 + 轻提示直通流程（当前原型是"勾选 → 大弹层"，可并存：单条快路径 / 批量重流程）。
3. **Q10（新增待决策）**：是否允许配置声明"默认整理"（一个记忆类型只绑一条默认配置，实现 Tana 式零选择直通）？建议：允许，但默认关闭，灰度观察误触率后再放开。

## 5. 结论

1. 「专属整理助理」在六个调研对象里**没有一家做成对话 Agent**，全部是"预置指令 + 固定入口 + 异步执行"的配置化形态 —— 与我们"整理配置"的设计同构，方向可确认。
2. **自动调用的关键是把路由决策前置到配置期**（Tana 挂在标签上、Notion 挂在按钮上、Reflect 挂在保存项上），触发期只做"命中即执行"。
3. 我们的最优组合：**配置声明适用范围 → 唯一命中直通 + 轻提示可撤销，多命中轻菜单，零命中引导建配置**；不做静默全自动化（Mem/Mem0 路线），保住园所场景对"口径正确"的强要求。
4. 「执行周期 + 完成通知」（aily 验证）与「写入时自动整理」（Mem0 方向）分别是 P1 后续与 P4 之后的演进方向，本期不扩。
