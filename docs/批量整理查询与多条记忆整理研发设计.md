# 批量整理查询与多条记忆整理研发设计

> 版本：v1.1  
> 日期：2026-10-07  
> 状态：核心能力已研发并验证  
> 适用模块：`frontend/src/views/organize`、`frontend/src/api/organize`、`internal/application/service/organize*`、`internal/handler/organize*`、`internal/types/organize*`  
> 相关文档：[整理模块现状与文档索引](整理模块现状与文档索引.md)、[多条记忆整理方案](多条记忆整理方案.md)、[多记忆两阶段整理方案](多记忆两阶段整理方案.md)、[三阶段整理流程落地方案](三阶段整理流程落地方案.md)

## 1. 执行摘要

### 1.1 产品定义

本需求不是让用户先手动勾选大量记忆，而是让用户通过整理指令描述：

1. 要查询哪一段时间、哪类记忆、哪些关键词；
2. 查询结果要整理成什么内容；
3. 最终生成一份可以回查、筛选和追溯的整理结果。

示例：

> 整理 2026 年 9 月 1 日至 9 月 30 日的招生咨询录音，提取家长顾虑、意向课程和下一步跟进事项，并按紧急程度排序。

系统应将指令拆分为：

```text
查询条件：2026-09-01 至 2026-10-01、招生咨询、录音
整理要求：提取家长顾虑、意向课程、下一步跟进事项，并按紧急程度排序
```

执行模型：

```text
自然语言指令
  -> 结构化查询计划
  -> 查询记忆
  -> 展示命中预览
  -> 固化输入快照
  -> 按预算拆分批次
  -> 批次整理
  -> 合并批次摘要
  -> 生成一份最终产物
```

### 1.2 核心结论

| 结论 | 研发要求 |
| --- | --- |
| 查询范围和整理要求是两个不同对象 | 分别存储、分别校验，不把整段指令直接拼入 SQL 或 prompt |
| 查询结果必须在任务创建时固定 | 保存实际 `memory_ids`、查询条件和记忆版本，执行过程中不动态补入新记忆 |
| 多条记忆不能一次性硬塞给模型 | 服务端按输入预算自动拆分批次 |
| 批次失败不能导致全部结果丢失 | 父任务聚合状态，支持只重试失败批次 |
| 同一记忆可以被不同整理使用 | 不做全局排除，只对相同整理意图做幂等判断 |
| 最终只生成一份用户可见结果 | 批次结果作为内部执行记录保存，不污染“我的整理”列表 |
| 任何排除、截断、冲突都必须可见 | 最终结果和任务详情展示覆盖数、失败数、排除原因和冲突项 |

### 1.3 本期不做

- 不把每条记忆默认拆成一个独立用户可见任务；
- 不把中间批次结果回写成新的记忆；
- 不对同一条记忆做全局去重；
- 不允许大模型直接生成 SQL；
- 不改变个人记忆、组织授权和公开知识库的权限边界；
- 不把整理模块扩展成 CRM 或通用数据库查询工具。

## 2. 当前实现基线

### 2.1 当前执行链路

当前 `OrganizeJob` 是单层执行记录：

- `CreateJob` 接收可选的 `memory_ids`；
- 未传 `memory_ids` 时，`selectOrganizeJobMemoryIDs` 默认取最近一批记忆；
- `ProcessOrganizeJob` 调用一次 `executeOrganizeJob`；
- `executeOrganizeJob` 加载全部输入记忆，构造一个 prompt，调用一次模型并生成一个产物；
- `organize_output_memories` 保存产物与来源记忆的关联。

主要代码：

| 文件 | 当前职责 |
| --- | --- |
| `internal/application/service/organize_workbench.go:247-305` | 创建整理任务 |
| `internal/application/service/organize_workbench.go:387-460` | 执行并完成整理任务 |
| `internal/application/service/organize_workbench.go:550-573` | 默认选择记忆 |
| `internal/application/service/organize_workbench.go:598-718` | 单次模型调用和产物落库 |
| `internal/application/service/organize_workbench.go:904-952` | 记忆装配和提示词预算 |
| `internal/application/repository/organize.go:710-774` | 产物与记忆关联的写入和读取 |
| `internal/types/organize_workbench.go:184-213` | `OrganizeJob` 当前模型 |
| `internal/handler/organize.go:270-352` | 任务创建、查询、重试、取消接口 |

### 2.2 当前限制

| 限制 | 影响 |
| --- | --- |
| 默认查询没有时间范围、类型和关键词条件 | 无法支持“某个时间段的某类记忆” |
| 默认取数上限和 prompt 总预算是两套限制 | 命中数量不等于实际参与整理数量 |
| prompt 构造存在单条和总量截断 | 超出预算时可能静默丢失输入 |
| 没有父任务和批次模型 | 无法展示“第几批”、重试单个失败批次 |
| 周期任务已有 `DedupeKey`，手动任务没有输入指纹 | 相同手动整理可能重复生成 |
| 前端主要显示最新任务状态 | 无法表达一个父任务下的多个批次 |

### 2.3 兼容原则

现有能力必须继续可用：

1. 现有 `memory_ids` 直接创建任务的 API 保持兼容；
2. 单条记忆整理仍然可以走单任务模式；
3. 现有配置、模板、任务、产物和服务归属关系不改变；
4. 旧任务没有查询快照和批次信息时，按历史单任务展示；
5. 新功能先通过配置或灰度开关启用，不强制重跑历史任务。

## 3. 业务概念与状态

### 3.1 核心对象

| 对象 | 定义 |
| --- | --- |
| 整理指令 | 用户描述查询范围和整理目标的自然语言 |
| 查询计划 | 对整理指令中查询部分的结构化、可校验表达 |
| 整理要求 | 对整理输出的字段、章节、排序和筛选要求 |
| 输入快照 | 任务创建时实际命中的记忆 ID、查询条件和记忆版本 |
| 父任务 | 用户可见的一次完整整理执行，最终对应一份产物 |
| 批次 | 父任务拆分出的内部执行单元，持有一组记忆 |
| 批次摘要 | 批次模型输出的压缩结论、字段、待办和来源引用 |
| 最终产物 | 合并所有成功批次后的唯一用户可见整理结果 |
| 整理意图指纹 | 用于判断是否重复提交相同整理的输入指纹 |

### 3.2 任务关系

```text
organize_config
  |
  +-- organize_job（父任务）
        |
        +-- organize_job_batches（批次 1）
        +-- organize_job_batches（批次 2）
        +-- organize_job_batches（批次 N）
        |
        +-- organize_output（最终产物）
```

批次不直接出现在用户的成果列表中。用户在父任务详情中查看批次进度和失败原因。

### 3.3 父任务状态

沿用现有状态，并补充批次语义：

| 状态 | 含义 |
| --- | --- |
| `queued` | 已完成查询快照，等待批次执行 |
| `running` | 正在执行批次 |
| `repairing` | 正在重试失败批次或修复汇总 |
| `completed` | 所有必要批次完成，已生成最终产物 |
| `fallback` | 有部分批次未完成，但已生成可用基础结果 |
| `failed` | 查询、执行或合并阶段无法生成结果 |
| `canceled` | 用户取消任务 |

父任务内部阶段：

```text
planning
  -> snapshotting
  -> batching
  -> processing_batches
  -> merging
  -> completed
```

### 3.4 批次状态

```text
queued -> running -> completed
                 \-> fallback
                 \-> failed
queued -> canceled
running -> canceled
```

## 4. 用户流程设计

### 4.1 按要求整理

1. 用户进入整理工作台，选择一个已有整理配置；
2. 输入本次整理要求；
3. 点击“预览整理范围”；
4. 后端解析查询计划并查询候选记忆；
5. 前端展示命中数量、样例、未就绪数量、重叠数量和预计批次数；
6. 用户确认后创建父任务；
7. 父任务固定输入快照并自动拆批；
8. 批次执行完成后生成最终产物。

### 4.2 预览展示

示例：

```text
整理范围
2026-09-01 00:00 至 2026-10-01 00:00
记忆类型：录音、录音卡
关键词：招生咨询

命中 128 条记忆
可处理 120 条
未完成转写 8 条
与其他整理重叠 35 条
预计拆分 10 批
```

用户操作：

- `继续整理`：默认，允许使用重叠记忆；
- `只处理同一配置未整理过的记忆`：只排除同配置、同模板版本、同查询范围已经成功处理的记忆；
- `查看重叠来源`：打开历史整理任务和产物列表；
- `取消`。

“未整理过”不能解释为“从未被任何整理使用过”，避免错误排除被其他业务模板需要的记忆。

### 4.3 查询无结果

查询结果为 0 条时：

- 不创建模型任务；
- 展示标准化查询条件；
- 给出调整建议，例如扩大时间范围、去掉关键词或选择其他记忆类型；
- 保留本次预览记录，不生成空产物。

### 4.4 查询结果变化

预览到确认之间如果命中数量发生变化，确认接口重新计算查询结果并返回差异：

```text
预览时 128 条，确认时 131 条
是否使用最新查询结果创建任务？
```

默认使用确认时的结果，并在任务快照中记录确认时间。

## 5. 指令解析与查询计划

### 5.1 查询和整理要求分离

输入：

```text
整理 2026 年 9 月的招生咨询录音，
提取家长顾虑、意向课程和下一步跟进事项，并按紧急程度排序。
```

解析结果：

```json
{
  "memory_filter": {
    "time_field": "occurred_at",
    "occurred_from": "2026-09-01T00:00:00+08:00",
    "occurred_to": "2026-10-01T00:00:00+08:00",
    "kinds": ["record", "audio", "audio_card"],
    "keyword": "招生咨询",
    "ready_only": false
  },
  "organize_requirement": {
    "fields": ["家长顾虑", "意向课程", "下一步跟进事项"],
    "sort": "紧急程度",
    "output_sections": ["线索概览", "重点顾虑", "跟进事项", "待确认"]
  },
  "ambiguities": []
}
```

### 5.2 查询计划字段

第一期支持：

| 字段 | 说明 |
| --- | --- |
| `time_field` | `occurred_at`，第一期固定使用发生时间 |
| `occurred_from` | 时间范围起点，含 |
| `occurred_to` | 时间范围终点，不含 |
| `kinds` | `note`、`record`、`audio`、`audio_card` |
| `keyword` | 标题、正文、来源中的关键词 |
| `sources` | 可选来源过滤 |
| `ready_only` | 是否只取已完成处理的记忆 |
| `limit` | 单次最大命中数，超过时需要提示或分页策略 |

暂不在第一期支持：

- 任意 SQL；
- 跨租户查询；
- 未经授权的组织成员记忆；
- 复杂布尔表达式；
- 模型自由定义字段名并直接下推数据库。

### 5.3 解析原则

1. 模型输出必须是受约束 JSON；
2. 后端校验时间、类型、数量和权限；
3. 无法确定时间范围时进入 `ambiguities`，要求用户确认；
4. “上周”“本月”等相对时间只在解析时转成绝对时间；
5. 手动任务以确认时的绝对时间为准；
6. 周期任务在每次实际触发时重新解析并固化时间窗口；
7. 模型不得直接访问数据库或拼接 SQL。

## 7. 批次规划与执行

### 7.1 批次规划原则

当前 prompt 预算以字符数控制，第一期继续沿用现有字符预算，不在本期强行切换 token 计量。

规划原则：

1. 先为模板、专家指令和输出要求预留预算；
2. 记忆输入使用总预算的 70%～80%；
3. 逐条累加记忆正文，超过预算前结束当前批次；
4. 同一批次保留完整记忆，不在批次内部静默截断；
5. 单条记忆超过单批预算时，进入“长记忆压缩”或失败状态；
6. 查询结果按发生时间排序，必要时按主题或来源做稳定分组；
7. 每个批次保存实际使用的 ID，不能只保存估算数量。

建议初始参数：

```text
organize_prompt_budget = 18000
batch_input_budget = 14000
single_memory_budget = 2200
max_batches_per_job = 100
max_memories_per_job = 1000
```

这些是保护上限，不是用户可见的固定条数承诺。后续应通过配置或模板策略调整。

### 7.2 批次模型输入

批次模型输入包含：

1. 模板版本快照；
2. 整理配置指令；
3. 本次整理要求；
4. 本批次记忆；
5. 输出契约；
6. 引用格式要求；
7. “不得基于未提供信息进行推断”的约束。

批次输出优先使用结构化结果：

```json
{
  "summary": "...",
  "fields": {},
  "conclusions": [],
  "todos": [],
  "excluded": [],
  "conflicts": [],
  "citations": [
    {
      "memory_id": "memory_1",
      "label": "[M1]"
    }
  ]
}
```

现有模板仍可以输出 Markdown。第一期可以先从 Markdown 中提取摘要和引用，后续再逐步升级为结构化输出。

### 7.3 合并阶段

合并阶段不能把所有批次全文再次拼入 prompt。应使用：

```text
批次摘要
结构化字段
关键结论
待办
冲突项
引用关系
```

合并规则：

- 相同事实按规范化事实键合并；
- 合并时保留所有来源记忆 ID；
- 同一事实来源不同但内容一致时合并引用；
- 内容冲突时保留冲突项，不自动覆盖；
- 被排除内容必须记录原因；
- 最终产物必须显示覆盖率。

## 8. 重叠记忆与幂等

### 8.1 允许重叠

以下情况允许重复使用记忆：

- 不同模板；
- 不同整理配置；
- 不同业务目标；
- 不同时间窗口；
- 同一模板但用户明确选择重新整理。

已有 `organize_output_memories` 关联表可以作为历史重叠计算基础。

### 8.2 相同整理意图

输入指纹由以下内容组成：

```text
tenant_id
user_id
config_id
template_key
template_version
normalized_instruction
sorted(memory_id + memory_updated_at/content_hash)
```

对相同指纹：

1. 如果存在运行中的任务，返回已有任务；
2. 如果存在已完成任务，返回已有任务并提示是否重新整理；
3. 如果用户选择强制重跑，创建新任务并保留旧结果；
4. 强制重跑不能覆盖旧产物。

### 8.3 批次级幂等

批次指纹由以下内容组成：

```text
parent_job_id
batch_index
sorted(memory_id + memory_version)
template_version
prompt_hash
```

重试时沿用批次 ID和输入快照，不能重新从当前记忆列表查询。

## 13. 权限与安全

1. 查询计划必须带当前 `tenant_id` 和 `user_id`；
2. `memory_ids` 显式输入和查询条件输入都必须经过同一权限校验；
3. 不允许通过时间范围和关键词跨用户搜索；
4. 查询预览结果只能返回当前用户有权看到的标题、类型、时间和摘要片段；
5. 批次日志不得写入完整记忆正文；
6. 任务重试必须校验父任务归属；
7. 公开发现内容、组织共享内容和个人记忆仍遵循现有授权边界；
8. 不允许把自然语言中的 SQL、脚本或系统提示词当作可执行内容。

## 17. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 自然语言时间解析错误 | 预览展示绝对时间，歧义必须确认 |
| 查询命中数量过大 | 设置最大数量并要求缩小范围或进入分层处理 |
| 批次摘要丢失细节 | 保留引用和结构化字段，最终结果显示覆盖率 |
| 合并阶段再次超预算 | 合并只使用批次摘要，必要时增加多级合并 |
| 同一记忆被错误全局排除 | 只按整理意图做幂等，不做全局去重 |
| 配置在任务中途变化 | 任务保存模板、指令和查询快照 |
| 任务重试产生重复结果 | 父任务和批次使用输入指纹及幂等校验 |
| 中间结果污染用户成果列表 | 批次结果单独落库，最终只生成父任务产物 |
| 模型输出格式不稳定 | 使用模板契约、结构化字段校验和 fallback |
| 队列积压 | 限制同父任务和同用户并发，增加耗时和失败指标 |

## 18. 最终验收标准

本需求完成必须同时满足：

1. 用户可以通过自然语言指定时间范围和记忆条件；
2. 系统可以展示标准化查询条件和命中数量；
3. 查询结果在任务创建时固定；
4. 任务不会因为输入过多而静默丢失记忆；
5. 多条记忆可以自动拆分为多个批次；
6. 批次失败可以独立重试；
7. 多个整理可以合法复用相同记忆；
8. 相同整理意图不会无提示重复生成；
9. 最终只产生一份用户可见汇总结果；
10. 最终结果显示覆盖率、失败项、排除项和冲突项；
11. 每条关键结论可以追溯到原始记忆；
12. 旧版单条整理接口和历史任务保持兼容；
13. PostgreSQL、SQLite、后端测试、前端类型检查和关键交互测试全部通过；
14. 灰度关闭后可以回到现有单任务路径。

```text
第四步：批次执行 + 失败重试
第五步：摘要合并 + 最终产物
第六步：前端时间线 + 灰度发布
```

最终产品口径：

> **一次整理任务不是一次模型调用，而是一次固定查询结果、可追踪执行、可部分重试并生成单一汇总产物的整理批次。**
