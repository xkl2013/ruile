## 1. 现状诊断

### 1.1 代码事实

发现页 = `organize_outputs` 表的聚合分发视图，全部逻辑集中在 `internal/application/service/organize_discover.go`（383 行）+ `OrganizeWorkspace.vue` 的 discover 区块（约 3000 行单文件组件的一部分）。

| # | 事实 | 代码位置 |
| --- | --- | --- |
| F1 | **每次请求全量拉取用户全部产物**，循环翻页直到取完，再在内存中过滤 / 排序 / 分页 | `organize_discover.go:59-85`（`listAllDiscoverOutputs`） |
| F2 | **「推荐」是伪推荐**：featured = 排序后从 offset 起轮转取 4 条，没有评分、没有衰减、没有个性化 | `organize_discover.go:157-174`（`pickDiscoverFeaturedOutputs`） |
| F3 | 排序权值写死：status 权重 → memory_count → updated_at → created_at → id | `organize_discover.go:127-155` |
| F4 | **过滤不筛状态**：archived 产物仍进入 feed，只是排序沉底（权重 0） | `organize_discover.go:282-295`（`discoverStatusWeight`），`filterDiscoverOutputs:110-125` 无 status 条件 |
| F5 | **8 个分类硬编码两份**：后端常量 + 前端常量，靠别名表打补丁 | `internal/types/organize.go:235-257`；`frontend/src/views/organize/discoverCategories.ts:17-26, 33-45` |
| F6 | 服务层还有第三份别名补丁（「团队运营与园长领导力」「空间设计」「教师成长」三个旧称） | `organize_discover.go:257-265, 372-380` |
| F7 | 分类值靠 `metadata` JSON 里的 `discover_category` 字符串，前端编辑保存时写入 | `organize_discover.go:246-267`；`OrganizeWorkspace.vue:1830-1831` |
| F8 | **搜索是内存 LIKE**：把 title / content / tags / creator_name 等 9 个来源拼成一个 haystack 再 `strings.Contains`，无相关性、无索引 | `organize_discover.go:204-221` |
| F9 | featured 与 feed **两次独立请求，各自全量拉取** | `OrganizeWorkspace.vue:1682-1742`（`loadDiscoverFeaturedData` / `loadDiscoverFeedData`） |
| F10 | 内容源单一：只有 outputs；记忆（organize_memories）完全不进发现页 | `organize_discover.go` 全文仅调用 `repo.ListOutputs` |
| F11 | 无埋点：推荐位点击率、分类使用率、搜索转化均不可观测 | 全仓无 discover 相关事件上报 |
| F12 | 冷启动无设计：新用户 0 条产物时，推荐位与 feed 均为空，无引导 | `pickDiscoverFeaturedOutputs:157-161` 返回空数组即止 |

### 1.2 问题定性

1. **性能问题（F1/F9）是结构性的**：单请求 O(N) 内存聚合，产物过千后每次切 tab、翻页、换一批都全量扫描。这不是「加缓存」能修好的，查询必须下推。
2. **分类硬编码（F5/F6）已两处打补丁**，是「双真源漂移」的活标本 —— `agent_type_presets.yaml` 注释里记录过同类教训。PRD v1.4 已定方向（模板 `scene` 聚合 + 接口下发），本方案落地它并清理三处别名补丁。
3. **推荐（F2/F3）与搜索（F8）是「发现」的核心体验，但目前两者都名不副实**：推荐没有「推荐」语义，搜索没有「找到」能力。发现页要成立的定位（见 §2），这两块必须重做。
4. **定位模糊（F4/F10/F12）**：现状发现页既不筛状态、又不含记忆、又无空态引导，说明它从未被当成一个独立产品面设计过 —— 它只是「成果列表换了个排法」。

## 2. 定位重定义

### 2.1 一句话

> **发现页是记录者本人的知识复用入口：让用户回头能快速找到、看懂、用上自己整理过的东西。**

与整条产品定义「大模型根据用户的要求，把用户的记忆整理成**便于自己查看**的数据」（整理模块重构 PRD §1.1）严格同源 —— 发现页就是「便于自己查看」这句话的**兑现面**：整理侧负责把产物做成结构化数据，发现侧负责让它可筛、可搜、可跳回。

### 2.2 三个候选定位与本方案的取舍

| 候选定位 | 说明 | 取舍 |
| --- | --- | --- |
| A. 个人回查入口 | 只服务产物创建者本人，优化回查效率 | ✅ **本方案采用**，与 audience: self 的产品定义一致 |
| B. 园所内共享广场 | 园长/教研员可看全园教师的整理成果 | ⏳ 有真实价值（幼儿园场景园长视角强），但涉及权限模型与受众边界，列为 Q4 待决策，不进本期 |
| C. 平台内容分发 | 平台运营向所有租户分发内容 | ❌ 与 metadata 中 creator_id 搜索暗示的旧设想有关，但与当前数据隔离模型（tenant_id + user_id 双重过滤）冲突，不做 |

## 3. 目标与边界

### 3.1 目标

| 编号 | 目标 | 衡量口径 |
| --- | --- | --- |
| D1 | 分类真源唯一 | 后端常量、前端常量、服务层别名补丁（F5/F6 三处）全部删除，分类由接口下发 |
| D2 | 查询下推 | 发现页单请求不再全量拉取；过滤 / 计数 / 分页 / 排序在 SQL 层完成 |
| D3 | 状态语义明确 | 推荐位只出 ready；feed 默认排除 archived，状态可筛选 |
| D4 | 排序可用 | feed 支持至少两种排序切换（最新 / 引用最多）；推荐位改为评分排序（recency 衰减 × 完成度 × 引用数） |
| D5 | 搜索可找到 | 搜索下推 SQL 并覆盖 title / summary / tags；语义搜索作为二期增强（见 Q3） |
| D6 | 与查看契约衔接 | 发现卡片展示结构化 `fields` 摘要；任一卡片可一跳回原始记忆（`citations` 锚点） |
| D7 | 可观测 | 埋点 4 个核心事件（曝光 / 点击 / tab 切换 / 搜索），admin 可看分类使用率 |
| D8 | 冷启动有引导 | 产物 < 阈值时展示「去整理」引导卡，深链至新建整理配置弹层 |

### 3.2 边界

**包含**：发现页签的数据层、服务层、API、前端重构；分类真源迁移；埋点。

**不包含**：

- 模板引擎与整理管线本身（走整理模块重构 PRD 主线）
- 产物编辑器（`OrganizeDocumentEditor.vue`）不动
- 园所内共享（定位 B）不在本期，见 Q4
- 不引入新的检索中间件；语义搜索复用 WeKnora 既有向量能力，见 Q3

## 4. 总体设计（六个支柱）

### 支柱 1：分类真源下沉为数据

- 新增 `organize_discover_categories` 表（key / label / sort_order / icon / enabled / created_at / updated_at），由平台在 admin 后台「资产治理」下维护，与整理模板管理同一入口。
- **模板 scene 与分类的关系**：整理模板的 `scene` 字段必须引用一个已启用的分类 key（后台保存时校验）。发现页 tab 由分类表驱动并按产物计数填充，满足 PRD v1.4 §10.6「分类来源改为模板 scene 聚合，响应结构不变」的承诺 —— 聚合方向是「分类表 ← 模板 scene 校验」，而不是「tab = 现有模板 scene 的并集」，否则删光某分类下所有模板时 tab 会消失，存量产物失去归属。
- 存量数据迁移：把 `metadata->>'discover_category'`（含全部别名变体）规范化后**拍平为 `organize_outputs.discover_category` 物理列**（见 §5），`metadata` 里的旧字段保留只读兼容一个版本期。
- 三处硬编码与别名补丁（F5/F6）删除；前端 `discoverCategories.ts` 改为调用分类接口 + 本地缓存。

### 支柱 2：查询下推

现状 F1 的全量内存聚合改为 SQL 层：

| 查询 | 下推后的形态 |
| --- | --- |
| tab 计数 | `SELECT discover_category, COUNT(*) FROM organize_outputs WHERE tenant_id=? AND user_id=? AND status<>'archived' AND deleted_at IS NULL GROUP BY discover_category` |
| feed 分页 | 按 `(tenant_id, user_id, discover_category, updated_at DESC)` 索引走 keyset/offset 分页 |
| 推荐位 | 评分排序下推为 SQL 表达式（见支柱 4），取前 4 条 |
| 搜索 | `title LIKE` / `source_summary LIKE` + `metadata->'tags'` JSONB 包含，走 §5 新索引 |

featured 与 feed 合并为**一次请求**（F9），响应内同时返回 `featured_outputs` 与首页 `items`，翻页 / 换一批走轻量子请求。

### 支柱 3：状态语义（修复 F4）

| 区域 | 规则 |
| --- | --- |
| 推荐位 | 仅 `ready` |
| feed 默认 | `ready` + `review` + `draft`，**排除 `archived`** |
| 状态筛选 | feed 增加状态 chip（全部 / 草稿 / 待确认 / 已就绪），默认「全部（不含已归档）」 |
| tab 计数 | 与 feed 默认口径一致，避免「tab 数字与列表条数对不上」 |

### 支柱 4：排序与推荐

- **feed 排序切换**（D4）：
  - `recent`（默认）：`updated_at DESC`
  - `most_cited`：`memory_count DESC, updated_at DESC`（memory_count 由 `organize_output_memories` 聚合，下推 COUNT）
- **推荐位评分**（替换 F2 的轮转窗口）：

  ```
  score = w1 × recency_decay(updated_at) + w2 × status_weight + w3 × log(1 + memory_count)
  ```

  初始权重 w1=0.5, w2=0.3, w3=0.2；recency 用指数半衰期（14 天半衰）。评分在 SQL 内计算（表达式或生成列），**不引入独立推荐服务**。`FeaturedOffset` 换一批交互保留，语义改为「跳过已看过的前 N 条」。
- 埋点回流后的个性化（点击加权）列为远期，不在本期承诺。

### 支柱 5：搜索升级（修复 F8）

- 一期：LIKE 下推 + 覆盖 title / source_summary / tags；去掉 haystack 里的 creator_name / user_id / icon 等无意义来源（F8 的 9 项裁到 3 项）。
- 二期（Q3）：WeKnora 内核本身具备向量检索能力，产物 content 可选入库索引，实现「上次关于影子的那次磨课」这类语义回查。是否做取决于延迟 / 成本 / 隐私评审，见 Q3。

### 支柱 6：冷启动与引导（修复 F12）

| 场景 | 表现 |
| --- | --- |
| 0 条产物 | 空态页：说明「发现」是什么 + 「去整理」主按钮，深链 `/platform/organize/hub?config=new`（对齐 PRD v1.4 §10.6 深链约定） |
| 1–5 条产物 | feed 照常，推荐位不足 4 条时按实际数量渲染，并附一张「继续整理」引导卡 |

## 5. 数据模型与迁移

### 5.1 新表：`organize_discover_categories`

```sql
CREATE TABLE organize_discover_categories (
    key        VARCHAR(64) PRIMARY KEY,
    label      VARCHAR(128) NOT NULL,
    sort_order INT NOT NULL DEFAULT 0,
    icon       VARCHAR(64) NOT NULL DEFAULT '',
    enabled    BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);
```

种子数据 = 现有 8 个分类（`internal/types/organize.go:246-257` 的清单原样迁移）。

### 5.2 改表：`organize_outputs`

```sql
ALTER TABLE organize_outputs ADD COLUMN discover_category VARCHAR(64) NOT NULL DEFAULT '';
-- 数据回填：规范化 metadata 中的 discover_category / category / discover_category_label
-- 及三个旧称别名（见 F6）后写入
CREATE INDEX idx_organize_outputs_discover
    ON organize_outputs(tenant_id, user_id, discover_category, updated_at DESC)
    WHERE deleted_at IS NULL AND status <> 'archived';
```

迁移编号取下一可用号（编写时最新为 000100，实施时以实际顺延为准），同步产出 `migrations/mysql/` 与 `migrations/sqlite/` 方言版本（项目既定约定）。

### 5.3 admin 侧

「资产治理」下新增「发现分类」管理页（列表 / 排序 / 启用停用 / 改名），导航注册进 `admin/src/config/navigation.ts` 的 `ADMIN_NAV_GROUPS`，复用 frontend 组件源码（admin 复用约定）。

## 6. API 契约

原则：**`GET /organize/discover` 响应结构不变**（PRD v1.4 已对外承诺），只做增量。

| 接口 | 变更 |
| --- | --- |
| `GET /organize/discover` | 新增可选参数 `sort`（`recent`/`most_cited`）、`status`（状态筛选）；响应新增 `categories` 字段（key/label/icon，接口下发，替代前端硬编码）；`tabs` 结构不变、计数口径变为 §支柱 3 的新口径 |
| `GET /organize/discover/categories`（新增） | 分类清单 + 各分类产物计数；前端 `discoverCategories.ts` 改为消费此接口并本地缓存 |
| admin：`/admin/discover-categories` CRUD（新增） | 平台维护分类；`g.SystemAdmin()` 守卫，不加 `/admin` 路径前缀（仓库惯例，路由守卫区分角色） |
| 埋点上报（新增） | `discover_impression` / `discover_click` / `discover_tab_switch` / `discover_search` |

兼容性：旧客户端不带新参数时行为等价（`sort=recent`、默认状态口径 —— 注意默认口径从「含 archived 沉底」变为「排除 archived」，这是一处**有意的破坏性语义修正**，见 §9 风险 R2）。

## 7. 前端方案

1. **拆组件**：`OrganizeWorkspace.vue` 已超 3000 行，把 discover 区块（模板 138–337 行、逻辑 773–896 行、样式 2785 行起）抽为 `components/DiscoverBoard.vue`，职责：tab 栏 / 推荐位 / feed / 状态 chip / 排序切换 / 空态引导。
2. **卡片结构化**（D6）：卡片正文从「content 截断」改为优先渲染 `fields` 摘要（查看契约），无 fields 时回退现状；卡片提供「查看原文」跳产物详情、「回到记忆」跳 citations 锚点（与 PRD v1.4 §10.6 的产物查看二级路由打通）。
3. **分类消费**：删除 `discoverCategories.ts` 硬编码，改接口下发 + 内存缓存；`normalizeDiscoverCategory` 别名逻辑仅保留在**数据回填脚本**中，前端不再需要。
4. **请求合并**：featured 与 feed 首屏合为一次请求（F9），`setDiscoverTab` 仅触发 feed 子请求。

## 9. 风险与验收标准

### 9.1 风险

| # | 风险 | 缓解 |
| --- | --- | --- |
| R1 | 分类回填遗漏别名变体，产物错分类或丢 tab | 回填脚本枚举 F5/F6 全部已知变体；回填后跑「未匹配计数 = 0」校验，未匹配项落告警表人工归 |
| R2 | 默认口径变化（archived 从沉底变为消失）属行为变更，老用户可能找不到归档内容 | 归档内容改由「状态筛选」入口可达；发版说明中明确 |
| R3 | 评分排序引入后推荐位结果不可解释 | 评分公式与权重后台可查；一期内权重不做动态化 |
| R4 | 与整理重构主线并发改动 `organize_outputs`，冲突 | 迁移编号与 PRD v1.4 迁移统一排队；discover_category 列与模板列（config_id/job_id/template_key 等）分属独立迁移文件 |

### 9.2 验收标准（节选）

- AC-D1：全仓 `grep` 不到发现分类的硬编码常量与别名补丁；新增分类仅需 admin 操作。
- AC-D2：万级产物租户下，`GET /organize/discover` P95 < 300ms（下推前为全量扫描，需压测对比留档）。
- AC-D3：推荐位 100% 为 ready；feed 默认不含 archived；tab 计数与列表条数一致。
- AC-D4：每张卡片可一跳回原始记忆；带 `fields` 的产物卡片优先展示结构化摘要。
- AC-D5：4 个埋点事件在 admin 看板可见，按分类 / 按日聚合。
